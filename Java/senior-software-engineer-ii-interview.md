## 一、这个岗位真正考察什么

| JD 要求 | 面试官想确认什么 | 需要准备的证据 |
| --- | --- | --- |
| Rich experience on software development, design and delivery | 能从需求、设计、实现、测试到生产交付负责，而不是只完成编码任务 | 一次完整交付案例、你的个人职责、质量门禁和上线结果 |
| Strong knowledge about Java / Micro Service / API | 能理解 Java 和 Spring 的运行机制，并设计清晰、可演进、可观测的服务与 API | 一个服务边界、一次 API 演进、一次分布式失败处理案例 |
| Performance tuning and troubleshooting | 能通过指标、日志、追踪、线程 dump、堆 dump 和数据库证据定位问题 | 一次 P99 延迟、线程池、GC、数据库或连接池问题 |
| Application security, especially API | 能把身份、授权、输入校验、密钥、审计和持续扫描落到系统中 | 一次 API 安全设计或安全问题修复案例 |
| Good communication in English | 能清晰说明方案、风险、取舍和结果，能与不同角色达成共识 | 2-3 个可用英语讲述的项目故事和架构说明 |

### Senior II 与普通开发的区别

面试官通常不只问“你会不会使用 Spring Boot”，还会观察你是否能够：

- 先澄清业务目标、流量、SLA、数据一致性、安全和交付约束。
- 根据业务边界和数据所有权拆分服务，而不是因为流行就拆微服务。
- 解释正常路径、超时、重复、乱序、重试、降级和恢复路径。
- 用指标和工具证明性能判断，而不是只说“加缓存”或“增加机器”。
- 把安全控制放进代码、配置、流水线和运行时监控。
- 说明自己的贡献、团队协作、决策依据和最终结果。

## 二、高分回答的通用结构

### 1. 技术题：结论 -> 原理 -> 取舍 -> 验证

例如回答“是否应该把系统拆成微服务”时，可以这样组织：

> 我不会仅根据系统规模决定是否拆分。首先看业务边界、数据所有权、独立发布需求、团队边界、故障隔离和独立扩展需求。如果订单和支付拥有不同的变化频率、合规要求和扩展压力，可以拆成独立服务；如果边界尚未稳定、团队较小且事务强耦合，模块化单体可能更合适。实施后我会用发布频率、P95 延迟、故障影响范围、MTTR 和运维成本验证拆分是否产生收益。

一个成熟回答至少包含：

1. 一句话给出推荐或判断。
2. 解释核心机制，不只说组件名称。
3. 说明适用条件和至少一个代价。
4. 说明如何测试、监控或验证。
5. 关联一段真实项目经历。

### 2. 经历题：STAR + 决策 + 复盘

- **Situation**：系统背景、规模、用户和具体问题。
- **Task**：你的责任、时间约束和成功标准。
- **Action**：分析、设计、实现、沟通和上线动作。
- **Result**：延迟、错误率、吞吐量、发布周期、成本或事故数量的变化。
- **Decision**：为什么选择这个方案，放弃了什么替代方案。
- **Learning**：沉淀了什么自动化、标准、告警或流程。

### 3. 被追问“如果失败怎么办”时

不要继续堆组件，先定义失败类型：

1. 是请求超时、重复提交、数据丢失、权限失败、消息重复，还是依赖不可用？
2. 通过超时、取消、幂等、限流、隔离、熔断、降级或死信如何保护？
3. 通过重试、补偿、重放、回滚、切流或人工处理如何恢复？
4. 通过哪些日志、指标、Trace、对账结果和演练证明已经恢复？

## 三、Java 基础与并发高频题

### Q1：`HashMap` 的工作原理是什么？为什么平均查找是 O(1)？

**核心回答：** `HashMap` 通过 key 的哈希值定位数组桶，再根据桶内节点比较哈希值和 `equals` 找到目标。平均 O(1) 建立在哈希分布均匀、扩容合理和 key 不被修改的前提上；发生碰撞时需要遍历桶内节点，现代 JDK 在桶过长时可能树化以降低最坏情况。

需要补充：

- `equals` 相等的对象必须有相同的 `hashCode`。
- 放入 Map 后，参与 `equals` 和 `hashCode` 的 key 字段不应改变。
- 初始容量、负载因子和扩容会影响内存和性能。
- `HashMap` 不是线程安全的；并发场景应按访问模式选择 `ConcurrentHashMap` 或更高层的缓存/状态方案。

**加分表达：** 不要把 O(1) 说成绝对保证。面试中应同时提到哈希质量、碰撞、扩容和并发语义。

### Q2：`ArrayList`、`LinkedList` 和 `CopyOnWriteArrayList` 如何选择？

- `ArrayList` 连续数组，随机访问快，尾部追加通常快，适合读多写少且需要索引访问的普通集合。
- `LinkedList` 节点分散，随机访问慢，节点分配和缓存局部性较差；不能只因为“中间插入 O(1)”就默认选择它，因为定位插入位置仍可能是 O(n)。
- `CopyOnWriteArrayList` 写操作复制底层数组，读不加锁，适合读极多、写极少、集合规模可控的配置或监听器列表，不适合频繁更新或大集合。

### Q3：`HashMap` 和 `ConcurrentHashMap` 有什么区别？

`ConcurrentHashMap` 通过更细粒度的并发控制和非阻塞读等机制支持并发访问，但它只保证集合操作的并发安全，不会自动保证多个业务步骤的原子性。

```java
// 单次原子操作
cache.computeIfAbsent(key, this::loadValue);

// 多步业务逻辑需要重新审视原子性和副作用
```

面试时应说明：

- `ConcurrentHashMap` 不允许 `null` key/value，避免并发读取时无法区分“没有值”和“值为 null”。
- `putIfAbsent`、`compute` 等复合方法有明确语义，但加载函数不应有不可控的长时间阻塞或外部副作用。
- 如果需要跨多个 key、数据库和消息系统的一致性，不能只换一个并发集合。

### Q4：Java 内存模型中的可见性、原子性和有序性是什么？

- **可见性**：一个线程修改共享变量后，其他线程能够看到最新值。
- **原子性**：一个操作不可被观察为只执行了一半，例如 `i++` 不是原子的。
- **有序性**：编译器、JIT 和 CPU 可能重排指令，但必须遵守 happens-before 规则。

`volatile` 主要提供可见性和一定的有序性，不保证复合操作的原子性。计数、状态转换等需要根据场景选择 `AtomicInteger`、锁、并发集合或无共享状态设计。

### Q5：`synchronized`、`ReentrantLock` 和原子类如何选择？

- `synchronized` 语义简单，自动释放锁，适合作为默认的互斥机制。
- `ReentrantLock` 提供可中断获取、超时尝试、公平策略和多个条件队列，但需要严格保证 `unlock` 在 `finally` 中执行。
- 原子类适合简单的单变量原子更新；`compareAndSet` 循环过多时可能造成 CPU 消耗。

选择时先确认共享状态和临界区，再评估锁竞争、等待时间、公平性、可取消性和死锁风险。不要为了“无锁”而把复杂状态改写成难以验证的 CAS 代码。

### Q6：线程池参数如何设计？为什么不建议直接使用无界队列？

线程池要根据任务类型和容量约束设计：

- CPU 密集型任务重点关注 CPU 核数、队列长度和并行度。
- I/O 密集型任务可以有更多并发，但受数据库连接池、下游配额和内存限制。
- 队列不能无限增长，否则流量高峰会转化为延迟和 OOM。
- 必须定义拒绝策略、超时、取消、监控和降级行为。

服务端通常不建议无条件使用 `Executors` 工厂方法，因为其默认线程数或队列策略可能不符合生产容量模型。应显式配置线程池，并监控 active count、queue size、completed task、rejected task 和任务耗时。

### Q7：`CompletableFuture` 的常见误区是什么？

`CompletableFuture` 可以组合异步操作，但不会自动消除阻塞。如果在线程池中调用同步数据库或 HTTP，仍会占满线程。

- 使用自定义线程池隔离不同类型的任务，不要让慢下游占满公共线程池。
- `thenCompose` 用于串联异步结果，`thenCombine` 用于组合相互独立的任务。
- 必须显式处理异常、超时和取消；`exceptionally`、`handle` 和 `whenComplete` 的职责不同。
- 并发调用下游前要设置上限，否则 `allOf` 可能制造流量尖峰。

### Q8：Java GC 问题如何回答才不像背概念？

先说明 GC 的目标是回收不可达对象，实际暂停和吞吐取决于 JDK、收集器、堆大小、对象分配速率、对象存活年龄和负载。

排查时关注：

1. 分配速率、Young GC 频率、Old GC、暂停时间和堆使用曲线。
2. 是否存在大对象、缓存无界增长、ThreadLocal 未清理、静态集合或请求对象被长期引用。
3. GC 日志、JFR、堆 dump 和应用指标是否相互印证。
4. 调整堆或切换收集器前，先证明瓶颈确实来自 GC，而不是数据库、锁或下游调用。

**不要说：** “把堆调大就能解决内存问题。”堆变大可能减少频繁回收，但也可能让问题延后并增加一次回收的成本。

## 四、Spring Boot 基础高频题

### Q9：`@SpringBootApplication` 做了什么？

它通常组合了三个能力：

- `@SpringBootConfiguration`：标识 Spring Boot 配置类。
- `@EnableAutoConfiguration`：根据 classpath、配置属性和条件注入自动配置 Bean。
- `@ComponentScan`：扫描当前包及子包中的组件。

自动配置不是魔法，也不是无条件创建所有 Bean。它通过 `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 等条件判断是否生效。排查自动配置时可以查看 condition evaluation report、启动日志和配置绑定结果。

### Q10：Spring IoC 和依赖注入的原理是什么？

IoC 表示对象的创建和依赖关系由容器管理。Spring 在启动时扫描配置和组件，创建 Bean、解析依赖、执行生命周期回调，并通过代理实现事务、缓存和安全等横切能力。

推荐使用构造器注入：

```java
@Service
public class OrderService {
    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}
```

构造器注入使依赖显式、对象更容易测试，也能尽早发现循环依赖。`@Autowired` 不是架构设计本身；当一个接口有多个实现时，应使用 `@Qualifier`、`@Primary` 或明确的工厂策略。

### Q11：Bean 的生命周期和常见作用域是什么？

典型生命周期包括实例化、依赖注入、Aware 回调、BeanPostProcessor 前置处理、初始化回调、后置处理和容器关闭时的销毁回调。

常见作用域：

- `singleton`：默认，每个 Spring 容器一个实例；共享状态必须线程安全。
- `prototype`：每次请求容器都可能返回新实例；销毁责任需要额外设计。
- Web 场景的 `request`、`session`：不能被单例直接长期持有。

**高频陷阱：** 单例 Bean 捕获请求级对象会造成生命周期错误；把可变业务状态放到单例字段中会产生并发问题。

### Q12：Spring AOP 的代理机制是什么？为什么自调用会导致 `@Transactional` 失效？

Spring AOP 通常通过 JDK 动态代理或 CGLIB 子类代理拦截方法调用。调用必须经过代理，事务、缓存或权限切面才有机会执行。

```java
@Service
public class PaymentService {
    public void placeOrder() {
        settle(); // 同一个对象内部直接调用，可能绕过代理
    }

    @Transactional
    public void settle() {
        // transaction may not be applied for self-invocation
    }
}
```

更好的做法是把事务边界放到被代理的外部服务方法，或拆分成职责清晰的 Bean。不要用注解名称推断行为，要理解代理边界、调用路径和事务传播属性。

### Q13：`@Transactional` 的常见误区有哪些？

- 默认只对运行时异常回滚；受检异常是否回滚要按业务明确配置。
- 事务边界应尽量短，不能在事务中执行长时间远程调用或等待用户输入。
- 同类内部调用可能绕过代理。
- 一个本地数据库事务不能自动覆盖远程服务、消息队列和另一个数据库。
- 事务方法中发布消息时可能出现数据库提交失败但消息已发送，或数据库成功但消息发送失败。

跨系统场景通常使用 Outbox、可靠消息、幂等消费者和补偿机制，而不是简单地把方法标记为 `@Transactional`。

### Q14：Spring Boot 配置、Profile 和配置优先级如何管理？

配置应外置，并按环境注入。`application.yml` 可以提供默认值，Profile 用于环境差异，但生产密钥不应直接提交到 Git。使用配置中心、密钥管理系统或平台 Secret 时，要明确谁能读取、如何轮换和如何审计。

需要关注：

- 配置绑定类型是否正确，启动时是否对必填配置做校验。
- 配置变更是否需要重启，动态刷新是否会造成线程池、连接池或客户端状态问题。
- 不把密码、JWT 签名密钥、数据库连接串和 Token 打进日志。
- 不要用 Profile 数量掩盖环境差异，关键配置应有 schema、默认值和变更审批。

### Q15：Spring Boot 中如何做统一异常处理和参数校验？

使用 Bean Validation 对输入做格式、范围和长度校验，使用 `@ControllerAdvice` 统一转换异常响应。错误响应应包含稳定的错误码、可读消息、Trace ID 和必要的字段错误，不应泄露堆栈、SQL、内部主机名或密钥信息。

```java
@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<ApiError> handleValidation(MethodArgumentNotValidException ex) {
        return ResponseEntity.badRequest()
            .body(ApiError.of("INVALID_ARGUMENT", "Request validation failed"));
    }
}
```

校验应分层：协议格式校验、领域规则校验、权限校验和数据库约束不能混为一谈。

### Q16：Spring Boot Actuator 有什么价值？生产环境如何使用？

Actuator 提供健康检查、指标、环境和应用信息等运维端点。生产配置应遵循最小暴露原则：

- 只暴露必要端点，并通过独立管理端口、网络策略和认证保护。
- 区分 liveness 与 readiness：进程活着不代表已经可以接收流量。
- 健康检查应避免把所有下游瞬时故障都转化为实例重启风暴。
- 将 Micrometer 指标接入监控系统，关注请求量、错误率、延迟分位数、线程池、连接池和业务指标。

## 五、Spring Cloud 与微服务高频题

> Spring Cloud 是一组微服务基础设施抽象。具体组件和版本应与 Spring Boot 版本、团队运维能力和组织平台一致，不要只根据组件名回答。

### Q17：Spring Cloud 微服务通常包含哪些能力？

可以按能力而不是产品名回答：

| 能力 | 常见实现方向 | 面试时要说明的边界 |
| --- | --- | --- |
| 服务发现 | Eureka、Consul、Nacos 或平台原生服务发现 | 注册中心自身高可用、过期实例、网络分区和客户端缓存 |
| API Gateway | Spring Cloud Gateway 或云平台 Gateway | 路由、认证前置、限流和观测，不承载领域逻辑 |
| 服务调用 | OpenFeign、WebClient、RestClient、gRPC | 超时、取消、重试、幂等和连接池 |
| 负载均衡 | Spring Cloud LoadBalancer 或平台 LB | 实例健康、故障摘除和跨区域策略 |
| 配置管理 | Config Server、Nacos、Consul 或平台配置 | 版本、审计、密钥、动态刷新和回滚 |
| 弹性治理 | Spring Cloud CircuitBreaker、Resilience4j | 超时、重试、隔离、熔断、限流和降级 |
| 事件集成 | Kafka、RabbitMQ、Pulsar 等 | 投递语义、重复、乱序、死信、重放和幂等 |

### Q18：服务发现的工作原理和风险是什么？

服务启动时向注册中心注册实例，定期发送心跳或续租；调用方从注册中心获取实例列表并进行负载均衡。真实生产环境还要处理实例启动未完成、优雅下线、网络分区、心跳延迟、缓存过期和注册中心故障。

高分回答应包含：

- readiness 通过后再接收流量，关闭时先摘除再等待连接排空。
- 客户端缓存可以避免注册中心短暂不可用，但会带来过期实例风险。
- 不能把注册中心当作绝对实时的服务状态来源。
- 需要监控实例数、注册失败、心跳超时、调用失败和异常拓扑变化。

### Q19：Spring Cloud Gateway 可以做什么，不能做什么？

适合放在 Gateway 的能力：TLS 终止、路由、认证前置、基础授权上下文、限流、请求大小限制、Trace 传播、统一错误格式和基础审计。

不适合放在 Gateway 的能力：复杂领域规则、跨多个服务的长事务、依赖业务数据库的决策和大量业务编排。Gateway 是关键基础设施，应具备多副本、无状态、低延迟、配置可回滚和故障演练能力。

### Q20：OpenFeign 调用远程服务时需要配置什么？

不要只说“加一个 `@FeignClient`”。至少要说明：

- 连接超时、读取超时和整体请求预算。
- 连接池、最大并发、响应体大小和线程池隔离。
- 哪些错误可重试，重试是否会重复写操作。
- 认证凭据、Trace context 和必要的请求头如何传播。
- 下游不可用时是否降级，以及降级结果是否会误导业务。
- 监控请求量、错误率、P95/P99、超时、重试和熔断状态。

示例配置概念：

```yaml
spring:
  cloud:
    openfeign:
      client:
        config:
          inventory-service:
            connectTimeout: 500
            readTimeout: 1500
```

具体属性名称应以项目使用的 Spring Cloud 版本文档为准，面试中重点是预算、失败语义和验证方式。

### Q21：熔断、重试、超时和限流如何配合？

推荐顺序是先定义请求预算和失败分类：

- **超时**：任何远程调用都必须有上限，避免线程和连接无限占用。
- **重试**：只针对明确的瞬时错误，使用有限次数、指数退避和随机抖动；写操作需要幂等。
- **熔断**：连续失败或慢调用达到阈值时暂时停止调用，给下游恢复机会。
- **隔离**：为不同下游分配独立线程池、信号量或连接池，阻止一个依赖拖垮全局。
- **限流**：保护入口和关键资源，配额应与容量和业务优先级对应。
- **降级**：返回真实且可接受的替代结果，不能把“未知”伪装成“成功”。

**常见失分点：** 在每一层都配置重试，会造成乘法级请求放大。整体预算必须小于上游调用方的超时预算。

### Q22：Spring Cloud Config 或配置中心如何做到安全和可回滚？

配置应版本化、可审计、按环境和服务隔离。敏感配置使用密钥管理系统或加密存储，不把明文密码放进普通配置仓库。

动态刷新需要谨慎：

- 连接池、线程池、密钥、路由和限流参数刷新时可能影响正在运行的请求。
- 配置变更应有 schema 校验、审批、灰度、回滚和变更后的验证。
- 配置客户端启动时如果中心不可用，应明确是快速失败、使用本地安全默认值还是暂时降级。
- 生产配置访问必须记录服务身份、版本和变更人。

### Q23：微服务之间如何保证数据一致性？

单服务内通过本地事务保证自身数据；跨服务流程一般采用最终一致性。常用设计是：

1. 业务数据和 Outbox 事件在同一个本地事务中提交。
2. 发布器可靠地读取 Outbox 并投递消息。
3. 消费者使用业务幂等键或消息 ID 去重。
4. 失败消息进入重试和死信流程。
5. 对无法自动恢复的业务提供补偿、对账和人工处理入口。

Saga 可以编排多个本地事务，并为每一步定义补偿动作。两阶段提交可能增加协调和可用性成本，只有在明确需要且基础设施支持时才考虑。

### Q24：消息至少一次、至多一次和恰好一次如何解释？

- **至多一次**：消息可能丢失，但不重复，适合可丢失的通知。
- **至少一次**：不轻易丢失，但可能重复，是企业系统常见语义；消费者必须幂等。
- **恰好一次**：通常需要限定边界，不能简单理解为整个业务流程绝对只执行一次。

消息系统的“只投递一次”不等于业务副作用只发生一次。数据库更新、邮件发送、库存扣减等动作需要业务幂等、去重表、唯一约束或可重入设计。

### Q25：Spring Cloud Stream 或 Kafka 消费者如何避免重复处理？

为每个业务事件设计稳定的 event ID 和业务幂等键。消费者处理时可以：

- 用数据库唯一约束记录已处理事件。
- 将业务更新与消费记录放在同一个本地事务中。
- 对外部副作用使用 Outbox 或可查询的执行状态。
- 处理重试、死信、乱序、过期消息和 schema 兼容。
- 监控消费延迟、积压、失败率、重平衡和死信数量。

不要只依赖内存 Set 去重，也不要把 offset 提交成功当作业务处理成功的证明。

### Q26：微服务日志、指标和链路追踪如何设计？

- **日志**：结构化 JSON，包含时间、服务、版本、环境、trace ID、span ID、业务关联 ID 和结果；不记录密码、Token 和不必要的个人信息。
- **指标**：请求量、错误率、P50/P95/P99、饱和度、线程池、连接池、JVM、消息积压和关键业务成功率。
- **追踪**：HTTP、消息、数据库和外部调用传播 Trace Context，用于识别长尾和级联调用。
- **告警**：关联 SLO 和业务影响，带 runbook，避免只有 CPU 告警。

注意指标标签不能包含无限基数的用户 ID、订单 ID 或 URL 原文，否则会导致监控系统自身成本和性能问题。

## 六、API 设计与应用安全

### Q27：如何设计一个高质量 REST API？

从契约和生命周期回答：

- 用资源表达业务对象，使用正确的 HTTP 方法和状态码。
- `POST` 创建资源通常返回 `201`，异步任务可返回 `202`，删除和更新要定义幂等性。
- 明确分页、排序、过滤、字段选择和最大 page size，避免无限制查询。
- 统一错误格式，返回稳定 error code、message、field errors 和 trace ID。
- 写操作支持幂等键，防止客户端重试造成重复订单或重复扣款。
- API 文档、契约测试、兼容性检查和弃用策略要进入交付流程。

### Q28：API 版本如何演进？什么变更是破坏性的？

新增可选字段通常比较兼容；删除字段、修改字段类型、改变语义、收紧校验、改变错误码含义和改变排序语义都可能破坏消费者。

我会先识别消费者并监控使用量，再定义兼容窗口、迁移文档、双版本策略、弃用日期和下线标准。版本可以使用 URL、Header 或媒体类型，关键是统一、可发现、可观测，而不是争论格式本身。

### Q29：OAuth2、OIDC、JWT、Session 分别解决什么问题？

- **OAuth 2.0**：授权框架，描述客户端如何获得访问资源的授权。
- **OIDC**：建立在 OAuth 2.0 之上的身份层，提供用户身份认证信息。
- **JWT**：一种令牌格式，不等于完整的认证授权方案。
- **Session**：服务端保存会话状态，客户端通常携带 session ID。

API 资源服务器应验证签名、issuer、audience、过期时间、not-before、算法和必要的 scope/claim。JWT Payload 只是编码，不是加密，不能放密码、密钥或不必要的敏感信息。高风险权限变更还需要考虑撤销、短期 access token、refresh token 轮换和密钥轮换。

### Q30：认证和授权有什么区别？如何设计 API 权限？

认证回答“你是谁”，授权回答“你能做什么”。API 不应只检查 token 有效，还应检查：

- 调用方身份、客户端类型和 token audience。
- scope、role、resource owner 和组织/租户边界。
- 对象级权限，例如用户只能访问自己组织的订单。
- 管理员、服务账号和普通用户的权限差异。
- 服务间调用是否需要 mTLS、短期凭据或 workload identity。

避免只在前端隐藏按钮；真正的授权必须在服务端强制执行，并记录安全相关决策。

### Q31：API 常见安全风险如何防护？

按威胁回答比罗列工具更有效：

- **注入**：参数化查询、ORM 正确使用、输入校验和最小数据库权限。
- **越权**：服务端做对象级和功能级授权，拒绝仅依赖用户提交的 tenant/user ID。
- **暴力破解和滥用**：速率限制、配额、账号锁定策略、风险检测和审计。
- **重放与重复提交**：TLS、短期 token、nonce 或 timestamp、幂等键和服务端去重。
- **敏感数据泄露**：日志脱敏、响应字段最小化、加密、密钥管理和数据分类。
- **SSRF**：限制目标地址、协议、重定向和云 metadata 地址，使用网络隔离。
- **CORS/CSRF**：根据浏览器调用模式配置可信 origin；Cookie 会话需要 CSRF 防护，Bearer token 的风险模型不同。
- **供应链**：依赖漏洞扫描、SBOM、镜像扫描、固定版本和快速升级流程。

### Q32：如何保护密码、Token 和密钥？

- 密码只保存强哈希结果，例如适用的慢哈希算法，不可逆加密不是密码存储方案。
- API Token 和 JWT 签名密钥放入密钥管理系统，不进入代码、镜像、日志、命令历史或普通配置文件。
- 采用最小权限、用途隔离、轮换、过期、撤销和访问审计。
- 密钥轮换要考虑双 key 兼容窗口、旧 token 失效策略和回滚方式。
- 安全扫描发现泄露时，不能只删除 Git 文件；必须立即撤销、重签发并检查访问日志。

### Q33：如何设计安全的 API 错误和审计？

对客户端返回稳定且不泄露内部细节的错误；服务端通过 trace ID 关联详细日志。审计日志至少应记录操作者、主体、时间、来源、动作、资源、结果和变更摘要，但不记录密码、完整 token 或不必要的敏感 payload。

审计日志应防篡改、限制访问、设置保留周期，并能够支持安全调查和合规查询。业务日志与安全审计日志可以有不同的存储、权限和保留策略。

## 七、性能调优与故障排查

### Q34：生产 API 延迟突然升高，你会如何排查？

按影响范围和证据逐层缩小：

1. 看 P50/P95/P99、错误率、吞吐量，确认是全部接口、单个接口、全部实例还是单实例。
2. 对比最近发布、配置、流量、依赖和数据库变化。
3. 用 Trace 找最慢的 span，区分应用计算、锁等待、数据库、网络、序列化和下游调用。
4. 查看线程池队列、活动线程、GC 暂停、连接池等待、数据库慢查询和下游超时。
5. 先执行低风险止血：回滚、暂停扩容推广、限流、关闭非核心功能或切换降级。
6. 复现和修复后，用相同或可解释的流量验证 P95/P99、错误率和业务成功率。

不要从“调大线程池”开始。线程池变大可能只是把连接池或数据库压力继续放大。

### Q35：如何排查线程池耗尽？

常见原因是同步阻塞 I/O、慢数据库、远程调用无超时、锁竞争、CPU 任务过多或队列无界增长。症状包括请求排队、P99 飙升、线程数上升但吞吐下降、连接池等待和大量超时。

排查证据：线程 dump、线程池 active/queue/rejected 指标、任务耗时、数据库连接池、HTTP 连接池和 Trace。修复方式包括真正使用异步 I/O、隔离线程池、设置超时和取消、限制并发、缩短临界区和保护下游。不要只提高 core/max pool size。

### Q36：数据库慢查询如何定位？

先区分应用端等待、连接池等待、网络传输和数据库执行时间。然后检查：

- SQL、参数、执行计划、索引和数据量。
- 全表扫描、低选择性条件、隐式类型转换、N+1 查询和过度返回字段。
- 锁等待、事务持续时间、连接池大小和数据库 CPU/IO。
- 分页方式；大 offset 可能越来越慢，可考虑基于游标或业务索引分页。
- ORM 是否在循环中触发查询、是否错误使用懒加载、是否拉取大量数据到内存。

优化后必须用真实数据和基准验证，并确认读优化没有破坏一致性和写入能力。

### Q37：Redis 可以解决什么问题？使用时有哪些风险？

Redis 适合缓存、短期状态、分布式限流、幂等记录、排行榜或队列等场景，但每种用途都要定义一致性、过期、容量和恢复语义。

缓存设计需要回答：

- key 如何命名、TTL 如何设置、是否需要主动失效。
- 缓存击穿、穿透、雪崩如何防护。
- 缓存 miss 时数据库能承受多少并发。
- Redis 不可用时是降级、失败还是读取源系统。
- 是否允许旧数据，更新顺序和双写失败如何处理。

不要把 Redis 当作没有备份的唯一事实源，除非系统明确接受其数据和恢复语义。

### Q38：如何排查 Java 内存持续增长？

先区分进程 RSS、Java heap、metaspace、direct buffer、线程栈和 native memory。然后：

1. 查看堆使用、分配速率、GC、Old Gen、线程数和 direct memory。
2. 在不同时间点获取 heap dump，对比存活对象和引用链。
3. 重点检查静态集合、无界缓存、ThreadLocal、监听器、定时任务、类加载器和请求对象引用。
4. 检查连接、文件、线程和 native buffer 等非堆资源。
5. 修复后在相同负载下验证对象存活曲线、GC 和 RSS。

“堆没有立即还给操作系统”不等于内存泄漏；需要结合存活对象和引用路径判断。

### Q39：性能优化的正确顺序是什么？

推荐顺序：

1. 先定义 SLO、容量和用户可感知的目标。
2. 通过指标、Trace、Profile、JFR、线程 dump、数据库执行计划确认瓶颈。
3. 先修复算法、查询、重复 I/O、无界并发和错误重试等根因。
4. 再评估缓存、批处理、连接复用、异步化、序列化和 JVM 参数。
5. 用负载测试、基准测试和生产指标验证收益与副作用。
6. 记录优化前后数据、成本和回滚方式。

性能优化不是“使用更多并发”，而是在资源预算内减少无效工作和长尾等待。

## 八、实际应用案例与架构题

### 案例一：设计一个订单微服务平台

**场景：** 用户通过 API 创建订单，订单需要校验库存、发起支付并发送通知。系统要求高峰期稳定、不能重复下单，订单状态最终需要可追踪。

**推荐架构：**

```text
客户端
  -> WAF / API Gateway
  -> Order Service
       -> Order DB + Outbox
       -> Message Broker
            -> Inventory Service
            -> Payment Service
            -> Notification Service
  -> Redis（短期缓存、幂等记录，按需要使用）
  -> Metrics / Logs / Traces
```

**回答要点：**

1. Order、Inventory、Payment、Notification 按业务能力和数据所有权划分，不共享业务表。
2. 创建订单使用 Idempotency-Key；服务端保存请求结果或唯一约束，重复请求返回同一业务结果。
3. 订单写入和 OrderCreated 事件通过 Outbox 在同一数据库事务中提交。
4. 库存和支付使用 Saga 或状态机推进，明确超时、拒绝、补偿和人工介入路径。
5. 消费者使用 event ID 或业务键幂等，处理重复、乱序、重试和死信。
6. API、消息和数据库都设置超时和容量边界，避免无限重试放大故障。
7. 监控订单成功率、重复订单、支付失败、消息积压、库存对账差异和 P99。

**必须主动说出的取舍：** 如果业务要求下单、库存和支付强一致，跨服务分布式事务会带来可用性和运维成本；应先确认业务允许的最终一致性窗口和补偿规则。团队规模较小时，模块化单体加 Outbox 可能比立即拆成多个服务更合适。

### 案例二：Spring Boot API 的 P99 从 300 ms 升到 3 s

**排查思路：**

- 先按版本、实例、接口和区域切分延迟，确认影响范围。
- 用 Trace 发现主要时间花在库存服务调用，而不是本地 Java 计算。
- 查看下游调用超时、重试次数、连接池等待和库存数据库慢查询。
- 发现调用方和网关都配置了重试，单个请求最多产生多次下游请求，形成放大。
- 临时关闭重复重试、限制并发并对非核心库存查询降级；随后修复调用预算和重试责任边界。
- 对库存查询增加合适索引和投影，使用负载测试验证 P99、错误率和数据库 CPU。

**面试表达：**

> 我不会先增加服务副本，因为证据表明瓶颈在下游等待和重复重试。止血时先降低放大效应，再修复 SQL 和调用策略，最后用 Trace、数据库指标和业务成功率确认结果。

### 案例三：API 安全设计

**场景：** 外部合作方调用订单查询和退款 API，系统需要区分合作方、用户和运营人员权限。

**设计要点：**

- 使用 OAuth2 client credentials 处理服务到服务调用；用户端使用 OIDC/OAuth2 登录。
- 资源服务器验证 issuer、audience、签名、时间窗口、scope 和必要 claims。
- 退款接口实施对象级授权、金额和状态校验、幂等键、审批或二次确认。
- Gateway 做基础认证、限流、请求大小限制和 Trace 传播；服务内部重新执行关键授权，不把 Gateway 当作唯一安全边界。
- 密钥放在密钥管理系统中，支持轮换和撤销；Token、密码和敏感个人信息不写日志。
- 对异常登录、权限拒绝、退款失败和管理操作记录审计事件。
- 流水线包含依赖扫描、SAST、秘密扫描、API 契约测试和 DAST；上线后监控异常调用。

### 案例四：设计低风险发布和回滚

**方案：**

1. 制作不可变镜像，构建、扫描、测试后晋级同一个制品。
2. 使用滚动、蓝绿或金丝雀发布，设置错误率、P95、业务成功率和资源阈值。
3. 数据库变更使用 expand-and-contract：先增加兼容字段，再切换读写，最后删除旧结构。
4. 应用支持优雅停机，先从服务发现摘除，再等待请求完成。
5. 发布中观察新旧版本、下游依赖、消息积压和关键业务交易。
6. 触发阈值时自动停止推广或切回旧版本，并验证数据兼容性。

**高分提醒：** “零停机”有前提：应用无状态或状态可外置，新旧版本兼容，数据库变更向后兼容，健康检查和回滚真实演练过。

### 案例五：微服务生产故障的回答模板

> 先确认影响范围、错误率、关键业务交易和最近变更，并指定 incident owner。若发布是高可信根因，我会暂停推广或回滚，同时保留日志、指标和时间线。恢复后用合成交易、业务方确认、错误率、延迟和依赖指标验证，而不是只看 Pod 为 Running。最后区分直接根因、促成因素和检测缺口，补充测试、告警、容量保护或发布门禁，并给每项改进指定 owner 和验证时间。

## 九、如何让面试官更加认可你

### 1. 每个技术方案都主动说一个 trade-off

可使用：

- “这个方案的收益是……，代价是……，在当前约束下我选择它是因为……。”
- “如果一致性要求提高到强一致，我会重新评估可用性、延迟和补偿成本。”
- “我会先测量，避免把应用瓶颈转移到数据库或缓存。”
- “在团队没有 Kubernetes 运维能力时，我不会仅因为它流行就引入更复杂的平台。”

### 2. 用指标代替形容词

少说“性能明显提升”“系统很稳定”，改成：

- P95/P99 从多少降到多少。
- 错误率、超时率、重复消息或死信数量如何变化。
- 发布周期、回滚时间、MTTD、MTTR 或人工操作量如何变化。
- 指标来自压测、监控、Trace、日志还是业务对账。

没有准确数字时，可以说测量方法和量级，不要编造精确百分比。

### 3. 说清楚“我”做了什么

不要整段只说“我们做了”。建议区分：

- 我负责识别问题、设计方案、实现哪个关键模块。
- 我组织了哪些评审，与哪些团队协调。
- 团队共同完成了哪些工作。
- 我如何处理反对意见、上线风险和后续改进。

### 4. 画架构图时从业务流开始

推荐顺序：用户动作 -> API 入口 -> 核心业务服务 -> 数据所有权 -> 同步/异步依赖 -> 安全 -> 观测 -> 部署和灾备。每加入一个组件，都说明它解决的问题、代价和验证方式。

### 5. 准备五类真实项目故事

| 故事 | 必须包含的内容 |
| --- | --- |
| 一次架构设计 | 业务目标、约束、候选方案、取舍、结果 |
| 一次性能问题 | 指标、证据、根因、修复、前后对比 |
| 一次生产事故 | 影响、止血、沟通、恢复、RCA、预防 |
| 一次安全改进 | 威胁、控制、验证、审计和持续检查 |
| 一次技术分歧 | 各方关注点、验证方式、决策和复盘 |

### 6. 常见失分信号

- 只罗列 Spring Cloud、Kafka、Redis、Kubernetes 名称，不说明为什么选择。
- 把微服务、异步、缓存和重试当成所有问题的默认答案。
- 说“保证 100% 安全”“绝对零停机”，却没有条件、证据和边界。
- 发生故障只讲重启和扩容，不讲数据完整性、影响范围和恢复验证。
- 说“使用 JWT 就安全”，忽略授权、密钥轮换、撤销、日志和对象级权限。
- 行为题全程使用“我们”，无法判断个人贡献。
- 把性能问题归因于 JVM 或 GC，却没有 dump、profile、Trace 或指标证据。

## 十、英文沟通准备

### 1. 技术方案表达模板

> **My recommendation is to ...** because the main constraints are ...
>
> **The main trade-off is ...** It increases/decreases ...
>
> **The failure modes I would design for are ...**
>
> **I would validate the solution by measuring ...**
>
> **In my previous project, I was responsible for ... and the result was ...**

### 2. 性能问题表达模板

> The latency regression was not caused by the Java computation itself. Distributed tracing showed that most of the time was spent waiting for a downstream service. We found duplicated retries at two layers, which amplified the traffic. We removed the duplicated retry policy, introduced a request budget, and validated the fix with P99 latency, downstream error rate, and database load.

### 3. 事故问题表达模板

> First, I would establish the impact and stop further rollout. If the latest release is the most likely cause, I would roll it back while preserving the evidence. Then I would verify recovery using business transactions, error rate, latency, and dependency health. After recovery, I would separate the direct root cause from contributing factors and add an automated guardrail to prevent recurrence.

### 4. 不知道答案时的表达

不要猜一个绝对结论，可以说：

> I have not used that exact component in production, so I would not make an unverified claim. My understanding is ... I would confirm the version-specific behavior from the official documentation and validate it with a small test or production-like benchmark.

这比编造确定答案更能体现 Senior 工程师的可靠性。

- [ ] 能说明 AOP 代理、自调用、`@Transactional` 和事务边界。
- [ ] 能解释 Spring Boot 自动配置、配置管理、校验、异常处理和 Actuator。

- [ ] 能说明服务发现、Gateway、Feign、负载均衡、配置中心和熔断的职责边界。

- [ ] 能解释服务拆分依据、数据所有权、Saga、Outbox 和幂等消费者。
- [ ] 能处理重复、乱序、死信、重放和消息积压。

### 性能与交付

- [ ] 能用英语在 2-3 分钟内讲清一个项目、一次故障和一个架构决策。

### 最后记住

> **先理解业务和约束，再选择技术；先设计失败和恢复，再描述正常路径；先用证据定位问题，再进行性能优化；先落实最小权限和审计，再谈 API 便利性；用真实结果证明自己的工程判断。**
