## 一、岗位核心能力与高分回答框架

### 1. 面试官真正考察什么

| 能力维度 | 面试官想确认的能力 | 可准备的证明材料 |
| --- | --- | --- |
| 业务理解 | 能把模糊业务问题转成口径、指标和可操作的报表 | 指标定义文档、需求澄清案例、用户采纳结果 |
| 数据处理 | 能可靠地连接、清洗、合并和验证多源数据 | Power Query 分层、数据质量规则、查询折叠案例 |
| 数据建模 | 能建立可扩展、可复用、性能可控的星型模型 | 事实表/维度表设计、关系图、粒度说明 |
| DAX | 理解上下文，能正确实现业务指标，而非只会套公式 | 复杂度量值、时间智能、同比环比和调试过程 |
| 可视化 | 能让不同角色快速发现异常并采取行动 | 首页设计、钻取路径、移动端或可访问性设计 |
| 工程化 | 能处理刷新、权限、发布、版本和故障 | 网关、增量刷新、RLS、部署管道、PBIP/Git |
| 性能与治理 | 能定位慢报表并控制数据访问和变更风险 | Performance Analyzer、模型优化、审计和监控案例 |

### 2. 高分回答结构：结论 -> 原理 -> 取舍 -> 验证

例如被问到“为什么需要星型模型”时，可以这样回答：

> 我优先采用星型模型：事实表存放可聚合的业务事件和外键，维度表存放描述属性，并用从维度到事实的单向关系过滤。这样业务人员可以按客户、产品、日期等维度一致地切分指标，DAX 的筛选路径更清晰，压缩和查询性能也通常更好。只有在源数据已经是稳定雪花结构、维度非常大且规范化能显著降低维护成本时，才会保留部分雪花结构；即使如此，也会避免让终端用户直接面对复杂关系。上线前我会用典型切片器组合核对汇总值、检查关系歧义，并通过 Performance Analyzer 比较优化前后的视觉对象耗时。

### 3. 项目题回答结构：STAR + 技术决策 + 结果

- **Situation（背景）**：业务部门、原有报表痛点、数据规模和数据来源。
- **Task（任务）**：你的职责、交付边界、刷新时效和安全要求。
- **Action（行动）**：需求澄清、数据分层、模型、DAX、权限、发布和培训。
- **Result（结果）**：用报表加载时间、刷新成功率、人工报表工时、活跃用户数或业务指标改善说明成果。
- **Decision（取舍）**：为何选择 Import、DirectQuery 或复合模型；为何将逻辑放在 SQL、Power Query 或 DAX。
- **Learning（沉淀）**：留下哪些指标字典、模板、监控、发布规范或可复用语义模型。

**注意：** 量化结果必须是自己可以解释的数据。不要编造“性能提升 90%”；应说明基线、测量方式、样本报表和限制条件。

## 二、平台架构与基础概念

### Q1：Power BI Desktop、Power BI Service、On-premises data gateway 分别负责什么？

**回答要点：**

| 组件 | 核心职责 | 常见操作 |
| --- | --- | --- |
| Power BI Desktop | 本地创作与调试 | 连接数据、Power Query 清洗、建模、写 DAX、制作 `.pbix` 或 PBIP 项目 |
| Power BI Service | 云端协作、分发和运维 | 工作区、语义模型、报表、仪表板、应用、刷新、订阅、RLS、血缘和部署 |
| On-premises data gateway | Service 与私有网络数据源之间的安全出站连接 | 配置数据源凭据、计划刷新、DirectQuery/实时连接 |

Desktop 负责“开发”，Service 负责“托管、共享、刷新和治理”。本地 SQL Server、私有网络 API 等不能被 Service 直接访问时，由网关从内网**主动发起出站连接**，避免为云端开放入站端口。

**常见误区：**

- 发布到 Service 后，Desktop 中的本地文件路径和凭据不一定能在 Service 中使用。
- 个人网关适合个人或临时使用；生产环境通常使用标准网关集群并由团队管理。
- 仪表板（Dashboard）是 Service 中将磁贴汇总到单页的对象；报表（Report）通常有多页、筛选和交互。二者不要混为一谈。

### Q2：什么是语义模型（Semantic model）？为什么不能每份报表各自导一遍数据？

语义模型是面向业务消费的数据层，包含表、关系、度量值、层级、格式、RLS 和业务术语。它把“原始字段”转换为“可被业务理解且可复用的指标和维度”。

将多个报表连接到同一个经过治理的语义模型，可获得：

1. **单一指标口径**：销售额、活跃客户、退货率只维护一次。
2. **较低的刷新和容量成本**：不为每个报表重复导入相同数据。
3. **统一安全策略**：RLS 和敏感字段控制在模型层。
4. **更可控的变更**：度量、描述、认证和血缘可集中治理。

代价是模型变更需更谨慎：应有负责人、影响分析、测试空间和版本发布机制，避免一个错误修改影响所有下游报表。

### Q3：Import、DirectQuery、Live connection、Direct Lake 和 Composite model 如何选择？

| 模式 | 特点 | 适用场景 | 主要风险 |
| --- | --- | --- | --- |
| Import | 数据压缩存入 VertiPaq 内存引擎，交互快 | 大多数可接受定时刷新的分析报表 | 数据时效受刷新周期和容量限制 |
| DirectQuery | 每次交互向底层源发送查询 | 需要接近实时、数据无法导入或必须留在源端 | 源库压力、网络延迟、SQL/DAX 转译限制 |
| Live connection | 报表连接已有 Analysis Services 或 Power BI 语义模型 | 复用已治理的企业模型 | 报表作者对模型改动能力受限 |
| Direct Lake | 在 Fabric 场景直接读取 OneLake 中 Delta 表，兼顾低延迟和大规模数据 | 已采用 Fabric Lakehouse/Warehouse 的分析平台 | 依赖 Fabric 架构、容量和表维护方式 |
| Composite model | 在一个模型中组合 Import、DirectQuery 或已有语义模型 | 热冷数据分层、渐进迁移、特定明细实时查询 | 关系、存储模式和性能更复杂 |

**选择原则：**

1. 默认优先 Import，因为列式压缩和内存查询通常能提供最好体验。
2. “实时”先明确是秒级、分钟级还是当天数据。若 15 分钟刷新已满足业务，不要因概念上的实时而引入 DirectQuery。
3. DirectQuery 前先验证源端索引、并发、查询折叠、SLA、超时和安全策略。
4. 对历史大、近期开销高的数据，可结合增量刷新和混合表，而不是全量 DirectQuery。

### Q4：Power BI 的数据流是怎样的？

典型链路如下：

```text
业务系统 / 文件 / API
          |
          v
Power Query 或数据工程层（清洗、标准化、质量校验）
          |
          v
事实表 + 维度表 -> 语义模型（关系、度量、RLS）
          |
          v
报表 / 仪表板 / App / Excel / 下游连接
          |
          v
业务用户决策、订阅、告警与反馈
```

资深候选人应说明每一层的责任边界：复杂可复用的数据集成逻辑优先下沉到数据仓库、Lakehouse 或数据流；语义层负责业务指标和安全；报表层负责呈现与有限的用户交互。不要把全部清洗、建模、指标和视觉计算都堆进单个 PBIX。

## 三、数据获取与 Power Query

### Q5：Power Query 和 DAX 的区别是什么？业务逻辑放在哪里？

| 对比项 | Power Query（M） | DAX |
| --- | --- | --- |
| 执行时机 | 刷新前，加载数据时 | 加载后，随模型计算或用户查询计算 |
| 主要目的 | 提取、清洗、转换、合并、整形 | 定义业务指标、筛选逻辑、时间智能和模型计算 |
| 结果 | 查询表或加载到模型的列 | 度量值、计算列、计算表 |
| 推荐逻辑 | 类型转换、去重、拆分、合并、历史清洗 | 销售额、同比、滚动 12 月、动态占比 |

**决策原则：**

- 可在源端完成且可复用的重型转换，优先使用 SQL、视图、dbt、ETL 或数据工程层。
- 与单行数据清洗有关的稳定逻辑放 Power Query，并尽量保留查询折叠。
- 随用户筛选器变化的聚合指标放 DAX 度量值。
- 不要用 DAX 计算列模拟 ETL，也不要在 Power Query 中硬编码依赖报表筛选上下文的指标。

### Q6：什么是查询折叠（Query folding）？为什么重要？

查询折叠是 Power Query 将后续转换尽可能翻译并下推到支持的源系统（如 SQL Server）执行的能力。例如筛选日期、选择列、分组可以被折叠成 SQL 的 `WHERE`、`SELECT` 和 `GROUP BY`。

它的重要性在于：

- 只从源端取回必要行和列，减少网络和网关压力。
- 利用数据库索引和计算资源，缩短刷新时间。
- 对增量刷新尤其关键；如果日期筛选不能下推，可能发生全表读取。

**排查和优化方法：**

1. 在 Power Query 中尽早完成筛行、选列和类型处理。
2. 在支持时用“查看本机查询”确认关键步骤能折叠；不可用不代表一定未折叠，但需要进一步验证。
3. 将阻断折叠的自定义函数、逐行调用、复杂 M 操作尽量移到后面，或下沉到源端视图。
4. 谨慎使用 `Table.Buffer`。它可能减少重复枚举，但也可能中断折叠并增加内存，不应作为默认优化手段。

### Q7：如何设计可维护的 Power Query？

建议采用分层查询，并关闭中间查询的加载：

```text
stg_SalesRaw        # 源连接、少量早期筛选
stg_CustomerRaw     # 源连接、少量早期筛选
dim_Customer        # 标准化后的维度
fct_Sales           # 清洗后的事实
```

实践要点：

- 使用参数管理服务器、数据库、文件路径、环境名称和日期边界，避免在多个查询中硬编码。
- 命名表达业务含义，例如 `fct_Sales`、`dim_Product`，不要保留 `Query1`。
- 每一步只做一类转换，关键步骤加简短说明。
- 明确设置数据类型，尤其是金额、日期、整数键和时区时间。
- 对关键业务键做空值、重复、范围和参照完整性检查；出现异常时应让刷新显式失败或产生可追踪的数据质量结果，不能静默吞掉问题。

### Q8：如何处理 Excel、CSV 等文件型数据源？

文件数据常见问题是列名变更、工作表名称变更、编码、日期格式不一致、重复文件和人工覆盖历史文件。

较成熟的处理方式是：

1. 约定投放目录、文件命名规范、最小字段集和交付频率。
2. 使用文件夹连接器合并同结构文件，并保留文件名、修改时间等审计字段。
3. 在加载前验证列是否存在、主键是否重复、金额是否可解析；不要将解析失败直接替换为 0。
4. 将原始文件保留在受控存储中，区分原始层与处理层。
5. 若文件已成为长期关键数据源，推动迁移至数据库、数据仓库或受治理的 Lakehouse。

## 四、维度建模与语义模型

### Q9：什么是事实表、维度表和粒度（Grain）？

- **事实表（Fact）**：记录可度量的业务事件，例如订单明细、库存每日快照、广告点击。通常包含外键、数值和业务日期。
- **维度表（Dimension）**：提供分析切片属性，例如客户名称、产品类别、区域、销售人员、日历。
- **粒度**：事实表中“一行代表什么”。例如“每个订单行、每个产品、每次发货”的订单明细粒度。

粒度是建模的起点。必须先明确它，才能判断一个字段是否应放入事实表、如何聚合、能否与另一张事实表直接合并。

**常见错误：** 将订单头金额与订单行明细放进同一张表后直接求和，导致订单金额按明细行被重复累计。正确做法是保留不同粒度的事实表，或在度量中按订单键去重聚合。

### Q10：为什么推荐星型模型，而不是一张“大宽表”？

星型模型以事实表为中心，多个维度表直接围绕事实表。与大宽表相比，它可以：

1. 避免客户、产品等属性在海量事实行上重复，降低模型大小。
2. 让关系和筛选方向明确，降低 DAX 的复杂度和歧义。
3. 让维度可在多个事实表间复用，实现一致切片。
4. 更适合 VertiPaq 列式压缩和业务自助分析。

大宽表在原型、小数据量或一次性数据探索中可以快速交付，但在长期生产模型中通常带来更高内存、难复用的口径以及难以维护的重复字段。

### Q11：关系的基数和交叉筛选方向如何设计？

**首选模式：**

```text
dim_Date (1)      -> (*) fct_Sales
dim_Product (1)   -> (*) fct_Sales
dim_Customer (1)  -> (*) fct_Sales
```

- 主键侧应唯一且非空，事实表保存外键。
- 大多数关系使用**单向**过滤：从维度表过滤事实表。
- 多对多关系不是错误，但应先检查是否缺少桥接表、维度键是否不唯一，或业务粒度是否混杂。
- 双向过滤只能在确有业务需求、筛选路径唯一且验证过性能时使用。它容易产生循环、歧义、意外的筛选传播和难调试的 DAX。

**桥接表示例：** 一个客户属于多个客户组，一个客户组也包含多个客户。可建立 `br_CustomerGroup`，存放 `CustomerKey` 与 `GroupKey`，再由客户组维度通过桥接表影响销售事实，而不是直接建立一个随意的多对多双向关系。

### Q12：角色扮演维度如何处理？

销售事实可能同时有订单日期、发货日期和到货日期，都指向日期维度。这称为角色扮演维度。

常见做法：

1. 保持一条活动关系，例如 `OrderDate -> dim_Date`。
2. 对其他日期建立非活动关系。
3. 在特定度量中用 `USERELATIONSHIP` 启用相应关系。

```DAX
发货销售额 =
CALCULATE (
    [销售额],
    USERELATIONSHIP ( fct_Sales[ShipDate], dim_Date[Date] )
)
```

当用户需要同时将订单日期和发货日期放在同一页面作为独立切片器时，也可以创建角色明确的日期维度副本，例如“订单日期”“发货日期”。选择哪种方式取决于交互需求、模型复杂度和培训成本。

### Q13：为什么需要独立且连续的日期表？

日期表提供完整、连续且唯一的日期序列，并包含年、季度、月、周、财务期间、排序列等属性。它能让时间智能函数在没有交易的日期仍能正确比较、累计和显示趋势。

**日期表要求：**

- 覆盖事实数据的最早到最晚日期，并预留合理未来期间。
- `Date` 列无重复、无空值、连续，数据类型为 Date 或 DateTime。
- 将其标记为日期表，并建立到事实日期键的关系。
- 月名称用月序号排序，避免“12月”排在“2月”前面。
- 明确财年起始月、周起始日和节假日口径，不要混用自然年与财年。

## 五、DAX 高频题

### Q14：度量值、计算列和计算表有什么区别？如何选择？

| 对象 | 计算时机 | 是否受报表筛选器影响 | 适用场景 |
| --- | --- | --- | --- |
| 度量值（Measure） | 查询时 | 是 | 销售额、利润率、同比、排名、动态 KPI |
| 计算列（Calculated column） | 数据刷新时 | 列值本身不随视觉筛选改变 | 分类标签、静态行级属性、关系键、排序列 |
| 计算表（Calculated table） | 数据刷新时 | 不随用户交互重新生成 | 日期表、静态桥接表、模型辅助表 |

优先使用度量值实现聚合指标。计算列会在模型中逐行存储，占用内存；如果只是为了在视觉对象中显示“销售额”或“是否达标”，通常应写成度量值。

### Q15：什么是行上下文、筛选上下文和上下文转换？

- **行上下文（Row context）**：DAX 公式逐行迭代时“当前行”的环境，常见于计算列和 `SUMX`、`FILTER` 等迭代器。
- **筛选上下文（Filter context）**：由切片器、视觉对象轴、页面筛选、关系和 `CALCULATE` 施加的可见数据范围。
- **上下文转换（Context transition）**：`CALCULATE` 在行上下文中执行时，会将当前行转换为对应列的筛选条件。

示例：

```DAX
销售额 = SUM ( fct_Sales[SalesAmount] )

客户销售额汇总 =
SUMX (
    dim_Customer,
    CALCULATE ( [销售额] )
)
```

在 `SUMX` 中，`dim_Customer` 提供行上下文；`CALCULATE` 将当前客户转换为筛选上下文，因此每次迭代计算该客户的销售额。

**面试关键点：** 不要只背定义。应能解释某个度量为何随着图表轴或切片器变化，以及为什么加入 `CALCULATE` 后结果不同。

### Q16：`CALCULATE` 的作用是什么？

`CALCULATE` 在修改后的筛选上下文中计算表达式，是 DAX 最核心的函数之一。它可以新增、覆盖或移除筛选，也会在必要时触发上下文转换。

```DAX
销售额 = SUM ( fct_Sales[SalesAmount] )

中国区销售额 =
CALCULATE (
    [销售额],
    dim_Geography[Country] = "中国"
)

全品类销售额 =
CALCULATE (
    [销售额],
    REMOVEFILTERS ( dim_Product[Category] )
)
```

若同一列已有筛选条件，普通布尔筛选可能覆盖它；需要在已有条件上取交集时，可以使用 `KEEPFILTERS`。这也是解释“为什么度量没有随着切片器变化”时应检查的重点。

### Q17：`SUM` 和 `SUMX` 的区别是什么？何时使用迭代器？

- `SUM ( 表[列] )` 直接对一列求和，效率通常更高。
- `SUMX ( 表, 表达式 )` 遍历表的每一行，计算表达式后再求和。

```DAX
销售额 = SUM ( fct_Sales[SalesAmount] )

折后销售额 =
SUMX (
    fct_Sales,
    fct_Sales[Quantity] * fct_Sales[UnitPrice] * ( 1 - fct_Sales[DiscountRate] )
)
```

当结果来自多个列、相关表字段或复杂逐行逻辑时使用 `X` 迭代器。若源数据已提供可加总的 `SalesAmount`，不要无理由改写成 `SUMX`，因为逐行迭代的成本通常更高。

### Q18：如何计算同比、环比和滚动 12 个月？

前提是存在规范日期表，且当前视觉对象使用日期表字段。

```DAX
销售额 = SUM ( fct_Sales[SalesAmount] )

去年同期销售额 =
CALCULATE (
    [销售额],
    SAMEPERIODLASTYEAR ( dim_Date[Date] )
)

同比增长额 = [销售额] - [去年同期销售额]

同比增长率 =
DIVIDE ( [同比增长额], [去年同期销售额] )

上月销售额 =
CALCULATE (
    [销售额],
    DATEADD ( dim_Date[Date], -1, MONTH )
)

滚动 12 月销售额 =
CALCULATE (
    [销售额],
    DATESINPERIOD ( dim_Date[Date], MAX ( dim_Date[Date] ), -12, MONTH )
)
```

**必须说明的边界：**

- 去年同期为空不应被替换成 0 后再显示“无限增长”；可使用 `DIVIDE` 的替代结果或显式返回 `BLANK()`。
- 财年、4-4-5 周历或非标准会计期间不应机械套自然年函数，应在日期表中定义期间映射后按业务日历计算。
- 月度视觉对象要使用“年月”字段，而不是孤立的月份名称，否则不同年份会被聚合在一起。

### Q19：`ALL`、`ALLSELECTED`、`REMOVEFILTERS` 和 `ALLEXCEPT` 如何理解？

这些函数用于控制筛选上下文，区别在于移除哪些筛选以及是否尊重外层选择。

```DAX
品类销售占比 =
DIVIDE (
    [销售额],
    CALCULATE ( [销售额], REMOVEFILTERS ( dim_Product[Category] ) )
)
```

- `REMOVEFILTERS`：清除指定表或列的筛选，表达意图清晰，常用于分母。
- `ALL`：返回移除筛选后的表/列，也常用于筛选修改；在现代 DAX 中，纯粹为清除筛选时优先使用语义更直观的 `REMOVEFILTERS`。
- `ALLSELECTED`：保留报表或页面的外部选择，忽略当前视觉对象的内部粒度，常用于“当前用户选择范围内的总计”。
- `ALLEXCEPT`：清除表中除指定列外的筛选。它很方便，但字段新增或筛选逻辑演变时可能难以维护；复杂场景中显式写出要移除/保留的筛选通常更安全。

使用前先回答：“分母要相对于全公司、当前国家、当前日期范围，还是当前页面选择？”这比死记函数更重要。

### Q20：如何实现动态排名和 Top N？

```DAX
产品销售排名 =
RANKX (
    ALLSELECTED ( dim_Product[ProductName] ),
    [销售额],
    ,
    DESC,
    DENSE
)
```

这里 `ALLSELECTED` 让排名在用户当前选定的日期、区域等范围内进行，同时忽略当前产品行本身的单项筛选。`DENSE` 表示并列后排名连续；若业务要求并列后跳号，可使用 `SKIP`。

**常见陷阱：**

- 不同产品显示同一排名时，检查是否把产品字段从排名集合中移除。
- 总计行的排名可能没有业务意义，应在非明细层级时返回空值或单独处理。
- Top N 视觉筛选和 DAX Top N 度量的交互不同，复杂需求应说明使用哪种方式及验证范围。

### Q21：如何使用 `RELATED`、`RELATEDTABLE` 和 `LOOKUPVALUE`？

- `RELATED`：在“多”端通过已有多对一关系取得“一”端的单个值。
- `RELATEDTABLE`：在“一”端获取相关“多”端的表，常用于计算列或迭代逻辑。
- `LOOKUPVALUE`：根据一个或多个条件查找值，但它不是关系设计的替代品。

若事实表与产品维度存在正确关系，优先使用关系和 `RELATED`，因为语义更明确、优化器更容易处理。大量使用 `LOOKUPVALUE` 往往说明关系、键唯一性或模型结构需要重新审视。

### Q22：如何调试一个 DAX 度量值？

建议按以下顺序定位：

1. **明确预期值**：在很小的时间、区域和产品范围中，先手工计算一个可验证样本。
2. **检查模型**：关系是否活动、方向是否正确、键值和日期是否匹配、是否有多对多或双向过滤。
3. **拆分变量**：用 `VAR` 将分子、分母、筛选后的中间值分开，临时放到表格视觉对象中验证。
4. **检查上下文**：观察矩阵行、列、切片器、页面筛选、视觉筛选、RLS 分别在施加什么条件。
5. **使用工具**：Performance Analyzer 找出慢视觉对象；DAX Studio 可查看查询、服务器时间和查询计划（需遵守公司工具和访问规范）。

示例：

```DAX
达成率 =
VAR Actual = [实际销售额]
VAR Target = [目标销售额]
RETURN
    DIVIDE ( Actual, Target )
```

变量既能避免重复计算，也让每个业务组成部分更容易验证。

## 六、可视化、交互和报表设计

### Q23：如何从零设计一张管理层首页？

先问“用户要基于这张报表做什么决策”，而不是先选图表。典型首页可按以下层次设计：

1. **顶部 KPI**：本期销售额、利润、目标达成率、同比/环比，以及状态颜色或趋势。
2. **中部趋势与结构**：时间趋势、区域/品类贡献、目标偏差来源。
3. **底部行动清单**：异常区域、Top/Bottom 产品、风险客户和可钻取入口。
4. **全局筛选**：期间、组织、地区等高频且业务能理解的筛选器。

设计原则：

- 一页围绕一个决策主题，避免塞满所有字段。
- 默认展示最近、最常用、可解释的范围；让用户能看出数据更新时间和指标定义入口。
- 颜色应有语义且一致，例如红色表示需关注，不应用彩虹色制造噪音。
- 数字使用统一单位、货币、千分位和小数位；KPI 的比较基准要明确。
- 使用工具提示页、钻取页和书签承载细节，而不是不断增加主页面图表。

### Q24：钻取（Drillthrough）、下钻（Drill down）和工具提示页如何选择？

| 功能 | 适用场景 | 示例 |
| --- | --- | --- |
| 下钻/展开 | 同一层级内逐级查看 | 年 -> 季 -> 月；区域 -> 省 -> 城市 |
| Drillthrough | 从汇总对象跳转到专门详情页 | 从异常客户进入客户 360 页面 |
| 报表页工具提示 | 悬停时展示简洁补充信息 | 悬停产品时展示毛利、库存和近月趋势 |

高分答案会强调：交互路径必须可发现且可返回。Drillthrough 页面应显示当前传入的上下文、提供返回按钮，并避免在详情页意外丢失关键筛选条件。

### Q25：如何处理“图表很好看，但业务人员不信任数据”？

先不要把问题当成单纯视觉问题，应建立可验证性：

1. 为每个 KPI 提供业务定义、分子分母、时间口径、数据来源、负责人和最后更新时间。
2. 提供明细表或 Drillthrough，让用户能从汇总数字追到订单、客户或交易记录。
3. 与权威系统/财务报表选择对账样本，解释差异是时区、刷新延迟、状态过滤、币种还是数据质量问题。
4. 显示数据刷新状态、排除规则和异常提示，避免“过期数据看起来像实时数据”。
5. 记录并修复口径问题；一旦发现错误，应明确影响范围和更正方式，不能默默修改历史数字。

### Q26：如何做好移动端和可访问性设计？

- 使用手机布局单独编排关键 KPI 和少量高频视觉对象，不是简单缩小桌面页面。
- 避免仅用颜色表达正负或状态；同时使用标签、图标、文字或形状。
- 保持足够颜色对比度，避免信息只靠悬停工具提示呈现。
- 设置有意义的视觉标题和替代文本，检查 Tab 顺序。
- 控制切片器数量和交互复杂度，保证小屏可点击、可读取。

## 七、性能优化与问题定位

### Q27：一个 Power BI 报表很慢，你如何系统定位？

先定义“慢”的位置，而不是直接修改 DAX。可按以下层次排查：

| 层次 | 典型问题 | 诊断方式 | 优化方向 |
| --- | --- | --- | --- |
| 数据源 | SQL 扫描大表、缺索引、并发高 | 源端查询计划、网关日志、DBA 协作 | 过滤下推、索引、汇总表、预计算 |
| 刷新/Power Query | 折叠中断、全量读取、合并过多 | 刷新历史、步骤检查、源端日志 | 尽早筛选、保留折叠、增量刷新 |
| 模型 | 宽表、高基数字符串、无用列、双向关系 | 模型视图、模型大小分析工具 | 星型模型、删除列、替换文本键、单向关系 |
| DAX | 复杂迭代器、大范围筛选、重复计算 | Performance Analyzer、DAX 查询分析 | 简化筛选、复用度量、减少迭代 |
| 视觉层 | 单页图表太多、视觉交互过多 | Performance Analyzer | 减少视觉对象、按需钻取、关闭无用交互 |

**推荐流程：**

1. 复现慢的页面、用户筛选和角色，记录基线耗时。
2. 用 Performance Analyzer 判断是 DAX 查询、视觉展示还是其他耗时。
3. 先修复最大瓶颈，一次只改一个可验证的假设。
4. 在典型和最坏筛选组合下回归指标正确性与响应时间。
5. 记录优化前后数据量、查询耗时和用户体验，而不是只说“感觉变快”。

### Q28：VertiPaq 模型优化的主要原则是什么？

VertiPaq 是高压缩的内存列式引擎。通常应：

1. **删除不使用的列和行**：这是最有效、最安全的优化之一。
2. **降低基数**：GUID、交易号、长文本、毫秒级时间戳等高基数列压缩率差。仅保留分析必需的键或将展示文本拆到维度表。
3. **使用整数代理键**：在可行时用整数键关联事实和维度，避免重复的大型字符串键。
4. **拆分日期时间**：若不需要精确时间，日期和时间可按需求拆分或降精度。
5. **保留星型结构**：减少事实表冗余属性和复杂关系。
6. **控制计算列**：优先用源端转换、Power Query 或度量值，避免在事实表中生成大量计算列。

优化必须以业务语义正确为前提。不能为了降低基数而删除审计、对账或合规必须保留的字段；这类字段可以放到受控明细模型或按需查询路径。

### Q29：如何优化 DAX 度量值？

常见做法：

- 基础度量值保持简单，例如 `[销售额] = SUM ( fct_Sales[SalesAmount] )`，其他度量基于它组合，避免同一逻辑多处复制。
- 在业务允许时优先使用列聚合而不是大事实表上的复杂 `X` 迭代器。
- 避免对大表使用不必要的 `FILTER ( 全表, ... )`；能用维度列的布尔筛选条件时优先使用它。
- 用变量复用表达式，减少重复计算并提高可读性。
- 让筛选发生在维度表而非事实表文本列，利用星型模型和关系传播。
- 不要为了“优化”牺牲正确性，例如误用 `ALL` 导致 RLS 或业务筛选被绕过。

### Q30：聚合表（Aggregation）和增量刷新分别解决什么问题？

- **聚合表**解决查询性能：为常用的按日、区域、品类等汇总查询提供预聚合数据，而保留明细表用于下钻或低频分析。
- **增量刷新**解决刷新效率和历史数据管理：历史分区不反复处理，只刷新最近变动的分区，并可根据策略保留历史数据。

两者可以结合：历史明细按分区保留，常用分析命中聚合表，必要时再查询明细。设计前需要了解用户最常见的粒度、历史回溯范围、迟到数据规律和源端变更检测字段。

## 八、刷新、网关与部署

### Q31：如何设计增量刷新？

标准增量刷新要求在 Power Query 中创建 `RangeStart` 和 `RangeEnd` 参数，并在事实日期/时间列上使用它们进行筛选。发布到 Service 后配置“存储历史期间”和“刷新最近期间”等策略。

关键注意事项：

1. 日期筛选必须尽量能查询折叠到源端，否则全量读取会抵消增量收益。
2. 使用与业务数据一致的时间边界，明确半开区间，如 `>= RangeStart` 且 `< RangeEnd`，避免分区边界重复。
3. 迟到到达或会回写的历史数据，需要将刷新窗口设得足够长，或配置检测数据变更的策略。
4. 首次发布仍可能需要加载大量历史数据，应评估容量、窗口和上线时间。
5. 上线后通过刷新历史、分区行为和对账结果验证策略，而不是只看配置已保存。

### Q32：刷新失败时如何排查？

先查看 Service 的刷新历史、错误详情、活动 ID 和失败时间，再按以下顺序排查：

1. **认证与权限**：数据源凭据是否过期，服务账号是否仍有读取权限。
2. **网关**：网关是否在线、版本是否受支持、数据源映射是否匹配、集群成员是否健康。
3. **网络与源端**：DNS、端口、VPN、防火墙、数据库负载、API 限流和超时。
4. **架构变化**：源列改名/删除、数据类型变化、Excel 表名变更、JSON 结构变化。
5. **数据质量**：日期/数值转换错误、异常空值、重复键导致关系失败。
6. **容量与限制**：内存、刷新并发、超时、容量节流或数据量激增。

处理原则是保留可追踪错误并通知责任人。不要用 `try ... otherwise null` 广泛吞掉错误，否则会把数据缺失伪装成“刷新成功”。

### Q33：如何管理开发、测试和生产环境？

成熟流程通常包含：

```text
开发工作区 -> 测试/UAT 工作区 -> 生产工作区
       |           |                 |
       v           v                 v
   开发数据源   脱敏或测试数据源     生产数据源
```

实践要点：

- 使用 Power Query 参数或部署规则切换服务器、数据库、API 地址和文件路径，避免手动修改查询。
- 生产工作区限制编辑权限，消费者通过 App 或只读权限访问。
- 在 UAT 验证数据刷新、RLS、关键指标、性能和视觉改动，再提升到生产。
- 对共享语义模型建立变更说明和回滚策略；破坏性字段更改应先评估下游影响。
- 使用 PBIP、TMDL 和 Git 等适合团队的方式管理源文件与代码审查；二进制 PBIX 不适合细粒度文本 diff。

### Q34：为什么网关要采用集群和服务账号？

单机网关有单点故障：主机重启、补丁、网络问题或个人离职都可能导致刷新和 DirectQuery 中断。生产环境宜采用网关集群实现高可用，并使用受控服务账号连接数据源。

服务账号应遵循最小权限原则、具备密码轮换和交接机制。不要让生产语义模型绑定某位开发人员的个人账号，否则人员变动会直接影响业务报表。

## 九、安全、治理和协作

### Q35：什么是行级安全（RLS）？如何实现动态 RLS？

RLS 在语义模型中限制用户能看到的行。静态 RLS 可以给角色写固定条件；动态 RLS 通常通过用户-组织映射表实现。

示意模型：

```text
sec_UserRegion[UPN] -> sec_UserRegion[RegionKey] -> dim_Region -> fct_Sales
```

角色筛选可类似：

```DAX
sec_UserRegion[UPN] = USERPRINCIPALNAME ()
```

然后通过关系将该用户可访问的区域筛选传播到销售事实表。

**验证要点：**

- 在 Desktop 使用“以角色身份查看”做逻辑测试；发布后还要用实际不同用户账号验证。
- 测试无映射用户、多区域用户、管理员、外部用户和空 UPN 的行为。
- 明确工作区管理员、成员等高权限角色的行为，并根据组织策略控制权限分配。
- RLS 不等同于数据脱敏；若字段本身不能被查看，应考虑对象级安全、单独模型或源端安全策略。

### Q36：RLS、OLS 和工作区权限有什么区别？

| 机制 | 控制对象 | 示例 |
| --- | --- | --- |
| 工作区/App 权限 | 谁能编辑、发布、共享或消费内容 | 开发者可编辑，业务用户只能看 App |
| RLS | 用户能看到哪些行 | 区域经理只能看自己区域销售 |
| OLS（对象级安全） | 用户能否看到表、列、对象 | 非 HR 用户不能看到薪资列 |
| 数据源权限 | 刷新/DirectQuery 访问源数据的身份 | 服务账号仅可读报表需要的视图 |

它们应该组合使用，不能用工作区只读权限代替 RLS，也不能因为有 RLS 就让所有人拥有语义模型的编辑权限。

### Q37：如何建立指标治理？

可建立“指标字典”并为每个关键指标记录：

- 指标名称、业务定义、业务目的和负责人；
- 公式、分子/分母、过滤条件、时间和币种口径；
- 数据来源、刷新频率、适用范围和已知限制；
- 语义模型中的度量名称、变更记录和测试用例。

在模型中使用显示文件夹、描述和一致命名，使报表作者优先复用认证度量而不是新建相似计算。对高影响指标设置评审、UAT 和变更通知机制。

### Q38：如何避免“自助 BI”失控？

自助 BI 的目标不是禁止业务分析，而是提供受控的自由度：

1. 数据团队提供经过认证的语义模型、核心维度、度量和数据质量说明。
2. 业务用户在受控工作区基于认证模型制作派生报表，而非各自导出 Excel 重算。
3. 明确谁可建模、谁可发布、谁可共享、谁只能查看。
4. 使用血缘、影响分析、使用指标和审计日志发现无人使用、重复或高风险内容。
5. 定期清理废弃模型和过期权限，保留关键内容的所有者与交接人。

## 十、综合场景与项目经历题

### Q39：请设计一个销售管理 Power BI 方案。

**需求假设：** 销售总监需要查看销售、毛利、目标达成、区域和产品表现；区域经理只能查看本区域；数据来自 ERP、CRM 和 Excel 目标文件，要求每日早晨 8 点前更新。

**推荐回答：**

1. **澄清口径**：确认销售额使用下单、发货还是开票口径；退货如何处理；目标按月还是按日分摊；币种、财年和组织层级定义。
2. **数据层**：ERP 提供订单明细/退货/产品主数据，CRM 提供客户属性，目标文件经校验后形成目标事实。长期方案将文件目标纳入受控数据平台。
3. **模型层**：`fct_Sales`、`fct_Return`、`fct_Target` 共享 `dim_Date`、`dim_Product`、`dim_Customer`、`dim_Region`、`dim_Salesperson`。先定义每张事实表粒度。
4. **指标层**：建立基础度量 `[销售额]`、`[退货额]`、`[毛利]`、`[目标额]`，再计算达成率、同比和排名。关键口径与财务对账。
5. **安全层**：用用户-区域映射实现动态 RLS；生产编辑权限只给受控开发组。
6. **报表层**：总监首页展示 KPI、趋势、目标偏差和风险清单；区域/产品分析页支持下钻；客户详情页支持 Drillthrough。
7. **运维层**：配置网关集群和服务账号，计划刷新后检查刷新状态；UAT 验证数据、RLS 和性能，再通过部署流程上线。

### Q40：业务方说“销售额和财务系统对不上”，你会怎么处理？

不要立即修改公式。按可复现的对账过程处理：

1. 明确双方的报表日期、时间区、币种、组织范围、状态过滤和数据刷新时间。
2. 选定一个小范围（如某日、某区域、几个订单）逐笔对比。
3. 检查 Power BI 的事实粒度、重复关联、订单取消/退货逻辑、汇率版本和晚到数据。
4. 对比源系统 SQL、ETL 后数据、模型明细和 DAX 度量值，定位差异出现在哪一层。
5. 记录根因和影响范围；若是口径差异，推动形成统一定义；若是缺陷，修复后回填、回归并告知用户。

**面试加分点：** 提到对账应有固定频率和自动化校验，而不是每次由业务人员发现后才被动处理。

### Q41：如何把一个 Excel 手工周报迁移为 Power BI？

迁移不等于把 Excel 图表复制到 Power BI。应分阶段进行：

1. 盘点现有 Excel 的数据来源、宏、人工调整、指标口径、收件人和真正使用的页面。
2. 与业务确认必须保留的口径，删除无人使用或无法解释的指标。
3. 将可重复的数据获取和转换自动化；对无法直接连接的文件建立受控投放和质量校验。
4. 先交付与原周报可对账的 MVP，再迭代新增钻取、订阅和异常洞察。
5. 并行运行一个或多个周期，对账通过后逐步停止手工流程。
6. 培训用户、设置所有者和支持渠道，观察使用率与反馈。

### Q42：请分享一次你解决 Power BI 性能问题的经历。

回答可使用以下模板，替换为真实经历：

> 某销售明细模型包含多年数据，首页打开需要约 20 秒。通过 Performance Analyzer，我确认主要耗时来自多个依赖大事实表迭代器的度量和页面上过多同时查询的视觉对象。接着检查模型，发现事实表保留了多个未使用的长文本和高基数字段，且产品维度存在双向关系。我先移除未使用字段、恢复单向星型关系，再将可预先计算的行级金额迁移到数据处理层，重写度量以复用基础聚合。对常用的月度区域分析增加了聚合策略，并将明细放入 Drillthrough 页面。最后在相同筛选条件下比较优化前后加载时间，并与财务抽样对账，确认指标没有变化。上线后继续监控刷新时间和用户反馈。

真正面试时，补充数据量、使用的诊断工具、每项优化的效果和你亲自负责的部分。

### Q43：如果领导要求“所有数据都实时”，你如何沟通？

先澄清实时的业务价值和允许延迟：

- 哪些决策确实需要秒级/分钟级，哪些每天早晨更新即可？
- 数据源是否能承受高并发查询？是否有索引、缓存和 SLA？
- 用户是需要最新汇总，还是需要随时查看明细？
- 失败、延迟或源端不可用时如何告警和降级？

然后提出分层方案：高频关键指标采用合适的实时/近实时路径，历史分析使用 Import 和增量刷新，明细按需查询或钻取。这样既满足关键时效，又避免所有页面都因 DirectQuery 而变慢或拖垮生产库。

### Q44：你如何处理需求频繁变化？

1. 将需求拆成指标、维度、筛选、交互、数据源和安全要求，记录验收标准。
2. 先确认变化是展示变化、口径变化还是底层数据变化；后三者的风险和验证成本不同。
3. 对高影响共享度量进行影响分析，明确受影响报表和用户。
4. 在开发/UAT 环境演示原型并得到确认，再进入生产。
5. 使用版本说明和变更日志，必要时保留兼容期或过渡指标。

高分候选人会强调：敏捷交付不代表绕过数据验证、权限审查和生产发布流程。
