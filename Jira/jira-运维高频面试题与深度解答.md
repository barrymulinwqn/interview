# Jira 运维高频面试题与深度解答

本文面向 Jira 管理员、Jira 运维工程师、Jira 平台工程师、ITSM/DevOps 平台工程师和审计公司内部工具负责人。内容以 **Jira Cloud 与 Jira Data Center** 为主；Jira Server 已结束产品生命周期，回答时应主动说明自己不会把 Server 的旧做法直接套用到 Cloud 或 Data Center。

这不是菜单记忆清单。高水平的 Jira 面试回答通常要同时覆盖：

- **业务目标**：这个配置解决什么流程问题，服务对象是谁。
- **数据模型**：项目、问题、工作流、字段、权限和索引如何关联。
- **运维风险**：变更影响、性能、可用性、回滚和数据一致性。
- **安全与审计**：最小权限、职责分离、证据留存、敏感数据保护。
- **验证方式**：如何证明配置生效、问题已解决且没有引入副作用。

> **版本提示：** Jira Cloud 的功能和界面由 Atlassian 持续发布；Jira Data Center 的功能、应用兼容性和部署方式受具体版本影响。面试中不要只报菜单名称，应说明 Cloud/DC 差异、版本假设和验证方法。

## 一、面试回答框架

### 1. 概念题

建议按以下顺序回答：

1. 一句话定义概念及其解决的问题。
2. 说明它在 Jira 数据模型或请求链路中的位置。
3. 结合一个真实项目举例。
4. 说明常见误区、边界和运维风险。

### 2. 故障题

使用“现象—范围—证据—假设—验证—修复—复盘”的顺序：

1. 先确认影响范围：单用户、单项目、全实例，还是只有 API 受影响。
2. 记录时间、最近变更、请求 ID、问题键、用户和错误信息。
3. 优先执行只读检查，避免在未知状态下批量修改。
4. 从最靠近故障现象的层开始排查：权限、配置、应用、网络、数据库、节点和外部依赖。
5. 修复后进行正向验证和负向验证，并保留审计证据。

### 3. 设计题

不要只回答“创建一个项目”。应明确：

- 谁可以创建、查看、编辑、审批和关闭问题？
- 工作流状态是否代表真实业务控制点？
- 哪些字段是必填，谁负责维护？
- 自动化失败时如何重试、告警和补偿？
- 如何支持审计、报表、备份、迁移和未来扩展？

## 二、平台定位与核心架构

## 1. Jira 是什么？它和普通工单系统有什么区别？

**参考回答：**

Jira 是以“问题（Issue）”为核心的数据和工作流平台。Issue 可以代表缺陷、任务、故事、服务请求、事件、变更或风险；用户通过工作流推动 Issue 在不同状态之间流转，并利用字段、评论、附件、链接、权限和审计记录形成可追踪的业务证据。

普通工单系统可能主要记录“谁提交、谁处理、处理结果”；Jira 更强调：

- 可配置的数据模型和项目边界；
- 复杂的状态、审批和条件控制；
- JQL 查询、报表、看板和跨项目追踪；
- REST API、Webhook、Automation 和应用生态；
- 开发、测试、发布、服务管理之间的关联。

**深层背景：**

Jira 的价值不是“把 Excel 搬到网页上”，而是把组织的工作流显式化。Issue、状态和变更历史组成了一个事件链，管理层可以看到工作积压和交付风险，工程团队可以看到依赖关系，审计人员可以追溯谁在什么时候改变了什么。

**常见误区：**

Jira 不是天然的 CMDB、监控系统或资产发现系统。它可以与这些系统集成，但不应把实时指标、完整资产发现或所有主数据都复制到 Jira 中。

## 2. Jira Cloud、Data Center 和旧 Server 有什么区别？

**参考回答：**

| 维度 | Jira Cloud | Jira Data Center | Jira Server |
|---|---|---|---|
| 托管方式 | Atlassian 托管 | 企业自托管或云上自建 | 已结束生命周期 |
| 升级 | 由 Atlassian 持续发布 | 企业控制版本和维护窗口 | 不应作为新建设计 |
| 扩展 | Marketplace、Forge、部分 Connect 能力 | Marketplace 应用、插件、脚本 | 旧方案，仅用于迁移理解 |
| 数据库运维 | 平台托管，用户关注配置和集成 | 企业负责数据库、节点、存储和备份 | 旧架构 |
| 高可用 | 由服务等级和平台能力保障 | 依赖多节点、负载均衡和共享服务 | 旧方案 |
| 定制边界 | 受平台 API 和安全模型约束 | 可进行更深的基础设施级运维 | 不应继续扩建 |

回答时重点不是背产品矩阵，而是说明：**部署模式决定责任边界**。Cloud 主要关注身份、权限、应用、API、数据治理和供应商控制；Data Center 还要负责节点、反向代理、数据库、共享文件、缓存、日志、容量和升级。

**深层背景：**

很多生产事故来自把 Data Center 的思路套到 Cloud，或把旧 Server 插件当作 Cloud 方案。例如，不能假设 Cloud 上可以直接访问数据库、修改服务器文件或执行同样的 ScriptRunner 脚本。

## 3. Jira Data Center 的典型请求链路是什么？

**参考回答：**

典型链路可以抽象为：

```text
用户/客户端
    -> DNS / WAF / 反向代理 / 负载均衡
    -> Jira 节点
    -> 本地缓存、应用逻辑、插件逻辑
    -> 数据库、共享文件系统、邮件服务、LDAP/SSO、外部 API
```

多个 Jira 节点共享数据库和必要的共享存储。节点之间还需要通过集群通信同步缓存失效和部分运行状态。某个节点能访问但其他节点不能访问，通常要检查节点健康、负载均衡、会话策略、共享存储、集群通信和节点配置是否一致。

**深层背景：**

“页面能打开”不等于 Jira 健康。一个请求可能在应用层成功、在数据库层变慢、在外部身份服务超时，或者在异步队列中等待。排障必须保留完整请求链路，不能只看浏览器报错。

## 4. Jira 的主要数据对象有哪些？

**参考回答：**

核心对象可以分为五层：

1. **组织层**：用户、组、目录、身份提供商、项目。
2. **问题层**：Issue、Issue Type、字段、评论、附件、标签、Issue Link。
3. **流程层**：Workflow、状态、Transition、条件、校验器、后置动作。
4. **访问层**：Permission Scheme、Issue Security Scheme、项目角色、通知方案。
5. **查询与展现层**：JQL、过滤器、看板、报表、仪表盘、订阅和 API。

这些对象不是彼此独立的。一个用户能否看到某个 Issue，通常要同时满足：

- 用户身份有效；
- 用户属于项目角色或满足项目权限；
- Issue 所属项目允许访问；
- Issue Security 没有进一步限制；
- JQL 或看板过滤器确实选中了该 Issue。

**深层背景：**

Jira 权限问题经常被误判为“少加了一个组”。实际结果是多个控制层叠加后的交集，不是简单的并集。

## 5. Project、Project Category 和 Team-managed/Company-managed Project 有什么区别？

**参考回答：**

- **Project** 是问题、配置、权限和报表的业务容器。
- **Project Category** 是项目的组织分类，便于导航、筛选和管理，不等于安全边界。
- **Company-managed project** 使用组织级共享方案，适合需要统一治理、跨项目报表、集中权限和标准工作流的环境。
- **Team-managed project** 由团队在项目内自助配置，适合边界清晰、变化快速的团队，但大量自定义后容易产生字段、状态和权限碎片化。

企业和审计场景通常要先定义标准项目模板，再决定哪些能力开放给项目管理员。项目自助不是无限制自由配置：应控制项目创建、工作流编辑、权限方案修改、自动化规则和应用安装。

**面试追问：为什么不能所有团队都使用 Team-managed？**

因为团队级自助会带来配置漂移：同名状态含义不同、同一报表无法统一、权限审计困难、迁移成本升高。相反，所有项目都强制使用一套配置也可能压制业务差异。正确答案是根据治理等级分层，而不是追求单一模式。

## 三、Issue、工作流与字段模型

## 6. Issue Type、Issue Type Scheme 和工作流的关系是什么？

**参考回答：**

- **Issue Type** 定义问题的业务类型，如 Bug、Task、Story、Incident、Change。
- **Issue Type Scheme** 决定某个项目可以使用哪些 Issue Type，以及默认类型。
- **Workflow** 定义 Issue 如何在状态间转换。
- **Workflow Scheme** 把 Issue Type 映射到具体 Workflow。

例如，一个开发项目可以让 Bug 走“新建—开发中—待测试—已解决—关闭”，而 Change 走“草稿—评估—批准—实施—验证—关闭”。Issue Type Scheme 决定项目能不能创建 Change；Workflow Scheme 决定 Change 使用哪条流程。

**深层背景：**

Issue Type 是业务语义，Workflow 是控制流程。不要为了少建一个 Issue Type，把所有业务都塞进一个类型再用大量字段区分；这样会导致报表、权限、SLA 和自动化难以维护。

## 7. Status、Resolution、Close 和 Done 有什么区别？

**参考回答：**

- **Status** 表示 Issue 当前处于哪个流程节点，如 Open、In Progress、Waiting、Done。
- **Resolution** 表示 Issue 以什么结果结束，如 Fixed、Won't Fix、Duplicate、Cannot Reproduce。
- **Close** 可能是一个状态，也可能只是团队对“已完成”的口头称呼。
- **Done** 通常是状态名称，但它本身不一定代表有正确的 Resolution。

在 Jira 中，关闭 Issue 时应明确设置 Resolution；重新打开时通常要清除 Resolution。否则会出现“看起来还在进行中，但 Resolution 已经是 Fixed”，或者报表把未完成 Issue 统计为已解决的问题。

**高频陷阱：**

不要只通过编辑 Resolution 字段来“关闭”问题，也不要在没有验证的情况下直接修改状态。状态变更应通过合法 Transition 完成，让条件、校验器、后置动作和审计链正常执行。

## 8. Workflow 的 Condition、Validator 和 Post Function 分别做什么？

**参考回答：**

以一个“批准变更”的 Transition 为例：

- **Condition**：决定谁能看到或执行这个 Transition，例如只有审批组成员可见。
- **Validator**：在执行时检查输入是否满足要求，例如风险等级、回滚方案、实施窗口不能为空。
- **Post Function**：Transition 成功后执行动作，例如更新字段、写入历史、触发事件、发送通知或调用自动化。

执行顺序可理解为：

```text
用户看到 Transition
    -> Condition 判断是否可见
    -> 用户提交
    -> Validator 校验输入
    -> 状态更新与后置动作
    -> 通知/自动化/索引等异步或后续处理
```

**深层背景：**

把所有逻辑都写进 Post Function 是危险的，因为校验失败太晚，可能已经产生不完整数据。把权限问题写在 Validator 里也会造成用户看得到但无法执行的糟糕体验。流程控制应分别放在正确层次。

## 9. Screen Scheme、Field Configuration 和 Issue Layout 有什么区别？

**参考回答：**

- **Screen** 决定创建、编辑、查看或 Transition 时展示哪些字段。
- **Screen Scheme** 把不同操作映射到对应 Screen。
- **Field Configuration** 控制字段是否隐藏、是否必填以及字段描述。
- **Field Configuration Scheme** 把字段配置绑定到项目和 Issue Type。
- **Issue Layout** 控制用户在 Issue 页面看到的字段布局和分组，具体能力受产品版本影响。

一个字段“看不见”可能是 Screen 没有它，也可能是 Field Configuration 隐藏了它；一个字段“看得见但不能提交”可能是上下文、权限、类型或校验器导致。排障时要按层检查，不能只改 Screen。

**运维建议：**

必填字段要有业务负责人和默认值策略。过多必填字段会促使用户随意填值，产生比“字段为空”更糟糕的伪数据。

## 10. Context、Custom Field 和字段治理应该怎么做？

**参考回答：**

自定义字段应先确认标准字段是否满足需求。确需新增时，至少定义：

- 字段名称、业务定义和数据类型；
- 可用项目、Issue Type 和上下文；
- 谁维护、谁读取、是否包含敏感信息；
- 是否需要出现在 Screen、JQL、报表和 API；
- 是否会影响索引、迁移、自动化和应用兼容性；
- 废弃时如何归档和验证引用关系。

字段上下文应尽量小，不要让一个字段无差别出现在所有项目和 Issue Type 中。字段数量过多会影响用户体验、配置可理解性、迁移复杂度和治理成本。

**审计视角：**

不要把密码、访问令牌、完整个人健康信息或不必要的敏感数据存进 Issue 字段、评论或附件。Jira 的可见范围一旦扩大，历史数据也可能被暴露。

## 四、权限、身份和审计

## 11. Jira 权限模型是怎样的？

**参考回答：**

项目权限通常通过以下机制组合：

1. **Global Permissions**：实例级能力，例如登录、创建共享过滤器、管理用户等。
2. **Project Permission Scheme**：项目级能力，例如浏览、创建、编辑、转换和管理项目。
3. **Project Role**：项目中的角色，如 Administrators、Developers、Service Desk Team。
4. **Group/User**：角色或权限的成员来源。
5. **Issue Security Scheme**：对单个 Issue 进一步限制可见范围。
6. **字段和工作流控制**：决定用户能否看到、填写或执行某项操作。

排查“用户为什么看不到 Issue”时，不能只问“有没有 Browse Project”。还要检查项目权限、Issue Security、Reporter/Assignee 规则、项目类型、用户目录同步和过滤器条件。

**最小权限原则：**

- 用组或项目角色授权，尽量避免直接给个人授权。
- 将项目管理权限和流程审批权限分开。
- 限制能修改 Permission Scheme、Workflow、Automation 和应用配置的管理员数量。
- 定期回顾离职、转岗、临时授权和服务账号。

## 12. Project Permission 和 Issue Security 有什么区别？

**参考回答：**

Project Permission 决定用户是否有权访问项目以及执行项目级操作；Issue Security 在用户已经具备项目访问权限后，再决定某个具体 Issue 是否对其可见。

例如，所有研发成员可以 Browse Project，但安全事件 Issue 只允许 Security Team、Reporter 和项目管理员看到，这就需要 Issue Security。

**常见错误：**

- 以为从项目角色移除用户就能自动隐藏所有历史 Issue。
- Issue Security 方案配置了，但创建或转换时没有正确设置 Security Level。
- 用 Issue Security 解决本应通过项目拆分解决的长期组织隔离问题。

Issue Security 会增加查询和排障复杂度。高敏感、强隔离的业务应评估是否需要独立项目、独立站点或更适合的专用系统。

## 13. Jira 如何接入 SSO、LDAP、SCIM？运维重点是什么？

**参考回答：**

- **SSO/SAML/OIDC** 主要解决认证：用户在哪里登录、如何完成多因素认证。
- **LDAP/目录同步** 主要解决用户和组信息从哪里来。
- **SCIM** 通常用于身份生命周期自动化：创建、更新、禁用用户和组成员关系。
- **Jira 权限** 仍决定用户登录后能做什么。

认证成功不等于授权成功。排障要区分：

```text
认证失败 -> IdP、证书、声明、时间、回调地址、域名
同步失败 -> 目录连接、映射、组同步、去重、生命周期
登录成功但无权限 -> Jira 组、项目角色、权限方案、Issue Security
```

**深层背景：**

最危险的场景是“离职用户仍能访问”或“外部组被错误映射到管理员角色”。应建立禁用延迟、组变更审批、管理员组告警和定期访问复核。

## 14. Jira 的审计日志能证明什么，不能证明什么？

**参考回答：**

审计能力通常可以帮助证明配置、用户、项目、权限、工作流或管理操作的变化，但不同产品版本、日志级别、保留周期和应用会影响证据完整性。Issue 历史、评论、工作日志、附件记录和管理员审计也不是完全相同的证据类型。

审计设计应回答：

- 谁做了操作？
- 何时做的？使用哪个账号、API Token 或服务账号？
- 改了什么，改前是什么，改后是什么？
- 是否经过审批？对应哪个变更单？
- 日志是否可被管理员修改或删除？
- 保留多久，是否导出到不可篡改存储？

**不能过度承诺：**

Jira 内置审计日志不是天然等同于完整的合规审计系统。高风险场景应将关键日志集中到 SIEM 或受控存储，并定义时间同步、访问控制、保留和完整性校验。

## 五、JQL、索引与数据一致性

## 15. JQL 和 SQL 有什么本质区别？

**参考回答：**

JQL 是 Jira 面向问题数据和索引的查询语言，不是对底层数据库执行任意 SQL。它描述用户关心的条件，例如：

```jql
project = PAY AND issuetype = Bug
AND statusCategory != Done
AND priority in (Highest, High)
ORDER BY updated DESC
```

JQL 的结果受用户权限、Issue Security、字段可搜索性、索引状态和产品能力影响。不能把 JQL 当成数据库管理工具，也不应在生产环境直接绕过应用层修改 Jira 数据库。

**深层背景：**

Jira 的搜索体验依赖应用层数据与索引的协同。数据库里“存在”不代表用户一定能搜索到，反之，缓存或索引异常也可能让页面和搜索结果短时不一致。

## 16. “JQL 查不到已存在的问题”如何排查？

**参考回答：**

建议按以下顺序：

1. 用问题键直接访问，确认 Issue 是否存在以及用户是否有 Browse 权限。
2. 去掉复杂条件，逐步增加 `project`、`issuetype`、`status`、字段条件。
3. 检查项目权限和 Issue Security。
4. 检查字段名称、字段上下文、选项值和日期时区。
5. 比较其他管理员或项目角色用户的查询结果。
6. 确认是否存在索引延迟、索引损坏或最近的大批量导入。
7. 检查插件提供的自定义字段是否仍可搜索。

不要一开始就重建全局索引。重建索引可能消耗大量 CPU、磁盘和数据库资源，应先确认范围、维护窗口、节点行为和回滚/降级策略。

## 17. Jira 为什么需要索引？重建索引有什么风险？

**参考回答：**

索引使 Jira 能够高效执行全文检索、字段过滤、排序和 JQL 查询。如果每次查询都直接扫描所有 Issue 和历史数据，大型实例会无法满足交互性能要求。

索引问题可能来自：

- 节点索引不同步；
- 批量写入后索引队列积压；
- 自定义字段或插件索引失败；
- 磁盘空间不足；
- 升级、恢复或异常关机后索引状态异常。

**风险：**

- 全量重建可能占用大量 CPU、内存、磁盘 I/O 和临时空间。
- 多节点环境可能造成节点间查询结果短时不同。
- 在业务高峰执行会放大延迟。
- 反复重建而不修复根因，会导致问题再次出现。

正确做法是先收集日志和指标，判断是索引延迟、局部损坏还是数据/插件问题，再选择节点级或全量操作。

## 18. 如何写出可维护、高性能的 JQL？

**参考回答：**

- 优先用项目、Issue Type、状态和时间范围缩小结果集。
- 使用稳定的字段和标准值，避免依赖易变的显示名称。
- 少用大量 `OR`、通配符和高成本文本搜索。
- 对共享过滤器设置所有者和复核周期。
- 不要在仪表盘中放置大量无边界、重复执行的过滤器。
- 大型报表应考虑定时计算、数据仓库或专门分析工具。

示例：

```jql
project = OPS
AND updated >= -30d
AND statusCategory != Done
AND assignee is not EMPTY
ORDER BY priority DESC, updated ASC
```

这里的时间范围不仅让查询更快，也让报表的业务含义更清楚。面试中应说明“正确性”和“性能”是同时考虑的。

## 六、自动化、API 与集成

## 19. Jira Automation、Webhook、REST API 和插件如何选择？

**参考回答：**

| 机制 | 适合场景 | 主要风险 |
|---|---|---|
| Automation | 简单的事件—条件—动作流程 | 循环触发、规则数量、执行配额、重试 |
| Webhook | Jira 事件实时通知外部系统 | 重复事件、签名验证、接收端不可用 |
| REST API | 外部系统主动读写 Jira | 认证、分页、限流、幂等、版本兼容 |
| Forge/Connect/Marketplace 应用 | 复杂扩展、界面和业务逻辑 | 权限范围、供应链、升级兼容、数据驻留 |
| Data Center 插件/脚本 | 受控环境内的深度定制 | JVM 资源、集群一致性、升级和安全风险 |

优先选择最小能力的方案。一个简单字段同步不应引入一个拥有全站写权限的大型插件。

## 20. REST API 运维需要关注什么？

**参考回答：**

至少要关注以下方面：

1. **认证**：优先使用 OAuth、受控 API Token 或专用服务账号，不在代码中硬编码凭据。
2. **权限**：服务账号只拥有所需项目和操作权限。
3. **分页**：不能假设一次请求返回所有 Issue。
4. **限流**：Cloud 和外部系统都可能限流，应识别 429、重试窗口和退避策略。
5. **幂等**：重试不能重复创建 Issue、评论或变更。
6. **超时和重试**：区分网络失败、4xx 参数/权限失败和 5xx 服务失败。
7. **审计**：记录请求来源、业务键、结果和关联变更单，但不要记录 Token。
8. **版本兼容**：关注 API 版本、字段 ID、应用字段和 Cloud/DC 差异。

稳健的同步流程应使用业务唯一键，例如外部系统的事件 ID，并在创建前查询是否已经同步成功：

```text
接收事件 -> 校验签名 -> 提取外部唯一键
    -> 查询已有映射
    -> 不存在则创建，存在则更新
    -> 保存 Jira key、外部 ID、版本和结果
    -> 失败进入重试/死信队列并告警
```

## 21. 如何设计 Jira 与 CI/CD、监控或 CMDB 的集成？

**参考回答：**

先定义“哪个系统对哪个事实负责”：

- 监控系统负责指标、告警和探测结果；
- CMDB 或资产系统负责资产主数据；
- Jira 负责工作项、审批、变更和处理证据；
- CI/CD 系统负责构建、部署和发布状态。

Jira 不应成为所有系统的万能数据库。集成中应明确：

- 事件去重键；
- 状态映射；
- 谁能关闭事件；
- 外部系统不可用时是否允许 Jira 操作；
- 重试、补偿、死信和人工处理；
- 字段和个人数据最小化；
- 关联链接与审计证据的保留策略。

**常见反模式：**

监控告警一来就创建一个 Issue，恢复后不做去重，最后产生数万条重复工单。更好的设计是使用事件指纹、时间窗口、服务维度和生命周期状态。

## 22. Automation 规则为什么会循环或失控？如何治理？

**参考回答：**

常见原因：

- 规则 A 修改字段触发规则 B，规则 B 又修改 A 监听的字段；
- Rule actor 拥有过高权限，修改了不应修改的项目；
- 失败重试没有上限；
- 批量更新产生大量事件；
- 规则条件过宽，任何 Issue 更新都触发。

治理措施：

- 明确触发字段和事件范围；
- 使用“由自动化更新”的标记、标签或变更来源判断；
- 为重试设置次数、退避和死信；
- 对批量动作设置上限和维护窗口；
- 为关键规则指定 owner、用途、数据范围和停用方案；
- 定期检查执行失败、执行量和配额；
- 在测试项目验证后再推广到生产。

## 七、Jira Service Management 与 ITSM

## 23. Jira Service Management（JSM）和普通 Jira Software 项目有什么区别？

**参考回答：**

JSM 在 Jira 问题模型之上增加面向服务管理的能力，例如门户、请求类型、客户、队列、SLA、审批、知识库、事件、变更和资产能力。普通 Jira Software 更偏向研发工作项、看板、版本和开发集成。

两者可以共享平台能力，但服务台设计必须关注：

- 客户是否应是 Jira 用户；
- 客户能看到哪些请求；
- 请求类型如何映射 Issue Type 和字段；
- SLA 如何计时、暂停和停止；
- 队列如何分派；
- 公共回复和内部备注如何隔离；
- 事件、问题和变更如何关联。

## 24. SLA 的计时逻辑如何设计？

**参考回答：**

一个 SLA 通常由以下部分组成：

- **目标**：如首次响应时间、解决时间。
- **开始条件**：请求创建、进入某状态或优先级变更。
- **暂停条件**：等待客户、等待供应商、维护窗口。
- **停止条件**：首次响应、解决、关闭或取消。
- **工作日历**：工作时间、节假日和时区。
- **目标时间**：根据优先级、服务和客户等级选择。

SLA 的深层难点不是“设置 4 小时”，而是确保状态和条件代表真实责任边界。例如把所有“等待外部信息”都暂停，可能人为提高达标率；完全不暂停，又会把不可控等待全部归责于支持团队。应定义可审计的暂停原因、证据和复核规则。

## 25. Incident、Problem、Change 应如何关联？

**参考回答：**

- **Incident**：尽快恢复服务。
- **Problem**：分析根因并减少重复事件。
- **Change**：受控地实施修复或改进。

典型关系：

```text
多个 Incident
    -> 一个 Problem / Known Error
    -> 一个或多个 Change
    -> 验证修复效果
    -> 更新知识库与监控
```

重大事件的高质量记录应包含影响、时间线、决策、沟通、临时恢复、根因、永久修复和行动项。不要把 RCA 直接写成“人为失误”；应分析技术、流程、权限、监控和组织因素。

## 八、性能、可用性与容量

## 26. Jira 页面变慢时，如何系统排查？

**参考回答：**

先确认“慢”的定义和范围：

- 所有页面还是某个项目/Issue？
- 所有用户还是某个用户/组？
- Web 页面慢还是 REST API 慢？
- 是持续变慢、特定时间变慢，还是最近变更后变慢？

然后按层排查：

1. 浏览器网络和请求耗时，确认服务端请求。
2. 反向代理、WAF、负载均衡和 TLS。
3. Jira 节点 CPU、内存、GC、线程池、请求队列和节点健康。
4. 数据库连接池、慢查询、锁等待、连接数和磁盘延迟。
5. 索引队列、批处理、Automation、邮件队列和插件任务。
6. 共享存储、附件访问和网络延迟。
7. 最近发布的字段、工作流、脚本、应用或大批量操作。

**不能接受的回答：**

“重启 Jira 就好了。”重启可能清空队列或释放资源，但会丢失证据、掩盖根因，甚至在集群中造成更大影响。应先采集指标、日志和线程信息，再选择低风险缓解措施。

## 27. Jira Data Center 如何实现高可用？

**参考回答：**

高可用不是“多启动几台节点”，而是端到端设计：

- 多个 Jira 应用节点；
- 健康检查和故障摘除；
- 负载均衡与合理的会话策略；
- 高可用数据库和明确的故障转移；
- 可靠的共享存储；
- 节点间通信和时间同步；
- 邮件、身份、缓存、外部 API 等依赖的可用性；
- 经过演练的备份、恢复和故障切换。

还要识别哪些组件是单点：数据库、共享存储、反向代理、许可证服务、身份提供商和邮件网关。应用节点多不等于 RTO/RPO 达标。

## 28. 如何制定 Jira 的备份、恢复和灾备方案？

**参考回答：**

先定义业务目标：

- **RPO**：最多能接受丢失多长时间的数据。
- **RTO**：最多能接受多长时间不可用。

Data Center 方案通常包括数据库备份、共享存储/附件、配置和密钥、插件版本、外部依赖信息，以及恢复文档。不能只备份数据库，因为附件、索引、配置和凭据引用可能影响可用性。

恢复流程应包含：

1. 选择干净环境或隔离恢复环境。
2. 恢复数据库和附件。
3. 安装兼容的 Jira/应用版本。
4. 恢复配置和安全参数。
5. 重建或验证索引。
6. 验证登录、权限、Issue、附件、工作流、通知和 API。
7. 记录恢复耗时、缺失数据和改进项。

**审计重点：**

备份成功不等于可恢复。至少定期执行恢复演练，并保存成功/失败证据、恢复时间和抽样校验结果。

## 29. Jira 容量规划应该看哪些指标？

**参考回答：**

不要只看 Issue 总数。应跟踪：

- 活跃用户、并发用户和 API 请求量；
- Issue、评论、附件和历史数据增长率；
- 数据库大小、连接数、慢查询和锁等待；
- 节点 CPU、内存、GC、线程池和响应时间；
- 索引大小、索引队列和重建耗时；
- 自动化执行量、失败率和队列长度；
- 报表、看板、过滤器的查询耗时；
- 附件存储增长和备份窗口；
- 许可证消耗与管理员数量。

根据增长趋势和峰值容量做规划，而不是等磁盘满或数据库连接耗尽再扩容。

## 九、升级、迁移与变更管理

## 30. Jira 升级前需要做哪些准备？

**参考回答：**

升级前至少完成：

1. 明确目标版本、支持矩阵和维护窗口。
2. 盘点 Marketplace 应用、插件、脚本、自定义字段和集成。
3. 阅读版本说明、已知问题和弃用项。
4. 验证数据库、JDK、操作系统、代理和共享存储兼容性。
5. 完成可验证的备份和恢复测试。
6. 在与生产相近的数据副本上演练。
7. 定义成功标准、监控项、回滚或恢复方案。
8. 提前通知用户、服务台、审计和业务负责人。

升级后要验证不仅是“能登录”，还包括登录/SSO、项目权限、创建和转换 Issue、JQL、通知、SLA、附件、自动化、API、报表、插件和集群节点健康。

**深层背景：**

升级风险主要来自隐性耦合：某个字段被脚本引用、某个插件依赖内部 API、某个报表依赖旧状态值。配置清单和自动化测试比人工点几下页面更可靠。

## 31. Jira 迁移项目有哪些高频风险？

**参考回答：**

常见迁移来源包括 Server/Data Center 到 Cloud、项目合并、实例拆分、跨站点迁移和工具替换。风险包括：

- 用户和组映射错误；
- Issue Key、链接、评论、附件或历史丢失；
- 工作流、权限、通知和自定义字段语义变化；
- 插件没有 Cloud 等价能力；
- 个人数据跨区域迁移；
- API 集成仍指向旧地址；
- JQL、报表和看板依赖旧项目/字段；
- 大数据量迁移超过窗口；
- 源系统在迁移期间继续写入造成差异。

成熟方案应包括清单、数据分类、试迁移、差异校验、冻结策略、切换窗口、回滚/并行运行和业务验收。验收不能只抽查几个 Issue，应按数量、关系、附件、权限、时间线和关键业务场景校验。

## 32. 如何安全执行 Jira 的批量修改？

**参考回答：**

批量修改前：

- 保存精确 JQL，记录预计数量和抽样结果；
- 明确业务负责人和审批；
- 导出变更前数据或建立可逆映射；
- 先在测试项目或少量样本执行；
- 确认通知、自动化、SLA 和索引副作用；
- 选择低峰期并设置监控。

批量修改后：

- 比较修改前后数量；
- 抽查状态、字段、评论、链接和权限；
- 检查自动化失败、邮件和索引队列；
- 生成执行日志和结果报告；
- 对异常记录执行补偿而不是盲目再次全量执行。

任何脚本都应具备明确范围、幂等性、限速、错误处理、停止条件和审计日志。

## 十、安全与审计公司场景

## 33. 审计公司最关注 Jira 的哪些控制点？

**参考回答：**

可以从以下控制域回答：

1. **访问控制**：SSO、MFA、最小权限、特权账号、离职禁用、定期访问复核。
2. **职责分离**：申请、审批、实施和复核不能由同一账号无约束完成。
3. **变更管理**：变更有目的、风险、审批、实施证据、回滚和结果。
4. **证据完整性**：Issue 历史、审批、附件和日志可追溯，保留策略明确。
5. **数据保护**：敏感数据最小化、传输和存储保护、数据驻留和第三方应用评估。
6. **运营监控**：失败任务、异常登录、管理员变更、集成错误和容量有告警。
7. **业务连续性**：备份、恢复、RTO/RPO 和灾备演练有证据。
8. **供应商治理**：Cloud 服务、Marketplace 应用、子处理者和服务等级有评估。

审计证据必须能够回答“谁、何时、做了什么、为什么、由谁批准、结果如何”，而不是只有一张当前配置截图。

## 34. 如何保护 Jira 中的敏感信息？

**参考回答：**

- 设计阶段先判断敏感数据是否必须进入 Jira。
- 使用项目隔离、Issue Security 和角色控制最小化可见范围。
- 不在评论、字段、附件或日志中保存密码、Token 和私钥。
- 对外部应用审查数据访问范围、存储地点和退出机制。
- 对服务账号使用短权限、轮换和独立凭据。
- 对 API 使用 TLS、签名验证、限流和来源限制。
- 定期扫描高风险字段和附件，并建立删除/归档流程。

**重要边界：**

权限配置不能弥补错误的数据放置。一个本来不应存入 Jira 的秘密，即使“只有管理员可见”，仍可能因导出、备份、插件或日志而扩大暴露面。

## 35. Jira 管理员账号为什么需要特别治理？

**参考回答：**

管理员可以修改权限、工作流、应用、字段、自动化甚至影响审计证据，因此管理员账号是高价值目标。治理措施包括：

- 使用个人实名账号，避免共享管理员账号；
- 管理员使用 MFA 和条件访问；
- 日常工作使用普通账号，按需临时提权；
- 特权操作关联变更单；
- 定期检查管理员组成员；
- 监控权限方案、SSO、应用安装和审计设置变化；
- 限制服务账号的交互式登录和全局权限。

## 十一、真实场景题与参考排障

## 36. 用户说“我有项目权限，但看不到某个 Issue”，你怎么处理？

**参考回答：**

先确认 Issue Key、用户账号、项目和访问时间，再按顺序检查：

1. Issue 是否存在，是否被移动、删除或迁移。
2. 用户是否有 Browse Project。
3. Issue Security Level 是否限制了用户、组、角色、Reporter 或 Assignee。
4. 用户目录同步是否正常，组成员是否过期。
5. 用户看到的是否是同名项目或错误站点。
6. JQL 是否额外排除了 Issue，过滤器是否由其他用户拥有。
7. 是否存在缓存、索引或应用异常。

修复后要用该用户实际登录验证，同时用一个不应访问的用户执行负向验证，防止为了“让他看到”而扩大了权限。

## 37. 某个 Transition 在管理员账号可见，普通用户看不到，怎么排查？

**参考回答：**

检查：

- Workflow Transition 的 Condition；
- 用户是否有对应项目权限；
- 用户是否属于指定项目角色或组；
- Issue 当前状态是否允许该 Transition；
- Issue Security 是否影响可见性；
- Transition 是否只对特定 Issue Type 或字段上下文生效；
- 是否有应用/脚本动态隐藏 Transition；
- 浏览器缓存和节点配置是否一致。

管理员可见不能证明普通用户路径正确，因为管理员经常绕过部分项目限制。应使用真实角色用户测试，而不是只用管理员验证。

## 38. 用户说“邮件没收到”，如何区分 Jira 和邮箱问题？

**参考回答：**

先确认事件是否应该发送邮件：

1. Issue 是否真的发生了触发通知的事件？
2. Notification Scheme 是否把事件发送给该用户、组、Reporter、Assignee 或项目角色？
3. 用户是否有 Browse Project 和 Issue Security 访问权限？
4. 用户邮箱是否正确、账号是否激活、是否退订或被抑制？
5. Jira 邮件队列是否积压或失败？
6. SMTP/API 邮件服务是否可达，凭据和证书是否正常？
7. 邮件是否到达网关但被隔离、退信或垃圾邮件系统拦截？

不要直接重复触发大量通知。先抽取一个 Issue 和一个收件人，追踪事件、Jira 出站日志、邮件网关和收件箱的完整链路。

## 39. Jira API 返回 401、403、404 或 429，分别怎么判断？

**参考回答：**

- **401**：认证信息无效、过期、格式错误，或请求没有携带正确凭据。
- **403**：身份已识别，但没有相应权限，或触发了安全策略/限流策略。
- **404**：资源不存在、路径/API 版本错误，或者出于安全原因对无权资源隐藏存在性。
- **429**：请求频率过高，需要遵守 Retry-After、退避和并发限制。

排查时记录 URL（隐去敏感参数）、方法、账号/服务账号、响应头、请求时间、Issue Key 和 Jira/网关请求 ID。不要用“把账号加成管理员”作为 API 排障的默认手段。

## 40. Jira 数据库磁盘快满时，你会怎么做？

**参考回答：**

先保护系统：

1. 确认是数据库数据文件、日志、临时文件、备份还是共享附件占满。
2. 评估增长速度、数据库健康和写入风险。
3. 暂停非必要的批处理、报表和大规模导入。
4. 按已审批的保留策略清理可删除对象，不能直接删除未知文件。
5. 扩容或增加存储前确认数据库和文件系统支持方式。
6. 检查日志轮转、备份失败、长事务和异常查询。
7. 验证数据库、Jira、索引和备份均恢复正常。

禁止直接删除数据库文件、Jira 数据目录或日志而不确认所有者、锁和恢复影响。磁盘告警本身也是容量治理失效的信号，应在事后补充阈值、趋势和责任人。

## 41. 如何判断一个 Jira 自动化规则是否造成系统变慢？

**参考回答：**

比较规则启用前后的执行量、失败率、平均耗时、触发来源和 Jira 节点指标。重点看：

- 是否监听了所有 Issue 更新；
- 是否对每次事件执行多个 JQL 查询；
- 是否批量修改同一批 Issue；
- 是否调用慢或不稳定的外部 API；
- 是否产生重复事件或递归；
- 是否与索引、邮件、Webhook 和 SLA 同时放大负载。

可以先在受控范围禁用或限流规则，再观察指标是否恢复，同时保留证据和回滚方案。不能为了性能直接删除规则，因为它可能承担审计或服务交付职责。

## 十二、架构设计与高级面试题

## 42. 设计一个受监管企业的 Jira 项目模板，你会怎么做？

**参考回答：**

我会先把模板拆成治理层和业务层：

**治理层：**

- 标准命名、项目负责人和数据分类；
- 默认权限、Issue Security 和项目角色；
- 标准审计字段、变更关联和敏感数据提醒；
- 统一工作流骨架与关闭条件；
- 默认通知、自动化、SLA 和报表；
- 项目创建、变更和回收流程。

**业务层：**

- 根据研发、服务台、风险、审计或变更管理选择 Issue Type；
- 定义必要而不是过量的字段；
- 把审批、实施、验证和关闭映射到可审计状态；
- 为例外流程定义升级和人工复核。

模板发布前在测试项目演练创建、编辑、权限、报表、API、备份和回收；生产中通过版本化变更管理维护模板，避免每个项目都随意复制后产生漂移。

## 43. 如何治理“项目越建越多、字段越加越多、工作流越来越复杂”？

**参考回答：**

建立平台治理委员会或明确的产品负责人，制定：

- 项目准入和退出标准；
- Issue Type、字段和状态的命名规范；
- 标准方案与例外方案；
- 自定义字段申请、影响评估和生命周期；
- 工作流复杂度、Transition 数量和权限变更评审；
- 共享过滤器、看板和自动化的 owner；
- 定期清理无用字段、项目、规则和应用。

治理的目标不是阻止变化，而是让变化可理解、可追踪、可回滚。每个配置都应有业务目的、负责人和停用条件。

## 44. 如何衡量 Jira 平台运维质量？

**参考回答：**

可以建立四类指标：

**稳定性：**

- 可用性、错误率、P95/P99 响应时间；
- 节点故障、数据库故障和集成失败次数；
- 备份成功率、恢复演练成功率、RTO/RPO。

**交付质量：**

- Jira 变更成功率；
- 回滚率和变更引发的事故；
- 自动化成功率和平均恢复时间；
- 升级/迁移缺陷数量。

**数据治理：**

- 项目、用户、组、字段和过滤器的复核完成率；
- 孤儿项目、过期账号、无 owner 规则；
- 敏感数据发现与处理时效。

**用户体验：**

- 页面/API 延迟；
- 服务台 SLA 达标率；
- 支持请求解决时间；
- 用户自助率和重复问题率。

不要只用 Issue 数量、关闭率或 SLA 达标率作为绩效指标，否则团队可能通过拆单、错误关闭或滥用暂停条件“优化数字”。

## 45. 如果你接手一个没有文档的 Jira 实例，前三十天怎么做？

**参考回答：**

**第一周：建立基线**

- 盘点版本、部署模式、节点、数据库、存储、应用和集成；
- 识别管理员、服务账号、关键项目和高风险权限；
- 检查备份、监控、日志、容量和已知事故；
- 暂停未经评估的高风险配置变更。

**第二周：理解业务和数据**

- 访谈平台 owner、服务台、开发、审计和安全团队；
- 识别关键工作流、SLA、审批和报表；
- 清点字段、项目、权限方案、自动化和共享过滤器；
- 找出没有 owner 的配置。

**第三周：降低明显风险**

- 清理过期管理员和服务账号权限；
- 修复备份/监控缺口；
- 为高风险变更增加审批和回滚；
- 为核心集成补充告警、重试和审计。

**第四周：形成治理路线图**

- 文档化现状和依赖；
- 定义标准项目模板和变更流程；
- 规划升级、性能、灾备、数据清理和迁移；
- 建立指标、责任人和季度复核机制。

先建立事实和控制，再做大规模重构；否则很容易把未知问题搬到新架构中。

## 十三、面试中的常见失分点

1. **只会点界面，不懂依赖关系。** 能创建工作流，但说不清 Permission Scheme、Issue Security 和字段上下文。
2. **把管理员权限当成解决方案。** 临时扩大权限可能掩盖配置错误，违反最小权限原则。
3. **只会重启、重建索引或清缓存。** 没有证据和根因分析的“万能操作”不适合生产环境。
4. **忽略 Cloud/DC 差异。** 把数据库直连、文件系统操作或旧插件方案直接用于 Cloud。
5. **只谈功能，不谈回滚。** 生产变更必须有影响评估、验证和失败处理。
6. **把 Jira 当作所有系统的主数据库。** 没有定义数据 owner 和同步边界。
7. **只关注成功路径。** 没有考虑重复事件、API 限流、外部系统不可用和补偿机制。
8. **忽略审计证据。** 说“配置好了”，但无法证明谁改的、何时改的、如何验证。
9. **把关闭率当作服务质量。** 忽略重开率、重复事件、用户满意度和问题复发。
10. **在 Issue 中存放秘密。** 评论、附件、导出、备份和日志都可能扩大泄露范围。

## 十四、可直接背诵的高级总结

> 我把 Jira 视为一个承载业务工作流的受治理平台，而不只是工单页面。运维时我会先明确 Cloud 还是 Data Center，以及数据、身份、数据库、附件、索引和外部集成的责任边界；配置上优先使用标准方案和最小权限，复杂逻辑放在正确的工作流、自动化或集成层；变更前做影响评估、备份和小范围验证，变更后验证正向和负向权限、通知、索引、API 和审计结果；发生故障时先界定范围并保留证据，再从权限、配置、应用、基础设施和外部依赖逐层排查。对审计和受监管场景，我会特别关注职责分离、敏感数据最小化、不可抵赖的操作记录、恢复演练以及 RTO/RPO，而不会用重启、扩大管理员权限或直接改数据库作为默认答案。
