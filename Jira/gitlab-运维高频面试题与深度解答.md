# GitLab 运维高频面试题与深度解答

本文面向 GitLab Self-Managed（Enterprise）管理员、GitLab 平台工程师、DevOps 工程师、CI/CD 运维工程师和企业级研发效能平台负责人。内容重点覆盖以下工作范围：

- GitLab Self-Managed 实例的日常运维、版本升级和补丁管理；
- GitLab CI/CD Runner 集群的部署、扩缩容和性能调优；
- 用户、Group、Project、SSO 和最小权限治理；
- 项目模板、CI/CD Pipeline 模板和 Group 级别策略；
- GitLab Geo、高可用、备份恢复和灾难演练；
- PostgreSQL、Redis、Gitaly、对象存储等依赖组件；
- GitLab API、自动化脚本以及 ServiceNow 工单协作；
- 审计、税务和咨询行业中对敏感代码、客户资料、职责分离和操作证据的要求。

> **版本提示：** GitLab 的功能、许可层级、配置项和 Helm Chart 结构会随版本变化。面试中不要把某个版本的菜单名称、配置字段或命令当成永久不变的事实；应说明版本假设，并以目标版本的官方文档、升级说明和预生产验证结果为准。

## 一、面试回答框架

### 1. 概念题的回答顺序

建议按照以下顺序回答：

1. 用一句话定义概念以及它解决的问题；
2. 说明它在 GitLab 请求链路或数据模型中的位置；
3. 结合生产环境中的一个例子；
4. 说明边界、依赖、风险和验证方式；
5. 如果存在 Omnibus 与 Helm、Self-Managed 与 GitLab.com 的差异，主动说明差异。

### 2. 故障题的排查顺序

使用“现象—范围—证据—假设—验证—修复—复盘”的顺序：

1. 先确认影响范围：单个用户、单个项目、一个 Runner、一个节点还是整个实例；
2. 记录发生时间、请求 ID、项目路径、用户、错误信息和最近变更；
3. 先执行只读检查，避免在未知状态下重启、扩容、重建索引或批量改权限；
4. 从距离现象最近的层开始排查，再向依赖组件扩展；
5. 修复后进行正向验证、负向验证和回归验证；
6. 保存日志、变更记录、工单编号和验证结果，形成可审计证据。

### 3. 设计题的回答重点

设计 GitLab 平台时，不能只回答“部署几个 Pod”或“开一个 Runner”。至少需要说明：

- 身份源、权限边界和 break-glass 管理员如何治理；
- Web、Sidekiq、Gitaly、PostgreSQL、Redis、对象存储之间如何解耦；
- 代码仓库、制品、备份和日志的保留策略；
- 版本升级、配置变更、数据库迁移和回滚如何执行；
- CI/CD 中不受信任代码如何隔离；
- RTO、RPO、Runners 容量、跨地域灾备和故障演练如何验证；
- 审计证据如何留存，敏感客户数据如何最小化。

## 二、GitLab 平台定位与核心架构

## 1. GitLab 是什么？它与 Git 有什么区别？

**参考回答：**

Git 是分布式版本控制系统，负责提交、分支、标签、合并和历史管理；GitLab 是围绕 Git 构建的一套研发协作和 DevSecOps 平台，提供：

- 远程 Git 仓库和代码评审；
- Group、Project、成员和权限管理；
- Merge Request、Issue、Wiki 和发布管理；
- CI/CD Pipeline、Runner、制品和环境；
- 安全扫描、审计事件、合规策略和 API；
- 企业身份集成、通知、监控和管理员运维能力。

因此，GitLab 运维不仅是“保证 Git clone 成功”，还要保证身份、权限、Web 请求、异步任务、仓库存储、数据库、制品、Runner 和外部集成整体可用。

**常见误区：**

- 把 GitLab 当成单体 Web 应用，只监控网页状态；
- 认为仓库备份等于完整备份，忽略 PostgreSQL、对象存储、配置和密钥；
- 只给用户开通项目权限，却不考虑 Group 继承、Protected Branch 和审批策略；
- 认为 Pipeline 成功完全由 GitLab Web 节点负责，忽略 Runner、网络、镜像仓库和凭据。

## 2. GitLab Self-Managed、GitLab.com 和 GitLab Dedicated 有什么区别？

**参考回答：**

| 维度 | GitLab Self-Managed | GitLab.com | GitLab Dedicated |
|---|---|---|---|
| 基础设施 | 企业负责部署、网络、系统和依赖组件 | GitLab 托管 | GitLab 提供隔离环境和托管能力 |
| 升级责任 | 企业负责版本、补丁和变更窗口 | 由平台方负责 | 由服务方按服务约定负责 |
| 数据边界 | 可自行控制网络、存储和备份 | 受平台能力和服务条款约束 | 提供更强的隔离和合规能力 |
| 故障排查 | 可查看主机、组件和数据库 | 主要依靠平台支持和公开能力 | 依赖服务边界和支持流程 |
| 本文重点 | Omnibus、Helm、数据库、Runner、Geo 和灾备 | 仅用于对比 | 仅用于对比 |

面试中如果题目明确要求 Self-Managed，就不能把“联系 GitLab 平台支持”作为默认排障方案。应说明自己会如何查看日志、组件健康、数据库、Gitaly、对象存储、Runner 和最近变更。

## 3. GitLab 的典型请求链路是什么？

**参考回答：**

一个用户访问项目页面、调用 API 或发起 Git 操作时，典型链路可以抽象为：

```text
用户或 CI Job
    -> DNS / 负载均衡 / WAF
    -> NGINX 或 Ingress
    -> Workhorse
    -> Puma / Rails
    -> PostgreSQL、Redis、Gitaly、对象存储、外部身份源
```

异步任务通常经过：

```text
Rails 产生任务
    -> Redis 队列
    -> Sidekiq
    -> PostgreSQL / Gitaly / 对象存储 / 外部系统
```

Runner 执行 Pipeline 时，还会涉及：

```text
GitLab API
    -> Runner 注册和任务轮询
    -> Executor（Shell、Docker、Kubernetes 等）
    -> 代码仓库、镜像仓库、依赖仓库、部署目标
```

排查页面慢、API 失败或 Pipeline 卡住时，应先定位请求在哪一层停止，而不是直接重启所有服务。

## 4. GitLab 的核心组件分别负责什么？

**参考回答：**

- **NGINX/Ingress：** 负责 TLS 终止、路由、连接和基本访问控制；
- **Workhorse：** 处理部分高吞吐请求，并把合适的请求转给 Rails；
- **Puma/Rails：** 提供 Web 页面、API、鉴权和业务逻辑；
- **Sidekiq：** 执行邮件、导入导出、Pipeline 处理等异步任务；
- **PostgreSQL：** 保存用户、项目、权限、Pipeline 元数据、配置和审计相关数据；
- **Redis：** 用于队列、缓存、会话或协调能力，具体用途随版本和配置而变化；
- **Gitaly：** 为 GitLab 提供仓库访问和 Git RPC 能力；
- **Praefect/Gitaly Cluster：** 在适用架构中为 Gitaly 提供仓库级高可用和一致性协调；
- **对象存储：** 保存 LFS、Job Artifacts、上传文件、Container Registry 或备份等大对象；
- **Runner：** 获取并执行 CI/CD Job；
- **Prometheus、日志和告警组件：** 提供可观测性。

关键点是：GitLab 不是所有组件都必须部署在同一台机器上。生产环境通常会根据容量、可用性和隔离要求拆分计算、数据库、仓库存储和对象存储。

## 5. Omnibus 和 Helm Chart 部署有什么区别？

**参考回答：**

| 维度 | Omnibus | GitLab Helm Chart |
|---|---|---|
| 部署形态 | Linux 软件包和系统服务 | Kubernetes 资源和容器 |
| 配置入口 | `gitlab.rb`、`gitlab-secrets.json` 等 | Helm values、Secret、ConfigMap |
| 生命周期 | 包管理器、`reconfigure`、系统服务 | Helm upgrade、滚动发布、Kubernetes 控制器 |
| 扩缩容 | 节点和组件级拆分，自动化程度取决于架构 | 更适合通过副本、节点池和自动扩缩容管理 |
| 依赖 | 可内置部分组件，也可接外部服务 | 生产环境通常考虑外部 PostgreSQL、Redis、对象存储和可靠的 Gitaly 方案 |
| 主要风险 | 配置漂移、升级顺序、单机资源瓶颈 | values 漂移、PVC、Pod 调度、Ingress、网络策略和版本兼容性 |

两者都不是“装完就结束”。都需要版本管理、配置审查、密钥保护、监控、备份、升级和恢复演练。

## 6. 什么时候选择 Omnibus，什么时候选择 Helm？

**参考回答：**

选择时不应只看“团队是否会 Kubernetes”，而要综合考虑：

- 企业是否已有成熟的 Kubernetes 平台、存储和安全基线；
- 是否需要容器化交付、弹性扩缩和统一平台治理；
- 数据库、Redis、对象存储、Gitaly 是否有可用的外部托管能力；
- 团队对 Linux 包、Kubernetes、Helm 和故障排查的掌握程度；
- 升级、监控、备份、审计和灾备流程是否已自动化；
- 组织的 RTO/RPO、网络隔离和合规要求。

如果团队只有一台可靠的 Linux 服务器、规模较小且需要快速稳定落地，Omnibus 可能更简单；如果已有成熟的 Kubernetes 生产平台，并且能处理有状态服务、持久化存储和跨集群灾备，Helm 可能更合适。无论选择哪种方式，都应避免把 PostgreSQL、Redis、对象存储和 Gitaly 的高可用责任隐含掉。

## 7. GitLab 的日常运维工作包括哪些内容？

**参考回答：**

日常运维可以分成几个维度：

**服务健康**

- Web、API、Sidekiq、Gitaly、Runner 和外部依赖健康；
- 错误率、延迟、队列积压、连接数和资源使用率；
- 证书、域名、Webhook 和外部身份源状态。

**容量与性能**

- CPU、内存、磁盘、IOPS、网络和文件描述符；
- PostgreSQL 连接、锁、慢查询、WAL、复制延迟和膨胀；
- Gitaly 请求耗时、大仓库、LFS 和对象存储容量；
- Runner 并发量、排队时长和执行耗时。

**安全与治理**

- 管理员、Owner、服务账号和访问令牌；
- SSO、SCIM/LDAP 同步、离职账号和过期权限；
- 审计事件、令牌轮换、密钥和敏感变量；
- Group/Project 的可见性、分支保护和合规规则。

**变更与恢复**

- 补丁、版本升级、配置变更和依赖升级；
- 备份成功率、恢复抽样和灾备演练；
- ServiceNow 工单、变更记录和事故复盘。

## 8. 如何管理 GitLab 的配置，避免配置漂移？

**参考回答：**

首先把配置分为三类：

1. **基础设施配置：** 操作系统、网络、负载均衡、Kubernetes、存储和数据库；
2. **GitLab 运行配置：** Omnibus 的 `gitlab.rb`、Helm values、Ingress、Runner 配置、对象存储和外部服务；
3. **业务治理配置：** Group、Project、权限、模板、Protected Branch、Pipeline 策略和集成。

建议：

- 将非机密配置纳入 Git 版本控制；
- 使用代码评审和变更审批；
- 密钥存放在受控的 Secret 管理系统，不提交到仓库；
- 每次变更记录版本、责任人、影响范围、验证和回滚方式；
- 通过自动化将配置应用到预生产，再推广到生产；
- 定期导出或盘点实际配置，与期望状态做差异比较。

不要把手工登录 Web 界面或直接修改生产 Pod 当成长期治理方式。

## 三、版本升级、补丁与变更管理

## 9. GitLab 版本升级前要做哪些准备？

**参考回答：**

我会按以下顺序准备：

1. 确认当前版本、目标版本、许可层级和官方升级路径；
2. 阅读目标版本和中间版本的升级说明、弃用项和已知问题；
3. 检查 Omnibus/Helm、Runner、Gitaly、数据库、Redis、插件和外部集成兼容性；
4. 检查数据库、仓库、对象存储、备份和磁盘空间；
5. 在预生产或恢复环境中执行一次接近真实数据规模的升级；
6. 记录升级前基线：登录、clone、push、MR、Pipeline、Runner、API、Webhook、备份和监控；
7. 完成备份，并确认备份可以读取或已经做过恢复验证；
8. 制定维护窗口、通信计划、成功标准、失败标准和回滚/恢复方案；
9. 为 SSO、Runner、ServiceNow 和管理团队安排验证人。

不能只说“先备份再升级”。备份是否可恢复、恢复需要多长时间、外部对象是否另行保护，决定了备份的实际价值。

## 10. GitLab 升级失败时如何回滚？

**参考回答：**

先区分两类情况：

- **应用包或容器启动失败：** 可能可以回到原版本并恢复原配置；
- **数据库迁移已经执行：** 不能假设简单降级包版本就是安全回滚，通常要遵循该版本支持的回滚路径，必要时从备份恢复到隔离环境，再切换流量。

升级前应明确：

- 是否支持目标版本到旧版本的降级；
- 数据库迁移是否可逆；
- Gitaly、Runner、对象存储和外部应用是否已经产生新格式数据；
- 采用版本回退、数据库恢复还是完整环境切换；
- DNS、负载均衡、证书、密钥和外部集成如何同步回退。

生产回滚不是“执行一个 downgrade 命令”。如果数据状态已经向前迁移，应优先采用经过演练的恢复或蓝绿/备用环境切换方案。

## 11. 如何制定 GitLab 补丁管理策略？

**参考回答：**

我会建立风险分级和时间目标：

- **关键安全漏洞：** 评估是否影响暴露面、认证、远程执行、Runner 隔离或敏感数据，必要时缩短窗口并执行紧急变更；
- **常规安全更新：** 纳入固定维护窗口，先做兼容性和回归验证；
- **功能版本升级：** 按季度或组织发布节奏规划，避免长期停留在不可维护版本；
- **操作系统和依赖组件补丁：** 与 GitLab 版本升级分开评估，避免一次变更多个未知变量。

每个补丁变更至少应包含：

- 漏洞或版本影响分析；
- 目标节点和组件；
- 预检查、备份和监控；
- 维护窗口和通知；
- 验证清单；
- 回滚或恢复方式；
- 证据、结果和后续动作。

## 12. 如何验证一次升级成功？

**参考回答：**

验证应覆盖功能、性能和治理：

**功能验证**

- 管理员和普通用户登录；
- SSO 登录、组同步或账号禁用；
- 查看项目、clone、push、创建 MR、评论和审批；
- 创建并执行成功、失败、取消和重试 Pipeline；
- Runner 注册、领取 Job、上传 Artifact；
- API、Webhook、ServiceNow 集成；
- 备份任务和监控告警。

**非功能验证**

- Web/API 错误率和延迟回到基线；
- Sidekiq 队列没有持续积压；
- Gitaly、PostgreSQL、Redis 和对象存储无异常；
- 磁盘、连接、内存和文件描述符正常；
- 审计事件能够记录关键操作。

**负向验证**

- 无权限用户不能读取私有项目；
- 非保护分支不能执行受限操作；
- 失效令牌不能调用 API；
- 非授权 Runner 不能获取敏感 Job；
- SSO 禁用用户不能继续访问。

## 四、高可用、Geo、备份与恢复

## 13. GitLab 高可用架构需要哪些组件？

**参考回答：**

一个生产级高可用方案通常包含：

- 多个无状态 Web/API 节点；
- 多个 Sidekiq 处理实例，并按队列或负载分配；
- 可靠的负载均衡和健康检查；
- Gitaly 高可用方案，必要时使用 Gitaly Cluster/Praefect；
- PostgreSQL 高可用和经过演练的主备切换；
- Redis 的高可用和故障切换；
- 对象存储的高可用、版本保护和生命周期治理；
- 独立 Runner 集群，避免 GitLab 节点故障导致所有流水线停止；
- 监控、日志、告警、备份和恢复环境。

高可用不是简单地“把 Web Pod 副本数改成 3”。如果 PostgreSQL、Redis、Gitaly 或对象存储仍是单点，整体可用性仍由最弱环节决定。

## 14. GitLab Geo 解决什么问题？它与普通备份有什么区别？

**参考回答：**

GitLab Geo 主要用于跨地域复制和灾难恢复场景。它可以将部分 GitLab 数据和仓库内容复制到 secondary site，并通过同步状态、验证和切换流程降低地域级故障的恢复时间。

它与备份的区别是：

- **备份：** 重点是获得某个时间点的数据副本，用于误删除、损坏或灾难后的恢复；
- **Geo：** 重点是跨站点保持可用副本，并为站点级切换提供基础；
- Geo 不是备份的替代品，也不能自动解决所有对象存储、外部集成、身份源和配置问题。

需要明确：

- primary 与 secondary 的角色；
- 数据库、仓库、LFS、Job Artifacts、上传文件和容器镜像的同步范围；
- 复制延迟和未同步数据如何处理；
- DNS、负载均衡、Runner、SSO、Webhook 和外部系统如何切换；
- 提升 secondary 前如何停止旧 primary、确认数据一致性并避免双主写入。

## 15. GitLab Geo 出现同步延迟时怎么排查？

**参考回答：**

我会先确认是全局延迟，还是某类数据延迟：

1. 记录 primary 和 secondary 的时间、站点状态和延迟指标；
2. 区分仓库、数据库事件、LFS、Artifact、上传文件或 Container Registry 的同步；
3. 检查 primary 到 secondary 的网络、带宽、TLS、DNS 和防火墙；
4. 检查 secondary 的处理队列、磁盘、IO、CPU、内存和数据库连接；
5. 查看失败记录、重试次数和具体项目；
6. 检查对象存储权限、生命周期、版本和配额；
7. 评估是否有大仓库、大文件或大量 Pipeline 造成积压；
8. 不直接删除队列或手工修改状态，先确认官方支持的重试和修复方式；
9. 确认延迟是否超出 RPO，并向业务说明可能丢失的最新变更范围。

排障结果应形成“当前同步到哪个时间点、哪些项目受影响、是否可以安全切换”的明确结论。

## 16. GitLab 备份应该包含哪些内容？

**参考回答：**

完整的恢复方案至少要考虑：

- PostgreSQL 数据；
- Git 仓库和仓库元数据；
- LFS 对象；
- Job Artifacts、上传文件、Package/Container Registry 等对象；
- GitLab 配置和密钥；
- TLS 证书及其保护方式；
- 外部对象存储中的数据和版本；
- Runner、Webhook、外部身份源和集成的配置；
- 监控、告警、DNS、负载均衡和基础设施定义。

GitLab 自带备份工具覆盖范围要以目标版本和实际配置为准。使用外部 PostgreSQL、对象存储、Redis 或 Helm 部署时，不能因为执行了一次 GitLab 备份命令，就认为所有外部数据都已被保护。

## 17. 如何设计 GitLab 的备份策略？

**参考回答：**

我会从 RPO、RTO 和恢复对象出发：

**备份频率**

- 数据库按业务可接受的数据丢失窗口执行备份；
- 仓库和对象按变化量、重要性和存储成本制定策略；
- 配置、密钥和基础设施定义在每次变更后保留版本；
- 备份本身采用与生产隔离的存储和权限。

**备份保护**

- 加密传输和静态加密；
- 不同账号或不同权限边界；
- 保留周期、不可变存储或版本保护；
- 防止生产凭据被用于删除备份；
- 监控备份成功率、大小异常和过期情况。

**恢复验证**

- 定期恢复到隔离环境；
- 验证用户、项目、仓库、MR、Pipeline 元数据、Artifact 和附件；
- 验证密钥、SSO、Runner 和外部集成；
- 记录实际恢复时间并与 RTO 比较；
- 明确最后一个可恢复时间点并计算 RPO。

## 18. 如何执行一次 GitLab 恢复演练？

**参考回答：**

恢复演练应该在不影响生产的隔离环境中执行：

1. 准备与生产版本、拓扑和依赖尽量接近的环境；
2. 获取指定时间点的 GitLab 备份、数据库备份、对象存储副本、配置和密钥；
3. 按受支持的恢复顺序恢复数据库、Git 数据和对象；
4. 恢复配置后，先关闭外部写入、Webhook、定时任务和通知；
5. 验证用户、组、项目、仓库、权限、MR、Pipeline 和制品；
6. 验证 API、SSO、Runner 和关键外部集成；
7. 测量恢复耗时、数据缺口和人工操作；
8. 删除或隔离演练环境中的敏感数据；
9. 输出演练报告，修正恢复脚本和文档。

恢复演练的目标不是证明“命令没有报错”，而是证明业务能够在约定时间内恢复，并且数据、权限和安全边界正确。

## 五、PostgreSQL、Gitaly、Redis 与存储

## 19. GitLab 使用 PostgreSQL 存储哪些信息？数据库故障如何影响 GitLab？

**参考回答：**

PostgreSQL 通常保存用户、组、项目、权限、配置、Issue、Merge Request、Pipeline 元数据、审计和许多业务状态。Git 仓库对象本身主要由 Gitaly 管理，但 GitLab 业务层仍需要数据库元数据来关联项目、用户和仓库。

数据库不可用时可能出现：

- 登录、项目页面和 API 失败；
- 权限计算无法完成；
- Pipeline 创建、状态更新和队列处理异常；
- 管理配置、审计和外部集成受影响；
- 已建立的 Git 操作也可能因鉴权或仓库定位失败而失败。

排查时要同时检查连接池、数据库主备、锁、磁盘、IO、WAL、复制延迟和网络，而不是只看 PostgreSQL 进程是否存在。

## 20. GitLab PostgreSQL 的日常运维重点是什么？

**参考回答：**

重点包括：

- 连接数、连接池和长事务；
- CPU、内存、磁盘、IOPS 和 WAL 增长；
- 慢查询、锁等待和阻塞链；
- 表和索引膨胀；
- autovacuum 是否正常工作；
- 主备复制状态、延迟和切换能力；
- 备份成功率和恢复时间；
- 数据库版本、扩展和 GitLab 支持矩阵。

生产环境不应未经评估直接执行 `VACUUM FULL`、删除表、修改 GitLab 内部数据或重建大量索引。需要先评估锁、空间、业务窗口和官方支持方式。

## 21. GitLab 页面变慢，但主机 CPU 不高，如何排查？

**参考回答：**

低 CPU 不代表系统没有瓶颈。我会按请求链路排查：

1. 确认是所有页面慢，还是特定项目、用户、API 或操作慢；
2. 查看 NGINX/Ingress、Workhorse、Puma 请求耗时和错误；
3. 检查 Puma 线程、请求队列、连接池和下游等待；
4. 检查 PostgreSQL 慢查询、锁、连接和 IO；
5. 检查 Gitaly 请求、仓库大小、Git 操作和存储延迟；
6. 检查 Redis 延迟、连接和 Sidekiq 队列；
7. 检查对象存储请求、网络和 TLS；
8. 对比最近发布、配置、数据增长和外部系统变化；
9. 用请求 ID 或时间窗口关联应用日志和依赖日志。

修复可能是优化查询、修正索引或权限范围、拆分大仓库、调整连接池、解决存储延迟，也可能是限制异常 API 调用。不能看到慢就盲目增加 Web 副本。

## 22. Gitaly 的作用是什么？为什么不建议把 Git 仓库简单放到共享 NFS？

**参考回答：**

Gitaly 为 GitLab 提供统一的仓库访问服务和 Git RPC 能力，使 Rails、Sidekiq 等组件不需要直接管理仓库文件。它还负责仓库相关操作的隔离、路由、监控和在适用架构中的复制协调。

直接依赖普通共享 NFS 可能带来：

- 文件锁、缓存一致性和延迟问题；
- 大量并发 Git 操作时性能不可预测；
- 故障时难以判断是 GitLab、网络还是存储问题；
- 备份、复制和仓库完整性验证复杂；
- 多节点同时访问造成更高的数据一致性风险。

实际方案应根据 GitLab 版本、规模和支持矩阵选择 Gitaly、Gitaly Cluster/Praefect 或经过验证的存储架构，而不是只看单次读写速度。

## 23. 如何排查 Git clone/push 失败？

**参考回答：**

先区分协议和范围：

- SSH 失败还是 HTTPS 失败；
- 所有项目失败还是单个仓库失败；
- clone 失败还是 push 失败；
- 认证失败、权限失败、仓库不存在，还是传输中断。

检查顺序：

1. DNS、负载均衡、TLS 和网络连通性；
2. SSH 端口、密钥、用户映射或 HTTPS 令牌；
3. 项目可见性、成员权限、Protected Branch 和 push 规则；
4. Rails/Workhorse/SSH/Gitaly 日志；
5. 仓库是否损坏、是否过大、是否有大文件；
6. Gitaly 节点、磁盘、IO、文件描述符和并发；
7. Git LFS、代理、超时和客户端版本；
8. 最近的权限、证书、仓库迁移或存储变更。

如果怀疑仓库损坏，应先保护现场、限制写入并执行官方支持的检查或恢复流程，不直接删除仓库目录或手工改 Git 文件。

## 六、Git、项目与权限治理

## 24. Group、Subgroup 和 Project 的关系是什么？

**参考回答：**

Project 是代码、Issue、Merge Request、Pipeline 和制品等资源的基本边界；Group 用于组织多个项目、统一成员、继承权限、变量、Runner 和治理策略；Subgroup 可以进一步表达部门、客户、产品线或环境边界。

设计时应考虑：

- Group 层级是否与组织责任和数据边界一致；
- 成员继承是否会造成越权；
- 项目 Owner 是否明确；
- Group 级变量、Runner 和策略是否会影响所有子项目；
- 客户项目、内部项目和共享模板是否需要不同的可见性和隔离。

不要为了方便把所有用户加入顶层 Group，也不要用无限层级掩盖职责不清的问题。

## 25. GitLab 的项目可见性和成员角色如何治理？

**参考回答：**

项目可见性通常需要在 Private、Internal、Public 等范围内选择；企业内部的客户代码、审计底稿、税务材料和咨询交付代码通常应默认为 Private，并通过 Group 和成员角色按需授权。

治理原则：

- 使用组和角色表达稳定的业务职责；
- 避免大量直接给个人授权；
- Owner、Maintainer、Developer、Reporter、Guest 等角色只授予完成工作所需的最低权限；
- 对高风险操作启用审批、保护分支和职责分离；
- 定期复核成员、继承权限、共享项目和访问令牌；
- 账号离职、转岗和项目结束时及时撤权。

需要注意，项目角色只是一个层次；Protected Branch、Group 策略、部署权限、Runner 和外部身份映射还会影响最终能力。

## 26. Protected Branch、Merge Request Approval 和 Code Owner 如何配合？

**参考回答：**

- **Protected Branch：** 限制谁可以直接 push、谁可以 merge，以及哪些角色可执行发布相关操作；
- **Merge Request Approval：** 要求特定人数、组或规则的审批；
- **Code Owner：** 根据文件路径指定代码责任人，要求对应人员参与审查；
- **CI/CD 规则：** 在合并前执行测试、扫描、许可证检查或合规检查。

在审计、税务和咨询行业中，可以将客户项目、生产部署配置和安全敏感目录分别设置责任人和审批要求。但要注意：

- 不能只依赖开发者自觉；
- 不能让提交者同时满足所有审批要求；
- 必须验证规则是否被分支、项目设置或特权角色绕过；
- 变更规则本身也应受审批和审计。

## 27. 如何设计 GitLab 项目模板和 Group 模板？

**参考回答：**

模板的目标是提供安全、可运行、可维护的默认值，而不是复制一份没人维护的示例代码。

一个合格的模板应包含：

- README、目录规范、分支和提交约定；
- 基础 `.gitlab-ci.yml` 或引用的 CI 模板；
- 依赖缓存、测试、构建、扫描和制品保留策略；
- Protected Branch、MR 审批、Code Owner 和默认标签；
- 项目 Owner、数据分类、客户/部门属性和联系人；
- 失败处理、通知、监控和 ServiceNow 关联约定；
- 模板版本、维护责任人和迁移说明。

模板应支持版本化和变更通知。不能随意修改模板后让所有现有项目隐式发生不可审计的行为变化。

## 28. 如何实施 Group 级别策略？

**参考回答：**

Group 级策略可以用于统一：

- CI/CD 变量和环境保护；
- Runner 允许范围；
- Pipeline 模板或合规流水线；
- 项目创建、可见性和命名约束；
- 合并审批、扫描和分支保护；
- 依赖、许可证和安全控制；
- 项目访问请求和成员复核。

实施时要先定义：

1. 哪些策略是强制的，哪些只是建议；
2. 适用哪些项目和例外由谁审批；
3. 失败时是阻断、告警还是创建工单；
4. 如何在预生产验证；
5. 如何处理历史项目和模板升级；
6. 如何通过 API 或报表证明所有项目都符合策略。

不同 GitLab 版本和许可层级支持的策略能力不同，应在面试中明确这一点。

## 七、SSO、LDAP、SCIM 与安全

## 29. SAML SSO、LDAP 和 SCIM 分别解决什么问题？

**参考回答：**

- **SAML SSO：** 解决用户登录认证，将登录交给企业身份提供商；
- **LDAP：** 可用于目录认证和用户/组同步，具体能力依赖配置和版本；
- **SCIM：** 解决账号生命周期自动化，例如创建、更新、禁用和组成员同步；
- **GitLab 本地账号：** 可作为受控的应急或特殊账号，但不应成为绕过企业身份治理的常规入口。

认证、授权和生命周期不是同一件事。即使 SSO 登录成功，也要确认用户在 GitLab 中的组、项目、角色和离职撤权是否正确。

## 30. GitLab SSO 登录失败如何排查？

**参考回答：**

先确认失败发生在哪一段：

1. 用户是否被身份提供商拒绝；
2. SAML/OIDC 响应是否返回 GitLab；
3. Entity ID、ACS URL、证书、签名、时钟和 NameID 是否一致；
4. 用户的邮箱、用户名或唯一标识是否发生变化；
5. Group/Role 映射是否正确；
6. GitLab 侧的 SSO 配置、审计日志和应用日志是否报错；
7. 反向代理、TLS、Cookie、跨域或多节点会话是否有问题；
8. 账号是否已被禁用、锁定或取消授权。

生产变更前应保留一个经过严格控制的 break-glass 管理员，并验证其存储、轮换、审批、使用告警和事后复核。不能为了修复 SSO 而长期关闭认证要求或给所有用户提升为管理员。

## 31. 如何治理 SCIM 或 LDAP 同步异常？

**参考回答：**

需要区分“同步失败”和“同步成功但映射错误”：

- 检查身份源到 GitLab 的网络、证书和令牌；
- 查看同步任务、事件和错误对象；
- 核对用户唯一标识、邮箱、组路径和大小写；
- 检查离职或转岗用户是否按预期禁用和撤权；
- 检查 Group 同步是否会覆盖人工授权；
- 对异常批量变更设置告警和暂停机制；
- 保留同步前后的用户数、组成员和高权限成员快照。

不要直接批量删除用户来“清理同步问题”。应先确认影响范围、保留数据需求、项目归属和恢复方式。

## 32. GitLab 管理员权限如何做最小化治理？

**参考回答：**

我会采用以下控制：

- 日常账号与管理员账号分离；
- 管理员权限按职责拆分，并限制使用场景；
- 强制 MFA 或企业身份保护；
- break-glass 账号离线或受控保存；
- 管理员操作启用审计和告警；
- 定期复核管理员、Owner、服务账号和访问令牌；
- 对高风险操作执行工单、审批和双人复核；
- 禁止使用共享管理员账号；
- 避免把数据库、主机 root 或 Kubernetes cluster-admin 当成普通运维权限。

真正的最小权限不是“少创建几个账号”，而是让人员在正常工作中不需要使用超出职责的权限。

## 33. GitLab 中哪些数据需要重点保护？

**参考回答：**

审计、税务和咨询企业的 GitLab 可能包含：

- 客户源代码和脚本；
- 客户信息、财务数据、税务资料和审计底稿；
- 生产环境配置、证书和部署脚本；
- CI/CD 变量、云凭据、数据库密码和 API Token；
- 安全扫描结果、漏洞信息和内部架构；
- Pipeline 日志、Artifact、上传附件和备份。

保护措施包括：

- 默认私有和最小授权；
- 敏感变量使用受控 Secret 或外部密钥系统；
- 禁止在 Issue、评论、日志和 Artifact 中打印秘密；
- 配置脱敏、保留期和删除策略；
- 审计导出和备份访问；
- 跨地域和第三方集成进行数据分类和加密；
- 对客户项目实行明确的 owner、成员、期限和撤权流程。

## 八、CI/CD Pipeline 与 Runner

## 34. GitLab CI/CD Pipeline 的基本执行流程是什么？

**参考回答：**

典型流程是：

1. Git push、Merge Request、定时任务或 API 触发 Pipeline；
2. GitLab 读取并校验 `.gitlab-ci.yml` 和引用的模板；
3. 根据 `workflow`、`rules`、分支、标签和变量决定是否创建 Job；
4. Job 进入对应阶段和队列；
5. 匹配标签、权限和能力的 Runner 领取 Job；
6. Runner 准备执行环境，拉取代码、镜像和依赖；
7. 执行脚本，上传日志、Artifact、测试报告或缓存；
8. GitLab 更新状态，触发后续 Job、部署、通知或外部集成。

排查 Pipeline 时要区分“没有创建”“创建了但没有 Job”“Job pending”“Job failed”“执行成功但结果未更新”这几类问题。

## 35. `stages`、`needs`、`rules`、`workflow` 和 `dependencies` 有什么区别？

**参考回答：**

- **`stages`：** 定义默认阶段顺序，同一阶段的 Job 通常可并行；
- **`needs`：** 声明 Job 之间的依赖，允许不等待整个 stage 完成而提前执行；
- **`workflow`：** 控制 Pipeline 是否创建；
- **`rules`：** 控制 Job 是否加入 Pipeline、何时执行以及变量；
- **`dependencies`：** 控制 Job 下载哪些前序 Job 的 Artifact，具体行为需结合版本和配置理解。

常见问题：

- `workflow` 允许创建 Pipeline，但所有 Job 的 `rules` 都不匹配；
- `rules` 写得过宽，push 和 MR 各创建一次重复 Pipeline；
- `needs` 形成不合理依赖，导致 Pipeline 不能运行；
- Artifact 依赖和缓存依赖混用，导致构建结果不稳定。

编写规则时要同时测试 push、MR、tag、scheduled、manual 和 API 触发场景。

## 36. GitLab Runner 的架构和执行器有哪些？

**参考回答：**

Runner 是执行 CI/CD Job 的代理。它从 GitLab 获取任务，在指定 Executor 中运行，再把日志和结果提交回 GitLab。

常见 Executor 包括：

- Shell；
- Docker；
- Docker Machine 或类似弹性方案；
- Kubernetes；
- 其他受版本支持的执行器。

选择时要考虑：

- Job 是否需要隔离和特权；
- 是否允许访问宿主机、内网和云资源；
- 构建镜像是否需要 Docker daemon；
- 启动耗时和弹性需求；
- 缓存、Artifact、网络和凭据；
- 失败 Job 是否会影响后续 Job。

Shell Runner 部署简单，但隔离弱；共享 Docker/Kubernetes Runner 更灵活，但必须严格治理特权、镜像、网络和服务账号。

## 37. Shared Runner、Group Runner 和 Project Runner 如何选择？

**参考回答：**

- **Instance/Shared Runner：** 适合多个项目共享的通用、低敏感构建任务；
- **Group Runner：** 适合某个部门、产品线或客户组共享；
- **Project Runner：** 适合特殊网络、专用工具链或高敏感项目。

选择原则：

- 按数据敏感度、网络边界和执行权限划分；
- 默认不让敏感项目使用不受控的共享 Runner；
- 用 tags 表达能力，不把 tags 当成安全边界；
- 保护 Runner Token，及时轮换和撤销；
- 限制 privileged 模式、宿主机挂载和内网访问；
- 定期清理离线、无 owner 和过期 Runner。

Runner 的 tags 只帮助调度，不能替代真正的授权和隔离。

## 38. Runner 集群如何扩缩容和性能调优？

**参考回答：**

先建立容量模型：

- Job 到达率；
- 每类 Job 的平均和 P95 执行时长；
- 并发数和排队时长；
- CPU、内存、磁盘、网络和镜像拉取时间；
- 高峰时段和发布窗口；
- 失败重试、手工 Job 和定时 Job 的比例。

调优方向：

- 按工具链、数据敏感度和资源类型拆分 Runner；
- 配置合理的 `concurrent`、每个 Runner 的并发和 Job 超时；
- 对 Kubernetes Runner 使用合适的节点池、资源请求和限制；
- 优化基础镜像、依赖缓存、镜像仓库和 Artifact；
- 对突发负载使用弹性扩容，同时限制最大规模；
- 对长任务、GPU、部署任务和普通测试任务分开调度；
- 监控 pending 时间、启动时间、执行时间和失败率。

不要只看 Runner 在线数量；在线但没有匹配标签、没有资源或无法访问依赖的 Runner，对用户来说仍然不可用。

## 39. Pipeline Job 一直处于 pending，怎么排查？

**参考回答：**

排查顺序：

1. 确认 Job 是否被 `rules`、`needs`、手工条件或依赖阻塞；
2. 查看 Job 的 tags，是否存在匹配且在线的 Runner；
3. 检查 Runner 是否被暂停、过期、锁定到其他项目或达到并发上限；
4. 检查 Runner 所在节点的 CPU、内存、磁盘和 Pod 配额；
5. 检查 Kubernetes 调度、节点 taint、镜像拉取和网络；
6. 检查保护分支、受保护变量和 Runner 保护设置；
7. 对比其他项目是否同时 pending，判断平台级还是项目级；
8. 查看 Runner 日志、GitLab Job 日志和队列指标。

修复后要验证一个普通 Job、一个受保护 Job 和一个失败重试 Job，避免只恢复了某个 tags 的场景。

## 40. Pipeline 失败时如何区分 GitLab、Runner 和脚本问题？

**参考回答：**

可以按阶段切分：

- **Pipeline 未创建：** 优先看 YAML 语法、`workflow`、触发条件和权限；
- **Job pending：** 优先看 Runner 注册、tags、并发和资源；
- **Job 启动失败：** 看镜像、Executor、网络、权限和工作目录；
- **脚本执行失败：** 看代码、依赖、环境变量、服务和返回码；
- **Artifact/日志上传失败：** 看 Runner 到 GitLab 的网络、存储和权限；
- **部署失败：** 看目标环境、凭据、审批、锁和外部平台；
- **重试结果不一致：** 看缓存、共享工作区、非幂等脚本和外部状态。

不要看到红色 Job 就直接重启 Runner。应先读取完整日志、失败命令、时间和环境信息。

## 41. GitLab CI/CD 变量和密钥如何安全管理？

**参考回答：**

原则是“最小范围、最短生命周期、可轮换、不可回显”：

- 使用受保护、掩码和适用环境范围的变量；
- 将敏感变量放在 Group 或 Project 的合适层级；
- 生产部署只允许受保护分支和受保护 Runner 使用；
- 尽量使用短期凭据、OIDC/Workload Identity 或云端临时身份；
- 不在脚本、Artifact、缓存和日志中打印秘密；
- 轮换后验证旧凭据已经失效；
- 对变量读取和变更保留审计；
- 处理 fork、外部 MR 和不受信任代码时禁止泄露受保护变量。

变量名称或掩码显示并不等于绝对安全。恶意脚本可能通过网络、错误信息、Artifact 或编码方式泄露秘密，因此执行环境隔离同样重要。

## 42. 如何设计可复用的 CI/CD Pipeline 模板？

**参考回答：**

建议将通用逻辑拆为可组合模板：

- 基础校验和工作流模板；
- 单元测试、集成测试和质量门禁模板；
- SAST、依赖、许可证和容器扫描模板；
- 构建和 Artifact 模板；
- 部署、回滚和环境保护模板；
- 审计证据、变更号和通知模板。

模板治理要包括：

- 版本化引用，避免所有项目无感跟随不兼容变更；
- 明确输入变量、默认值和输出 Artifact；
- 对失败、重试、超时和取消定义行为；
- 在示例项目、预生产和关键业务项目中验证；
- 发布变更日志和迁移说明；
- 对不符合策略的项目生成报告或工单。

在受监管环境中，模板还应统一收集变更单号、审批信息、构建版本、制品摘要和部署结果。

## 九、API、自动化与 ServiceNow

## 43. GitLab API 自动化脚本要注意什么？

**参考回答：**

一个生产级脚本至少应考虑：

- 使用合适的认证方式和最小权限；
- 处理分页，不假设一次返回全部数据；
- 对 429、5xx、网络超时和临时错误做有限重试；
- 使用指数退避和随机抖动，避免雪崩；
- 记录请求范围、对象 ID、结果和失败原因；
- 设计幂等行为，重复执行不会重复创建或破坏数据；
- 对删除、批量修改和权限变化设置 dry-run、审批或二次确认；
- 校验 API 响应，不把 HTTP 200 误当成业务成功；
- 保护 Token，避免出现在命令行历史、日志和 Pipeline 输出；
- 根据 GitLab 版本和 API 生命周期处理弃用。

批量修改前应先导出对象清单和变更前状态，分批执行，并保留可恢复信息。

## 44. 如何设计幂等的 GitLab 自动化？

**参考回答：**

以“声明目标状态”而不是“重复执行动作”为核心：

1. 用稳定的项目路径、Group ID 或外部业务 ID 定位对象；
2. 先读取当前状态；
3. 只有当前状态与目标状态不一致时才修改；
4. 使用唯一键或标签避免重复创建；
5. 对部分成功记录 checkpoint，支持从失败批次继续；
6. 对删除和降权设置人工审批；
7. 完成后重新读取并验证最终状态。

例如同步项目成员时，不应每次都执行“添加成员”，而应比较期望成员集合和实际成员集合，再分别处理新增、保留和撤销。

## 45. GitLab API 限流或大量请求失败时怎么处理？

**参考回答：**

先确认是否为平台限流、反向代理限流、数据库压力还是脚本逻辑错误：

- 读取响应状态、限流头和请求时间；
- 查看脚本是否没有分页、重复查询或并发过高；
- 降低并发，增加退避和抖动；
- 使用批量接口或缓存，减少重复读取；
- 对不可重试的 4xx 不要无限重试；
- 对 429、部分 5xx 和网络错误进行有限重试；
- 使用相关 ID 和批次号追踪结果；
- 在平台压力恢复前暂停大规模写入。

如果脚本本身造成实例性能下降，应立即停止或降速，并通过 ServiceNow/事故流程记录影响和后续改进。

## 46. GitLab 与 ServiceNow 如何集成？

**参考回答：**

应先明确业务对象和责任边界：

- Incident：GitLab 服务不可用、Runner 大面积失败、SSO 故障；
- Request：项目创建、成员申请、Runner 申请、模板申请；
- Change：版本升级、配置变更、权限策略和集群扩容；
- Problem：重复故障、性能退化和架构根因。

集成方式可以使用 API、Webhook、中间服务或已有连接器。关键设计点：

- 用项目、Pipeline、MR、变更单号建立双向关联；
- 定义字段映射、状态同步和负责人；
- 处理重复事件、重试、幂等和接口限流；
- 不将密码、Token、客户敏感资料写入工单；
- 保存请求 ID、时间线、批准人、变更内容和验证结果；
- 外部系统不可用时，GitLab 核心功能不能被同步逻辑无限阻塞；
- 明确哪些状态以 GitLab 为准，哪些状态以 ServiceNow 为准。

## 47. 用户通过 ServiceNow 提交 GitLab 权限申请，如何设计流程？

**参考回答：**

流程应包括：

1. 申请人、项目、目标 Group/Project、所需角色和期限；
2. 数据分类、客户归属和业务 owner；
3. 项目 Owner 或数据 owner 审批；
4. 高风险角色或生产访问的额外审批；
5. 自动化校验用户身份、项目存在性和权限边界；
6. 通过 GitLab API 授权并记录返回结果；
7. 向申请人回写完成状态和到期时间；
8. 到期自动提醒、撤权或重新审批；
9. 定期对比 GitLab 实际成员与工单记录。

自动化失败时必须显式报错并创建待处理状态，不能返回“成功”但实际没有授权。

## 十、监控、日志与故障排查

## 48. GitLab 平台应该监控哪些指标？

**参考回答：**

**可用性**

- Web/API 成功率、错误率和延迟；
- SSH/HTTPS clone、push 和项目访问；
- SSO、API、Webhook 和外部集成；
- 关键组件健康和节点状态。

**容量与性能**

- CPU、内存、磁盘、IOPS、网络和文件描述符；
- Puma/Workhorse 请求、Sidekiq 队列和 Redis；
- PostgreSQL 连接、锁、慢查询、WAL 和复制延迟；
- Gitaly 请求量、耗时、错误和仓库容量；
- 对象存储请求失败和空间；
- Runner 在线数、pending 时间、并发和失败率。

**业务指标**

- Pipeline 成功率和 P95 时长；
- MR 从创建到合并的时间；
- 部署失败率和回滚率；
- ServiceNow 工单 SLA；
- 备份成功率、恢复时长和 Geo 延迟。

告警应有 owner、优先级、运行手册和升级路径，避免只收集大量无法行动的指标。

## 49. GitLab 日志排查应该关注哪些信息？

**参考回答：**

优先收集：

- 时间戳和时区；
- 用户、项目路径、Pipeline/Job ID；
- 请求 ID、Trace ID 或相关关联标识；
- HTTP 状态、错误码和耗时；
- 组件名称和节点；
- 最近变更、发布版本和配置版本；
- 下游 PostgreSQL、Redis、Gitaly、对象存储或身份源错误。

日志排查应尽量使用时间窗口和关联 ID，而不是盲目收集全部日志。导出日志给外部团队前，要脱敏客户名称、邮箱、Token、路径、代码片段和请求参数。

## 50. GitLab Web/API 返回 502、503 或 500，如何区分？

**参考回答：**

- **502：** 常见于代理无法从上游获得有效响应，重点看负载均衡、Ingress、Workhorse、Puma、超时和连接；
- **503：** 常见于服务不可用、健康检查失败、资源耗尽或维护状态，重点看副本、节点、依赖和调度；
- **500：** 通常是应用内部异常，也可能由数据库、Gitaly、Redis 或配置错误触发，重点看 Rails 和关联组件日志。

排查步骤：

1. 记录具体 URL、用户、时间和请求 ID；
2. 判断单节点、单接口还是全局；
3. 检查代理和 GitLab 应用层；
4. 检查数据库、Redis、Gitaly 和对象存储；
5. 对比最近变更和资源指标；
6. 进行只读验证和小范围重试；
7. 修复后确认错误率、延迟和业务操作恢复。

重启可能暂时消除症状，但不能替代根因分析。

## 51. Sidekiq 队列持续积压怎么办？

**参考回答：**

先确认积压的是哪个队列以及任务类型：

- 邮件、Pipeline、导入导出、Geo、Webhook 还是其他队列；
- 是否所有队列都慢，还是单个队列；
- 任务数量增加还是单个任务执行时间变长；
- 是否存在失败重试风暴。

然后检查：

- Sidekiq 进程数、CPU、内存和线程；
- Redis 延迟、连接和容量；
- PostgreSQL 连接、锁和慢查询；
- Gitaly、对象存储和外部 API；
- 最近发布、批量操作或脚本；
- 是否可以安全暂停非关键任务。

处理方式可能是扩容对应 Worker、限流批量任务、修复下游依赖或清理失败重试。不能直接删除队列，因为这可能造成业务状态丢失。

## 十一、典型故障场景题

## 52. 用户反馈“GitLab 整个平台打不开”，你怎么处理？

**参考回答：**

先判断是真正不可用还是某个网络区域、DNS 或身份源不可用：

1. 从多个网络位置验证 DNS、TLS、负载均衡和健康检查；
2. 查看监控、错误率和最近变更；
3. 检查 Web/Ingress/NGINX、Workhorse、Puma 和节点；
4. 检查 PostgreSQL、Redis、Gitaly 和对象存储；
5. 确认是否是证书过期、域名解析、WAF 或防火墙变化；
6. 读取关键日志并记录请求 ID；
7. 根据影响范围启动 Sev-1/Sev-2 事故流程；
8. 优先恢复核心读写和认证，再恢复非核心集成；
9. 持续向 ServiceNow 和利益相关者更新影响、进展和预计时间；
10. 恢复后验证普通用户、管理员、API、Git 操作和 Pipeline。

如果是节点故障，应先从负载均衡摘除异常节点；如果是数据库或存储故障，应按灾备 runbook 处理，而不是同时重启所有组件。

## 53. 只有一个项目的 Pipeline 全部失败，其他项目正常，怎么排查？

**参考回答：**

优先定位项目级差异：

- `.gitlab-ci.yml` 或引用模板最近是否变更；
- Job tags 是否指向不存在或不适用的 Runner；
- 项目变量、受保护变量和环境变量是否变化；
- 项目是否使用了特殊镜像、依赖、网络或部署目标；
- 分支保护、审批、项目级 Runner 和权限；
- 仓库是否损坏、子模块是否不可访问；
- Artifact、缓存或容器镜像是否过期；
- Service Account、Token 或云凭据是否失效。

用一个最小的诊断 Job 验证 Runner、网络和基础命令，再逐步恢复复杂步骤，避免一次修改所有配置。

## 54. 所有 Runner 都离线了，GitLab 页面正常，怎么办？

**参考回答：**

这通常是 Runner 侧、网络或凭据问题，不应首先重启 GitLab Web：

1. 确认 Runner 服务、Pod、节点和容器状态；
2. 验证 Runner 到 GitLab 的 DNS、TLS、代理和网络；
3. 检查 Runner Token、注册信息和版本兼容性；
4. 检查 Runner 主机的磁盘、CPU、内存和时间同步；
5. 查看 Runner 日志中的注册、轮询和证书错误；
6. 如果使用 Kubernetes，检查控制器、ServiceAccount、RBAC、节点调度和镜像拉取；
7. 确认 GitLab API 是否仅对 Runner 网络不可达；
8. 恢复后验证普通、受保护和并发 Job。

不要在没有确认原因的情况下批量重新注册 Runner，否则可能导致重复 Runner、权限泄露和原有配置丢失。

## 55. 用户说“有项目权限，但看不到项目或文件”，怎么排查？

**参考回答：**

需要分别检查：

- 用户登录的是不是预期账号；
- 项目路径是否改变、项目是否迁移或归档；
- Group 继承成员关系是否有效；
- 项目可见性和用户角色；
- Issue/代码访问权限是否受项目设置影响；
- 分支保护是否只限制操作，还是误认为限制查看；
- 仓库、LFS 或对象存储是否损坏；
- SSO/SCIM 同步是否撤销或覆盖了权限；
- 是否是缓存或索引问题。

先使用一个已知正常用户和一个最小权限用户对比，再查审计事件和成员来源。不要直接把用户提升为 Maintainer 来“验证”。

## 56. 升级后 SSO 正常，但 Pipeline 全部无法执行，怎么处理？

**参考回答：**

这是典型的“平台登录恢复，但执行链路未恢复”问题。检查：

- Runner 与 GitLab 版本和 API 兼容性；
- Runner Token、注册状态和 tags；
- 受保护变量、受保护 Runner 和分支规则；
- Runner 到 GitLab、镜像仓库、依赖仓库的网络；
- Docker/Kubernetes Executor 的权限、RBAC 和节点；
- 升级后证书、域名或代理配置；
- GitLab API、Job 请求和 Artifact 上传日志。

应先运行最小诊断 Job，再恢复一条低风险流水线，最后验证生产部署流水线和受保护变量。

## 57. PostgreSQL 磁盘空间快速增长，如何处理？

**参考回答：**

先保护数据，不要直接删除数据库文件：

1. 查看数据目录、WAL、归档、临时文件、日志和备份占用；
2. 检查长事务、复制槽、复制延迟和归档失败；
3. 检查表/索引膨胀、autovacuum 和异常批量写入；
4. 查看最近的 Pipeline、审计、导入、脚本或升级；
5. 确认备库和备份链路没有阻塞 WAL 清理；
6. 临时扩容磁盘或转移合规允许的日志；
7. 按官方和 DBA 评估执行清理、vacuum 或归档；
8. 修复导致持续增长的任务，并设置容量告警。

如果磁盘即将耗尽，应启动容量事故流程，优先保证数据库和 WAL 的写入空间，并明确哪些清理动作经过批准且可恢复。

## 58. GitLab Geo secondary 站点需要提升为 primary，关键步骤是什么？

**参考回答：**

这是高风险灾备切换，必须按演练过的 runbook 执行：

1. 确认原 primary 的故障范围和最后可写时间；
2. 防止原 primary 恢复后继续接收写入，避免双主；
3. 评估 secondary 的数据库、仓库、对象和配置同步延迟；
4. 记录可能丢失的变更和受影响项目；
5. 按版本支持的流程提升 secondary；
6. 切换 DNS、负载均衡、Runner、Webhook、SSO 和外部系统；
7. 执行登录、clone、push、MR、Pipeline、API 和权限验证；
8. 监控错误率、队列、数据库和仓库存储；
9. 通知业务当前站点和数据时间点；
10. 灾难结束后规划原站点重建、重新同步和回切。

不能只执行“promote”命令就宣布成功，外部依赖和写入隔离同样重要。

## 十二、审计、税务与咨询行业场景

## 59. 审计、税务和咨询公司的 GitLab 运维有哪些特殊要求？

**参考回答：**

这类企业通常同时面对客户数据保密、项目隔离、监管检查、跨地域协作和职责分离要求。GitLab 平台应重点关注：

- 客户项目之间的访问隔离；
- 代码、文档、底稿、扫描结果和制品的数据分类；
- 离职、转岗和项目结束后的及时撤权；
- 管理员、项目 Owner、代码提交者和审批者的职责分离；
- 关键变更的 ServiceNow 工单、审批和验证证据；
- 备份、恢复和 Geo 数据是否跨越受限区域；
- 共享 Runner 是否会暴露客户数据或密钥；
- Pipeline 日志和 Artifact 的保留、脱敏和删除；
- 供应商、外包人员和临时账号的期限控制；
- 审计事件的留存、导出、保护和检索。

回答时应体现“平台可用性 + 数据保密性 + 操作可追溯性 + 业务连续性”的平衡，而不是只关注构建速度。

## 60. 如何设计客户项目之间的隔离？

**参考回答：**

我会从多个边界同时控制：

- 使用不同的顶层 Group 或清晰的 Subgroup；
- 项目默认 Private，限制跨组共享；
- 通过角色和组同步控制成员；
- 对敏感项目使用专用 Runner、网络和执行账号；
- 禁止共享缓存、宿主机挂载和不受控 Artifact；
- 对变量、镜像、依赖和部署目标分离；
- 对客户项目设置 owner、数据分类、访问期限和定期复核；
- 对跨项目模板和公共库使用只读、版本化和审批机制；
- 在备份、Geo、日志和 ServiceNow 中同样落实数据边界。

只把项目放在不同目录并不能形成安全隔离；继承权限、Group Runner、共享变量和外部集成可能重新建立数据通道。

## 61. 如何在 GitLab 中落实职责分离？

**参考回答：**

可以将职责拆为：

- 平台管理员：基础设施、版本和组件运维；
- 身份管理员：SSO、SCIM/LDAP 和账号生命周期；
- 项目 Owner：项目成员和业务配置；
- 开发者：代码提交和 MR；
- 审批者/Code Owner：独立审查；
- 发布或运维人员：生产部署；
- 审计/安全人员：查看证据和复核，不直接修改业务配置。

在技术上使用 Protected Branch、Approval Rule、Protected Environment、受保护变量、专用 Runner 和 ServiceNow Change 关联；在流程上要求审批人与实施人分离，保留变更前后状态和验证证据。

不要仅以“有审批按钮”判断职责分离有效，还要验证提交者是否可以自批、管理员是否可以绕过、例外如何记录。

## 62. 如何证明一次生产部署是可审计的？

**参考回答：**

至少应能够关联以下信息：

- 变更单号和批准人；
- 代码提交 SHA、Merge Request 和审批记录；
- Pipeline ID、运行时间、Runner 和模板版本；
- 构建制品摘要、依赖版本和扫描结果；
- 部署目标、执行人和环境；
- GitLab 与 ServiceNow 的状态；
- 失败、重试、回滚和验证结果；
- 相关日志、审计事件和保留策略。

证据应能回答“谁在什么时间、基于哪个版本、经过谁批准、部署到哪里、结果如何、失败时如何处理”。不要只保存一张成功截图，因为截图无法证明完整链路和未发生越权。

## 63. 客户代码或秘密误提交到 GitLab，如何处理？

**参考回答：**

先按安全事件处理，而不是简单删除一行文件：

1. 识别泄露内容、项目范围、分支、Tag、MR、Artifact、缓存和备份；
2. 立即吊销或轮换密钥、Token、证书和云权限；
3. 限制访问并保留必要证据；
4. 从 Git 历史中清理敏感内容，评估镜像、Fork、缓存和外部同步；
5. 检查日志、下载记录和潜在访问者；
6. 按客户、法律、合规和安全流程通知相关方；
7. 恢复受控访问，并验证旧秘密不可用；
8. 增加 Secret Detection、Push Rule、MR 检查和培训；
9. 在 ServiceNow 中记录事件、影响、决定和复盘。

仅从当前分支删除文件并不能使历史、Artifact、缓存和备份中的秘密消失。

## 64. 如何管理项目结束、客户交付和数据保留？

**参考回答：**

项目结束不应简单删除项目。应先确认：

- 客户合同和保留要求；
- 代码、Pipeline、Artifact、Issue、MR 和审计记录的保留期限；
- 项目 owner、法律保留和导出需求；
- 成员、Token、Runner、Webhook 和部署凭据；
- 备份和 Geo 副本中是否还存在数据；
- 是否需要归档、只读、移交或安全删除。

推荐采用“到期提醒—业务确认—冻结写入—导出/归档—撤权—按批准删除—验证删除”的流程，并保留审批和结果证据。

## 十三、架构设计与高级面试题

## 65. 设计一个企业级 GitLab Self-Managed 平台，你会怎么做？

**参考回答：**

我会分层设计：

**访问层**

- DNS、负载均衡、WAF、TLS 和网络分区；
- Web/API 多节点；
- SSH 和 HTTPS 入口；
- 管理平面与用户访问平面适当隔离。

**应用层**

- Puma/Workhorse 多副本；
- Sidekiq 按队列和负载拆分；
- 版本化的配置和密钥管理；
- 统一日志、指标和告警。

**数据层**

- 高可用 PostgreSQL；
- 可靠的 Redis；
- Gitaly 或 Gitaly Cluster/Praefect；
- 对象存储及其版本和生命周期；
- 独立备份、恢复和 Geo。

**执行层**

- 通用、专用、受保护和高敏感 Runner 分层；
- Docker/Kubernetes Executor 隔离；
- 资源配额、并发、弹性和网络控制。

**治理层**

- SSO、SCIM/LDAP、MFA 和 break-glass；
- Group/Project 模板和策略；
- Protected Branch、审批、Code Owner 和环境保护；
- ServiceNow 变更和访问流程；
- 定期权限、备份、恢复和灾备演练。

最终设计要由规模、RTO/RPO、预算、团队能力和合规边界共同决定。

## 66. 如何为 Runner 集群做容量规划？

**参考回答：**

先采集至少一个完整业务周期的数据：

- 每小时 Job 数和到达率；
- P50/P95 执行时长；
- 并发峰值和排队时间；
- 不同 Job 的 CPU、内存、磁盘和网络使用；
- 镜像拉取和依赖下载耗时；
- 发布窗口、月末、季末和审计高峰；
- 失败重试和手工任务。

可以用近似关系估算所需并发：

```text
所需并发 ≈ 峰值到达率 × 平均执行时间 × 安全系数
```

然后按 Job 类型拆分队列和 Runner，设置资源 requests/limits、最大并发和扩缩容上限。容量验证不能只看平均值，应关注 P95/P99 排队时间和最差情况下的资源争用。

## 67. 如何降低 GitLab 平台的升级风险？

**参考回答：**

- 保持受支持版本，避免跨越过大的版本跨度；
- 维护版本、插件、Runner、数据库和操作系统兼容矩阵；
- 用生产数据规模的脱敏副本在预生产演练；
- 将应用升级、数据库变更、操作系统补丁和网络变更尽量分批；
- 自动化基线检查、备份校验和冒烟测试；
- 使用维护窗口、冻结窗口和明确的回滚/恢复条件；
- 升级后观察错误率、队列、数据库、Gitaly、Runner 和外部集成；
- 对失败原因和手工步骤进行复盘，持续减少不可重复操作。

成熟团队的升级流程重点不是“有没有人会执行命令”，而是“能否可预测、可验证、可恢复地执行”。

## 68. 如何治理 GitLab 平台的技术债务？

**参考回答：**

先建立清单和优先级：

- 不受支持的 GitLab、Runner、数据库和操作系统版本；
- 无 owner 的 Group、Project、Runner、Token 和 Webhook；
- 手工配置和配置漂移；
- 没有恢复验证的备份；
- 共享管理员、共享 Runner 和长期静态凭据；
- 大仓库、过期 Artifact 和无限增长的日志；
- 重复模板、复杂规则和无法解释的例外。

按安全、可用性、合规和成本排序，给每项指定责任人、目标日期、风险接受人和验证方法。技术债务治理不应只是升级版本，还要减少不可审计的手工流程。

## 十四、面试中的常见失分点

1. **只会安装 GitLab，不会运维依赖。** 没有说明 PostgreSQL、Redis、Gitaly、对象存储和 Runner。
2. **把 `gitlab-ctl reconfigure` 或 Helm upgrade 当成万能修复。** 没有评估影响、备份和回滚。
3. **只谈副本数，不谈数据层。** Web 节点增加并不能自动解决数据库、Gitaly 或对象存储单点。
4. **把备份命令成功等同于可恢复。** 没有验证外部对象、密钥、配置和实际恢复时间。
5. **把 Geo 当成备份。** 没有说明复制延迟、切换、双主和外部集成。
6. **把 Runner tags 当成安全边界。** 忽略 Executor、特权模式、网络和服务账号。
7. **只会给用户加权限。** 没有检查 Group 继承、SSO、Protected Branch 和审批规则。
8. **在生产环境直接改数据库或仓库文件。** 没有先查官方支持路径和恢复方案。
9. **CI/CD 只回答 YAML 语法。** 没有覆盖缓存、Artifact、变量、Runner、镜像和外部依赖。
10. **用无限重试处理 API 错误。** 可能造成重复创建、平台压力和数据不一致。
11. **忽略 ServiceNow 工单的证据价值。** 没有把变更、批准、实施、验证和回滚关联起来。
12. **忽略客户数据和审计要求。** 没有讨论项目隔离、保留期限、撤权和日志脱敏。
13. **只看成功路径。** 没有说明 SSO 中断、Runner 全离线、Geo 延迟和恢复失败怎么办。
14. **只说“监控 CPU 和内存”。** 没有说明队列、数据库锁、Gitaly、Pipeline 排队和备份指标。

## 十六、可直接背诵的高级总结

> 我把 GitLab Self-Managed 视为一个同时承载代码、身份、流水线、制品和审计证据的企业级平台，而不只是一个 Git Web 页面。运维时我会先明确版本、部署模式和责任边界，再把 Web、Sidekiq、PostgreSQL、Redis、Gitaly、对象存储和 Runner 作为完整链路治理。版本升级和配置变更前，我会核对兼容矩阵、备份和恢复能力，在预生产环境验证，并明确成功、失败和恢复条件。权限方面坚持最小权限、Group 继承治理、SSO 生命周期、Protected Branch、审批和职责分离；CI/CD 方面重点关注 Runner 隔离、变量保护、并发容量、制品和可重复性；灾备方面区分高可用、Geo、备份和恢复演练，明确 RTO、RPO、同步延迟和双主风险。发生故障时，我会先界定影响范围并保留证据，再按请求链路逐层排查，修复后做正向和负向验证。对于审计、税务和咨询场景，我会额外关注客户项目隔离、敏感数据最小化、凭据轮换、ServiceNow 变更关联、操作不可抵赖以及项目结束后的归档和安全删除。
