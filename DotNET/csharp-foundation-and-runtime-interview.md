## 二、类型系统与语言基础

### Q1：值类型和引用类型有什么区别？值类型一定分配在栈上吗？

**核心回答：**

- 值类型变量直接包含数据，赋值和按值传参通常会复制数据。
- 引用类型变量包含对象引用，赋值通常只复制引用，多个变量可能指向同一个对象。
- 值类型包括数值类型、`bool`、`char`、`enum`、`struct` 和 `record struct`；引用类型包括 `class`、数组、委托、接口和 `string`。
- “值类型在栈上、引用类型在堆上”只是入门级简化，不能作为严格结论。值类型可以作为对象字段存在于堆上，也可以装箱到堆上；引用本身也可能是栈上的局部变量。

```csharp
public struct Point
{
    public int X { get; set; }
}

var first = new Point { X = 1 };
var second = first;
second.X = 2;

Console.WriteLine(first.X);  // 1
```

**面试官追问：** `class` 字段中的 `struct` 是否单独分配？不是。它通常内嵌在包含对象的数据布局中，不会因为是值类型就单独分配一个对象。

**易错点：** 性能判断不能只看“栈还是堆”，还要考虑复制大小、逃逸、装箱、缓存局部性和 GC 压力。

### Q2：`ref`、`out`、`in` 和普通参数有什么区别？

| 参数形式 | 调用前要求 | 方法内行为 | 典型用途 |
| --- | --- | --- | --- |
| 普通参数 | 传入一个值 | 修改形参不影响调用方变量 | 默认选择 |
| `ref` | 调用方必须初始化 | 可读可写，修改会回写 | 原地修改已有值 |
| `out` | 调用方不必初始化 | 返回前必须赋值 | 多返回值、`TryParse` |
| `in` | 调用方传入变量或可转换值 | 只读引用 | 避免复制较大的结构体 |

```csharp
static bool TryGetValue(string text, out int value)
{
    return int.TryParse(text, out value);
}

static void Update(ref int value, in int increment)
{
    value += increment;
}
```

**追问：** `in` 一定比普通参数快吗？不一定。对于小型结构体，引用传递本身也有成本；只有在结构体较大、调用频繁且确实避免复制时才可能有收益。应通过基准测试确认。

---

### Q3：装箱和拆箱发生了什么？如何避免？

**核心回答：**

- 装箱是把值类型包装成 `object` 或其实现的接口类型，运行时通常需要创建对象并复制值。
- 拆箱是从装箱对象中取回值类型，需要进行类型检查，随后复制出值。
- 装箱会增加分配和 GC 压力，拆箱还可能因类型不匹配抛出 `InvalidCastException`。

```csharp
int number = 42;
object boxed = number;
int unboxed = (int)boxed;

IComparable comparable = number;
```

**常见来源：** 非泛型集合、把结构体作为接口使用、字符串格式化中的隐式转换、未正确使用泛型的 API。

**避免方式：** 使用 `List<int>`、`Dictionary<int, T>` 等泛型集合；使用泛型方法；在热路径中检查接口调用和格式化是否产生装箱。

**追问：** `Nullable<T>` 什么时候装箱？有值时装箱为底层值类型的对象；没有值时装箱结果为 `null`。

---

### Q4：`string` 为什么是引用类型，却经常表现得像值类型？

`string` 是引用类型，但具有不可变性。对字符串进行“修改”时，实际是创建新的字符串对象，原对象不会被改变，因此多个变量共享同一个字符串时不会产生可见的相互修改。

```csharp
string first = "ab";
string second = first;
second += "c";

Console.WriteLine(first);   // ab
Console.WriteLine(second);  // abc
```

- 字符串字面量通常经过字符串驻留（interning），相同字面量可能共享实例。
- 不应依赖驻留来判断所有字符串引用是否相同。
- 大量拼接应考虑 `StringBuilder`，但要根据实际场景判断；编译器会优化部分简单拼接。
- `string` 的相等性重载比较内容，而不是只比较引用。

**追问：** 为什么字符串适合作为 `Dictionary` 的键？因为它不可变，哈希值和内容在放入字典后不会因外部修改而变化。

---

### Q5：`class`、`struct`、`record class` 和 `record struct` 如何选择？

| 类型 | 默认语义 | 适合场景 |
| --- | --- | --- |
| `class` | 引用语义，默认引用相等 | 有身份、可变状态、生命周期较长的对象 |
| `struct` | 值语义，默认字段逐项比较 | 小型、短生命周期、逻辑上表示一个值的类型 |
| `record class` | 引用类型，默认值相等 | DTO、不可变数据模型、需要值相等的引用对象 |
| `record struct` | 值类型，默认值相等 | 小型数据组合、需要值语义的结构体 |

结构体通常应满足：体积较小、逻辑上是一个值、尽量不可变。较大的可变结构体容易产生复制和状态混淆问题。

**追问：** `record` 的值相等是否代表深度比较？默认通常比较组成成员的相等性，但成员本身如果是引用类型，是否深度比较取决于成员类型的相等实现，并不是无条件递归深拷贝。

### Q6：`==`、`Equals`、`ReferenceEquals` 和 `GetHashCode` 的关系是什么？

- `ReferenceEquals(a, b)` 判断两个变量是否引用同一个对象；对值类型使用时会发生装箱，不适合用来做值比较。
- `Equals` 表示逻辑相等，具体行为由类型实现；`object.Equals` 默认对引用类型通常按引用判断。
- `==` 是可重载运算符。`string`、数值类型和部分自定义类型可能按值比较。
- 如果两个对象相等，则必须返回相同的哈希值；反过来哈希值相同不代表对象相等。

作为 `Dictionary` 或 `HashSet` 的键时，类型必须满足：

1. 相等对象的哈希值一致。
2. 放入集合后，参与相等和哈希计算的状态不能被改变。
3. `Equals` 与 `GetHashCode` 的逻辑保持一致。

**易错点：** 重写 `Equals` 却不重写 `GetHashCode`，会导致字典查找和集合去重出现异常行为。

---

### Q7：接口、抽象类和多态的底层区别是什么？

- 抽象类可以保存字段、构造函数、已实现方法和访问修饰符，适合表达“有共同实现或状态的基类”。
- 接口表达能力契约，一个类可以实现多个接口；现代 C# 接口也可以提供默认实现，但不应因此把接口当成传统基类使用。
- 多态调用通常需要运行时根据对象实际类型选择实现。具体调用策略和优化由 CLR、JIT 及类型布局共同决定，业务代码不应依赖私有实现细节。

**面试官更关注：** 你是否使用抽象来隔离变化，是否避免为了“方便测试”而创建没有行为的接口，以及是否理解接口并不自动带来好的架构。

---

### Q8：泛型相比 `object` 有什么价值？泛型约束有什么作用？

泛型可以在编译期保留类型信息，减少强制转换和装箱，并让 API 的契约更明确。

```csharp
static T CreateDefault<T>() where T : new()
{
    return new T();
}

static T Max<T>(T left, T right) where T : IComparable<T>
{
    return left.CompareTo(right) >= 0 ? left : right;
}
```

常见约束包括 `class`、`struct`、`notnull`、基类、接口和 `new()`。约束让编译器知道类型具备哪些能力，也能减少运行时检查。

**追问：** C# 泛型是类型擦除吗？不是 Java 式的简单类型擦除。CLR 会根据泛型类型参数生成或共享适合的运行时代码；值类型和引用类型的处理可能不同，具体实现由 CLR 和 JIT 优化。

## 三、CLR、IL、JIT 与程序集

### Q9：一段 C# 代码从编译到执行经历了什么？

典型流程如下：

```text
C# 源代码
    ↓ 编译器（Roslyn）
IL + 元数据 + 程序集（EXE / DLL）
    ↓ CLR 加载类型和方法
JIT / NativeAOT 等执行方案生成机器码
    ↓
CPU 执行
```

- 编译器负责语法、类型检查、生成 IL 和元数据。
- CLR 负责程序集加载、类型系统、异常处理、线程、GC、运行时安全和执行管理。
- JIT 通常在方法首次执行或需要时将 IL 转换为当前平台的机器码，并可能进行内联、边界检查消除等优化。
- 发布模式、Tiered Compilation、ReadyToRun、AOT 等会影响实际编译时机和性能表现。

**追问：** IL 是机器码吗？不是。IL 是面向 CLR 的中间指令，最终通常需要由 JIT 或其他编译方式变成目标平台机器码。

---

### Q10：什么是 CLR、CTS、CLS 和 BCL？

- **CLR（Common Language Runtime）**：.NET 的运行时，提供 GC、异常、线程、类型加载和代码执行等能力。
- **CTS（Common Type System）**：定义 .NET 类型的统一规则，包括值类型、引用类型、继承和成员等。
- **CLS（Common Language Specification）**：跨 .NET 语言互操作时应遵守的公共子集。
- **BCL（Base Class Library）**：基础类库，如集合、文件、网络、日期和任务相关 API。

**面试表达：** C# 是语言，CLR 是运行时，BCL 是类库；三者不是同一个概念。

---

### Q11：程序集、元数据、类型加载和依赖解析分别是什么？

程序集通常是 `.dll` 或 `.exe` 文件，包含 IL、元数据、清单和资源。元数据描述类型、方法、字段、引用及特性等信息，反射和运行时类型检查都依赖这些信息。

运行时加载程序集时，需要处理：

- 依赖程序集的定位和解析。
- 类型定义和引用的解析。
- 类型初始化，例如静态字段和静态构造函数。
- 版本、加载上下文和可见性。

现代 .NET 使用 `AssemblyLoadContext` 管理加载隔离和插件场景。不同加载上下文中的同名类型不一定被视为同一个类型。

**易错点：** “程序集加载成功”不代表所有类型依赖都已经初始化；很多问题会在首次访问具体类型或方法时才暴露。

---

### Q12：JIT、AOT、Tiered Compilation 和内联如何影响性能？

- **JIT**：运行时针对当前 CPU 和运行路径生成机器码，启动时可能有编译成本，但能进行运行时优化。
- **AOT**：在部署前生成原生代码，通常有更快启动和更小运行时依赖，但动态特性、反射和平台适配需要额外考虑。
- **Tiered Compilation**：先快速生成可执行代码，运行一段时间后再对热点方法进行更积极的优化。
- **Inlining（内联）**：把小方法的调用体直接嵌入调用方，减少调用开销，并为后续优化提供机会；是否内联由 JIT 决定。

**面试官追问：** 为什么 Debug 和 Release 性能不同？优化开关、调试信息、JIT 行为、代码路径和运行配置都可能不同，不能仅凭一次手工测试下结论。

## 四、内存管理与 GC

### Q13：GC 管理什么？`Dispose` 管理什么？

- GC 负责回收不再可达的托管对象内存。
- `Dispose` 是应用约定，用于及时释放文件句柄、数据库连接、Socket、非托管内存等资源；它不会让托管对象立刻从堆上消失。
- 一个实现 `IDisposable` 的对象仍然可能需要等待 GC 回收自身托管内存。
- `using` / `await using` 的核心作用是确保在作用域结束时调用 `Dispose` / `DisposeAsync`。

```csharp
await using var connection = new DbConnection();
await connection.OpenAsync();
```

**追问：** 只要实现了 `IDisposable` 就一定要写终结器吗？不一定。只有直接拥有需要终结的非托管资源时才考虑终结器；如果只是持有已经正确实现 `IDisposable` 的托管资源，通常只需转发释放，不应随意增加终结器。

---

### Q14：GC 的代际回收是怎么回事？为什么分代有意义？

常见的托管堆分为第 0 代、第 1 代和第 2 代：

- 第 0 代用于新分配对象，短命对象通常在这里快速回收。
- 存活过若干次回收的对象会晋升到更老的代。
- 第 2 代通常保存生命周期较长的对象，回收成本更高。

分代假设是“多数对象生命期较短”，因此优先回收新对象可以降低平均成本。回收过程中 GC 可能暂停应用线程，并进行对象标记、清扫、压缩或重定位。

**注意：** 不同 GC 模式和运行时版本的实现细节会变化。面试中应说“典型行为”，不要把内部算法描述成永恒不变的规则。

---

### Q15：LOH、POH 和大对象分配有什么影响？

- **LOH（Large Object Heap）** 用于大对象分配。大对象的移动和压缩成本较高，容易带来内存碎片和较长的回收暂停。
- **POH（Pinned Object Heap）** 用于部分固定对象，减少固定对象对普通堆压缩的干扰。
- 大数组、批量缓冲区和大字符串可能进入 LOH。频繁创建和丢弃大对象会造成分配压力。
- 复用缓冲区、使用 `ArrayPool<T>`、控制批次大小可以降低压力，但池化也会延长对象存活时间，不能盲目使用。

**追问：** `GC.Collect()` 能解决内存问题吗？它只能请求 GC，不会解决仍被引用的对象、非托管资源泄漏、缓存无限增长或对象池误用等根因。生产代码不应把强制 GC 当作常规优化手段。

---

### Q16：什么是可达性、内存泄漏和事件导致的泄漏？

GC 判断对象是否可回收的核心不是“有没有业务需要”，而是从 GC Root 是否仍然可达。常见 Root 包括线程栈、静态字段、活动句柄和仍在执行的方法引用。

托管代码也可能出现“内存泄漏”，例如：

- 静态集合持续保存对象。
- 长生命周期发布者持有短生命周期订阅者的事件处理器。
- 定时器、后台任务或缓存没有取消和清理。
- 非托管资源、原生缓冲区或句柄未释放。

```csharp
publisher.Changed += subscriber.HandleChanged;

publisher.Changed -= subscriber.HandleChanged;
```

**诊断思路：** 先观察进程内存、GC 次数和分配速率，再用堆快照查看保留路径（retention path），确认是谁让对象保持可达。

---

### Q17：终结器、`SafeHandle` 和 `GC.SuppressFinalize` 的作用是什么？

终结器允许运行时在对象回收前执行最后清理，但执行时机不确定，且会增加对象进入终结队列的成本。它不适合代替确定性的资源释放。

推荐优先使用 `SafeHandle` 封装操作系统句柄，并通过 `IDisposable` 及时释放。成功执行 `Dispose` 后调用 `GC.SuppressFinalize(this)`，可以避免对象继续进入终结流程。

**边界：** 终结器执行时，其他托管对象可能已经处于不可预测的清理状态，因此终结器中应尽量只处理直接拥有的非托管资源。

## 五、集合、泛型与 LINQ

### Q18：`List<T>`、`LinkedList<T>`、`Array` 如何选择？

| 类型 | 特征 | 适用场景 |
| --- | --- | --- |
| `T[]` | 固定长度、连续存储、索引快 | 长度确定、需要低开销访问 |
| `List<T>` | 动态数组、索引快、尾部追加通常快 | 默认的顺序集合选择 |
| `LinkedList<T>` | 节点分散、已知节点位置时插入删除快 | 需要频繁在节点处插入删除且不依赖索引 |

`LinkedList<T>` 不会因为“插入删除是 O(1)”就普遍更快。查找节点、节点分配和缓存局部性都可能让它输给 `List<T>`。应根据访问模式和基准测试选择。

---

### Q19：`Dictionary<TKey, TValue>` 的底层原理是什么？

字典通常使用哈希表：

1. 根据键计算哈希值。
2. 将哈希值映射到桶。
3. 在桶对应的条目中比较哈希值和键是否相等。
4. 冲突时沿着冲突链或条目结构继续查找。
5. 容量不足时扩容并重新分布条目。

平均查找复杂度接近 $O(1)$，但哈希冲突、扩容、糟糕的哈希函数或可变键都会影响性能和正确性。

**使用要求：** 键的相等判断和哈希值必须稳定；不要在加入字典后改变参与 `Equals` / `GetHashCode` 的字段。

**追问：** `ConcurrentDictionary` 是否所有操作都自动组成业务事务？不是。单次 API 操作提供相应的线程安全保证，但多个操作组合起来仍可能产生竞态，需要使用原子 API 或外部同步。

---

### Q20：`IEnumerable<T>`、`ICollection<T>`、`IList<T>` 和 `IQueryable<T>` 有什么区别？

- `IEnumerable<T>` 表示可以被枚举，通常在当前进程中执行委托。
- `ICollection<T>` 增加数量和修改等集合能力。
- `IList<T>` 增加按索引访问和插入删除。
- `IQueryable<T>` 表示可被查询提供程序解析的表达式树，执行位置可能是数据库或其他外部系统。

**关键区别：**

```csharp
IEnumerable<Order> localQuery = orders.Where(order => order.Total > 100);
IQueryable<Order> remoteQuery = dbContext.Orders.Where(order => order.Total > 100);
```

`IEnumerable` 的 `Where` 通常接受 `Func<T, bool>`；`IQueryable` 通常接受 `Expression<Func<T, bool>>`，提供程序会尝试将表达式翻译成 SQL。

**易错点：** 在 `IQueryable` 上过早调用 `ToList()` 会把后续过滤带回内存执行，可能造成大量数据传输；但复杂表达式也可能无法被数据库翻译，应查看实际生成的 SQL。

---

### Q21：LINQ 延迟执行、立即执行和重复枚举有什么影响？

- `Where`、`Select`、`OrderBy` 等通常返回延迟执行的查询。
- `ToList`、`ToArray`、`Count`、`First`、`Any` 等会触发执行，其中部分操作只消费必要数据，部分操作需要完整遍历。
- 延迟查询捕获的是数据源和委托，真正枚举时可能看到已经变化的数据。
- 重复枚举可能重复计算、重复访问数据库或重复触发副作用。

```csharp
var query = source.Where(item => item.IsActive);
var first = query.FirstOrDefault();
var all = query.ToList();
```

**面试官追问：** `IEnumerable` 查询本身通常不是缓存；需要缓存时显式物化，但要评估内存和一致性成本。

---

### Q22：`yield return` 是怎么工作的？

编译器会把包含 `yield return` 的方法转换为一个实现枚举器协议的状态机。方法调用时通常不会立即执行主体，调用方开始枚举后才逐步运行到下一个 `yield return`。

优点：

- 延迟生成数据。
- 适合流式处理，降低一次性内存占用。
- 可以在消费方提前停止时避免生成全部结果。

风险：

- 数据源的生命周期必须覆盖枚举过程。
- 多次枚举可能重复执行代码。
- 如果迭代器中打开资源，应确保枚举器被正确释放。

---

## 六、委托、事件与反射

### Q23：委托、事件和 Lambda 的关系是什么？

- 委托是类型安全的方法引用，可以保存一个或多个目标方法。
- Lambda 是创建匿名函数的语法，通常会转换成委托或表达式树。
- 事件通常以委托为基础，封装发布订阅关系；事件拥有者可以触发事件，外部订阅者通常只能 `+=` 和 `-=`。

```csharp
public event EventHandler? Completed;

public void Finish()
{
    Completed?.Invoke(this, EventArgs.Empty);
}
```

事件最常见的泄漏风险是：长生命周期发布者持有短生命周期订阅者，订阅者不取消订阅就无法被回收。

---

### Q24：闭包是什么？为什么循环变量和异步代码中容易出问题？

闭包是函数捕获外部变量后形成的环境。被捕获的局部变量可能被编译器提升到一个对象中，使其生命周期超过原本的代码块。

```csharp
var actions = new List<Action>();

for (var index = 0; index < 3; index++)
{
    var captured = index;
    actions.Add(() => Console.WriteLine(captured));
}
```

捕获变量时要注意：

- 捕获的是变量，而不是执行当时的值。
- 循环和异步延迟执行会放大这个区别。
- 闭包可能导致额外分配和对象存活时间延长。

**追问：** 如何排查？检查 lambda 是否捕获外部变量，必要时在循环体内创建局部副本，并用基准测试确认分配影响。

---

### Q25：反射有什么代价？如何在热路径中降低影响？

反射提供运行时发现类型、读取特性、创建对象和调用成员的能力，但通常存在：

- 元数据查找和绑定成本。
- 参数检查和类型转换成本。
- 可能产生额外分配。
- 对裁剪、AOT 和可见性规则更敏感。

常见优化方式：

- 在启动阶段扫描并缓存 `Type`、`PropertyInfo` 或委托。
- 避免每个请求重复查找同一个成员。
- 对高频调用使用编译表达式、源代码生成或直接调用。
- 使用反射时明确考虑 NativeAOT 和 trimming 场景。

反射不是绝对不能用，关键是把它放在合适的频率和生命周期内。

---

## 七、异常、资源释放与字符串

### Q26：异常处理的原则是什么？`throw` 和 `throw ex` 有什么区别？

异常适合表示异常情况，不应把它作为普通分支控制流。应在能处理、能补充上下文或能转换抽象边界的地方捕获。

```csharp
try
{
    ProcessOrder(order);
}
catch (OrderNotFoundException exception)
{
    throw new InvalidOperationException("Order processing failed.", exception);
}
```

- `throw;` 重新抛出当前异常并保留原始堆栈信息。
- `throw exception;` 会重置堆栈起点，影响诊断。
- 包装异常时应把原异常作为 `InnerException`，保留根因。
- 不要捕获 `Exception` 后静默吞掉，也不要只记录消息而丢失异常对象和堆栈。

**追问：** 异常性能差在哪里？异常路径涉及对象创建、堆栈捕获和展开；正常路径不应依赖抛异常来判断常见失败。

---

### Q27：`using`、`try/finally` 和 `await using` 的关系是什么？

`using` 是资源释放语法糖，编译后会形成类似 `try/finally` 的结构，在离开作用域时调用 `Dispose`。`await using` 对应异步释放，会调用 `DisposeAsync`。

```csharp
await using (var stream = new AsyncResource())
{
    await stream.WriteAsync(data);
}
```

**资源释放顺序：** 多个嵌套或同一声明区域的资源通常按后声明先释放。异步释放场景必须让调用链支持异步等待，不能随意改成同步阻塞。

---

### Q28：为什么字符串拼接有时用 `StringBuilder`，有时直接用 `+`？

字符串不可变，重复拼接可能创建多个中间字符串。`StringBuilder` 通过可变缓冲区减少中间对象，适合循环中大量或不确定次数的拼接。

但简单的少量拼接中，编译器和运行时可能已经做了优化，`StringBuilder` 反而增加代码复杂度。应根据循环次数、结果大小和测量结果选择。

**补充：** 结构化日志应优先使用日志框架的模板参数，而不是先用字符串插值把消息拼好，以便延迟格式化并保留结构化字段。

---

## 八、异步编程与线程模型

### Q29：`async/await` 的底层工作原理是什么？

编译器会把异步方法转换为状态机。遇到尚未完成的 `await` 时：

1. 保存当前执行状态。
2. 注册 continuation（后续逻辑）。
3. 将控制权返回给调用方。
4. 异步操作完成后恢复状态机，继续执行后续代码。

`await` 本身不会自动创建一个新线程。I/O 异步通常依靠操作系统的异步机制；CPU 密集型工作若需要并行，才可能显式使用线程池或专用线程。

```csharp
public async Task<string> LoadAsync(HttpClient client, CancellationToken cancellationToken)
{
    return await client.GetStringAsync("https://example.com", cancellationToken);
}
```

**追问：** `async void` 什么时候可以用？主要用于事件处理器；普通业务方法应返回 `Task` 或 `Task<T>`，以便调用方等待、捕获异常和组合任务。

---

### Q30：`Task`、`Thread`、线程池和 `ValueTask` 有什么区别？

- `Thread` 表示一个实际执行线程，创建和维护成本高，适合少量长期运行且需要独立线程语义的任务。
- `Task` 表示一个异步操作或未来结果，不等同于一个线程；它常由线程池、I/O 完成机制或其他调度器支持。
- 线程池复用线程，适合大量短任务，但阻塞线程会造成线程池饥饿。
- `ValueTask<T>` 可以避免某些已经同步完成场景下的 `Task` 分配，但使用约束更多，不能默认替代 `Task<T>`。

**`ValueTask` 注意事项：** 通常只能消费一次，不能随意多次等待或长期保存；只有在高频、可测量的分配热点中才考虑使用。

---

### Q31：为什么同步阻塞异步代码可能死锁？如何避免？

典型风险是调用 `.Result`、`.Wait()` 或同步锁等待异步任务，而异步 continuation 又需要回到被阻塞的上下文，例如 UI 线程或旧式 ASP.NET 请求上下文。

```csharp
var result = GetDataAsync().Result;
```

避免方式：

- 异步调用链一路使用 `await`，不要在异步边界同步阻塞。
- 库代码根据需求使用 `ConfigureAwait(false)`，避免无必要地捕获上下文。
- 使用超时和取消，而不是无限等待。
- ASP.NET Core 默认没有传统 ASP.NET 那种请求 `SynchronizationContext`，但阻塞仍会占用线程并造成线程池饥饿，不能因此认为阻塞是安全的。

---

### Q32：并发、并行、异步分别是什么？

- **并发**：多个任务在时间上交错推进，不要求同时执行。
- **并行**：多个任务在不同执行单元上同时运行，通常用于 CPU 密集型工作。
- **异步**：调用方发起操作后不必阻塞等待，尤其适合 I/O 等待。

一个异步 I/O 操作可以并发但不占用线程等待；一个 `Parallel.ForEach` 是并行执行，但不代表它适合 I/O；`Task.Run` 也不是解决所有异步问题的通用工具。

---

### Q33：`CancellationToken` 如何正确使用？

取消是协作式的，不是强制终止线程。调用方创建并持有 `CancellationTokenSource`，将 token 传入整个调用链；被调用方应在支持取消的 API 中继续传递，并在自定义长循环中检查。

```csharp
public async Task ProcessAsync(
    IReadOnlyList<Item> items,
    CancellationToken cancellationToken)
{
    foreach (var item in items)
    {
        cancellationToken.ThrowIfCancellationRequested();
        await ProcessItemAsync(item, cancellationToken);
    }
}
```

不要把取消异常无条件吞掉；应根据业务决定是向上抛出、转换为请求取消结果，还是记录后结束。

---

## 九、并发、锁与内存模型

### Q34：`lock`、`Monitor`、`Mutex`、`SemaphoreSlim` 如何选择？

| 工具 | 作用范围 | 适用场景 |
| --- | --- | --- |
| `lock` | 进程内托管对象 | 保护短小的同步临界区 |
| `Monitor` | `lock` 的底层能力之一 | 需要超时、条件等待等细粒度控制 |
| `Mutex` | 可跨进程 | 操作系统级互斥，成本较高 |
| `SemaphoreSlim` | 进程内计数信号量，支持异步等待 | 限制并发数、异步资源访问 |

```csharp
private readonly object syncRoot = new();

lock (syncRoot)
{
    UpdateState();
}
```

不要锁 `this`、字符串或公共可见对象，因为外部代码可能获得同一锁导致不可控竞争和死锁。锁内不要执行不可控的 I/O 或调用外部代码。

---

### Q35：`volatile`、`Interlocked` 和 `lock` 的区别是什么？

- `volatile` 主要保证特定字段读写的可见性和有限的重排序约束，不保证复合操作的原子性。
- `Interlocked` 为特定整数、引用等提供原子读改写操作，如递增、交换和比较交换。
- `lock` 同时提供互斥、可见性和临界区保护，适合多个字段需要保持一致的操作。

```csharp
private int counter;

public void Increment()
{
    Interlocked.Increment(ref counter);
}
```

**关键陷阱：** `volatile int count; count++;` 仍然不是原子操作，因为它包含读、加一、写三个步骤。需要原子递增时使用 `Interlocked.Increment`，需要保护一组状态时使用锁或更合适的并发结构。

---

### Q36：什么是死锁？如何分析和预防？

死锁通常满足四个条件：互斥、占有且等待、不可剥夺、循环等待。

预防和排查方法：

- 规定统一的锁获取顺序。
- 缩小临界区，避免嵌套锁。
- 使用带超时的等待并记录锁竞争。
- 不要在锁内同步等待异步任务。
- 避免在锁内调用未知的外部代码。
- 发生问题时采集线程栈和转储，构建线程等待图，而不是只看 CPU 使用率。

**区别：** 线程池饥饿、长时间锁竞争和死锁都会表现为请求变慢，但根因不同，需要结合线程状态和转储判断。

---

### Q37：什么是线程安全？`ConcurrentDictionary` 是否能替代所有锁？

线程安全不是“没有锁”，而是多个线程并发访问时仍能满足类型约定和业务不变量。线程安全集合保证的是集合自身的操作，不自动保证跨多个集合或多步业务逻辑的一致性。

```csharp
var cache = new ConcurrentDictionary<string, Lazy<Item>>();
var value = cache.GetOrAdd(
    key,
    _ => new Lazy<Item>(CreateItem)).Value;
```

即使使用 `GetOrAdd`，值工厂的执行时机和次数也需要结合 API 语义理解；如果创建操作有副作用，不能假设它只会执行一次。对于复杂状态，显式锁、状态机或数据库事务可能更合适。

---

## 十、性能与工程实践追问

### Q38：如何判断一个方法是否产生了装箱或额外分配？

推荐从三层验证：

1. **源码检查**：观察值类型到 `object` / 接口的转换、插值字符串、闭包、LINQ 链和枚举器。
2. **基准测试**：使用 BenchmarkDotNet 对比分配字节数、吞吐量和延迟。
3. **运行时诊断**：结合 GC 计数、分配速率、堆快照和事件追踪工具确认。

不要只因为代码“看起来短”就认为它没有分配，也不要因为一次 GC 就断定存在泄漏。

---

### Q39：为什么高并发服务会出现线程池饥饿？

常见原因是在线程池线程上执行同步阻塞：数据库同步调用、网络同步调用、`.Result` / `.Wait()`、长时间锁等待或不受控的 CPU 任务。当线程池线程都在等待时，新请求无法及时获得线程，延迟会进一步升高。

排查和改进：

- 使用真正支持异步的 I/O API。
- 移除异步链中的同步阻塞。
- 限制 CPU 密集型任务的并发度。
- 观察线程池线程数、队列长度、请求延迟和外部依赖耗时。
- 不要仅靠提高最小线程数来掩盖阻塞根因。

---

### Q40：如何设计一个高性能但可维护的 C# API？

可以从以下顺序考虑：

1. 先定义清晰的所有权、生命周期、错误和取消语义。
2. 默认使用简单、可读、正确的实现。
3. 确认热路径后，再优化分配、复制、锁和 I/O。
4. 使用泛型避免不必要的装箱，使用合适的集合和批处理。
5. 对异步 API 传递 `CancellationToken`，避免同步阻塞。
6. 用基准测试和生产指标验证优化收益。
7. 说明优化的代价，例如对象池可能增加状态复杂度，`ValueTask` 可能增加调用约束，缓存可能造成一致性问题。

**面试官想听到的不是“越快越好”，而是你能在正确性、可维护性和资源成本之间做出有依据的取舍。**

---

### Q41：如何排查一个 .NET 服务的内存持续增长？

建议按以下路径排查：

1. 区分进程工作集增长、托管堆增长、非托管内存增长和本机库分配。
2. 观察 GC 堆大小、代际回收次数、LOH、分配速率和存活对象。
3. 获取不同时间点的堆快照，比较增长最快的类型。
4. 查看对象保留路径，重点检查静态集合、缓存、事件、定时器、后台任务和请求作用域泄漏。
5. 检查 `IDisposable` 资源、句柄、Socket 和原生缓冲区。
6. 修复后用相同负载复测，确认增长曲线和回收行为改善。

**易错点：** “GC 没有马上把内存还给操作系统”不等于泄漏。运行时可能保留已申请的堆空间供后续分配使用。

---

### Q42：为什么不能只根据 Big-O 选择集合？

Big-O 描述规模增长趋势，不代表真实常数、内存布局和硬件缓存行为。实际选择还要考虑：

- 数据规模和访问频率。
- 随机访问还是顺序扫描。
- 分配次数和对象大小。
- CPU 缓存局部性。
- 并发读写需求。
- 扩容、排序、哈希质量和序列化成本。

面试中可以先给出复杂度，再说明决定性因素，并提出用真实数据做基准测试。这比单纯背诵“字典是 $O(1)$、链表插入是 $O(1)$”更完整。
