### 1. 这个岗位和普通高级开发的区别

普通高级开发通常需要证明“我能把功能做出来”；Senior Technical Consultant 还需要证明：

- 我能先澄清业务目标、约束和成功指标，再选择技术方案。
- 我能识别方案的风险、依赖、迁移成本和未来演进路径。
- 我能让其他团队按照共同标准交付，而不是所有问题都由我亲自解决。
- 我能在不确定性中给出可验证的建议，并在证据变化时调整判断。
- 我能向技术人员讲实现细节，也能向业务方讲成本、风险、时间和结果。

## 二、高分回答的通用结构

### 1. 技术题：结论 -> 原理 -> 取舍 -> 验证

回答技术题时，可以使用下面的顺序：

1. **先给结论**：直接说明你的推荐方案和适用条件。
2. **解释原理**：说明运行机制、边界和关键依赖。
3. **比较取舍**：至少提到一个成本、风险或不适用场景。
4. **说明验证**：说清楚用什么指标、测试或监控来证明方案有效。
5. **联系项目**：补充一个真实的使用场景和结果。

例如，不要只说“使用微服务提高扩展性”，而要说：

> 我不会因为系统规模大就默认拆成微服务。我会先根据业务能力、数据所有权、团队边界和独立发布需求划分服务。对高并发且可异步处理的订单通知模块，可以独立部署并通过消息队列解耦；但强事务、强一致且由同一团队维护的模块，初期保留在模块化单体中可能更合理。最后用吞吐量、发布频率、故障隔离和运维成本验证拆分是否带来收益。

### 2. 经历题：STAR + 决策 + 复盘

行为题建议使用：

- **S - Situation**：项目背景、用户、系统规模和原有问题。
- **T - Task**：你的责任、时间限制和成功标准。
- **A - Action**：你做了哪些分析、决策、沟通和落地动作。
- **R - Result**：用数据说明结果，例如延迟、错误率、部署频率、成本或事故数量。
- **Decision**：为什么选择这个方案，放弃了什么替代方案。
- **Learning**：后来沉淀了什么标准、自动化或团队能力。

### 3. 面试官持续追问时的思路

当面试官问“如果失败怎么办”，不要立刻继续增加组件。可以按以下层次回答：

1. 先定义失败：超时、重复、数据丢失、权限失败、区域故障还是发布失败。
2. 说明保护措施：超时、取消、重试上限、幂等、隔离、限流、降级和告警。
3. 说明恢复方式：回滚、重放、补偿、切换或人工介入。
4. 说明如何验证：日志、追踪、业务对账、合成监控和演练。

## 三、.NET 与 ASP.NET Core 高频题

### Q1：`async/await` 如何工作？如何避免错误使用异步？

**高频回答：**

- `async/await` 通常不会自动创建新线程。I/O 操作等待期间，当前线程可以返回线程池处理其他工作；操作完成后，状态机继续执行后续代码。
- `Task` 表示一个异步操作，`Task<T>` 表示带结果的异步操作；线程是执行资源，不能把两者当成同一个概念。
- ASP.NET Core 服务中，数据库、HTTP、文件等 I/O 应使用真正的异步 API，避免在请求线程上同步阻塞。
- CPU 密集型工作需要单独评估线程池、并行度和后台任务模型，不能简单包一层 `Task.Run`。

**常见追问和边界：**

- `.Result`、`.Wait()` 可能造成线程池饥饿、延迟放大，某些同步上下文中还可能死锁。
- 异步方法要传递 `CancellationToken`，让客户端断开或请求超时后能停止无意义工作。
- `Task.WhenAll` 适合彼此独立的并发 I/O，但要考虑下游限流、异常聚合和取消。
- 不要在每次请求中创建 `HttpClient`；使用 `IHttpClientFactory` 管理 handler 生命周期和策略。

**加分表达：**

> 我会同时观察线程池队列长度、请求延迟、下游连接池和取消率。异步代码是否正确，不能只看代码里有没有 `await`，还要看它是否减少了阻塞并能在压力下保持可控的并发度。

### Q2：ASP.NET Core 中间件、过滤器和端点过滤器有什么区别？

**回答要点：**

- **Middleware** 位于整个 HTTP 管道，可处理跨应用的日志、异常、认证、请求上下文和响应头。
- **MVC Filter** 作用在 MVC 控制器或 Action 生命周期中，适合授权、Action 前后处理、结果处理和异常过滤。
- **Endpoint Filter** 适合 Minimal API 或特定端点的参数校验、结果处理和横切逻辑。
- 选择时看作用范围：应用级别用 Middleware，控制器或端点级别用 Filter；不要把业务规则藏在难以追踪的横切逻辑里。

**必须提到的细节：** 中间件注册顺序影响行为。认证必须先于授权，异常处理应尽量包住后续管道，终端映射不能提前截断需要执行的中间件。

### Q3：DI 的 Transient、Scoped、Singleton 如何选择？有哪些陷阱？

| 生命周期 | 典型用途 | 主要风险 |
| --- | --- | --- |
| Transient | 无状态、轻量服务 | 频繁创建对象，依赖图过重时产生额外分配 |
| Scoped | 请求范围的业务服务、`DbContext` | 不能被 Singleton 长期持有 |
| Singleton | 线程安全的配置、缓存、工厂 | 共享状态竞争、内存增长、捕获 Scoped 依赖 |

**高分答案应补充：**

- Singleton 必须是线程安全的，不能因为注册成功就假定并发访问安全。
- `DbContext` 通常是 Scoped，不能跨请求共享，也不应并行执行多个操作。
- 后台服务需要显式创建 scope，不能直接把请求级依赖当作 Singleton 使用。
- 测试时要检查服务注册和生命周期，而不只是对类做单元测试。

### Q4：如何设计一个企业级 ASP.NET Core Web API？

可以从以下层次回答：

1. **契约**：资源建模、HTTP 语义、统一错误响应、分页、过滤、幂等键和版本策略。
2. **边界**：API 层只负责协议适配，业务规则放在应用或领域层，基础设施通过接口隔离。
3. **安全**：OIDC/OAuth 2.0、JWT 验证、授权策略、输入校验、限流、审计和敏感数据保护。
4. **可靠性**：超时、取消、重试边界、熔断或隔离、幂等和异常分类。
5. **可观测性**：结构化日志、相关性 ID、分布式追踪、指标和业务事件。
6. **交付**：契约测试、集成测试、容器化、配置外置、健康检查和可回滚发布。

**不要只说“使用 Clean Architecture”。** 面试官会继续问每一层解决了什么问题、增加了什么成本，以及是否真的能隔离变化。架构名称不是结果，清晰的依赖方向和可验证的边界才是结果。

### Q5：如何处理 API 的版本、兼容性和演进？

- 新增可选字段通常比修改已有字段更兼容；删除、改名、改变语义或收紧校验都可能破坏客户端。
- 先定义弃用周期、迁移文档、监控和责任人，再推出新版本。
- 对内部服务可以优先使用契约测试和消费者驱动契约，避免只靠人工联调。
- 版本策略可以是 URL、Header 或媒体类型，但关键是保持一致、可发现、可监控，而不是争论格式本身。
- 数据库和 API 需要分别考虑兼容窗口。滚动发布期间，旧版本和新版本可能同时运行。

**高分表达：**

> 我把 API 演进看成消费者迁移问题，而不是路由改名问题。每次破坏性变更都要有影响清单、兼容期、使用量监控、迁移负责人和下线标准。

### Q6：EF Core 查询慢时，你如何定位和优化？

**排查顺序：**

1. 先确认是应用等待、数据库执行、网络传输还是序列化耗时。
2. 查看生成的 SQL、执行计划、索引、锁等待、连接池和数据量变化。
3. 检查是否发生 N+1 查询、过度 `Include`、不必要的跟踪、重复枚举或把大量数据拉到内存后再过滤。
4. 读操作按场景考虑投影、`AsNoTracking`、分页、批量查询和合适的索引。
5. 用基准测试和生产级数据验证优化，确认不会牺牲正确性或造成新的数据库压力。

**边界：** 不要把所有慢查询都归因于 EF Core，也不要看到慢就盲目加缓存。缓存需要明确失效策略、一致性要求、容量和命中率。

### Q7：如何为 .NET 服务设计弹性调用？

需要区分错误类型：

- **可重试**：短暂网络故障、部分 5xx、限流响应；应遵守 `Retry-After`，使用指数退避和随机抖动。
- **不可重试**：参数错误、权限失败、业务拒绝；重试只会放大流量或延迟。
- **超时**：每个下游调用都应有明确超时，不能无限等待。
- **重复风险**：写操作重试前必须有幂等键或可证明的去重机制。
- **级联故障**：通过断路器、并发隔离、限流、队列和降级保护调用方与被调用方。

可以使用 `HttpClientFactory` 配合 Polly 或 .NET resilience pipeline，但要说明策略顺序、重试次数、总体请求预算和监控指标。

### Q8：如何保护 ASP.NET Core 应用？

从纵深防御回答：

- 身份认证与授权分离；用 policy、role 或 resource-based authorization 表达业务权限。
- 对输入做模型校验、长度限制和业务校验；使用参数化查询，避免注入。
- 使用安全的密钥管理，不把密码、令牌写入代码、镜像、日志或配置仓库。
- 配置 HTTPS、合理的 CORS、响应头、CSRF 防护场景、速率限制和请求大小限制。
- 记录安全事件和管理操作，但不记录 token、密码和不必要的个人敏感数据。
- 把依赖扫描、镜像扫描、SAST、DAST 和安全测试纳入交付流程。

当被问到“怎样保证安全”时，不要只回答一个工具名。要说明威胁、控制措施、证据和持续检查方式。

### Q9：生产环境出现 .NET API 延迟升高，你如何排查？

1. 先确认影响范围：全部接口还是单个端点，全部实例还是单个可用区，用户请求还是后台任务。
2. 比较 P50、P95、P99，不用平均值掩盖长尾延迟。
3. 查看最近部署、配置、流量变化、线程池、GC、连接池、数据库等待和下游调用。
4. 用 trace 找出耗时最长的 span，用日志关联具体请求，用指标判断是否为系统性问题。
5. 先采取低风险措施，例如回滚、限流、扩容或关闭非核心功能，再继续根因分析。
6. 通过业务交易、错误率、延迟和资源指标验证恢复，并补充 RCA 和预防性动作。

## 四、AWS、微服务与容器高频题

### Q10：如何把一个 .NET 单体系统迁移到 AWS？

**不要直接回答“拆成微服务并部署到 Kubernetes”。** 推荐分阶段回答：

1. **评估**：梳理业务能力、依赖、数据流、流量模式、合规要求、SLA、RTO/RPO 和团队能力。
2. **先建立基础**：账号与环境隔离、VPC、子网、IAM、日志、密钥、IaC、网络连接和成本标签。
3. **选择迁移路径**：短期可先容器化或使用托管运行时降低迁移风险；稳定后再按业务边界逐步拆分。
4. **拆分优先级**：选择变化频繁、边界清晰、可独立扩展或故障隔离价值高的模块。
5. **数据迁移**：定义所有权、同步方式、回滚和校验；避免在没有一致性方案时简单拆数据库。
6. **渐进发布**：使用双写或 CDC 时明确最终一致性和补偿；用灰度、流量切换和可回滚策略控制风险。
7. **验证结果**：比较功能正确性、性能、可用性、成本、发布速度和运维复杂度。

### Q11：ECS、EKS、Lambda 或 EC2 如何选择？

不要背服务对比表，应先看约束：

| 场景 | 倾向选择 | 需要承认的代价 |
| --- | --- | --- |
| 已有容器、希望减少集群运维 | ECS/Fargate | 编排生态和部分控制能力不如自管 Kubernetes 灵活 |
| 多团队已有 Kubernetes 能力，需要统一平台 | EKS | 集群、升级、网络、RBAC 和成本治理复杂 |
| 事件驱动、执行时间可控、无状态 | Lambda | 启动延迟、执行限制、运行时约束和供应商耦合 |
| 特殊系统依赖、长驻进程或精细主机控制 | EC2 | 补丁、容量、可用性和主机运维责任更多 |

**面试官认可的重点：** 你会根据团队运维能力、流量稳定性、启动时间、合规、成本、可移植性和故障模型做选择，而不是把最复杂的平台当成高级方案。

### Q12：如何划分微服务边界？

使用业务能力、数据所有权、事务边界、变化频率、团队边界和扩展需求共同判断。一个服务应尽量拥有自己的业务规则和数据，不通过共享数据库表形成隐式耦合。

**需要回答的反例：**

- 服务太小会增加网络调用、部署、测试和观测成本。
- 共享数据库能短期降低迁移成本，但会削弱独立演进和故障隔离。
- 按技术层拆成“用户服务、数据库服务、日志服务”通常不是有价值的业务边界。
- 不是所有模块都需要异步；强一致、低延迟的流程可能需要同步调用或模块化单体。

### Q13：微服务之间如何处理数据一致性？

- 单个服务内部使用本地事务保证自身数据正确。
- 跨服务流程优先考虑最终一致性、事件驱动和 Saga，而不是分布式两阶段提交。
- 使用 Outbox Pattern 保证业务数据与待发布事件在同一事务内落盘，再由发布器可靠投递。
- 消费者必须幂等，消息要考虑至少一次投递、重复、乱序、延迟、死信和重放。
- 对需要人工处理的失败，设计补偿、对账和运营入口，而不是让消息静默丢失。

**加分表达：**

> 最终一致性不是“不保证一致”，而是明确一致性目标、可接受延迟、检测方式和修复路径。设计时我会同时画出正常路径、重复消息路径和补偿路径。

### Q14：如何设计一个稳定的 API Gateway 和微服务入口？

Gateway 可以承担认证前置、路由、限流、TLS 终止、请求大小限制、相关性信息和基础观测，但不应承载复杂领域逻辑。

需要说明：

- 内外部 API 的信任边界和认证方式。
- 超时、重试、熔断、限流和配额如何避免集中式放大故障。
- Gateway 自身如何高可用、扩展和发布。
- 如何避免把所有服务调用串成高延迟的同步链。
- 失败响应如何保持契约一致，并隐藏内部拓扑和敏感信息。

### Q15：容器化 .NET 应用时有哪些关键点？

- 使用多阶段构建减少镜像体积，固定基础镜像版本并扫描漏洞。
- 应用以非 root 用户运行，配置和密钥通过运行环境注入。
- 正确处理 `SIGTERM`、优雅关闭、健康检查和 `CancellationToken`。
- 日志输出到标准输出，由平台统一收集；不要在容器内依赖本地持久文件。
- 明确 CPU、内存、临时磁盘和连接数边界，避免“能启动”但无法稳定运行。
- 镜像不可变，构建一次后在不同环境晋级，避免环境间重新编译出不同产物。

### Q16：如何设计 AWS 上的高可用和灾难恢复？

先问清业务能接受什么，再讨论多可用区还是多区域：

- **RTO**：服务恢复所允许的最长时间。
- **RPO**：数据恢复点最多允许丢失的时间范围。
- 多 AZ 主要应对单个组件或可用区故障；多区域带来更高成本、数据复制、路由和运维复杂度。
- 备份不仅要有策略，还要定期恢复演练，验证数据、权限、配置、密钥、DNS 和依赖是否完整。
- 明确故障切换的触发条件、责任人、通信方式、回切方法和数据一致性检查。

**不要说“多副本就等于灾备”。** 多副本只能解决部分故障，还要看数据持久化、依赖服务、部署能力和人工操作路径。

## 五、CI/CD、安全、可观测性与伸缩

### Q17：你会如何设计 .NET 项目的 CI/CD 流水线？

一个成熟流水线至少包括：

1. 还原依赖、编译和单元测试。
2. 集成测试、契约测试和必要的数据库测试。
3. 静态分析、依赖漏洞扫描、秘密扫描和容器镜像扫描。
4. 生成带版本号的不可变制品，并保存测试与扫描证据。
5. 部署到接近生产的环境，执行 smoke test 和关键业务交易验证。
6. 使用批准、变更记录和环境保护规则控制生产发布。
7. 通过滚动、蓝绿或金丝雀发布降低风险，设定自动中止和回滚条件。
8. 发布后观察错误率、延迟、资源、业务成功率和日志，确认旧版本兼容窗口。

**关键原则：** 生产环境应晋级已经测试过的同一个制品，而不是到生产环境重新构建。

### Q18：如何做到零停机或低风险发布？

先说明“零停机”不是绝对承诺，而是需要满足架构和业务条件：

- 应用无状态或状态可外置，实例可滚动替换。
- 新旧版本在兼容窗口内可以同时运行。
- 数据库变更遵循 expand-and-contract：先增加兼容结构，再迁移读写，最后删除旧结构。
- 使用健康检查、连接排空、优雅关闭、灰度流量和自动回滚。
- 通过业务指标而不是只有进程存活来判断发布是否成功。

### Q19：如何建立团队级安全标准？

从“标准、自动检查、例外、证据”四个部分回答：

- 标准：身份、密钥、网络、日志、数据分类、依赖和镜像的最低要求。
- 自动检查：把规则加入模板、代码扫描、IaC 扫描、流水线门禁和运行时监控。
- 例外：记录原因、风险、补偿控制、批准人和到期时间，避免永久豁免。
- 证据：保留扫描结果、审批记录、修复记录、访问审计和定期复核结果。

技术顾问的价值不是宣称“系统绝对安全”，而是建立可重复、可审计、能持续改善的控制机制。

### Q20：如何设计微服务的可观测性？

- **日志**：结构化、带时间、服务名、版本、环境、trace ID 和业务关联键；禁止泄露秘密和敏感数据。
- **指标**：请求量、错误率、延迟分位数、饱和度、队列深度、重试、死信和业务成功率。
- **追踪**：跨 API、消息、数据库和外部依赖传播 trace context，识别长尾 span。
- **告警**：可行动、去重、和 SLO 或业务影响关联，并链接 runbook。
- **验证**：用故障演练和历史事故回放检查是否能发现、定位和证明恢复。

### Q21：如何平衡性能、可靠性和云成本？

先定义业务目标和预算，再测量瓶颈：

- 通过缓存、批处理、异步化、连接复用和索引减少无效工作。
- 通过自动伸缩、合适实例、存储分层和非生产环境调度控制成本。
- 不用缓存掩盖错误的数据模型，不用无限重试掩盖下游不稳定，也不用过度扩容替代根因分析。
- 追踪单位业务成本，例如每千次请求、每笔订单或每份报告的云成本。
- 在架构评审中同时记录性能目标、可靠性目标、成本预算和验证方法。

## 六、架构治理与技术领导力题

### Q22：你如何主持一次架构设计评审？

**评审前：**

- 明确问题、目标、非目标、约束、成功指标和决策期限。
- 要求提供上下文、现状、候选方案、数据流、失败场景、安全、成本、迁移和回滚。
- 提前邀请开发、运维、安全、数据、业务和受影响系统的代表。

**评审中：**

- 先确认共同目标，再逐项讨论关键风险和不可逆决策。
- 追问容量假设、依赖、故障模式、数据所有权、权限和运维责任。
- 区分“必须满足”“应该满足”和“以后可以演进”的要求。
- 让反对意见变成可验证的问题，必要时安排 spike 或 PoC，而不是靠职级投票。

**评审后：**

- 输出 ADR，记录背景、决策、替代方案、后果和复审条件。
- 为行动项指定负责人和截止时间，跟踪到落地。
- 在实现和生产运行后复盘假设是否成立。

### Q23：如何建立团队编码和架构标准，又不让团队觉得被管控？

1. 先从事故、重复劳动、交付质量或安全风险中找真实问题。
2. 让团队参与标准设计，区分不可妥协的底线与可按场景调整的建议。
3. 提供模板、示例、脚手架和自动化检查，减少靠记忆执行。
4. 设立合理的例外流程，要求说明风险和补偿措施。
5. 用指标评估标准是否有效，例如缺陷率、交付周期、恢复时间、扫描发现和采用率。

**高分表达：** 标准的目的不是让所有代码看起来一样，而是减少高风险差异，把团队精力留给真正需要判断的问题。

### Q24：团队在技术选型上意见不一致，你怎么处理？

可以这样回答：

- 先分别理解各方真正关心的风险：交付期限、学习成本、性能、支持周期、合规还是团队技能。
- 把争论转成决策矩阵，列出业务权重、成本、风险和验证方式。
- 对不确定且可逆的选择做小范围 PoC；对不可逆决策提高评审深度。
- 记录决策和未选择方案的原因，不把不同意见变成个人对错。
- 决策确定后统一执行；如果证据后来变化，按约定的复审条件重新评估。

### Q25：你如何指导初级或中级工程师？

不要只说“我会 code review”。可以说明一个完整闭环：

- 用小而真实的任务让对方负责设计、实现、测试和上线的一部分。
- Review 时解释判断标准和风险，而不是只改代码。
- 通过结对编程、设计演练、故障复盘和技术分享建立能力。
- 为成长设定可观察目标，例如独立完成一个 API、主持一次评审或处理一类告警。
- 在给予自主权的同时设置安全边界和及时反馈。

### Q26：如何向业务方解释一个技术债或架构风险？

不要只说“代码质量不好”。把技术问题翻译成业务结果：

- 影响哪个客户流程或收入场景？
- 发生概率、影响范围和最坏后果是什么？
- 当前有什么控制，剩余风险是多少？
- 修复需要多少时间、成本和停机窗口？
- 不修复的代价如何随时间增长？
- 如何分阶段降低风险，并用什么指标判断投资有效？

例如：

> 当前共享数据库导致每次发布都需要多个团队同时回归，近三次发布平均延迟 2 天。我的建议不是立即全面拆库，而是先为订单模块建立数据访问边界和契约测试，用一个迭代验证发布周期能否缩短，再根据证据决定后续迁移投入。

### Q27：描述一次你处理生产事故或重大技术问题的经历。

建议按下面的答案顺序准备真实案例：

1. 影响：哪些用户、交易或业务流程受影响，严重程度如何。
2. 指挥：谁负责 incident command、技术排查、沟通和记录。
3. 止血：选择了回滚、流量控制、扩容、故障切换还是功能降级，为什么。
4. 证据：日志、指标、追踪、部署记录和时间线如何支持判断。
5. 恢复：如何从技术和业务两个角度确认服务恢复。
6. 根因：根因、促成因素和检测缺口分别是什么。
7. 改进：增加了什么测试、告警、标准、自动化或演练，谁负责以及何时验证。

**面试官最关注的信号：** 你是否保持冷静、保护证据、明确责任、及时沟通，并把一次事故转化为系统改进，而不是只讲“我重启了服务”。

### Q28：多个 stakeholder 对优先级有冲突时，你如何推动决策？

- 先确认每方目标和硬性约束，不把“更重要”当作结论。
- 建立透明的排序标准：客户影响、风险、合规、收入、时间敏感性、依赖和实现成本。
- 提供至少两个选项及其后果，明确推荐项和需要业务方承担的风险。
- 把决定、假设、负责人和复审时间写下来，避免会后出现不同版本。
- 如果无法在团队层解决，带着事实、选项和建议升级，而不是只报告冲突。

## 七、综合架构场景题

### Q29：设计一个 AWS 上的企业订单平台，后端使用 ASP.NET Core

**推荐回答结构：**

```text
客户端
  -> CDN / WAF / API Gateway
  -> ASP.NET Core API（ECS 或 EKS）
  -> 订单服务 -> 关系型数据库
             -> Outbox -> 消息总线 -> 库存、支付、通知服务
  -> Redis 或托管缓存（按一致性要求使用）
  -> 日志、指标、追踪和告警平台
```

说明时覆盖以下内容：

1. **边界**：订单、库存、支付和通知拥有各自业务规则；不要共享数据库表。
2. **一致性**：下单使用幂等键；订单状态通过事件和 Saga 推进；失败进入死信或补偿流程。
3. **安全**：身份认证、服务间授权、密钥托管、私有子网、加密和审计。
4. **可靠性**：超时、有限重试、限流、熔断、隔离、健康检查和多 AZ。
5. **交付**：容器镜像扫描、不可变制品、灰度发布、数据库向后兼容和自动回滚。
6. **指标**：订单成功率、P95/P99 延迟、重复订单数、消息积压、支付失败率、库存对账差异和单位交易成本。

最后明确取舍：如果团队规模小、领域边界尚未稳定，可以先用模块化单体和可靠消息边界，避免为了“微服务”承担不必要的运维成本。

### Q30：发布后 API 错误率升高，你会怎么处理？

**第一阶段：恢复服务**

- 确认影响范围和错误类型，建立事件沟通渠道。
- 对比发布版本和健康版本，检查配置、数据库迁移、依赖、流量和基础设施事件。
- 如果发布是高可信根因，按预案暂停推广、回滚或切换流量；不要同时修改多个变量。

**第二阶段：确认恢复**

- 观察错误率、延迟、资源、依赖和关键业务交易。
- 用合成请求和业务方确认验证，不因单个健康检查变绿就宣布结束。

**第三阶段：防止复发**

- 做时间线和 RCA，区分直接根因与促成因素。
- 增加缺失的测试、发布门禁、兼容性检查、告警或回滚自动化。
- 给每个改进项指定 owner、期限和验证方式。

### Q31：客户希望“尽快上云”，但安全和运维团队认为方案风险过高，你怎么办？

先把“尽快”和“安全”转成可衡量的目标，而不是让双方继续用口号争论：

- 识别必须满足的控制：身份、数据分类、网络隔离、日志、密钥、备份、恢复和审批。
- 提供分阶段方案：先迁移低风险、可回滚的工作负载，完成基础平台和监控，再迁移关键系统。
- 对每个例外写清剩余风险、补偿控制、批准人和到期时间。
- 设定 go/no-go 标准，使用 PoC、负载测试和恢复演练验证。
- 向客户说明每个选项对时间、成本、风险和未来扩展的影响，并给出明确推荐。

### Q32：如何判断一次架构改造是否成功？

不能只看“服务已经上线”。至少从四类指标判断：

| 维度 | 示例指标 |
| --- | --- |
| 业务 | 关键流程成功率、业务处理时延、客户投诉或人工操作量 |
| 技术 | P95/P99 延迟、错误率、吞吐量、故障隔离效果 |
| 交付 | 发布频率、变更失败率、回滚时间、测试自动化覆盖的关键路径 |
| 运维与成本 | MTTD、MTTR、告警噪声、云成本、值班负担和容量余量 |

改造前先建立基线，改造后在相同或可解释的流量条件下比较；否则“提升了很多”缺乏可信度。

## 八、让面试官更认可你的表达方式

### 1. 每个答案都说出一个 trade-off

优秀候选人不会把技术方案描述成没有代价的万能解。可以主动使用：

- “这个方案的收益是……，代价是……，我在当前约束下选择它的原因是……”
- “如果一致性要求从最终一致性提升到强一致，我会重新评估……”。
- “在团队没有 Kubernetes 运维能力时，我不会因为它流行就引入 EKS。”
- “这个优化需要先测量，否则可能把压力从应用转移到数据库。”

### 2. 用指标代替形容词

少说“性能明显提升”“系统非常稳定”，多说：

- P95 延迟从多少降到多少。
- 错误率、超时率或重复消息数量变化多少。
- 发布周期、回滚时间或人工操作减少多少。
- 每月事故数、MTTR、云成本或资源利用率变化多少。
- 指标来自哪个监控、测试或业务对账。

没有确切数字时，可以诚实说明测量方式和量级，不要临时编造精确百分比。

### 3. 主动区分“我做了什么”和“团队做了什么”

使用“我负责定义目标、组织评审、实现关键部分、协调安全团队、推动上线”；再说明“团队共同完成了哪些工作”。这样既体现个人贡献，也体现 Senior Technical Consultant 应有的协作能力。

### 4. 画图时从业务流开始

架构题可以按以下顺序画：

1. 用户和关键业务动作。
2. API 或入口。
3. 核心业务服务和数据所有权。
4. 同步调用、异步事件和外部依赖。
5. 安全、观测、部署和灾备横切能力。
6. 一个成功路径和两个失败路径。

每放一个组件，都说明它解决什么问题；如果不能说明价值，就不要为了显得复杂而添加。

### 5. 五类经历必须准备真实版本

| 经历 | 面试官要听到什么 |
| --- | --- |
| 一次架构设计 | 约束、候选方案、取舍、决策和结果 |
| 一次生产故障 | 影响、止血、证据、沟通、RCA 和预防 |
| 一次技术分歧 | 如何理解对方、如何验证、如何接受最终决策 |
| 一次团队指导 | 如何提升他人能力，而不是自己接管任务 |
| 一次业务妥协 | 如何把风险透明化，并设计分阶段或补偿方案 |

### 6. 可以使用的高分句式

- “我先确认业务目标和不可妥协的约束，再决定是否需要这个技术。”
- “这里的关键不是选择哪个云服务，而是明确故障模型、数据所有权和恢复目标。”
- “我会把这个决定写成 ADR，并定义什么时候需要复审。”
- “这个写操作可能被重试，所以幂等性是接口契约的一部分。”
- “我会用业务指标确认恢复，而不是只看进程和基础设施指标。”
- “我会把安全要求放进模板和流水线门禁，而不是依赖发布前人工提醒。”
- “我推荐先做一个可逆的 PoC，验证最不确定的假设。”

### 7. 常见失分信号

- 只罗列 AWS、设计模式和中间件名称，不说明为什么选择。
- 把微服务、Kubernetes、事件驱动当成所有问题的默认答案。
- 说“保证 100% 安全”“绝对零停机”而没有条件、证据和边界。
- 生产事故只讲重启、扩容或回滚，不讲数据完整性、沟通和复盘。
- 把代码规范说成个人偏好，无法说明它解决的团队问题。
- 行为题使用“我们”讲完整故事，却说不清自己的职责和贡献。
- 面对追问时继续增加组件，回避成本、失败路径和运维责任。

## 九、面试前自检清单

### 技术深度

- [ ] 能解释 `async/await`、DI、EF Core、API 契约和弹性策略的原理与边界。
- [ ] 能画出一个 ASP.NET Core + AWS + 数据库 + 消息系统的架构图。
- [ ] 能说清微服务拆分、一致性、幂等、重试、死信和补偿。
- [ ] 能说明容器、CI/CD、灰度发布、回滚和数据库兼容迁移。
- [ ] 能定义可观测性指标，并从指标、日志和追踪定位问题。

### 架构与治理

- [ ] 准备至少一个 ADR 或架构评审案例。
- [ ] 能说明安全、可用性、性能、成本和可运维性的权衡。
- [ ] 能把标准落到模板、自动化检查和例外治理，而不是停留在文档。
- [ ] 能给出 RTO、RPO、SLO 或容量假设，而不是只说“高可用”。

### 领导力与沟通

- [ ] 准备一次技术分歧、一次事故、一次团队指导和一次业务妥协案例。
- [ ] 每个案例都有个人职责、决策依据、结果指标和后续改进。
- [ ] 能用业务语言解释技术风险、成本、时间和收益。
- [ ] 能在不知道答案时说明假设、验证步骤和需要咨询的专家，而不是编造确定结论。

### 最后一分钟复习

面试前只需记住这条主线：

> **先理解业务目标，再做架构决策；先识别失败和风险，再谈实现；用自动化和标准保证落地；用指标和真实结果证明价值。**
