## 一、面试回答框架

面对 Kafka 面试题，可以按下面的顺序组织答案：

1. **先给结论**：用一句话说明核心机制。
2. **再讲数据路径**：消息从生产者到 Broker，再到消费者，具体经过哪些组件。
3. **说明边界条件**：单分区顺序、消费位点、重平衡、故障切换等。
4. **给出参数或方案**：只列真正影响结论的配置，不要堆参数。
5. **说明代价与监控**：吞吐、延迟、可靠性、磁盘、网络和运维成本如何取舍。

例如被问到“如何保证消息不丢失”，不要只回答 `acks=all`。完整答案应包括生产者确认、Broker 副本、`min.insync.replicas`、消费者提交位点、业务处理失败重试、死信和监控等多个环节。

## 二、Kafka 基础概念

### 1. Kafka 是什么？适合解决什么问题？

**答案：**

Kafka 是一个分布式事件流平台。它把消息以追加日志的形式写入 Topic 的分区，并允许多个消费者按照自己的进度读取数据。

Kafka 适合：

- 服务之间的异步解耦和削峰填谷。
- 日志、埋点、CDC、交易事件等持续数据的采集和分发。
- 一个事件被多个下游系统独立消费。
- 对吞吐量、可扩展性和可回放能力有要求的场景。

Kafka 不应被简单理解为“带队列功能的数据库”。它更像一个可持久化、可分区、可复制的事件日志。消息是否删除由保留策略决定，消费者通常通过 Offset 记录自己的读取位置。

**面试加分点：**

Kafka 擅长顺序追加和批量读写，但不适合用来做任意条件查询、低延迟请求响应、复杂事务数据库或无限期保存所有数据的唯一存储。

### 2. Kafka 的核心组件有哪些？

**答案：**

- **Producer**：将消息发送到 Topic 的某个分区。
- **Broker**：Kafka 服务节点，负责接收、持久化、复制和提供消息读取服务。
- **Topic**：逻辑上的事件类别，例如 `order-created`。
- **Partition**：Topic 的物理分片，是并行度和有序性的基本单位。
- **Consumer**：读取并处理消息的客户端。
- **Consumer Group**：一组协同消费同一个 Topic 的消费者实例。
- **Offset**：消费者在某个分区中的读取位置。
- **Controller**：负责集群元数据和分区状态管理。在 KRaft 模式下由 Controller 节点组成 Controller quorum；早期架构使用 ZooKeeper 保存部分集群元数据。

### 3. Topic、Partition、Replica 分别是什么？

**答案：**

- **Topic** 是业务上的消息分类。
- **Partition** 是 Topic 的分区。每个分区中的消息有单调递增的 Offset，并且只能保证分区内顺序。
- **Replica** 是分区副本。一个分区通常有一个 Leader 和多个 Follower，副本分布在不同 Broker 上。

例如一个 Topic 有 6 个分区、复制因子为 3，逻辑上有 6 个分区，物理上有 18 份副本。每条消息只写入一个分区的 Leader，再由 Follower 复制。

### 4. Kafka 为什么要分区？分区数应该如何设置？

**答案：**

分区的主要作用是：

- 把数据分散到多个 Broker，进行水平扩展。
- 允许多个消费者并行读取。
- 让生产和消费可以批量、并行进行。

分区数不能只按当前流量设置，还要考虑未来的消费并行度、Broker 数量、单分区吞吐、保留数据量和元数据开销。

需要注意：

- 一个消费组对一个分区同一时刻最多由一个消费者实例处理。
- 分区数增加后不能自动恢复原有全局顺序。
- 分区数变更可能改变按 Key 分区的映射，尤其是默认分区器使用分区总数参与计算时。
- 分区太多会增加文件句柄、内存、选举、重平衡和监控成本。

**实践建议：**先用压测测出单分区吞吐，再按目标吞吐、消费者并行度和故障余量估算，并预留增长空间。

### 5. Kafka 如何保证消息顺序？

**答案：**

Kafka 只能保证**同一分区内**消息按照 Offset 顺序存储和读取，不能天然保证一个 Topic 所有分区之间的全局顺序。

要保证同一个业务实体的顺序，例如同一个订单或账户：

1. 使用稳定的业务 Key。
2. 让同一个 Key 总是进入同一个分区。
3. 消费端不要把同一分区的消息无序并发处理，或自行维护同 Key 的处理顺序。
4. 处理失败时不能简单跳过前面的消息，否则后续消息可能先被处理。

如果必须全局有序，可以只使用一个分区，但代价是吞吐和并行度受到限制。顺序和吞吐通常需要做业务范围上的取舍。

### 6. Kafka 和传统消息队列有什么区别？

| 对比项 | Kafka | 传统队列模型 |
|---|---|---|
| 数据模型 | 持久化事件日志 | 消息通常被消费后确认并移除 |
| 消费方式 | 消费者按 Offset 拉取，可回放 | 常见为 Broker 推送或队列确认 |
| 并行模型 | Topic 分区 + Consumer Group | 队列消费者竞争消费 |
| 多下游消费 | 每个消费组独立维护 Offset | 常需要复制队列或配置多个订阅 |
| 典型优势 | 高吞吐、可扩展、可回放 | 请求级投递、复杂路由、单条确认体验较好 |
| 典型风险 | 分区规划和重平衡较复杂 | 高吞吐、历史回放和大规模扩展可能受限 |

实际选型还要看消息路由、延迟、投递语义、事务、运维能力和生态，不应只按“吞吐量高低”决定。

### 7. Kafka 的消息结构是什么？

**答案：**

一条 Kafka Record 通常包含：

- Key
- Value
- Headers
- Timestamp
- Offset（由分区日志分配）
- Partition（由生产过程确定）

Kafka 不理解 Value 内部的业务结构。JSON、Avro、Protobuf 等格式需要由应用和 Schema 管理体系约定。生产消息时建议携带事件类型、事件版本、业务主键、产生时间和追踪 ID，便于演进、审计和排障。

### 8. Kafka 为什么吞吐量高？

**答案：**

主要原因包括：

- 分区提供水平并行能力。
- 追加写日志避免大量随机写。
- 顺序 I/O、批量发送和批量拉取减少系统调用。
- Page Cache 利用操作系统缓存。
- 零拷贝减少数据在用户态和内核态之间的复制。
- Producer、Broker、Consumer 都支持流水线和异步处理。
- Broker 通常不追踪每个消费者的独立投递状态，只保存日志和消费位点。

吞吐高不代表延迟永远低。批量大小、等待时间、复制确认、压缩和磁盘性能都会影响延迟。

### 9. Kafka 使用拉模式还是推模式？为什么？

**答案：**

Kafka 的 Consumer 主要采用拉模式：消费者主动向 Broker 发送 Fetch 请求。

拉模式的优点：

- 消费者可以按照自己的处理能力控制读取速度。
- 便于批量拉取，提高吞吐。
- 消费者可以根据 Offset 回放历史数据。
- 不同消费者可以使用不同的消费速度。

代价是消费者需要合理配置 Fetch 参数并处理空轮询、长轮询和积压监控。Kafka 的 Fetch 请求通常不是简单的立即返回，Broker 可以等待数据达到条件或超时后返回，以减少无效请求。

## 三、生产者面试题

### 10. Producer 如何决定消息发送到哪个分区？

**答案：**

常见规则是：

- 如果明确指定 Partition，直接发送到指定分区。
- 如果有 Key，分区器通常根据 Key 计算分区，使相同 Key 稳定地落到同一分区。
- 没有 Key 时，生产者会在可用分区之间进行负载分配；具体行为取决于客户端版本和分区器配置。

如果业务依赖顺序，应使用稳定 Key，而不要依赖“无 Key 时碰巧按顺序发送”。如果使用自定义分区器，还要确保生产端升级后行为兼容。

### 11. `acks=0`、`acks=1`、`acks=all` 有什么区别？

**答案：**

- `acks=0`：生产者不等待 Broker 确认，延迟低、吞吐高，但无法感知发送失败，可靠性最低。
- `acks=1`：Leader 写入本地日志后确认。若 Leader 在 Follower 复制前故障，可能丢失已确认消息。
- `acks=all`：Leader 等待满足同步复制条件的副本确认。通常配合 `min.insync.replicas` 使用，可以提高持久性。

`acks=all` 也不是绝对不丢：如果副本数不足、配置允许不安全选主、磁盘或集群发生超出设计范围的故障，仍需要结合副本和故障策略分析。

### 12. `enable.idempotence` 解决什么问题？

**答案：**

幂等生产者通过 Producer ID 和每个分区的序列号，让 Broker 能识别重试产生的重复写入，从而避免同一生产者会话中的重复记录。

它主要解决网络抖动、响应丢失导致的生产重试重复，不等于业务层的全局幂等。生产者重启、业务重复发送、跨系统重复投递仍可能需要业务唯一 ID 和消费端去重。

启用幂等生产通常要使用兼容的可靠性配置，例如 `acks=all`，并注意客户端版本对默认配置和 `max.in.flight.requests.per.connection` 的约束。不要只依赖一个配置名来宣称“业务不会重复”。

### 13. Producer 重试为什么可能造成消息乱序？

**答案：**

假设同一个连接上有多个未完成请求：

1. 消息 A 发送请求失败或响应超时。
2. 消息 B 先成功写入。
3. A 重试后才写入。
4. Broker 中可能出现 B 在 A 前面。

幂等生产者可以在协议层防止重复和处理部分序列问题，但业务仍应正确设置重试、并发请求数和错误处理策略。若强顺序是硬要求，还要限制同一分区的并发发送，并确保失败处理不会跳过前序消息。

### 14. `batch.size` 和 `linger.ms` 如何影响性能？

**答案：**

- `batch.size` 是单个分区待发送批次的目标大小。批次越大，压缩和网络利用率通常越好，但会占用更多内存。
- `linger.ms` 是等待更多消息加入当前批次的时间上限。适当增加可以提高批量度，但会增加少量发送延迟。

二者不是越大越好。低延迟系统需要控制等待时间；高吞吐系统可通过批量和压缩换取网络效率。应观察发送延迟、批次大小、压缩率、请求速率、BufferPool 等指标后调参。

### 15. `buffer.memory` 满了会发生什么？

**答案：**

生产者会在本地缓冲尚未发送的记录。当 Broker 处理慢、网络拥塞或生产速度持续超过发送速度时，缓冲池可能耗尽。此时 `send()` 获取缓冲空间会等待，超过 `max.block.ms` 后抛出异常。

排查时应区分：

- Broker 写入或复制变慢。
- 网络带宽不足。
- 批次和压缩配置不合理。
- 下游磁盘或 ISR 状态异常。
- 应用生产速率超过集群容量。

单纯无限增大 `buffer.memory` 只能延迟故障并增加应用内存压力。

### 16. Producer 如何处理发送失败？

**答案：**

常见策略是：

- 对可重试错误启用有限次数或时间窗口内的重试。
- 对不可重试错误记录失败事件并告警。
- 使用异步发送回调或 Future 检查最终结果，不能只调用 `send()` 就认为成功。
- 使用幂等生产减少重试重复。
- 对无法发送的业务消息写入本地持久化、补偿表或专用失败 Topic，避免静默丢弃。
- 设计超时、熔断和背压，防止 Broker 故障拖垮业务线程池。

如果业务要求“用户请求成功就必须有事件”，还要设计业务数据库 Outbox、事务消息或可靠补偿，而不是只依赖内存中的 Producer 缓冲区。

### 17. Kafka 消息压缩有什么收益和代价？

**答案：**

压缩可以减少网络流量和磁盘占用，批次越大通常压缩效果越好。常见算法包括 gzip、snappy、lz4 和 zstd，最终选择取决于 CPU、压缩率和延迟目标。

压缩会消耗生产端和 Broker 端的 CPU，解压也会消耗消费者 CPU。应使用真实消息样本压测，而不是只比较算法名称。压缩通常按 Record Batch 工作，零散小消息的压缩收益不明显。

## 四、消费者与消费组面试题

### 18. Consumer Group 是什么？如何实现消费并行？

**答案：**

Consumer Group 是一组共同消费 Topic 的消费者实例。一个分区在同一消费组内同一时刻只会分配给一个消费者，因此：

- 分区是并行消费的上限。
- 消费者数量大于分区数时，多出的消费者会处于空闲状态。
- 同一个 Topic 被不同消费组消费时，每个消费组都有独立的 Offset，互不影响。

例如 Topic 有 8 个分区，消费组有 3 个实例，最多有 3 个实例同时工作；如果有 12 个实例，最多仍只有 8 个实例分到分区。

### 19. Kafka 的 Offset 是什么？保存在哪里？

**答案：**

Offset 是分区内的消息位置。消费者通常提交的是“下一条要读取的 Offset”。消费组提交的位点保存在内部 Topic `__consumer_offsets` 中，也可以在客户端中手动保存到外部存储，但外部保存会增加一致性和运维复杂度。

需要区分：

- **Current position**：消费者当前准备读取的位置。
- **Committed offset**：已经提交给消费组的位点。
- **Log end offset**：分区当前末尾位置。
- **Consumer lag**：通常是 Log End Offset 减去消费者位点，具体工具对定义可能略有差异。

### 20. 自动提交和手动提交有什么区别？

**答案：**

自动提交由客户端按照配置周期提交当前消费位置，代码简单，但可能出现：

- Offset 已提交，业务处理尚未完成，进程崩溃后消息不会再次读取，造成业务层丢失。
- 批量处理时间超过提交周期，提交时机与业务完成时机不匹配。

手动提交可以在业务处理成功后提交：

- `commitSync` 通常等待提交结果，语义清晰但可能阻塞。
- `commitAsync` 延迟较低，但要处理回调失败，并防止旧提交覆盖新进度。

更重要的不是选“自动”还是“手动”，而是明确提交点与业务成功点的关系。常见可靠模式是处理成功后再提交，并让业务处理具备幂等性。

### 21. `auto.offset.reset` 有哪些选项？什么时候生效？

**答案：**

常见选项：

- `earliest`：没有有效已提交位点时，从保留数据的最早位置开始。
- `latest`：没有有效已提交位点时，从当前末尾开始，通常不会读取历史消息。
- `none`：没有有效位点时直接报错，由应用显式处理。

它只在消费组没有有效 Offset，或已提交 Offset 超出当前保留范围时生效。已有有效 Offset 时，修改该配置不会让消费者从头开始。要重放历史消息，应使用新的消费组或显式重置消费组位点。

### 22. 什么是 Rebalance？为什么会发生？

**答案：**

Rebalance 是消费组重新分配分区的过程。发生原因包括：

- 消费者加入或退出消费组。
- 消费者心跳超时，被协调器认为失活。
- 消费者处理消息过久，超过 `max.poll.interval.ms`。
- Topic 分区数发生变化。
- 订阅关系或消费组成员信息发生变化。

Rebalance 期间部分分区可能暂停消费，频繁重平衡会造成延迟抖动、重复处理和吞吐下降。

优化方向：

- 处理长任务时调整 `max.poll.interval.ms`，同时控制单次 `poll()` 返回数量。
- 调整 `session.timeout.ms`、`heartbeat.interval.ms`，避免网络短抖动造成误判。
- 使用合适的分配策略，例如 Cooperative Sticky，降低全量撤销和重新分配。
- 控制实例生命周期，优雅关闭消费者。
- 使用静态成员配置减少短暂重启造成的分配变化，但要注意实例长期失联的检测。

### 23. `poll()` 很慢会有什么问题？

**答案：**

Kafka Consumer 需要持续调用 `poll()`，以维持心跳、处理组协议和获取消息。若业务处理阻塞太久，可能超过 `max.poll.interval.ms`，消费者会被踢出消费组并触发重平衡。

常用处理方式：

- 减少每次拉取和处理的消息量。
- 把耗时任务移到工作线程池，但要严格管理分区内顺序和 Offset 提交。
- 将慢任务拆分或异步化。
- 让 `max.poll.interval.ms` 大于最坏处理时间，并设置合理的上限。
- 对处理结果、失败重试和关闭流程设计清晰的状态机。

简单地增加超时时间只能降低重平衡频率，不能解决处理线程长期阻塞和消费积压。

### 24. 如何实现消费端幂等？

**答案：**

Kafka 的“至少一次”语义意味着同一消息可能被重复处理。消费端需要根据业务要求实现幂等，例如：

- 使用事件 ID 或业务唯一键建立去重表。
- 数据库写入使用唯一约束、UPSERT 或条件更新。
- 状态更新带版本号，拒绝旧版本覆盖新版本。
- 外部 API 使用幂等请求号。
- 对账、扣款等关键操作采用业务流水号和状态机。

不要把 Offset 当作业务幂等键，因为同一业务事件可能重新生产而拥有不同 Offset。去重记录与业务写入如果必须原子完成，应放在同一个数据库事务中，或采用 Outbox、事务消费者等更完整的方案。

### 25. Consumer Lag 是什么？如何排查？

**答案：**

Consumer Lag 反映消费位置落后于生产位置的程度，常见近似值为：

```text
Lag = Log End Offset - Consumer Committed/Current Offset
```

排查步骤：

1. 判断是所有分区积压，还是少数分区积压。
2. 对比生产速率、消费速率、单条处理耗时和批量大小。
3. 检查是否发生频繁 Rebalance、异常重试或死循环。
4. 检查消费者实例 CPU、GC、线程池、连接池和下游数据库。
5. 检查 Broker 请求延迟、网络、磁盘和 ISR 状态。
6. 判断是否存在热点 Key，使一个分区远超其他分区。
7. 评估临时增加消费者、扩分区、降级业务或旁路重放的风险。

Lag 不一定代表故障。离线批处理、故意延迟消费或保留历史数据时，也可能存在可接受的 Lag。应定义按分区、按时间和按业务优先级的告警阈值。

### 26. 消费者如何安全处理 Poison Message？

**答案：**

Poison Message 是反复处理都会失败的消息。如果消费者一直重试并且不推进 Offset，可能阻塞整个分区。

常见设计：

1. 记录失败原因、Topic、Partition、Offset 和事件 ID。
2. 对瞬时错误进行有限次数、带退避的重试。
3. 对确定性错误发送到重试 Topic 或死信 Topic，并保存原始消息和错误上下文。
4. 只有在失败消息已经被可靠记录后，才提交该位置，避免分区永久卡住。
5. 提供人工修复、重新投递和审计能力。

重试 Topic 的延迟级别、顺序影响和消息过期策略需要提前定义。不要用无限同步重试替代故障处理设计。

## 五、可靠性与消息语义

### 27. Kafka 有哪些消息投递语义？

**答案：**

- **At-most-once（至多一次）**：先提交 Offset，再处理消息。可能丢消息，但通常不会重复。
- **At-least-once（至少一次）**：先处理消息，成功后再提交 Offset。进程在处理成功、提交前崩溃时可能重复，不能保证不重复。
- **Exactly-once（精确一次）**：在特定边界内让一条输入记录对下游结果只产生一次可见效果，需要事务、隔离级别和参与系统共同支持。

大多数普通消费者默认更接近至少一次。工程上更常见的可靠方案是“至少一次投递 + 业务幂等”，因为它对外部数据库和第三方系统更容易落地。

### 28. 如何设计 Kafka 消息不丢失方案？

**答案：**

要分层回答：

**生产端：**

- 使用 `acks=all`。
- 开启幂等生产。
- 配置有限重试和合理超时。
- 检查异步发送结果，不静默忽略异常。

**Broker 端：**

- 使用合理的复制因子，副本分布在不同故障域。
- 设置 `min.insync.replicas`，避免只有一个副本时仍成功确认。
- 生产者使用 `acks=all` 时，ISR 不满足要求应让发送失败而不是假装成功。
- 禁止或谨慎使用不安全 Leader 选举。
- 监控 Under Replicated Partitions、Offline Partitions、磁盘和网络。

**消费端：**

- 业务处理成功后再提交 Offset。
- 对重复消费实施幂等。
- 失败进入可观测的重试或死信链路。

**业务系统：**

如果数据库写入和 Kafka 发送必须保持一致，应考虑 Outbox、CDC、Kafka 事务或可重试补偿。仅提高 Kafka 的 `acks`，无法解决“数据库已提交但事件未发送”的双写问题。

### 29. 如何理解 `replication.factor`、ISR、`min.insync.replicas`？

**答案：**

- `replication.factor`：分区总副本数，包括 Leader。
- ISR（In-Sync Replicas）：当前被认为与 Leader 保持同步、具备参与安全选主资格的副本集合。
- `min.insync.replicas`：写入使用 `acks=all` 时，要求至少有多少个 ISR 才接受写入。

例如复制因子为 3，`min.insync.replicas=2`：当 ISR 为 3 或 2 时可以写入；ISR 降到 1 时，使用 `acks=all` 的生产请求应失败。这会牺牲部分可写性，换取更强的数据安全边界。

常见错误是只设置复制因子，不设置 `min.insync.replicas`，然后使用默认或不严格的确认方式。

### 30. 什么是 Kafka 事务？Exactly-once 如何实现？

**答案：**

Kafka 事务允许生产者把多条消息、多个分区的写入作为一个原子批次提交，也可以把消费位点提交纳入事务。消费者使用 `isolation.level=read_committed` 时，只读取已提交事务中的消息。

典型的 consume-transform-produce 流程：

1. 消费输入消息。
2. 开启 Kafka 事务。
3. 写入输出 Topic。
4. 将输入消费位点作为事务的一部分提交。
5. 提交事务；失败则中止并重试。

要注意：Kafka 事务主要保证 Kafka 内部读写链路。它不能自动使 Kafka 写入和外部 MySQL、HTTP API、邮件系统等操作成为一个分布式原子事务。外部系统仍需要幂等、事务表、Outbox 或补偿机制。

### 31. Leader 故障时 Kafka 如何处理？

**答案：**

当分区 Leader 所在 Broker 故障时，Controller 会从 ISR 中选择新的 Leader，并通知客户端更新元数据。生产者和消费者发现旧 Leader 不可用后，会刷新元数据并重试。

安全性取决于：

- 新 Leader 是否来自 ISR。
- 已确认数据是否已经复制到足够副本。
- 是否允许从非同步副本中选主。
- 客户端重试和超时配置是否合理。

故障切换期间可能出现短暂不可写、请求失败、延迟上升或重复处理，业务需要具备重试和幂等能力。

### 32. 什么是 Unclean Leader Election？为什么通常关闭？

**答案：**

Unclean Leader Election 允许从不在 ISR 中的副本中选出 Leader。这样可能提高分区可用性，但旧 Leader 尚未复制的数据可能丢失，甚至造成日志回退。

对金融、订单、计费等数据完整性要求高的场景，通常关闭不安全选主，并通过多副本、跨故障域、容量冗余和故障演练提高可用性。是否打开必须基于业务对“可用但可能丢数据”的容忍度决策。

## 六、存储、复制与集群面试题

### 33. Kafka 的日志存储结构是什么？

**答案：**

每个分区对应一个日志目录，日志由多个 Segment 文件组成。Segment 通常包含数据文件以及 Offset、时间索引等索引文件。消息按 Offset 追加写入当前活跃 Segment，达到大小或时间条件后滚动生成新 Segment。

Segment 化的好处是：

- 删除过期数据时按 Segment 批量删除。
- 索引不会无限增长到一个文件。
- 日志恢复和管理粒度更合理。

Kafka 的 Offset 是逻辑位置，不应直接当作磁盘字节偏移。读取通常先通过索引定位，再从日志文件顺序读取。

### 34. Kafka 的数据为什么能保留很久？消息什么时候删除？

**答案：**

Kafka 的保留策略通常按时间或日志总大小工作：

- `retention.ms` 控制消息保留时间。
- `retention.bytes` 控制分区日志保留大小。
- 删除通常以 Segment 为单位，而不是逐条即时删除。

因此超过保留时间的消息可能不会在同一秒被删除，实际删除时机还受 Segment 滚动和清理线程影响。

消费者是否读取过不决定消息是否删除。只要消息仍在保留范围内，新的消费组仍可以从历史 Offset 开始读取。

### 35. Log Compaction 是什么？适合什么场景？

**答案：**

Log Compaction 按 Key 保留较新的记录，目标是最终保留每个 Key 的最新状态，同时可能保留部分旧记录。带空 Value 的 Tombstone 可表示删除标记，经过相关保留时间后可被清理。

适合：

- 账户最新状态。
- 配置、用户资料、设备状态等可按 Key 重建的状态 Topic。
- 需要通过日志恢复当前快照的场景。

它不等于“立刻只保留一条”，也不保证消费者永远看不到旧记录。Compaction 是后台异步过程，仍应设置时间保留、磁盘和清理线程参数。

### 36. Kafka 如何进行副本同步？什么是 HW 和 LEO？

**答案：**

- **LEO（Log End Offset）**：某个副本本地日志末端的下一个 Offset。
- **High Watermark（HW）**：消费者通常可以安全读取到的边界，通常不超过所有相关同步副本都已确认的范围。

Follower 从 Leader 拉取数据并更新自己的日志。Leader 根据副本同步进度推进 HW。消费者通常只能读取 HW 之前的消息，避免读到未来可能回退的数据。

面试时还可以补充：Leader Epoch 用于帮助副本和客户端识别 Leader 变更，减少故障恢复时的日志不一致风险。

### 37. Kafka 使用 ZooKeeper 和 KRaft 有什么区别？

**答案：**

早期 Kafka 将部分集群元数据、Controller 选举和配置协调交给 ZooKeeper。KRaft 将元数据管理和 Controller quorum 纳入 Kafka 自身，通过 Raft 风格的元数据日志管理集群状态。

KRaft 的目标包括：

- 减少外部依赖。
- 统一 Kafka 元数据和运维模型。
- 改善大规模分区场景下的元数据管理。
- 让 Controller 具备更清晰的仲裁和故障模型。

迁移或部署时必须严格按照目标 Kafka 版本的官方兼容矩阵和升级流程操作，不能把 ZooKeeper 配置直接删除后启动生产集群。面试回答应说明版本、迁移路径和回滚方案，而不是只说“KRaft 更快”。

### 38. Controller 负责什么？Broker 挂掉时谁来处理？

**答案：**

Controller 负责维护和发布集群级元数据，例如 Broker 注册、分区 Leader 选举、副本状态变化和部分配置变更。具体职责会随 Kafka 版本和 KRaft/ZooKeeper 架构有所变化。

Broker 故障后，Controller 负责检测故障、为受影响分区选择新 Leader，并发布元数据更新。它不是所有数据读写的中央转发器，正常消息读写主要由客户端直接访问承载分区 Leader 的 Broker。

### 39. 为什么副本要跨可用区部署？

**答案：**

如果 3 个副本都在同一个可用区，可用区级故障会同时影响所有副本。将副本分布到不同可用区，可以降低单个机房、电源或网络域故障导致的数据不可用风险。

但跨可用区复制会增加网络延迟和跨区流量成本。应结合副本放置策略、Rack Awareness、`min.insync.replicas`、故障域容量和云厂商网络费用共同设计。

## 七、性能与容量规划

### 40. Kafka 性能优化应该从哪些方面入手？

**答案：**

**生产端：**

- 增大有效批次，合理设置 `linger.ms`。
- 开启合适的压缩。
- 使用异步发送并控制并发。
- 避免单条同步发送。
- 选择合理的消息大小和 Key 分布。

**Broker 端：**

- 使用足够快的磁盘和网络。
- 监控 Page Cache、磁盘利用率、请求队列和复制延迟。
- 合理设置日志目录和分区分布。
- 避免分区数量远超集群管理能力。

**消费者端：**

- 增大批量拉取并批量处理。
- 合理使用线程池，但不破坏分区内顺序。
- 提高下游写入效率，避免单条数据库提交。
- 控制重试和死信流量。

优化必须先确定瓶颈是 CPU、磁盘、网络、Broker 请求、消费者处理还是下游系统，不能盲目修改参数。

### 41. 如何估算 Kafka 集群容量？

**答案：**

至少估算下面几个维度：

```text
原始写入量 = 平均消息大小 × 每秒消息数
网络与磁盘写入量 ≈ 原始写入量 × 副本数
保留容量 = 原始写入量 × 保留时长 × 副本数 × 压缩/膨胀系数
```

还要加入：

- 峰值流量和突发流量。
- Broker 故障时剩余节点的承载能力。
- Rebalance、Leader 迁移和副本重建带来的额外流量。
- 磁盘不能长期使用到 100%，要预留清理和故障空间。
- 消费组数量、分区数和连接数带来的内存、文件句柄与请求开销。

设计时应做容量压测和故障压测，不能只用平均流量计算。

### 42. 消息太大有什么问题？如何处理？

**答案：**

大消息会增加网络传输、内存、GC、复制、重试和消费者处理压力，还可能触发生产者、Broker、消费者三端大小限制不一致的问题。

优先方案：

- 只在 Kafka 中传递事件和对象引用，把大文件放到对象存储。
- 拆分消息，并携带批次 ID、序号、总片数和校验信息。
- 压缩 Payload，但要评估 CPU 和故障重试成本。
- 统一检查 Producer、Broker、Consumer 的消息大小配置。

“把最大消息限制全部调大”通常只是把问题推迟到内存和网络层。

### 43. Kafka 中的热点分区是什么？如何解决？

**答案：**

热点分区是少数分区承载了远高于平均值的流量，常见原因是 Key 分布不均、某个租户或账户极其活跃，或者自定义分区器逻辑不合理。

解决方向：

- 统计 Key 的频率和分区分布。
- 对允许乱序的业务使用更均匀的 Key。
- 对热点实体拆分为多个逻辑 Key，并在消费端重组顺序。
- 增加分区只能扩大整体并行度，不能自动解决固定热点 Key。
- 对强顺序业务明确“顺序范围”，不要要求全局顺序。

### 44. Kafka 什么时候应该扩分区？扩分区有什么风险？

**答案：**

当现有分区无法满足目标吞吐、消费者并行度或未来增长时可以扩分区。扩分区会增加并发能力，但风险包括：

- 旧消息不会自动重新均衡到新分区。
- 默认按 Key 分区的映射可能变化，同一个 Key 未来可能落到不同分区。
- 消费组会发生分配变化。
- 分区数增加会提高元数据和运维成本。

如果业务强依赖 Key 顺序，应在建 Topic 时预留足够分区，或使用能保证兼容映射的分区策略，并进行迁移验证。

## 八、运维与故障排查

### 45. 生产者发送超时，应该如何排查？

**答案：**

按链路排查：

1. 确认 Topic 和分区 Leader 是否存在，客户端 `advertised.listeners` 是否可达。
2. 查看生产者错误类型：超时、认证、授权、消息过大、未知 Topic 还是 Not Enough Replicas。
3. 检查 Broker 请求延迟、网络、磁盘 I/O、CPU、请求队列和 GC。
4. 查看 ISR 是否收缩、是否存在 Under Replicated Partitions。
5. 检查 `acks`、`delivery.timeout.ms`、`request.timeout.ms` 和重试配置的关系。
6. 检查 Topic 是否启用限流、配额或 ACL 拒绝。
7. 验证发送回调或 Future 是否正确处理最终异常。

不要一开始就把所有超时时间调大。先确定是服务端变慢、网络不可达还是配置不兼容。

### 46. 消费者突然停止消费，如何排查？

**答案：**

检查顺序可以是：

- 进程是否存活，是否发生 OOM、死锁或线程池耗尽。
- 是否仍在持续调用 `poll()`。
- 是否因为处理太慢超过 `max.poll.interval.ms`。
- 是否频繁 Rebalance，或被其他实例抢占分区。
- 是否发生认证、授权、反序列化或消息格式异常。
- 消费组是否有分区分配，提交 Offset 是否前进。
- Broker 是否能响应 Fetch 请求。
- 是否被下游数据库、HTTP 服务或限流拖住。

需要同时查看应用日志、消费组状态、Lag、Broker 指标和下游依赖，不能只看“消费者进程还在运行”。

### 47. 什么是 Under-Replicated Partitions？如何处理？

**答案：**

Under-Replicated Partition（URP）表示分区当前 ISR 数量少于副本总数，说明至少一个 Follower 没有及时跟上 Leader。短暂网络抖动可能导致临时 URP，持续 URP 则说明存在风险。

排查方向：

- Follower Broker 的磁盘延迟、磁盘空间和 I/O 饱和度。
- Broker 间网络丢包、带宽和连接错误。
- GC、CPU、线程池和请求队列。
- 分区是否过于集中或存在热点。
- 副本重建、Leader 迁移是否造成额外负载。

恢复时先解决 Broker 或网络根因，再观察 ISR 是否恢复。不要在根因未解决时盲目增加副本迁移并发，避免集群雪崩。

### 48. `advertised.listeners` 配错会导致什么问题？

**答案：**

客户端首先连接 Bootstrap Server 获取集群元数据，随后会根据元数据连接真正承载分区 Leader 的 Broker。如果 Broker 对外公布的地址是容器内地址、内网地址或不可解析的主机名，客户端可能表现为：

- 能连接 Bootstrap，但发送或消费时失败。
- 部分 Broker 正常，部分 Broker 超时。
- 云环境、容器环境或跨网络环境中频繁出现连接错误。

配置 Listener 时要区分监听地址和对外公布地址，并根据内外网、TLS、SASL 和端口规划分别配置。排查时要从客户端网络命名空间验证每一个公布地址的可达性。

### 49. 如何安全地重放 Kafka 历史消息？

**答案：**

推荐使用新的消费组进行重放，避免影响线上消费组。步骤通常包括：

1. 明确时间范围、分区范围和目标业务。
2. 创建独立消费组，设置合适的起始 Offset。
3. 以只读、旁路或幂等方式运行重放程序。
4. 先在小范围验证消息格式、顺序和下游副作用。
5. 监控重放速率、Lag、下游压力和重复数据。
6. 完成后保存审计记录，必要时清理消费组。

如果必须重置原消费组，先暂停消费者、记录当前位点、评估重复处理和下游影响，再执行重置，不能直接在生产环境使用命令行盲目回退。

### 50. Kafka 安全如何设计？

**答案：**

常见安全层次：

- **传输加密**：TLS，防止网络窃听和篡改。
- **身份认证**：SASL、TLS Client Authentication 等。
- **授权**：ACL，按 Topic、Group、Cluster 等资源最小授权。
- **数据保护**：敏感字段脱敏、密钥管理、Schema 校验和访问审计。
- **运维安全**：限制管理接口、分离管理员与应用账号、审计配置变更。
- **网络隔离**：安全组、防火墙、专用子网和跨域访问控制。

应用账号不应拥有集群级管理权限。还要考虑消息保留期、备份、删除策略和合规审计，Kafka 中的消息不应被默认视为“内部数据”。

## 九、Kafka 设计题

### 51. 设计一个订单事件系统，如何保证可靠和可追踪？

**参考答案：**

可以采用以下设计：

- 按事件类型拆分 Topic，例如 `order-created`、`order-paid`、`order-cancelled`，或采用统一事件 Topic 配合事件类型字段，具体取决于消费者隔离和治理需求。
- 使用 `order_id` 作为 Key，保证同一订单在同一分区内有序。
- 设置合理复制因子、跨可用区副本和 `min.insync.replicas`。
- 生产端开启幂等和可靠确认。
- 业务数据库使用 Outbox，保证订单状态提交与事件记录在一个本地事务内完成，再由发布程序发送到 Kafka。
- 消费者采用至少一次处理 + 业务幂等，使用事件 ID 或订单状态版本去重。
- 失败消息进入重试和死信链路，不能阻塞整个订单分区。
- 消息带上事件 ID、订单 ID、版本号、产生时间、来源服务和 Trace ID。
- 监控生产失败、消费 Lag、重试量、死信量、订单状态不一致和端到端延迟。

如果支付还依赖外部支付网关，不能声称 Kafka 事务可以覆盖支付网关；必须通过幂等支付请求、状态查询和补偿对账闭环处理。

### 52. 设计日志采集平台，如何防止日志高峰压垮系统？

**参考答案：**

- 采集端进行本地缓冲、批量发送、压缩和有限重试。
- 按应用、环境和日志类型规划 Topic，避免把所有流量塞入一个不可治理的 Topic。
- 设置保留时间和分层存储，原始日志不一定永久保留在 Kafka。
- 生产端和 Topic 配额限制异常应用，防止单个租户耗尽集群资源。
- 对高峰设置背压和降级策略，例如降低低价值 Debug 日志采样率。
- 下游分析使用独立消费组，重放不影响实时消费。
- 监控入口速率、Broker 磁盘、网络、请求延迟、消费 Lag 和丢弃/采样量。
- 对日志字段进行脱敏，避免把密码、Token 和个人敏感信息写入消息。

关键是先明确“哪些日志绝不能丢、哪些可以采样、保留多久、谁负责恢复”，而不是只扩大 Kafka 集群。

### 53. Kafka 和数据库之间如何实现最终一致？

**参考答案：**

最常见的可靠方案是 Outbox Pattern：

1. 业务事务同时写入业务表和 Outbox 事件表。
2. 发布器或 CDC 读取 Outbox 事件。
3. 事件成功发送到 Kafka 后记录发布状态或由 CDC 推进位点。
4. 失败时重试，消费者使用事件 ID 幂等。
5. 通过对账任务发现长期未发布或处理失败的事件。

如果是 Kafka 消费后写数据库，则采用“数据库事务写业务结果和消费记录”，用事件 ID 建唯一约束，然后在事务成功后推进 Kafka Offset。Kafka Offset 提交和数据库事务不是同一个事务，所以重复消费是正常的，关键是让重复执行结果不产生额外副作用。

### 54. 如何设计延迟消息和定时重试？

**参考答案：**

Kafka 本身不是专门的延迟队列。可选方案包括：

- 使用不同延迟级别的重试 Topic，例如 1 分钟、5 分钟、30 分钟，由调度消费者按时间转发。
- 消息携带 `next_attempt_at`，消费者读取后判断是否到期；若未到期，需要避免阻塞整个分区。
- 使用外部调度器或延迟队列，并在到期后重新写入 Kafka。
- 对大规模定时事件使用专门的时间轮、数据库调度表或云消息服务。

设计时要说明顺序、重复、重试上限、死信、堆积和重启恢复。简单地 `sleep` 当前消费线程会阻塞分区并可能触发重平衡。

### 55. 如何实现跨集群容灾？

**参考答案：**

需要先确定 RPO、RTO、主备方向和是否要求双活。常见方案是使用 MirrorMaker 2 等复制工具，将指定 Topic 和消费组位点复制到灾备集群。

需要考虑：

- Topic、ACL、Schema 和配置是否同步。
- 复制延迟和网络带宽。
- 双向复制是否造成环路和重复。
- 切换时生产者和消费者如何修改 Bootstrap 地址。
- 消费组 Offset 如何映射。
- DNS、证书、权限、数据校验和回切流程。
- 灾备演练是否真的验证了业务恢复，而不只是复制任务显示绿色。

跨集群复制不能自动解决业务幂等和外部系统一致性，切换后仍要依靠事件 ID、状态机和对账。

## 十、常见追问与易错点

### 56. “Kafka 能保证 Exactly Once，所以业务不会重复”对吗？

不对。Kafka 的事务可以在 Kafka 读写范围内提供更强的原子性和可见性，但外部数据库、HTTP 服务、邮件、支付网关等不自动加入 Kafka 事务。跨系统仍要做幂等、Outbox、状态机和补偿。

### 57. “一个 Topic 只有一个消费者，所以顺序就一定正确”对吗？

不完整。顺序的基本边界是分区。即使只有一个消费者，如果生产消息分布在多个分区，仍没有 Topic 全局顺序；如果消费者内部使用异步线程，也可能破坏处理顺序。

### 58. “消息消费成功了就可以提交 Offset”对吗？

要先定义“成功”。如果只是 `poll()` 返回，不能提交；如果数据库事务、外部 API 或状态更新已经可靠完成，才可以提交。提交 Offset 不代表外部副作用已经成功。

### 59. “增加消费者数量就能消除 Lag”对吗？

不一定。消费者数不能超过有效分区并行度；如果瓶颈在下游数据库、热点分区、网络、反序列化或单条处理耗时，盲目增加实例可能只会增加连接和重平衡压力。

### 60. “Kafka 数据写入磁盘就绝对不会丢”对吗？

不对。还要考虑生产确认、复制完成、ISR、Leader 选举、磁盘损坏、机房故障、配置和运维误操作。可靠性是端到端属性，不是某一个“写磁盘”动作决定的。

### 61. “扩分区一定兼容原有 Key 顺序”对吗？

不一定。按分区数计算的分区器可能在分区数变化后让同一个 Key 映射到新分区，从而改变该 Key 的后续顺序边界。强顺序业务必须在扩分区前评估分区器和迁移方案。

### 62. Kafka 集群中最值得优先监控哪些指标？

至少包括：

- Consumer Lag、消费速率和重平衡次数。
- 生产请求错误率、请求延迟、发送失败和重试。
- Under-Replicated Partitions、Offline Partitions、ISR 变化。
- Broker 磁盘使用率、磁盘 I/O、网络吞吐、CPU 和 JVM/GC。
- Leader 分布是否均衡。
- Controller 状态和元数据请求。
- Topic/Partition 数量、消息大小和保留空间。
- 重试 Topic、死信 Topic 和业务处理失败量。

监控应关联业务指标，例如订单事件延迟、支付状态不一致，而不只是看 Broker 是否存活。

## 十一、面试速记清单

### 基础必答

- Topic 是逻辑分类，Partition 是并行和顺序边界。
- 同一 Partition 内有序，Topic 全局不天然有序。
- Consumer Group 内一个 Partition 同时只分配给一个消费者。
- Offset 是分区内位置，消费组位点保存在 `__consumer_offsets`。
- 消息保留由时间、大小或 Compaction 策略决定，与是否消费无关。

### 可靠性必答

- 生产可靠性：`acks=all`、幂等、重试、发送结果检查。
- Broker 可靠性：复制因子、ISR、`min.insync.replicas`、故障域。
- 消费可靠性：处理成功后提交、幂等、重试和死信。
- Exactly-once 有边界，不能自动覆盖外部系统。

### 排障必答

- 先区分生产、Broker、复制、消费和下游瓶颈。
- Lag 要按分区看，注意热点分区。
- `poll()` 处理太久会触发重平衡。
- `advertised.listeners` 错误会导致 Bootstrap 能连但实际 Broker 不可达。
- URP 持续存在说明副本同步存在风险。

### 设计题必答

- 明确顺序范围、吞吐目标、峰值、保留期和 RPO/RTO。
- 说明 Key、分区数、复制因子和故障域。
- 说明重复、失败、重试、死信和幂等策略。
- 说明 Schema 演进、权限、监控、审计和容量扩展。
- 对数据库、支付、HTTP 等外部系统说明一致性边界。

## 结语

Kafka 面试的核心不是背诵配置，而是能把以下链路讲完整：

```text
业务事件
  -> Producer 分区与确认
  -> Broker 日志、复制与故障切换
  -> Consumer Group 分配与 Offset
  -> 业务处理、幂等、重试与死信
  -> 监控、告警、容量和容灾
```

回答生产问题时，优先说明数据是否允许丢失、是否允许重复、顺序的边界在哪里，以及故障后如何恢复和验证。这样的答案通常比单独罗列参数更接近真实架构设计。
