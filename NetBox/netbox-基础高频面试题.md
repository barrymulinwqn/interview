# NetBox 基础高频面试题

本指南面向网络工程师、网络自动化工程师、网络运维工程师、DCIM/IPAM 管理员和平台工程师的 NetBox 面试。题目聚焦基础概念与高频实际场景，并提供可直接组织成口头回答的解释。

> **使用方式：** 不要逐字背诵。每题都应结合自己的网络规模、设备类型、地址规划、自动化工具或一次实际治理经历补充例子。面对“如何做”的题目，回答应包含目标、建模选择、风险控制、验证方式和后续维护。

## 回答方法

对概念题，建议按以下顺序回答：

1. 用一句话定义概念和它解决的问题。
2. 说明它在 NetBox 数据模型中的位置和关键关联对象。
3. 给出一个真实网络场景的例子。
4. 说明常见误区或治理边界。

对排障、设计和自动化题，建议按以下顺序回答：

1. 明确现象、影响范围、数据权威来源与最近变更。
2. 先执行只读检查，避免在未确认现状时修改源数据。
3. 说明具体的建模、配置或恢复步骤。
4. 用 UI、API、对象计数、日志或自动化结果验证。
5. 解释权限、审计、回滚和长期治理措施。

## 一、定位、价值与架构

## 1. 什么是 NetBox？它解决什么问题？

**参考回答：** NetBox 是用于网络基础设施建模和记录的开源平台，核心能力是 IP 地址管理（IPAM）和数据中心基础设施管理（DCIM）。它把站点、机柜、设备、接口、连接、IP、VLAN、VRF、线路、虚拟机等信息放进统一的数据模型，使团队拥有可信、可查询、可自动化使用的网络资源目录。

它解决的通常不是“缺少一个表格”，而是信息分散、来源不一致、地址重复分配、设备连接关系不清、自动化脚本使用过期数据等问题。NetBox 为网络自动化提供了结构化的权威输入，但它本身不是设备配置下发系统，也不会自动发现或配置全部网络设备。

**高频追问：** 与传统 CMDB 相比有什么区别？NetBox 的数据模型围绕网络工程实践设计，特别强调 IPAM、设备组件、机柜、物理连接和网络覆盖等对象；它可以与 CMDB 集成，但不是简单替代所有企业 CMDB 能力。

## 2. 什么是 Source of Truth？为什么 NetBox 适合做网络 Source of Truth？

**参考回答：** Source of Truth 是经过治理、具有明确责任人和变更流程的权威数据来源。对同一类事实，例如“某个 IP 地址分配给哪台设备的哪个接口”，团队应知道以哪个系统的数据为准，不能让 Excel、监控系统、设备配置和多个数据库同时成为权威来源。

NetBox 适合承担这个角色，因为它提供了结构化模型、关系约束、状态字段、权限控制、变更日志、REST/GraphQL API、Webhook、事件规则和自定义校验。自动化流程可以从 NetBox 读取意图与资源分配，再向设备、DNS、云平台、监控或 CMDB 同步结果。

**易错点：** 不能只因为“把数据导进 NetBox”就称为 Source of Truth。还必须定义数据所有者、录入或同步责任、变更流程、质量检查、冲突处理和定期审计。

## 3. NetBox 的核心功能模块有哪些？

**参考回答：** 面试中可以按业务域回答：

- **DCIM：** 区域、站点、位置、机柜、厂商、设备类型、设备、组件、接口、电缆、供电和无线等。
- **IPAM：** RIR、ASN、聚合网段、VRF、VLAN、前缀、地址范围、IP 地址、FHRP 组和路由目标等。
- **组织与租户：** 租户、联系人、团队和对象所有权。
- **线路与电路：** 服务供应商、电路类型、电路和终端。
- **虚拟化：** 集群、集群类型、虚拟机和虚拟接口。
- **自动化与扩展：** REST API、GraphQL API、Webhook、事件规则、自定义字段、自定义校验、导出模板、配置上下文、脚本和插件。

回答时不必罗列所有菜单，而应说明这些模块的关系。例如，设备属于站点和设备角色，接口可通过电缆连接，接口可分配 IP，IP 和前缀可关联 VRF，设备和 IP 可由租户归属。

## 4. NetBox 的典型技术架构是什么？

**参考回答：** NetBox 是基于 Python 和 Django 的 Web 应用。生产架构通常包括反向代理或 Ingress、NetBox Web 应用、后台 Worker、PostgreSQL 和 Redis 或 Valkey。Web 应用处理 UI 和 API 请求；PostgreSQL 保存权威业务数据；Redis/Valkey 负责缓存和异步任务队列；Worker 执行 Webhook、脚本或后台任务。

在容器或 Kubernetes 环境中，Web 和 Worker 可作为不同工作负载运行，数据库和键值服务可以外置。附件、脚本和报表必须使用持久卷或对象存储，不能依赖容器本地文件系统。

**高频追问：** 为什么数据库比 Redis 更重要？PostgreSQL 包含权威业务数据；Redis/Valkey 的缓存和队列通常不作为迁移或灾备恢复的主要数据源，恢复时需要避免遗留任务重复执行。

## 5. NetBox 为什么不等于 NMS、CMDB 或配置管理工具？

**参考回答：** NMS 主要采集运行状态、性能和告警；CMDB 关注更宽泛的业务服务、资产、关系和流程；配置管理工具负责生成、审核或下发设备配置。NetBox 重点是网络资源的意图与事实建模，特别适合成为这些系统共享的网络数据源。

例如，NetBox 可以保存交换机、接口、管理 IP 和线路关系；监控平台从 NetBox 获取设备清单；Ansible 根据 NetBox 的接口和 IP 数据生成配置；CMDB 通过 API 关联业务服务。但是设备是否在线、端口流量是否异常，仍应由 NMS 或遥测系统负责。

## 6. 怎样评估一个 NetBox 实施是否成功？

**参考回答：** 成功不应只看录入对象数量，而要看数据是否真的驱动运营。可定义的指标包括：已纳管站点、设备和地址的覆盖率；关键字段完整率；IP 冲突率；无主设备或无归属前缀比例；自动化任务成功率；从 NetBox 生成配置或清单的覆盖率；审计发现与修正周期；人工查询和变更耗时。

还要有质量控制：对象所有者、必填字段、自定义校验、周期盘点、变更日志审计，以及自动化与实际设备状态的比对。高质量的少量数据比大量不可信数据更有价值。

## 二、组织、DCIM 与物理层建模

## 7. Region、Site、Location 和 Rack 分别是什么？如何建模？

**参考回答：** 它们描述不同层级的物理组织：

- **Region：** 地理或运营管理层级，例如“华东”“上海”。Region 可以有层级。
- **Site：** 实际站点或机房园区，例如“上海数据中心 A”。设备、机柜、前缀和 VLAN 等常关联到 Site。
- **Location：** 站点内部的细分位置，例如楼栋、楼层、机房、机柜区或配线区。
- **Rack：** 放置设备的实体机柜，通常记录高度、宽度、类型、角色、位置和租户等。

推荐从稳定的业务边界开始：Region 用于行政或地理层级，Site 表示可独立运营的物理站点，Location 用于站点内部导航，Rack 用于真实机柜。不要把不同抽象层级混用，例如把每个机柜都创建成 Site，会增加查询和权限复杂度。

## 8. 什么是 Tenant？它和 Site、设备、前缀有什么关系？

**参考回答：** Tenant 表示资源归属方，可以是客户、业务部门、子公司、项目、环境租户或托管对象。Tenant 不等于 Site：一个租户可以跨多个站点，一个站点也可托管多个租户。

Tenant 可以关联设备、机柜、前缀、IP、VLAN、电路、虚拟机等对象。这样可以按归属进行查询、授权、计费辅助和资源审计。例如托管网络中，可以为客户 A 的设备、网段和电路打上 Tenant A，再通过对象权限限制客户 A 只查看自己的对象。

**易错点：** Tenant 不是安全边界的替代品。多租户隔离仍应依赖用户组、对象权限和必要的 API 权限设计。

## 9. Manufacturer、Device Type、Device Role、Platform 各自有什么作用？

**参考回答：** 这四个对象分别回答“谁生产”“硬件是什么”“业务中做什么”“运行什么系统”：

- **Manufacturer：** 厂商，例如 Cisco、Juniper、HPE。
- **Device Type：** 具体硬件型号及其物理规格，例如高度、前后深度、接口模板、模块槽位和电源位。
- **Device Role：** 在网络中承担的角色，例如核心交换机、接入交换机、边界路由器、防火墙或控制器。
- **Platform：** 操作系统或网络平台，例如 IOS-XE、Junos、EOS，可用于配置渲染、自动化选择和设备分类。

正确拆分可以避免重复建模。同一型号设备可有多个角色，同一角色可使用多个型号，同一平台可运行在多个型号上。

## 10. 设备类型模板为什么重要？

**参考回答：** Device Type 中可以预定义接口、前后端端口、控制台端口、电源端口、模块槽位和设备高度等。创建实际 Device 时，NetBox 可以根据模板生成标准化组件，从而减少手工漏建和接口命名不一致。

例如某交换机型号有 48 个千兆电口和 4 个上联口，应该在 Device Type 中定义统一模板。新建设备时所有接口按标准出现，自动化系统可依赖一致的接口名称。对模块化设备，还要模型化模块类型和模块槽位，避免把所有插槽抽象为随意命名的接口。

**高频追问：** 模板变更会自动修改已有设备吗？一般不应假设会自动回填。应评估已有实例，使用受控脚本或批量变更补齐，避免直接修改模板后产生数据不一致。

## 11. Device 和 Virtual Machine 有什么区别？

**参考回答：** Device 用于表示物理设备，例如交换机、路由器、防火墙、服务器和 PDU；Virtual Machine 用于表示运行在虚拟化集群中的虚拟机。两者都有接口和 IP 等概念，但归属和生命周期不同：物理设备通常放在 Site、Rack 和 Location 中，虚拟机通常关联 Cluster 和虚拟化平台。

服务器可以在 NetBox 中既有物理 Device，也有该服务器承载的 Virtual Machine；不能因为虚拟机存在就忽略宿主机、集群或管理网络的建模。实际使用时，应根据组织边界明确 NetBox 记录到哪一层，避免重复维护。

## 12. 什么是 Interface？接口类型、速度和状态如何维护？

**参考回答：** Interface 是设备上的网络接口，可以表示物理端口、虚拟接口、LAG、SVI、子接口、管理接口或其他逻辑接口。接口通常需要记录名称、类型、启用状态、描述、MAC 地址、MTU、速率、父子关系、LAG 成员关系、桥接关系和 VLAN 配置等。

接口类型必须尽量反映硬件能力，例如千兆、10G、25G、100G 或虚拟接口类型。端口是否 administratively enabled 属于设计意图或当前配置快照的一部分，不应凭猜测维护。大规模环境应通过设备类型模板、同步工具或受控脚本保持接口命名与状态一致。

## 13. Cable、Front Port 和 Rear Port 有什么区别？

**参考回答：** Cable 表示两个可端接对象之间的物理连线。常见端接对象包括设备接口、控制台端口、电源端口、前端端口和后端端口。Cable 记录线缆类型、颜色、长度、标签和两端端点。

Front Port 和 Rear Port 用于建模配线架等被动组件。Front Port 表示用户或跳线可见的一面，Rear Port 表示设备侧或干线侧的一面；一个 Rear Port 可以映射到一个或多个 Front Port。这能使 NetBox 从设备端口追踪经过配线架的完整链路，而不是只记录一条没有中间层的抽象连接。

**易错点：** Cable 不等于三层邻居关系。Cable 描述物理连接；协议邻居、逻辑互联和路由关系需要在相关模型或外部系统中表达。

## 14. 什么是 Cable Path？它对运维有什么价值？

**参考回答：** Cable Path 是 NetBox 根据电缆、前后端端口和传递关系推导出的端到端物理路径。例如，从交换机接口出发，经过跳线、配线架前端端口、后端端口和干线，最终到服务器网卡。

它的价值在于变更影响分析和故障定位。维护人员可以在断链或扩容前查看一条端口路径涉及哪些机柜、面板和端点；数据中心团队也能减少“机柜标签有但真实跳线关系缺失”的情况。要使 Cable Path 可靠，组件和端接关系必须完整录入。

## 15. 如何在 NetBox 中记录 LAG、VLAN 和 Trunk/Access 关系？

**参考回答：** LAG 可作为逻辑接口创建，再把成员物理接口关联到该 LAG。这样可以明确聚合组、成员端口和逻辑接口上的 IP 或 VLAN 归属。VLAN 应先在 IPAM 中建立 VLAN Group 和 VLAN，再在接口上以 Access、Tagged 或其他合适模式关联。

Access 接口一般关联一个未打标签 VLAN；Trunk 接口一般通过 Tagged VLAN 列表或约定的全部 VLAN 标记来表示。不同设备平台的配置语法不同，NetBox 中应保持抽象模型一致，并在自动化模板中转换为平台命令。

**易错点：** 不要只把 VLAN 编号写进接口描述。应创建规范 VLAN 对象并建立关系，才能进行冲突检查、范围查询和自动化。

## 三、IPAM、路由与地址规划

## 16. IPAM 的核心对象有哪些？它们之间如何关联？

**参考回答：** IPAM 的主要对象包括 RIR、ASN、聚合网段、VRF、路由目标、VLAN、前缀、地址范围和 IP 地址。常见关系是：聚合网段描述组织持有的大块地址空间；前缀是可分配或已分配的子网；IP 地址属于某个前缀或地址范围，并可以分配给设备或虚拟机接口；VRF 用来隔离地址空间；VLAN 表示二层广播域，并可关联到站点、组和前缀。

完整建模需要从业务意图出发。例如，某租户在北京站点有一个 VRF，VRF 中分配一个 `/24` 前缀，其中地址分配给接入网关、服务器和设备管理接口；二层 VLAN 与这个前缀对应或具有关联关系。

## 17. Prefix、IP Range 和 IP Address 有什么区别？

**参考回答：** Prefix 是 CIDR 网络块，例如 `10.10.20.0/24`，用于表示可路由或可分配的子网。IP Range 是一个连续地址区间，例如 `10.10.20.100-10.10.20.150`，常用于 DHCP 地址池、预留范围或不按子网表达的连续分配范围。IP Address 是一个具体 IPv4 或 IPv6 地址，例如 `10.10.20.10/24`。

Prefix 用于地址层级规划和利用率计算；IP Range 用于表达可分配连续区间；IP Address 用于记录实际分配。地址记录里保留前缀长度很重要，因为它提供子网掩码语义，不能仅记录裸地址字符串。

## 18. 什么是 VRF？什么时候需要使用 VRF？

**参考回答：** VRF 是独立的三层路由和地址空间。不同 VRF 可以使用相同的 RFC1918 地址而不冲突，例如多个客户、生产与测试环境、不同业务域或多租户网络。

在 NetBox 中，VRF 应关联到前缀、IP 地址、路由目标和相关租户或站点。使用 VRF 时，查询和自动化必须带上 VRF 上下文：`10.0.0.1` 在 VRF A 和 VRF B 中可能是不同对象。是否允许全局地址空间唯一、如何命名 VRF、何时创建 VRF，都应由组织地址治理规范决定。

**高频追问：** 所有网络都需要 VRF 吗？不需要。没有重叠地址、多租户隔离或独立路由域需求时，简单的全局地址空间更易维护。不要为了“看起来专业”而无依据地创建大量 VRF。

## 19. 如何防止 IP 地址冲突和地址数据漂移？

**参考回答：** 首先在 NetBox 中定义唯一性策略，例如是否强制全局唯一、哪些重叠地址必须在 VRF 内隔离。分配地址时通过 UI、API 或自动化流程从 NetBox 查询可用地址并立即创建分配记录，而不是先从 Excel 取地址、之后再补录。

其次要把变化纳入流程：DHCP、云平台、虚拟化平台、设备配置和 DNS 的地址变化，应通过 API 同步或定期比对。可以使用自定义校验确保状态、租户、角色、DNS 名称或关联接口满足规则，并通过审计报告找出“已分配但没有接口”“接口有地址但状态不一致”等异常。

## 20. Aggregates 和 Prefixes 的区别是什么？

**参考回答：** Aggregate 表示组织从 RIR、运营商或上级地址池获得的大块地址空间，例如公网地址段或企业总地址块。Prefix 表示在某个地址空间内规划和分配的具体网络段，例如从一个 `/16` Aggregate 划分出的多个站点 `/24`。

Aggregate 有助于表达地址资源的来源和总体边界，Prefix 支持更细的层级分配、父子关系、利用率和站点或租户归属。不要把所有子网都直接建成 Aggregate，否则会失去地址规划层级。

## 21. VLAN 和 VLAN Group 的作用是什么？

**参考回答：** VLAN 表示二层分段，至少包含 VLAN ID、名称、状态和作用范围。VLAN Group 用于给 VLAN ID 定义作用域或编号空间，例如每个站点、每个租户、每个交换域可以有独立 VLAN Group，因此不同 Group 中可使用相同 VLAN ID。

VLAN 还可以关联站点、租户、前缀和接口。合理使用 VLAN Group 可避免把所有 VLAN 放在一个全局编号空间，同时让自动化明确“VLAN 100 在哪个站点或网络域中”的语义。

## 22. 什么是 ASN 和 Route Target？

**参考回答：** ASN 是自治系统号，用于 BGP 标识路由域或网络实体，可以是公有或私有 ASN。Route Target 常用于 MPLS L3VPN/EVPN 等场景，通过导入和导出策略控制 VRF 之间的路由泄露与路由分发。

在 NetBox 中维护 ASN、VRF 和 Route Target 的关系，有助于自动化生成 BGP、VRF 或 VPN 配置，并能审计某个租户或站点使用的路由标识。基础面试中，重点说明它们是控制平面和租户隔离建模的一部分，不要把 Route Target 与普通 VLAN 或 IP 前缀混为一谈。

## 23. FHRP Group 在 NetBox 中的用途是什么？

**参考回答：** FHRP Group 用于记录 VRRP、HSRP 等第一跳冗余协议的逻辑网关组。它可以把一个虚拟网关 IP、协议、组号和成员设备接口关联起来，使团队知道“某个默认网关地址”不是单台设备的普通接口地址，而是冗余组提供的服务地址。

这对故障处理和自动化很重要：当网关切换时，业务 VIP 不变，但活跃设备可能变化。正确建模可以避免把 VIP 错分配给某台设备，同时让配置生成器知道需要在哪些设备上渲染 FHRP 配置。

## 四、数据治理、扩展与配置建模

## 24. Tag、自定义字段和自定义校验分别该在什么时候使用？

**参考回答：** 三者解决的问题不同：

- **Tag：** 用于灵活分类和筛选，例如“待盘点”“核心业务”“自动化管理”。适合多值、跨对象、变化快的标签。
- **自定义字段：** 用于补充稳定、结构化且需要在对象上长期维护的业务属性，例如资产编号、维护窗口、机房门禁编号或合规等级。
- **自定义校验：** 用 Python 定义数据规则，例如生产设备必须设置租户和监控级别，某类端口名称必须符合命名格式。

应避免把所有事情放进 Tag 或描述字段。需要筛选、导出、自动化使用和治理的关键数据，应使用合适的结构化字段，并配合校验和权限。

## 25. 什么是 Configuration Context？它和设备配置文件有什么区别？

**参考回答：** Configuration Context 是可按区域、站点、位置、租户、设备角色、设备平台、设备类型或单个设备等范围匹配的结构化 JSON/YAML 数据。NetBox 会将符合条件的上下文数据合并，供配置渲染、脚本或 API 使用。

它不是运行设备上的完整配置备份。它更像可复用的意图或变量层，例如 NTP 服务器、DNS、SNMP、BGP 模板参数、站点 VLAN 范围或管理域名。最终设备配置通常由 Jinja2 模板、自动化平台或配置渲染功能生成。

**易错点：** 不应把密码、私钥或完整运行配置明文塞进 Context Data。敏感数据应来自专用密钥管理系统。

## 26. 什么是 Config Template 和 Config Rendering？

**参考回答：** Config Template 通常是使用 Jinja2 的模板，Configuration Context、设备对象、接口、IP、前缀和自定义字段等提供变量。Config Rendering 根据模板和上下文生成某台设备的候选配置或片段。

这使网络配置具备可重复性：地址、接口和邻居信息从 NetBox 读取，不再由工程师手工复制到多份模板。高质量实现还应有模板版本控制、CI 渲染测试、语法检查、同行评审、差异审查和受控下发。NetBox 可生成意图配置，但不等于已经安全下发到设备。

## 27. 什么是 Custom Script？使用时有哪些风险？

**参考回答：** Custom Script 是在 NetBox 中运行的 Python 脚本，适合执行批量建模、数据校验、对象同步或受控运维任务。它能利用 NetBox ORM、表单参数和事务机制，使重复操作标准化。

风险在于 Script 能批量修改权威数据，甚至可与外部系统交互。因此应使用代码仓库、代码审查、最小权限、输入校验、dry-run 或审批流程、日志、幂等设计、超时控制和测试环境验证。对有外部副作用的脚本，例如创建设备、写 DNS 或触发网络变更，应区分“计划”“执行”“验证”三个步骤。

## 28. Plugin、Custom Script 和外部自动化工具如何选择？

**参考回答：** Custom Script 适合部署内的、明确且受控的批量任务；Plugin 适合需要新增数据模型、UI、API、菜单或深度业务逻辑的长期能力，但升级和兼容性成本更高；外部自动化工具，如 Ansible、Terraform、Python 服务或 CI/CD，适合配置下发、跨系统编排和持续同步。

选择原则是最小复杂度：一次性或小范围数据治理优先脚本；需要长期扩展 NetBox 领域模型时考虑 Plugin；需要调用大量外部系统或进行异步编排时使用外部自动化。无论采用哪种方式，NetBox 中的数据契约、权限和审计必须清晰。

## 五、权限、审计与安全

## 29. NetBox 的权限模型如何工作？

**参考回答：** NetBox 基于 Django 的用户和用户组，并通过对象权限（Object Permissions）控制谁可以查看、添加、修改或删除某类对象。权限可以按对象类型、动作和约束条件定义，并分配给用户或组。

设计时应采用最小权限。例如，机房团队可维护机柜和电缆，网络团队可维护 IPAM 和设备接口，自动化服务账户只能读取或修改它负责的特定对象范围。超级管理员只用于受控管理任务，不应用作日常 API 或批处理账号。

**高频追问：** 如何实现按租户隔离？可以基于 Tenant、Site、Tag 等对象属性设计权限约束和用户组，但必须实际测试 UI 和 API 的读写行为，不能假设菜单隐藏就代表数据不可访问。

## 30. API Token 应如何管理？

**参考回答：** API Token 应对应明确的用户或服务账户，并按最小权限原则授权。不同自动化系统、环境和用途应使用不同 Token，避免共享管理员 Token。Token 应存放在密钥管理系统、CI/CD Secret 或 Kubernetes Secret 中，不能写入代码、Git、日志、工单截图或聊天记录。

治理措施包括设置失效或轮换策略、记录所有者和用途、限制服务账户权限、在离职或系统下线时撤销 Token、监控异常 API 调用，并在 Token 泄露时立即撤销和重新签发。对 API 读取与修改操作，也应通过变更日志和外部审计日志建立可追溯性。

## 31. NetBox 如何记录变更？变更日志有什么用？

**参考回答：** NetBox 会记录对象的创建、修改和删除等变更信息，通常包含时间、操作用户、对象类型、对象标识、变更前后数据和请求上下文。变更日志有助于排障、审计、回溯数据漂移和确认自动化行为。

例如，发现一个生产前缀的网关地址被改动后，可以先查询该 IP 或关联对象的变更记录，确认修改人、时间、来源和字段差异，再决定是否回滚。变更日志不是完整备份，也不能代替数据库备份；它是审计和定位工具。

## 32. 如何保护 NetBox 的生产安全？

**参考回答：** 从多个层面回答：

- **网络：** 使用 HTTPS，限制管理入口，数据库和 Redis/Valkey 不对公网开放，必要时配置 NetworkPolicy 或防火墙。
- **身份：** 使用强密码、MFA 或企业 SSO/LDAP/OIDC，禁用不必要的本地管理员，按组授予最小权限。
- **密钥：** 将 `SECRET_KEY`、API Token Pepper、数据库密码、SMTP/LDAP 凭据放进密钥系统；保持备份且避免泄露。
- **应用：** 禁用生产 Debug，设置正确的 `ALLOWED_HOSTS`、CSRF 信任来源和 CORS，审查插件与脚本。
- **运维：** 固定镜像与 Chart 版本、及时修复漏洞、记录变更、备份并进行恢复演练。

回答不能只说“加密码”。NetBox 保存的网络拓扑、地址和资产信息本身敏感，读权限同样需要严格控制。

## 六、API、自动化与集成

## 33. NetBox REST API 如何使用？

**参考回答：** NetBox 提供 REST API，通常在 `/api/` 路径下按应用和对象类型组织，例如 DCIM、IPAM、Tenancy 和 Virtualization。客户端使用 Token 认证，以 JSON 表示对象，可进行筛选、分页、创建、更新和删除。

基本调用示例：

```bash
export NETBOX_URL="https://netbox.example.com"
export NETBOX_TOKEN="<存放在密钥系统中的 Token>"

curl -sS \
  -H "Authorization: Token $NETBOX_TOKEN" \
  -H "Accept: application/json" \
  "$NETBOX_URL/api/dcim/devices/?site=beijing-dc-01&status=active"
```

生产自动化应处理分页、超时、重试、HTTP 状态码、幂等性和并发冲突。创建对象前用唯一字段查询是否已存在，更新时限定允许修改的字段，并记录变更来源。不要将 Token 放在命令历史或日志中。

## 34. REST API 和 GraphQL API 如何选择？

**参考回答：** REST API 资源模型清晰，适合标准的 CRUD、过滤、批量工作流和多数自动化工具集成。GraphQL API 允许客户端一次请求指定对象及其关联字段，适合复杂读取、减少多次 REST 调用和构建报表或门户。

一般建议：写操作、通用集成和明确对象生命周期优先 REST；需要跨多层关系的复杂只读查询时考虑 GraphQL。无论使用哪种 API，都要控制字段范围、分页、权限、查询复杂度和 Token 安全。

## 35. Webhook 和 Event Rule 的关系是什么？

**参考回答：** Event Rule 定义“什么对象在发生什么事件时要触发动作”，例如设备创建、IP 修改或电路状态变更。Webhook 是其中一种动作类型，它向外部 HTTP 服务发送事件数据，使 NetBox 可以通知 CMDB、工单、监控、DNS 或自动化平台。

安全设计包括：使用 HTTPS、签名或共享密钥、最小化事件范围、幂等接收端、超时和重试策略、失败监控，以及测试环境隔离。接收端必须假设事件可能重复、乱序或延迟，不能简单把“收到一次 Webhook”当作绝对一致的状态证明。

## 36. 如何把 NetBox 与 Ansible、Terraform 或 Nornir 集成？

**参考回答：** NetBox 通常是资源与意图数据源，自动化工具通过 API 或官方/社区 Inventory 插件查询站点、设备、角色、平台、接口、IP、标签和配置上下文。Ansible 可把 NetBox 作为动态 Inventory；Terraform 可以用数据源读取已分配资源或用 provider 管理部分 NetBox 对象；Nornir 或 Python 程序可根据查询结果选择设备并执行校验或配置生成。

关键不在于“能调 API”，而在于建立数据契约：哪些字段必填、谁负责更新、设备名称和接口命名如何规范、何时允许自动化写回 NetBox、失败如何处理。自动化应先在只读或 dry-run 模式验证，再进行受控写入和配置下发。

## 七、部署、备份、迁移与排错

## 37. NetBox 常见部署方式有哪些？生产环境怎样选择？

**参考回答：** 常见方式有原生部署、官方 `netbox-docker` Docker Compose 部署和官方 `netbox-chart` Helm Chart 的 Kubernetes 部署。原生部署控制细节最多，但需要自行管理 Python、Gunicorn、Worker、PostgreSQL、Redis 和反向代理；Docker Compose 简化单机或小规模部署；Kubernetes Helm Chart 适合已有成熟集群、GitOps、Ingress、外部数据库、对象存储和可观测性能力的团队。

选择依据是团队运维成熟度、可用性目标、数据库托管能力、存储能力、升级流程和监控体系。不要因为业务系统使用 Kubernetes 就强行把 NetBox 放到 Kubernetes；同样也不要在需要高可用和自动化治理时只依赖一台没有备份的单机 Docker 主机。

## 38. 为什么 NetBox 需要 PostgreSQL、Redis/Valkey 和 Worker？

**参考回答：** PostgreSQL 存储权威的结构化业务数据，包括设备、IP、用户、权限和变更日志。Redis/Valkey 提供缓存和任务队列。Worker 从任务队列中执行异步工作，例如 Webhook、脚本或后台 Job，避免 Web 请求长时间阻塞。

因此遇到“页面可打开但 Webhook 不执行”时，不能只检查 Web Pod 或容器，还必须检查 Worker、Redis/Valkey 连接、队列积压、凭据、网络和 Worker 日志。数据库备份是灾备核心，而缓存和队列一般不直接恢复，以免过期任务在恢复后再次执行。

## 39. NetBox 备份应包含哪些内容？

**参考回答：** 完整备份至少包括：

1. **PostgreSQL 数据库：** 包含所有权威业务对象、用户、权限和变更记录。
2. **Media 附件：** 用户上传的图片和文件。
3. **Scripts 与 Reports：** 自定义代码及相关依赖。
4. **应用配置：** 域名、认证、邮件、插件、存储和集成配置。
5. **关键 Secret：** 特别是 `SECRET_KEY` 和 API Token Pepper；缺失后现有会话或 Token 可能受影响。
6. **部署声明：** Docker Compose 文件、Helm values、Chart/镜像版本和反向代理配置。

备份必须异地保存、加密、设置保留策略，并在隔离环境定期恢复演练。只有“备份成功”日志不等于能恢复，恢复验证才是最终证据。

## 40. 如何将 NetBox 迁移到新服务器或 Kubernetes？

**参考回答：** 原则是先完成**同版本迁移**，再单独升级。具体步骤是：盘点源端版本、数据库、附件、脚本、报表、配置、插件和 Secret；在目标端部署相同 NetBox 版本；在测试环境演练数据库与文件恢复；正式窗口冻结源端写入、Worker、Webhook 和自动化；生成最终逻辑数据库备份并复制持久化文件；在目标端恢复、比较对象计数和执行业务验收；最后切换 DNS 或负载均衡。

回滚关键在于保持源端处于可恢复但停止写入的状态。不能同时进行迁移、大版本升级、PostgreSQL 主版本更换和插件变更，否则问题难以定位。详细步骤可参考本仓库的 [NetBox/netbox-迁移指南.md](netbox-迁移指南.md)。

## 41. NetBox 升级前后要检查什么？

**参考回答：** 升级前要阅读当前版本到目标版本之间的所有发布说明，特别是破坏性变更、数据库迁移、依赖最低版本、配置弃用和插件兼容性。先备份数据库、附件、脚本、配置和 Secret，并在测试环境用生产数据副本演练。

升级后检查 Web 与 Worker 健康、数据库迁移日志、`manage.py check`、登录、API、关键对象查询、附件、插件、Webhook 和自动化任务。跨大版本升级应遵循官方升级路径，必要时先升级到当前大版本的最后一个小版本再跨大版本。Helm 或容器版本回退并不能自动逆转数据库 schema 迁移，真正回滚依赖升级前备份。

## 42. 页面出现 `DisallowedHost`、CSRF 错误或 400 时如何排查？

**参考回答：** 这类问题多与反向代理、域名和 Django 安全设置有关。首先确认用户实际访问的协议和域名，然后检查：

- `ALLOWED_HOSTS` 是否包含实际 FQDN。
- `CSRF_TRUSTED_ORIGINS` 是否包含带协议的完整地址，例如 `https://netbox.example.com`。
- Nginx、Ingress 或负载均衡是否正确传递 `Host` 和 `X-Forwarded-Proto`。
- HTTP 到 HTTPS 重定向是否导致域名或协议不一致。
- Kubernetes Ingress、Service 和应用配置是否指向同一个生产域名。

修改后重新部署或重启相应工作负载，并用浏览器和 `curl -I` 验证。不要通过把 `ALLOWED_HOSTS` 永久设置为 `*` 或关闭 CSRF 保护来规避问题。

## 43. Web 正常但后台任务、Webhook 或脚本不执行，如何处理？

**参考回答：** 按链路排查：先确认 Worker 是否运行且健康；再检查 Worker 日志、Redis/Valkey 连接和认证、任务队列状态、数据库连接、Webhook 是否启用、网络出口、DNS/TLS 和接收端响应。确认触发事件确实匹配 Event Rule，并检查任务是否因权限、超时、异常或重试策略失败。

处理时先避免重复触发有副作用的任务。可以在测试对象上验证一个最小 Webhook，再逐步扩大范围。对于 Kubernetes，分别检查 Web Deployment、Worker Deployment、Secret 注入、NetworkPolicy 和 Pod 事件；对于 Docker Compose，分别检查 `netbox`、`netbox-worker` 和 Redis/Valkey 容器。

## 44. 如何处理 NetBox 中的数据质量问题？

**参考回答：** 数据质量治理应先分类问题：缺失、重复、错误、过期、关系断裂和命名不一致。然后定义权威来源和修复优先级。例如，生产设备缺少站点或角色、已分配 IP 没有关联接口、物理电缆只有一端、前缀没有租户或状态，都属于可量化的质量问题。

治理手段包括字段标准、设备类型模板、批量导入规则、自定义字段、自定义校验、Tag、API 巡检脚本、定期盘点、变更审批和责任分配。修复大批量数据前应先导出、备份、在测试环境演练，并记录可回滚的变更范围。不要用删除对象快速“清理”问题，因为可能破坏 IP、接口、电缆和变更历史关系。

## 八、场景题与面试总结

## 45. 面试官要求“从零开始用 NetBox 管理一个新数据中心”，你如何回答？

**参考回答：** 我会分阶段实施，而不是一次性录入全部信息：

1. **调研与规范：** 定义站点层级、租户、设备命名、接口命名、地址规划、VLAN/VRF 作用域、状态、数据责任人与变更流程。
2. **基础模型：** 创建 Region、Site、Location、Rack、厂商、设备类型、设备角色、平台、租户和联系人。
3. **IPAM 先行：** 导入 Aggregate、VRF、VLAN、Prefix 和 IP 规划，避免设备上架后地址信息仍在表格中。
4. **DCIM 落地：** 建立机柜、设备、接口、管理 IP、电缆和供电关系；优先覆盖核心链路和高风险设备。
5. **集成自动化：** 将 NetBox 接入 Ansible、监控、DNS、CMDB 或配置渲染，并先用只读同步验证数据质量。
6. **治理运营：** 用权限、审核、变更日志、定期校验、备份恢复演练和质量指标维持可信度。

关键是把“数据录入项目”变成“持续运营的数据产品”。

## 46. 面试时如何展示自己对 NetBox 的真实经验？

**参考回答：** 最有说服力的是一个完整案例：说明网络规模与痛点，例如 IP 分配依赖 Excel、设备接口命名混乱、自动化库存不可信；解释你如何设计 Site、Tenant、VRF、VLAN、Prefix、Device Type 和接口模板；展示如何通过 API、Ansible 或脚本接入自动化；最后给出结果，例如地址冲突下降、变更可追溯、设备上线更快、自动化失败率下降或盘点时间缩短。

还应主动说出限制与改进：哪些数据仍需人工维护、哪些系统还没有打通、如何避免双写、如何处理历史脏数据、如何验证备份恢复。这比只说“我会使用 NetBox API”更能体现工程判断力。

## 面试前自查清单

- [ ] 能用一句话说明 NetBox、IPAM、DCIM 和 Source of Truth 的区别与关系。
- [ ] 能讲清 Site、Location、Rack、Tenant、Device Type、Device Role、Platform 的建模边界。
- [ ] 能解释 Prefix、IP Range、IP、VLAN、VRF、Aggregate、ASN 和 Route Target。
- [ ] 能区分物理 Cable、Cable Path、接口、LAG 与三层邻居关系。
- [ ] 能说明 Tag、自定义字段、自定义校验、Configuration Context、Script 和 Plugin 的使用边界。
- [ ] 能说明用户组、对象权限、API Token、变更日志和最小权限原则。
- [ ] 能描述 REST API、GraphQL、Webhook、Event Rule 与 Ansible/Terraform/Nornir 集成方式。
- [ ] 能说明 PostgreSQL、Redis/Valkey、Worker、附件存储、备份恢复与升级风险。
- [ ] 能回答从单机迁移、Kubernetes 部署、DNS/HTTPS 和常见反向代理错误的排查思路。
- [ ] 已准备至少一个真实项目案例，包含问题、行动、证据、结果与复盘。
