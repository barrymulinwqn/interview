## 一、面试考察重点

### 1. 初级开发工程师

- 是否理解组件、模板、指令、管道、服务和依赖注入的职责。
- 是否能够使用 Angular CLI 创建页面、配置路由、调用 HTTP API 和处理表单。
- 是否知道 Observable 的基本生命周期，能避免订阅泄漏。
- 是否能写出可读、可测试、符合 Angular 约定的代码。

### 2. 中高级开发工程师

- 能否解释变更检测、Zone、Signals、RxJS 和模板更新之间的关系。
- 能否按业务边界组织 feature、data-access、UI 和 shared 代码。
- 能否处理加载、空数据、错误、重试、取消、权限和离线等非正常路径。
- 能否通过指标、Profile、Bundle 分析和真实压测证明优化有效。

### 3. 架构师或技术负责人

- 能否设计可演进的前端架构，而不是只讨论目录结构。
- 能否处理多团队协作、依赖治理、版本升级、设计系统和发布策略。
- 能否在 SPA、SSR、预渲染、微前端、模块化单体之间做出有依据的选择。
- 能否把安全、可观测性、质量门禁和运维成本纳入设计。

### 4. 高分回答的通用框架

面对任何 Angular 架构题，可以依次说明：

1. **业务目标**：用户是谁，核心流程是什么，成功指标是什么。
2. **约束条件**：首屏性能、SEO、浏览器、流量、团队、交付周期和后端契约。
3. **方案边界**：组件如何拆分，状态由谁拥有，数据如何流动。
4. **失败路径**：超时、重复请求、权限变化、刷新、网络中断和服务端错误怎么处理。
5. **验证与演进**：如何测试、监控、灰度和回滚，未来需求变化时哪里需要调整。

## 二、Angular 基础题

### Q1：Angular 是什么？它与传统 jQuery 或轻量级库有什么区别？

**核心回答：** Angular 是一个以 TypeScript 为主、提供组件化 UI、依赖注入、路由、表单、HTTP、测试和构建工具链的完整前端框架。它不仅负责视图渲染，还约定了应用的组织方式和运行时边界。

Angular 与只提供视图层的库相比，优势是工程约束和能力完整，适合大型团队和长期维护的应用；代价是学习曲线、框架升级和运行时抽象更多。选型不能只看语法，应结合团队规模、应用生命周期、SEO、性能预算和现有生态。

### Q2：Angular 应用的基本组成是什么？

- **Component**：管理一块 UI 及其交互，包含类、模板和样式。
- **Template**：声明视图结构、数据绑定和事件绑定。
- **Directive**：复用 DOM 或行为，分为属性指令和结构性能力。
- **Pipe**：把输入值转换为模板展示值。
- **Service**：承载可复用的业务逻辑、数据访问或基础设施能力。
- **Dependency Injection**：负责创建和提供服务依赖。
- **Router**：根据 URL 映射组件、参数、守卫和数据加载。
- **Form**：管理输入值、校验状态和提交行为。

组件应保持聚焦。不要把所有 API 调用、缓存、权限、表单规则和模板逻辑堆到一个页面组件中。

### Q3：Standalone Component 与 NgModule 有什么区别？

Standalone 组件可以在自身的 `imports` 中声明模板所需的组件、指令、管道和模块，不必依赖声明它的 NgModule。新应用通常可以以 standalone API 组织，路由也可以通过 `loadComponent` 或 `loadChildren` 实现按路由懒加载。

NgModule 仍可能存在于旧项目、第三方库或特定兼容场景中。迁移时重点不是机械地删除所有模块，而是明确依赖边界、检查 provider 作用域、处理循环依赖并逐步迁移。

```ts
@Component({
  selector: 'app-user-list',
  standalone: true,
  imports: [CommonModule, UserCardComponent],
  template: '<app-user-card *ngFor="let user of users" [user]="user" />'
})
export class UserListComponent {
  users = [];
}
```

### Q4：Angular 生命周期有哪些？常用钩子如何选择？

常见顺序包括：`constructor`、`ngOnChanges`、`ngOnInit`、`ngDoCheck`、`ngAfterContentInit`、`ngAfterContentChecked`、`ngAfterViewInit`、`ngAfterViewChecked` 和 `ngOnDestroy`。不同 Angular 版本还可能提供基于渲染时机的函数式生命周期 API。

- `constructor`：只做依赖注入和轻量初始化，不依赖输入属性。
- `ngOnChanges`：响应 `@Input` 的引用变化，适合根据输入重新计算。
- `ngOnInit`：初始化依赖输入值的逻辑和数据加载。
- `ngAfterViewInit`：需要访问视图子节点时使用，但要谨慎处理同步修改导致的检查错误。
- `ngOnDestroy`：释放订阅、定时器、DOM 监听和第三方实例。
- `ngDoCheck`、`ngAfterViewChecked`：调用频率高，不应放置昂贵计算。

### Q5：什么是数据绑定？Angular 支持哪些绑定方式？

- 插值：`{{ title }}`，把表达式结果显示到文本中。
- 属性绑定：`[disabled]="isSaving"`，把值写入 DOM 属性或组件输入。
- 事件绑定：`(click)="save()"`，响应 DOM 或组件事件。
- 双向绑定：`[(ngModel)]="name"`，是属性绑定和事件绑定的组合。
- 输入输出：组件通过 `@Input` 接收数据，通过 `@Output` 发出事件；新版本也可使用对应的 signal-based API。

推荐让数据流尽量单向：父组件持有状态，子组件通过输入获得数据，通过事件表达用户意图。双向绑定适合简单表单，不宜成为复杂业务状态的默认通信方式。

### Q6：`@Input` 和 `@Output` 如何通信？什么时候需要共享服务？

父子组件之间优先使用输入和输出，因为依赖关系显式、测试简单。兄弟组件或跨越多层组件时，可以由共同父组件提升状态，或者使用按作用域提供的 facade/service。

共享服务适合多个组件确实共享同一业务状态或基础设施能力的场景。不要为了避免写一个事件就把所有状态放进全局 service，否则会隐藏依赖、增加调试成本并使组件生命周期难以推断。

### Q7：什么是纯管道和非纯管道？

纯管道默认只在输入值的引用或基本值发生变化时重新计算，适合无副作用、计算结果只由输入决定的转换。非纯管道会在更多变更检测周期执行，可能带来明显性能开销。

```ts
@Pipe({ name: 'fullName', pure: true })
export class FullNamePipe implements PipeTransform {
  transform(user: User): string {
    return `${user.firstName} ${user.lastName}`;
  }
}
```

不要在管道中进行 HTTP 请求、修改共享状态或依赖不可见的外部变量。过滤大列表时，优先在组件或 facade 中计算稳定结果，并配合 `trackBy` 或 `@for` 的稳定 key。

### Q8：结构性指令和属性指令有什么区别？

属性指令改变元素的属性、样式或行为；结构性指令改变模板结构，例如条件渲染和列表渲染。现代 Angular 的控制流语法提供了 `@if`、`@for`、`@switch` 等块语法，但其核心问题仍然是视图创建、销毁和更新。

```html
@if (user(); as currentUser) {
  <app-profile [user]="currentUser" />
} @else {
  <app-login />
}
```

### Q9：为什么不建议在模板中调用复杂方法？

模板表达式可能在变更检测中被多次求值。复杂方法可能导致重复计算、额外对象创建、网络副作用或结果不稳定，从而造成性能问题或检查错误。

更好的方式是使用稳定字段、computed signal、纯 pipe、选择器或 facade 预先计算结果。模板方法可以存在，但应保持轻量、无副作用且成本可证明。

### Q10：Angular 中如何处理错误？

错误处理要分层：

- 组件层：展示用户可理解的状态，并允许重试或恢复。
- 数据访问层：统一转换 HTTP 错误、超时和业务错误。
- 全局层：通过 `ErrorHandler`、日志服务和监控上报未知错误。
- 路由层：处理加载失败、权限失败和 resolver 错误。
- 交互层：防止重复提交，避免把堆栈信息直接展示给用户。

错误处理不应简单地在每个 `subscribe` 中复制一份 toast 逻辑。应区分可恢复错误、需要重新认证的错误、参数错误和系统故障，并定义统一的用户体验。

## 三、组件与模板

### Q11：组件应该如何拆分？

按职责和变化原因拆分，而不是按 HTML 标签数量拆分。一个常见边界是：

- **Page / Container**：负责路由参数、页面级状态和用户流程。
- **Feature**：负责一个业务用例，例如订单编辑或报表筛选。
- **Presentational UI**：通过输入和输出工作，不直接访问后端。
- **Data access / Facade**：封装查询、命令、缓存和状态组合。
- **Shared / Core**：放置真正跨业务复用的基础能力。

拆分后应能独立测试、独立理解，并且不会因为一个小字段变化而牵动大量无关组件。

### Q12：如何避免 `ExpressionChangedAfterItHasBeenCheckedError`？

这个错误通常说明一个绑定值在当前检查完成后又被同步修改，导致 Angular 发现视图前后结果不一致。常见原因包括在 `ngAfterViewInit` 中同步修改绑定值、模板 getter 每次返回不同结果、子组件反向修改父组件状态。

优先修正数据流和生命周期设计：把初始化提前到合适的阶段，使用输入变化或显式状态更新；不要用延时器掩盖问题。只有在明确理解渲染时机后，才考虑调度到下一次渲染或使用变更检测 API。

### Q13：如何设计可复用的表格组件？

先定义使用场景和稳定契约：列定义、行模型、排序、分页、筛选、选择、加载、空态、错误态和无障碍支持。

- 表格组件只负责展示和用户事件，不直接绑定某个业务 API。
- 通过泛型或明确的列配置保持类型安全。
- 大数据量使用虚拟滚动、服务端分页或服务端排序，不把所有数据一次性塞进 DOM。
- 选择状态应明确是页面状态还是跨页面状态。
- 输出事件应描述用户意图，例如 `sortChanged`、`pageChanged`，而不是暴露内部 DOM 细节。

### Q14：内容投影 `ng-content` 适合什么场景？

内容投影适合让容器组件控制布局，而调用方提供局部内容，例如卡片、对话框、布局壳和表单字段区域。它可以降低组件对具体内容的耦合，但过度使用会让数据流和调试边界变得不清晰。

如果需要动态创建、销毁或按条件控制组件实例，应考虑动态组件、模板引用或更明确的输入输出契约，而不是把所有逻辑塞进投影内容。

### Q15：`ViewChild` 和直接操作 DOM 有哪些风险？

`ViewChild` 可以访问子组件、指令或元素引用，但应优先调用组件或指令暴露的行为，而不是修改内部 DOM。直接使用 `nativeElement` 可能破坏 Angular 的渲染抽象，影响 SSR、Web Worker、测试和安全性。

必须操作 DOM 时，使用 `Renderer2` 或封装好的指令，并考虑生命周期、清理、焦点管理、浏览器兼容和服务端环境。

### Q16：Angular 表单有哪些类型？如何选择？

- **Template-driven forms**：模板中声明多，适合简单表单和快速开发。
- **Reactive forms**：表单模型在 TypeScript 中显式定义，适合复杂校验、动态字段和可测试业务。
- **Typed reactive forms**：通过类型信息减少控件值为 `any` 的风险，适合长期维护的业务系统。
- **Signal-based forms**：取决于项目采用的 Angular 版本和相关 API 的成熟度，不能不加验证地替换现有表单方案。

复杂表单应把校验规则、字段状态、异步校验和提交命令分开。提交时要处理禁用态、重复点击、服务端校验错误和离开页面确认。

### Q17：同步校验和异步校验有什么区别？

同步校验可以立即根据当前值返回错误；异步校验通常访问服务器或其他异步资源，返回 Observable 或 Promise。异步校验应设置取消和去抖策略，避免用户每输入一个字符就发出请求，并且要正确处理 `pending` 状态。

用户名是否已存在是典型异步校验，但最终提交时仍必须由后端再次校验，不能把前端校验当作安全边界。

### Q18：如何实现自定义表单控件？

实现 `ControlValueAccessor`，把 Angular 表单模型与内部 UI 控件连接起来：

- `writeValue`：外部模型更新时同步内部值。
- `registerOnChange`：内部值改变时通知表单。
- `registerOnTouched`：控件失去焦点时通知触摸状态。
- `setDisabledState`：同步禁用状态。

还要正确提供 `NG_VALUE_ACCESSOR`，处理初始值、空值、失焦、禁用、校验、键盘操作和无障碍属性。

## 四、依赖注入与模块化

### Q19：Angular 依赖注入解决了什么问题？

依赖注入把对象的创建和使用分离，使组件依赖接口或服务而不是自行实例化具体实现。这样便于替换实现、配置作用域、编写测试和管理生命周期。

```ts
@Injectable({ providedIn: 'root' })
export class UserApi {
  private readonly http = inject(HttpClient);
}
```

依赖注入不是全局变量的别名。服务的作用域、实例数量、缓存行为和模块边界必须设计清楚。

### Q20：`providedIn: 'root'`、组件级 provider 和 `providedIn: 'any'` 有什么区别？

- `providedIn: 'root'`：通常在应用根注入器中提供单例，且支持被构建工具移除未使用代码。
- 组件级 `providers`：在该组件注入器及其子树中创建实例，组件销毁时作用域结束。
- `providedIn: 'any'`：实例行为与注入器边界有关，适合特定懒加载隔离场景，但必须验证实际实例语义。

如果服务持有页面状态，组件级 provider 往往比根级单例更合适；如果服务是认证、配置或基础 HTTP 能力，根级作用域通常更自然。

### Q21：Angular 的注入器层级如何理解？

Angular 使用层级化注入器寻找依赖。组件请求服务时，通常会从当前节点的注入器向上查找，直到环境注入器或根注入器。懒加载路由、组件 provider 和环境 provider 都可能建立新的边界。

面试时应能解释一个服务为什么出现多个实例：可能是同一服务在组件 `providers`、路由 provider 和根 provider 中被重复提供。多个实例会影响缓存、事件总线和状态一致性。

### Q22：`useClass`、`useValue`、`useFactory`、`useExisting` 的区别是什么？

- `useClass`：用指定类创建实例。
- `useValue`：提供一个固定对象或值，适合配置和测试替身。
- `useFactory`：通过工厂函数按依赖和运行环境计算实例。
- `useExisting`：为已有 token 创建别名，不会创建第二个实例。

工厂 provider 适合根据环境配置选择实现，但要避免把大量业务分支塞进 DI 配置，导致启动逻辑难以测试。

### Q23：`InjectionToken` 解决什么问题？

当依赖不是一个具体类时，例如接口、配置对象、函数或多实现集合，可以用 `InjectionToken` 提供类型安全的注入标识。TypeScript 接口在运行时不存在，不能直接作为 DI token。

```ts
export const API_BASE_URL = new InjectionToken<string>('API_BASE_URL');

export const appConfig = {
  providers: [
    { provide: API_BASE_URL, useValue: '/api' }
  ]
};
```

### Q24：Interceptor 有哪些典型用途？

HTTP interceptor 适合横切逻辑，例如添加认证信息、关联请求 ID、统一处理错误、记录耗时和实现缓存策略。每个 interceptor 应保持单一职责，不能在其中偷偷修改业务请求语义。

认证 token 刷新要重点处理并发请求：多个请求同时收到 401 时，应避免无限递归和重复刷新，并让等待中的请求共享刷新结果。登出、刷新失败和原请求重试次数都要有明确规则。

### Q25：怎样组织大型 Angular 项目的目录？

推荐按业务 feature 组织，而不是把所有组件、服务和模型分别放在全局目录：

```text
src/app/
  core/
    auth/
    http/
    config/
  shared/
    ui/
    directives/
    pipes/
  features/
    orders/
      pages/
      ui/
      data-access/
      routes.ts
  app.routes.ts
```

`core` 放应用级基础能力，`shared` 放真正跨 feature 复用的无业务组件，`features` 保持业务内聚。目录只是结果，真正重要的是依赖方向：UI 不应反向依赖页面，shared 不应依赖具体 feature。

## 五、变更检测与 Signals

### Q26：Angular 变更检测是如何工作的？

Angular 会检查组件树中模板绑定的值，并在值可能变化时更新 DOM。传统模式通常借助 Zone.js 感知异步任务，再触发应用级检查；`OnPush` 会缩小组件被检查的条件。Signals 则提供了更精确的依赖追踪和更新通知机制。

不要把变更检测简单描述为“每次都刷新整个页面”。Angular 更新的是需要更新的视图绑定；性能问题通常来自检查范围过大、模板计算昂贵、对象引用频繁变化或列表 DOM 过多。

### Q27：`Default` 和 `OnPush` 策略有什么区别？

`Default` 策略下，组件更容易在应用级变更检测中被检查；`OnPush` 通常在以下情况下触发检查：

- 输入值的引用发生变化。
- 组件或子树中的事件触发。
- 模板读取的 signal 发生变化。
- 组件显式调用 `markForCheck` 或相关更新 API。
- 某些异步绑定机制通知视图更新。

使用 `OnPush` 后必须遵循不可变更新习惯：不要原地修改输入对象或数组后期待子组件自动发现。应创建新引用，或使用 signal、Observable 和明确的变更通知。

### Q28：为什么修改数组元素后视图可能不更新？

如果子组件使用 `OnPush`，下面的代码只修改了原数组引用：

```ts
this.items.push(newItem);
```

父组件传给子组件的引用没有变化，子组件可能不会按预期检查。更稳妥的方式是创建新引用：

```ts
this.items = [...this.items, newItem];
```

如果使用 signal，应通过 `set` 或 `update` 更新，并遵守 signal 中对象和数组的不可变约定。不可变更新也更有利于调试、缓存和时间旅行测试。

### Q29：什么是 Angular Signals？`signal`、`computed` 和 `effect` 如何选择？

- `signal`：可写的响应式状态容器。
- `computed`：由其他 signal 派生的只读值，适合纯计算。
- `effect`：响应 signal 变化执行副作用，例如日志、同步外部 API 或非 UI 集成。

```ts
count = signal(0);
doubleCount = computed(() => this.count() * 2);

increment(): void {
  this.count.update(value => value + 1);
}
```

不要用 `effect` 代替状态建模。一个 effect 再去写另一个 signal，容易产生循环、隐藏依赖和难以预测的执行顺序；派生状态优先使用 `computed`，业务命令应在明确的事件处理函数中执行。

### Q30：Signals 与 RxJS 如何选择？可以混用吗？

可以混用，但要明确边界：

- Signals 适合组件局部状态、同步派生状态和模板消费。
- RxJS 适合事件流、异步请求、取消、重试、节流、组合和长生命周期流。
- HTTP 返回 Observable 时，可在数据访问层保留 Observable，在组件边界使用适配工具转为 signal，或反向转换。

选择标准不是“新技术一定替代旧技术”，而是看数据是否是时间序列、是否需要流操作、是否需要取消和是否跨边界共享。迁移时不要同时改变状态模型、API 契约和组件结构，否则很难定位回归。

### Q31：什么时候使用 `ChangeDetectorRef`？

常用方法包括 `markForCheck`、`detectChanges`、`detach` 和 `reattach`。它们是低层控制手段，适合与第三方库、手动渲染、极高频数据或特殊性能场景集成。

优先修复状态流和组件边界，不要到处调用 `detectChanges()`。手动检测可能掩盖生命周期错误，还会让测试和后续维护更困难。

### Q32：`trackBy` 或 `@for track` 为什么重要？

列表刷新时，Angular 需要判断旧 DOM 节点和新数据之间的对应关系。稳定的 key 能让框架复用未变化的节点，避免输入焦点丢失、动画重置和大量 DOM 重建。

```html
@for (item of items(); track item.id) {
  <app-row [item]="item" />
}
```

key 必须稳定且唯一。不要使用可能变化的数组索引作为长期身份标识，尤其是在插入、删除、排序和分页场景中。

## 六、RxJS 与异步编程

### Q33：Observable 和 Promise 有什么区别？

Promise 通常表示一次异步结果，创建后就会开始执行；Observable 表示可订阅的数据流，支持零次、一次或多次值，并且通常在订阅时执行。Observable 还提供取消、组合、重试、节流和背压等流操作能力。

Angular 的 `HttpClient` Observable 通常是冷流，每次订阅可能发起一次请求。是否共享结果要显式设计，不能因为“Observable 可以多次订阅”就假设请求只发送一次。

### Q34：冷 Observable 和热 Observable 是什么？

- **冷 Observable**：每个订阅者拥有自己的执行过程，例如一次 HTTP 请求。
- **热 Observable**：数据源独立于订阅者，例如 DOM 事件、WebSocket 或共享 Subject。

`shareReplay` 可以共享一次执行结果，但要考虑缓存是否过期、错误是否缓存、引用计数和销毁时机。把所有 HTTP 请求都加 `shareReplay(1)` 可能造成陈旧数据或长期内存占用。

### Q35：`Subject`、`BehaviorSubject` 和 `ReplaySubject` 有什么区别？

- `Subject`：只向当前订阅者广播，不保存历史值。
- `BehaviorSubject`：需要初始值，并向新订阅者立即发送最新值。
- `ReplaySubject`：缓存指定数量或时间窗口内的历史值，再发送给新订阅者。

状态服务常见 `BehaviorSubject`，但 signal 或 facade 也可能更适合局部状态。`ReplaySubject` 的缓存边界必须明确，否则可能保留大量对象。

### Q36：`switchMap`、`mergeMap`、`concatMap` 和 `exhaustMap` 如何选择？

| 操作符 | 并发语义 | 典型场景 |
| --- | --- | --- |
| `switchMap` | 新流到来时取消旧流 | 搜索联想、路由参数查询 |
| `mergeMap` | 并行处理多个流 | 独立任务并发执行 |
| `concatMap` | 按顺序排队处理 | 有序写操作、队列任务 |
| `exhaustMap` | 处理期间忽略新流 | 防止重复提交、只接受一次点击 |

关键不是背定义，而是先回答：新请求来了，旧请求应该取消、并行、排队，还是忽略？

### Q37：如何避免订阅泄漏？

优先使用模板的 `async` pipe 或 Angular 提供的销毁绑定机制。手动订阅时，要绑定组件生命周期，或在 service 中明确管理订阅的所有权。

```ts
readonly users$ = this.userApi.getUsers();
```

```html
@if (users$ | async; as users) {
  <app-user-list [users]="users" />
}
```

还要注意不是所有泄漏都来自未取消订阅。无限增长的缓存、DOM 监听、WebSocket、定时器、第三方插件和闭包引用同样需要在生命周期结束时清理。

### Q38：`catchError` 应该放在哪里？

放置位置决定错误影响范围。放在内部高阶流中，通常只结束当前请求并让外层流继续；放在外层，可能导致整个交互流结束。

```ts
searchResults$ = this.searchTerm$.pipe(
  debounceTime(250),
  distinctUntilChanged(),
  switchMap(term => this.api.search(term).pipe(
    catchError(() => of([]))
  ))
);
```

错误恢复值必须符合业务语义。把所有错误都替换成空数组可能让用户误以为“没有数据”，因此应同时保留错误状态或给出可重试入口。

### Q39：`debounceTime` 和 `throttleTime` 的区别是什么？

`debounceTime` 在一段时间内没有新值后才发出最后一个值，适合搜索框输入；`throttleTime` 在时间窗口内限制发出频率，适合滚动、拖拽或高频事件。两者都只是降低处理频率，不等于取消后端已经发出的请求。

### Q40：如何设计一个搜索框的请求流？

应包含输入清洗、去重、去抖、旧请求取消、加载态、空结果、错误恢复和销毁处理：

```ts
readonly query = new FormControl('', { nonNullable: true });
readonly results$ = this.query.valueChanges.pipe(
  map(value => value.trim()),
  debounceTime(250),
  distinctUntilChanged(),
  filter(value => value.length >= 2),
  switchMap(value => this.searchApi.search(value).pipe(
    catchError(() => of([]))
  ))
);
```

如果后端不支持取消，前端即使取消了订阅也不能阻止服务端已接收的请求，因此写操作仍需幂等，服务端也要用请求 ID 或版本号处理乱序结果。

## 七、Angular 架构设计

### Q41：如何设计 Angular 大型应用的架构分层？

可以采用以下逻辑分层：

1. **展示层**：纯 UI 组件、布局、可访问性和交互事件。
2. **用例层**：页面流程、表单提交、加载态和用户意图编排。
3. **数据访问层**：HTTP、缓存、序列化、DTO 转换和错误映射。
4. **领域层**：业务规则、状态转换和与 UI 无关的模型。
5. **基础设施层**：认证、配置、日志、Feature Flag 和监控。

不要求每个 feature 都机械地建立五层，但依赖方向要清楚。UI 不应直接处理复杂 DTO 映射，组件也不应各自实现一套 token 刷新和缓存逻辑。

### Q42：Facade 模式在 Angular 中解决什么问题？

Facade 为页面或 feature 提供稳定的业务入口，隐藏多个 API、状态流和副作用的组合。例如页面只调用 `loadOrders()` 和 `approveOrder()`，不需要知道请求、缓存、刷新和错误映射细节。

Facade 不应变成“上帝服务”。如果一个 facade 同时管理十几个不相关业务流程，应继续按用例或子领域拆分。判断标准是调用者是否能通过它表达业务意图，且内部实现可独立演进。

### Q43：Angular 中如何管理全局状态？

先判断是否真的需要全局状态：

- 组件局部状态使用 signal 或组件内 Observable。
- 一个页面或 feature 共享的状态使用 feature service 或 facade。
- 多路由、多模块共享且有复杂事件流时，再选择成熟的状态库。

全局状态应区分 server state、session state、UI state 和 derived state。不要把所有 HTTP 响应永久复制到全局 store，也不要让 store 直接暴露可被任意组件修改的内部 Subject。

### Q44：什么时候使用状态管理库，什么时候不用？

当状态跨越多个路由、更新来源多、需要可预测事件、调试记录、持久化或团队统一约定时，状态管理库有价值。若只是一个列表页的加载和筛选，引入完整 store 可能增加 ceremony 和认知成本。

决策应考虑状态复杂度、团队熟悉度、调试收益、Bundle 成本和迁移成本，而不是以项目规模作为唯一指标。

### Q45：如何设计 Angular 微前端？

先判断微前端解决的是组织和独立交付问题，还是技术拆分问题。需要明确：

- 主应用与子应用的路由、认证、权限、菜单和错误边界。
- Angular 版本和运行时共享策略，避免重复加载或版本冲突。
- 设计系统、主题、国际化和公共依赖的所有权。
- 子应用之间是否共享状态，事件契约如何版本化。
- 独立发布失败时如何回滚、降级和观测。

如果团队边界、发布节奏和运行时隔离没有真实需求，模块化单体通常更简单。微前端不能自动解决代码耦合，反而会引入部署、调试和契约治理成本。

### Q46：如何处理前后端 API 契约？

建议使用 OpenAPI、代码生成或共享 schema 定义请求和响应，明确字段可选性、分页、排序、错误格式、版本策略和幂等语义。

- DTO 不一定等同于领域模型或页面模型。
- 数据访问层负责转换和兼容旧字段。
- 对破坏性变更建立契约测试。
- 错误响应应包含稳定的机器可读 code 和用户可展示的 message。

不要让模板直接依赖后端返回的深层嵌套结构，否则后端小改动会传播到大量组件。

### Q47：如何设计登录、权限和路由保护？

认证解决“你是谁”，授权解决“你能做什么”。路由守卫只能改善导航体验，不能替代服务端授权；任何 API 都必须在服务端重新验证身份、权限、租户和资源归属。

前端应统一处理 token 生命周期、登录过期、无权限页面、回跳地址校验、加载态和登出清理。权限模型最好使用能力或权限 code，而不是在模板中散落角色字符串和业务判断。

### Q48：如何实现可配置的菜单和权限按钮？

将菜单、路由元数据和权限能力建立清晰映射，由统一的权限服务或 guard 判断。按钮级权限应是用户体验控制，不是安全控制。

配置应支持隐藏、禁用、无权限提示和异步权限加载，且不能把服务器下发的任意字符串直接当作组件名、模板或可执行代码。

### Q49：如何做国际化和主题切换？

国际化需要考虑翻译资源加载、复数规则、日期数字格式、时区、RTL、文本扩展和动态内容。不要通过字符串拼接构造句子，应让翻译资源控制完整语句。

主题切换可使用 CSS custom properties 配合设计 token，并处理初始化闪烁、系统主题、对比度和第三方组件适配。主题 token 应有所有权和命名规则，避免业务页面直接依赖某个组件内部 CSS 类名。

## 八、性能优化

### Q50：Angular 性能问题应该如何排查？

先测量再优化：

1. 区分首屏、交互响应、路由切换、列表滚动和后台请求性能。
2. 使用浏览器 Performance、Angular DevTools、Lighthouse 和构建统计定位瓶颈。
3. 查看变更检测耗时、长任务、组件渲染数量、Bundle 体积、网络瀑布和内存增长。
4. 每次只改变一个主要因素，并在代表性设备和网络下复测。

常见根因包括大列表 DOM、重复请求、过大的初始 chunk、图片和字体、模板重复计算、无界缓存以及第三方脚本。

### Q51：`OnPush` 能解决所有性能问题吗？

不能。`OnPush` 可以减少不必要的组件检查，但不能解决大 DOM、昂贵计算、重复 HTTP、图片过大、主线程长任务或内存泄漏。它也要求团队理解引用变化和响应式通知。

性能优化应组合使用：合理组件边界、稳定列表 key、虚拟滚动、懒加载、预加载策略、缓存、服务端分页、Web Worker 和更小的代码分割。

### Q52：如何优化大列表？

- 使用稳定的 `trackBy` 或 `@for track`。
- 使用分页或服务端查询，限制一次传输和渲染的数据量。
- 需要大量行时使用 CDK virtual scroll，并处理动态行高和键盘访问。
- 避免每一行创建复杂管道、订阅和新对象。
- 只在确实需要时渲染详情、菜单和操作面板。

虚拟滚动不是所有列表的默认答案。它会影响滚动定位、SEO、复制、可访问性和动态高度，需要用真实交互验证。

### Q53：如何减少初始 Bundle 体积？

- 按路由或 feature 做 lazy loading。
- 检查构建统计，移除未使用依赖和重复库。
- 避免在根入口导入仅少数页面使用的大型库。
- 选择合适的预加载策略，平衡用户下一步导航与网络占用。
- 优化图片、字体、source map 发布策略和缓存头。

不要只追求 Bundle 数字。还要关注真实用户的 LCP、INP、CLS、TTFB、错误率和业务完成时间。

### Q54：如何设计缓存？

先区分缓存对象：静态资源、配置、查询结果、用户会话、权限和表单草稿的有效期与一致性要求不同。

- HTTP 缓存优先解决静态资源和可缓存 GET。
- 内存缓存要有 key、TTL、容量、失效和并发请求合并策略。
- 用户或租户敏感数据不能无边界地存入共享缓存。
- 写操作后要明确失效、局部更新还是重新查询。
- 版本化资源和 API 缓存策略要配合部署回滚。

缓存不是免费加速器。陈旧数据、登出后的残留数据、内存增长和跨标签页不一致都要纳入设计。

### Q55：如何处理重复 HTTP 请求？

先区分是同一组件重复订阅、多个组件同时查询、路由重复加载，还是浏览器重试。可以在数据访问层使用共享请求、缓存、请求去重或 facade 统一编排，但要定义缓存失效和错误恢复。

写请求不能因为“共享”就被错误地合并。查询可共享，命令通常需要幂等键、请求状态和明确的重复提交策略。

### Q56：什么时候使用 Web Worker？

当 CPU 密集型计算明显阻塞主线程，例如大型数据解析、加密、图像处理或复杂转换，可以考虑 Web Worker。需要评估数据序列化和传输成本、浏览器支持、调试复杂度以及是否能通过服务端计算或更高效算法解决。

Worker 不适合直接访问 DOM。主线程与 Worker 之间应定义可版本化的消息协议，并支持取消、错误和超时。

### Q57：Angular 应用如何做可观测性？

至少需要：

- 前端错误：错误类型、版本、路由、用户操作上下文和关联请求 ID。
- 性能指标：导航、资源加载、Core Web Vitals、API 延迟和长任务。
- 业务指标：登录成功、提交成功、失败原因和关键流程耗时。
- 网络诊断：状态码、重试、超时、后端 trace ID。

日志要脱敏，不记录 token、密码、完整个人信息或不必要的表单内容。前端监控应支持采样、版本关联和 source map 管理。

## 九、路由、SSR 与部署

### Q58：Angular Router 的核心概念有哪些？

路由配置把 URL 映射到组件，并可携带参数、查询参数、子路由、懒加载、守卫、resolver、路由数据和重定向规则。

推荐按 feature 定义路由，使用懒加载隔离业务 chunk。路由守卫用于导航前的体验和流程控制，resolver 适合必须在进入页面前准备的数据，但要防止 resolver 阻塞导航太久；非关键数据可以进入页面后渐进加载。

### Q59：路由守卫有哪些类型？

常见类型包括控制是否允许进入、是否允许离开、是否允许加载子路由以及是否把匹配到的 URL 重定向到其他路由。不同版本的 API 名称可能有变化，回答时应结合项目版本。

守卫逻辑应轻量、可测试、可取消，并避免在守卫中重复实现认证刷新和业务加载。守卫失败时要区分跳转登录、展示无权限页和返回原页面。

### Q60：Resolver 适合什么场景？

当页面没有关键数据就无法正确渲染，或必须在路由激活前完成权限相关数据准备时，resolver 有价值。它的代价是延迟路由激活，错误也可能阻止用户进入页面。

对于可选数据、慢查询和复杂聚合，通常更适合先展示页面骨架和加载状态，再通过 facade 获取数据。面试中要说明为什么这个数据必须阻塞导航。

### Q61：Angular SSR、预渲染和纯 CSR 如何选择？

- **CSR**：浏览器下载 JavaScript 后渲染，交互模型简单，适合内部系统和 SEO 不重要的应用。
- **SSR**：服务端生成请求对应的 HTML，有利于首屏和 SEO，但要处理服务端运行时、缓存、请求隔离和 hydration。
- **预渲染**：构建时生成页面，适合内容相对稳定的公开页面。

选择取决于 SEO、首屏性能、内容更新频率、服务端成本、部署环境和数据隐私。SSR 不能自动解决所有性能问题，服务端渲染和客户端 hydration 的总成本都要测量。

### Q62：SSR 应用中浏览器 API 如何处理？

`window`、`document`、`localStorage`、`navigator` 等对象在服务端可能不存在。使用平台判断、注入的抽象或仅在浏览器生命周期中执行相关逻辑，并为服务端路径提供合理行为。

还要注意：

- 服务端不能共享不同用户的请求状态。
- 认证 cookie 和缓存头要防止跨用户泄露。
- 随机数、当前时间和客户端专属数据可能造成 hydration 不一致。
- 第三方浏览器插件可能不支持 SSR，需要隔离或延迟加载。

### Q63：什么是 hydration？常见问题有哪些？

Hydration 让客户端复用服务端已经生成的 DOM，并接管交互，而不是无条件重新创建全部 DOM。服务端和客户端对模板结果的判断必须一致。

常见问题是服务端和客户端时间、随机值、地区格式、用户状态或浏览器专属 API 不一致，导致 hydration mismatch。修复方向是稳定初始数据、延迟浏览器专属内容、传递服务端状态并避免渲染期副作用。

### Q64：Angular 应用如何部署和回滚？

构建产物应使用内容哈希，静态资源设置长期缓存，入口 HTML 设置较短缓存或重新验证。部署需要保证入口文件引用的资源版本存在，避免新旧 HTML 与资源错配。

回滚时应考虑：服务端 API 兼容性、缓存清理、SSR 节点版本、Feature Flag、source map、监控告警和数据库迁移。前端发布不是只把 `dist` 目录复制到服务器。

## 十、安全、测试与工程化

### Q65：Angular 如何防范 XSS？

Angular 模板默认会对插值和属性绑定进行上下文相关的安全处理。风险通常来自把不可信字符串当作 HTML、URL、资源地址或脚本使用，或者绕过安全机制。

- 尽量使用插值和普通属性绑定，不拼接 HTML。
- 谨慎使用 `innerHTML` 和 `DomSanitizer` 的 bypass API。
- 不要把用户输入放入脚本、样式或资源 URL 上下文。
- 配置 CSP、Trusted Types 和服务端输出编码。
- 前端校验只是体验优化，后端必须重新校验和授权。

### Q66：JWT 放在哪里？如何回答更严谨？

没有对所有应用都正确的单一答案。`localStorage` 容易受到 XSS 读取；HttpOnly cookie 不能被 JavaScript 读取，但要设计 CSRF 防护、SameSite、Secure、域和过期策略。还需要考虑刷新 token、撤销、跨标签页登出和 SSR。

关键是说明威胁模型和完整方案，而不是简单说“JWT 一定放 localStorage”或“一定放 cookie”。敏感 token、日志和错误上报都必须避免泄漏。

### Q67：Angular 单元测试、集成测试和端到端测试如何分工？

- **单元测试**：验证纯函数、pipe、validator、service 和组件局部行为，反馈快。
- **集成测试**：验证组件、模板、DI、HTTP mock、路由和状态组合。
- **端到端测试**：验证真实用户流程、权限、跨页面跳转和关键业务。

测试应关注公开行为而非内部实现。不要为了提高覆盖率大量断言私有字段或框架内部调用次数。

### Q68：HTTP 测试应该验证什么？

应验证请求 URL、方法、参数、请求体、认证头、错误映射和重试语义，同时模拟成功、超时、401、403、404、429 和 5xx 等关键路径。

测试不应访问真实生产服务。请求匹配要足够严格，避免测试因为“随便返回一个响应”而掩盖 URL 或方法错误。

### Q69：如何测试 RxJS 异步逻辑？

简单逻辑可以订阅并断言输出；涉及时间、去抖、重试和顺序时，使用虚拟时间或 marble 测试更可靠。测试应覆盖：

- 输入事件的顺序和去重。
- 旧请求取消或新请求覆盖。
- 错误恢复后外层流是否继续。
- 组件销毁后的订阅是否停止。
- 重试次数、退避和最终错误。

### Q70：如何提升 Angular 项目的代码质量？

- 启用严格 TypeScript 和模板类型检查。
- 使用 ESLint、格式化、预提交检查和 CI 质量门禁。
- 对公共库建立 API 兼容策略和变更日志。
- 对高风险页面配置 E2E、视觉回归和性能预算。
- 升级 Angular、TypeScript、RxJS 和 Node 时先阅读兼容矩阵并分阶段验证。

代码质量不是工具数量，而是团队能否及时发现错误、理解改动影响并可靠发布。

### Q71：如何升级一个大型 Angular 项目？

先建立当前版本、Node、TypeScript、RxJS、构建器、第三方库和浏览器支持矩阵，记录现有测试和构建基线。然后按官方迁移路径逐版本升级，优先处理弃用 API、模板错误和构建问题。

每一步都应有：

1. 可重复的构建和测试。
2. 关键页面的 E2E 或人工验收。
3. Bundle、Core Web Vitals 和错误率对比。
4. 回滚方案和兼容窗口。

不要在同一个 PR 中同时升级框架、重写状态管理、迁移 standalone 和重构目录，除非有明确的拆分策略。

### Q72：如何设计 Angular 共享组件库？

共享库应有稳定的公共 API、设计 token、无障碍规范、主题机制、文档、示例、变更日志和兼容策略。组件应避免依赖某个业务 feature，输入输出要表达语义而不是暴露内部实现。

重点验证：键盘操作、焦点管理、屏幕阅读器、表单状态、RTL、响应式、错误态和版本升级。共享库的最大成本通常不是第一次开发，而是跨团队维护和破坏性变更协调。

## 十一、高频场景题

### Q73：用户连续点击“提交订单”三次，前端如何处理？

前端在提交过程中禁用按钮或使用 `exhaustMap` 防止重复触发，但这只能改善客户端行为。服务端必须使用幂等键、业务唯一约束或状态机防止重复创建。请求超时后不能简单重试非幂等写操作，应先查询订单状态或使用幂等重试。

回答时补充：按钮恢复时机、错误提示、网络断开、页面刷新、重复响应和审计日志如何处理。

### Q74：搜索请求返回乱序，页面展示了旧结果，如何解决？

使用 `switchMap` 让新查询取消旧订阅，并在响应中携带查询词或请求版本做保护。后端已经处理的请求可能仍在运行，因此前端取消不等于服务端取消；服务端或客户端必须丢弃过期响应。

### Q75：登录 token 过期时多个请求同时返回 401，如何避免刷新风暴？

使用单例认证服务维护一个正在进行的刷新 Observable 或 Promise，让其他请求等待同一刷新结果。刷新成功后重放原请求；刷新失败则清理会话并跳转登录；刷新接口自身不能再次进入同样的重试逻辑。

必须限制重试次数，避免 401、刷新、重放之间形成无限循环，并处理并发登出和跨标签页状态同步。

### Q76：一个页面首屏很慢，你会如何定位？

先用真实设备和网络确认是 TTFB、JavaScript 下载、脚本执行、渲染、图片字体还是后端 API。再检查初始 chunk、路由是否懒加载、是否存在阻塞 resolver、重复请求、大量同步计算和第三方脚本。

优化方案要与证据对应：拆分 chunk、调整预加载、延迟非关键组件、压缩媒体、缓存 API 或改进后端查询。上线后比较 LCP、INP、错误率和业务转化，而不是只看本地 Lighthouse。

### Q77：一个列表有十万条数据，如何设计？

通常不把十万条一次性返回和渲染。先确定用户是否需要全量数据；优先使用服务端分页、筛选、排序和导出任务。页面使用虚拟滚动或有限窗口，并提供加载、空态、错误、定位和可访问性。

如果必须本地处理全量数据，应评估内存、Worker、分块处理、取消和弱设备体验，并设置明确的数据上限。

### Q78：两个页面需要共享筛选条件和结果，怎么做？

先判断状态范围和生命周期。如果只在一个流程内共享，用 feature facade 或路由 query params；如果需要刷新后恢复，考虑 URL、session storage 或服务端草稿；如果多个区域实时联动且逻辑复杂，再使用受约束的状态 store。

不要为了“共享”把状态直接放根级 service 并永久保留。需要定义清理、回退、浏览器前进后退和权限变化时的行为。

### Q79：如何设计离线和网络恢复？

区分可缓存读取、可离线编辑和不可离线操作。读取可使用 Service Worker 或本地缓存；编辑需要本地队列、冲突策略、版本号、重试和用户可见的同步状态；敏感操作通常要求在线确认。

网络恢复后不能无条件重放所有命令。要处理过期权限、重复提交、服务端状态变化和用户取消，并提供人工解决冲突的入口。

### Q80：如何把一个 Angular 单体拆成多团队可协作的系统？

先按业务边界和发布责任拆 feature，再建立依赖规则、公共库所有权、API 契约、设计系统和 CI 门禁。可以先做模块化单体，使用 lint 或依赖图防止跨 feature 私有实现互相引用。

只有当团队自治、独立发布和故障隔离收益足够覆盖运行时复杂度时，才考虑微前端。架构演进要有迁移边界和回滚路径，不能只改目录名称。

### Q81：如何设计一个可取消、可重试的文件上传？

上传流程需要进度、暂停或取消、失败重试、文件校验、断点续传、并发限制、服务端幂等和最终确认。HTTP 请求可通过取消机制停止客户端等待，但服务端可能已经接收部分数据。

大文件应考虑分片和上传会话；重试应使用指数退避并限制次数；文件名、大小、类型和内容必须在服务端校验，不能只信任浏览器提供的 MIME 类型。

### Q82：如何设计一个可访问的 Angular 组件？

先优先使用原生 HTML 语义，再补充 ARIA。确保键盘可操作、焦点顺序合理、焦点可见、状态可被屏幕阅读器感知、颜色对比度足够，并覆盖加载、错误、禁用和动态更新状态。

不要把 `div` 加上 `role="button"` 就认为完成了按钮组件。还要实现键盘事件、焦点管理和正确的禁用语义，并通过自动化工具和真实辅助技术验证。

### Q83：生产环境出现内存持续上涨，你怎么排查？

先确认是浏览器标签页、SSR 进程还是构建节点的内存增长。前端页面检查 Performance Memory、heap snapshot、长生命周期订阅、WebSocket、定时器、DOM 监听、第三方实例和无界缓存；SSR 还要检查请求数据是否被放到全局变量或单例中。

通过重复进入退出页面、切换路由、执行关键流程和对比快照定位保留路径。不要仅通过增加内存或刷新页面规避问题。

### Q84：如何回答“为什么选择 Angular 而不是 React/Vue”？

先承认三者都能完成常见 UI 开发，再根据约束回答。Angular 的优势通常是完整框架、强约定、TypeScript、DI、路由、表单、测试和大型团队协作的一致性；代价是框架范围较大、升级需要治理、自由组合空间较小。

真正成熟的答案还应说明团队技能、现有生态、招聘、应用生命周期、SSR、性能、迁移成本和交付风险，而不是进行绝对化的优劣比较。
