## 一、面试考察重点

### 1. 初级开发工程师

- 是否理解组件、模板、指令、计算属性、侦听器和生命周期的基本职责。
- 是否能够使用 Vue 3 创建页面、处理表单、调用 API 和配置基础路由。
- 是否理解 `ref`、`reactive`、`computed` 和 `watch` 的常见用法。
- 是否能写出可读、可测试、符合 Vue 数据流习惯的代码。

### 2. 中高级开发工程师

- 能否解释 Vue 的依赖收集、触发更新、虚拟 DOM、组件更新和 `nextTick`。
- 能否正确使用 Composition API、composable、Pinia 和异步请求状态。
- 能否按业务边界组织 feature、UI、data-access 和共享基础能力。
- 能否通过 DevTools、性能录制、Bundle 分析和真实指标证明优化有效。

### 3. 架构师或技术负责人

- 能否设计可演进的 Vue 应用架构，并明确状态、数据和依赖的所有权。
- 能否处理多团队协作、设计系统、共享组件库、微前端、版本升级和发布策略。
- 能否在 CSR、SSR、预渲染、Nuxt 和纯客户端 SPA 之间做出有依据的选择。
- 能否把安全、可观测性、质量门禁、成本和回滚纳入整体设计。

### 4. 高分回答的通用框架

面对 Vue 架构题，可以依次说明：

1. **业务目标**：用户是谁，核心流程是什么，成功指标是什么。
2. **约束条件**：首屏性能、SEO、浏览器、流量、团队、交付周期和后端契约。
3. **状态边界**：哪些是组件局部状态，哪些是 URL state、server state 或共享业务 state。
4. **失败路径**：超时、重复提交、权限变化、刷新、网络中断和服务端错误怎么处理。
5. **验证与演进**：如何测试、监控、灰度和回滚，未来需求变化时哪里需要调整。

## 二、Vue 基础题

### Q1：Vue 是什么？它与 jQuery 或传统模板引擎有什么区别？

**核心回答：** Vue 是一个以组件为核心的渐进式 UI 框架，使用声明式模板和响应式数据描述界面。当响应式状态变化时，Vue 会根据依赖关系调度组件更新，并将必要变化提交到 DOM。

Vue 提供组件、模板、响应式系统、指令和生态工具，但路由、状态管理、数据请求和 SSR 由官方生态或上层框架提供。它的优势是渐进式采用、模板可读性和响应式模型；代价是需要理解响应式边界、模板编译和生态约定。

### Q2：Vue 应用的基本组成是什么？

- **Component**：管理一块 UI、状态和交互。
- **Template**：声明 DOM 结构、数据绑定、事件和条件/列表渲染。
- **Directive**：向元素或组件添加特殊行为，例如 `v-if`、`v-for` 和 `v-model`。
- **Computed**：从响应式状态派生并缓存结果。
- **Watch**：观察状态变化并执行副作用。
- **Composable**：封装可复用的状态逻辑和副作用。
- **Plugin**：向应用注册全局能力、provider 或组件。
- **Renderer**：把虚拟节点或模板结果更新到 DOM、SSR 或其他宿主环境。

组件应保持聚焦。不要把所有 API 调用、缓存、权限、表单规则和布局细节堆进一个页面组件。

### Q3：Vue 2 和 Vue 3 的主要区别是什么？

Vue 3 使用基于 Proxy 的响应式系统，提供 Composition API、`<script setup>`、更好的 TypeScript 支持、Teleport、Suspense 和更灵活的应用实例 API。Vue 2 主要使用 `Object.defineProperty`，以 Options API 为主。

迁移时不能只把 `data` 改成 `ref`。还要检查生命周期、全局 API、插件、过滤器、事件总线、响应式边界、第三方组件和构建工具兼容性。回答版本差异时应以项目实际版本为准。

### Q4：Options API 和 Composition API 如何选择？

Options API 按 `data`、`methods`、`computed`、`watch` 和生命周期组织代码，初学者容易理解，适合简单组件和已有 Vue 2 风格项目。Composition API 按业务逻辑组织状态、计算和副作用，更适合复杂组件、逻辑复用和 TypeScript。

两者可以共存，但同一个组件不应无规则地把同一业务逻辑拆散到两种风格。迁移或新建大型 feature 时，优先保持团队统一、依赖边界清晰和可测试性。

### Q5：Vue 的模板编译做了什么？

Vue 模板会被编译成创建虚拟节点的渲染函数。编译器能够识别静态节点、动态绑定、事件和列表，并在适用时生成优化标记，帮助运行时减少不必要的工作。

模板不是普通 HTML 字符串，也不是把所有表达式都交给浏览器执行。复杂业务计算不要堆在模板表达式里，应移到 `computed`、composable 或领域函数中。

### Q6：什么是虚拟 DOM？Vue 为什么需要它？

虚拟 DOM 是对真实 DOM 的 JavaScript 描述。状态变化后，Vue 生成新的虚拟节点树，比较新旧结果，再把必要更新提交给宿主环境。

它减少了手动操作 DOM 的复杂度，并为跨平台渲染、SSR 和编译优化提供基础。但虚拟 DOM 不是零成本抽象；大列表、昂贵计算、频繁组件更新和大量 DOM 仍然需要单独优化。

### Q7：`v-if` 和 `v-show` 有什么区别？

- `v-if` 根据条件创建或销毁节点和组件，初次条件为 false 时不会创建；切换成本较高。
- `v-show` 通常保留节点，只切换 CSS display，初始渲染成本较高但切换成本低。

频繁切换且组件状态需要保留时可考虑 `v-show`；条件很少变化、内容昂贵或不应存在于 DOM 时使用 `v-if`。还要考虑事件监听、无障碍树、动画和隐藏内容是否需要继续存在。

### Q8：`v-for` 为什么需要 `key`？

`key` 帮助 Vue 识别列表项的稳定身份，从而正确复用、移动或销毁组件和 DOM。key 应来自业务上稳定且唯一的身份，例如数据库 ID。

数组索引只在列表永不插入、删除、排序且项身份没有局部状态时才可能适用。在表单列表、可拖拽排序、过滤和分页场景中，使用索引很容易造成输入值、焦点或局部状态错配。

### Q9：`v-model` 的本质是什么？

在原生元素上，`v-model` 通常是 value 属性绑定与 input/change 事件监听的组合；在组件上，它是约定的 prop 和更新事件组合。Vue 3 还支持更明确的多模型绑定和 `defineModel` 等能力，具体取决于版本。

```vue
<UserNameInput v-model="userName" />
```

复杂组件应明确值的类型、更新时机、修饰符、空值和校验行为。不要把 `v-model` 当作任意双向修改的许可，状态所有权仍要清晰。

### Q10：计算属性和方法有什么区别？

`computed` 会根据响应式依赖缓存结果，依赖没有变化时重复读取不会重新计算；方法在模板每次求值时都可能执行。计算属性适合纯的派生值，方法适合轻量、需要参数或不适合缓存的行为。

```ts
const fullName = computed(() => `${firstName.value} ${lastName.value}`);
```

计算属性应尽量无副作用，不要在其中发请求、修改状态或依赖不可见的外部变量。

### Q11：`watch` 和 `watchEffect` 有什么区别？

- `watch` 需要明确监听源，能够访问新旧值，适合精确控制触发条件。
- `watchEffect` 会自动收集执行过程中读取的响应式依赖，适合依赖关系简单、希望立即运行的副作用。

```ts
watch(
  () => route.params.id,
  id => loadUser(id),
  { immediate: true }
);

watchEffect(() => {
  document.title = pageTitle.value;
});
```

两者都不应代替计算属性。能由状态同步计算出的值应使用 `computed`，不要用 watch 把一个状态复制到另一个状态。

### Q12：什么是 `nextTick`？什么时候使用？

Vue 通常会批量调度响应式更新，不会在每次赋值后立即同步修改 DOM。`nextTick` 用于等待本轮更新提交后再读取或操作 DOM。

```ts
isOpen.value = true;
await nextTick();
dialogRef.value?.focus();
```

`nextTick` 不应被当作修复数据流问题的万能延时器。若频繁依赖它，先检查是否应该通过状态、生命周期、模板 ref 或组件接口表达意图。

## 三、组件、模板与通信

### Q13：Vue 组件应该如何拆分？

按职责和变化原因拆分，而不是按模板行数拆分。一个常见边界是：

- **Page / Container**：负责路由参数、页面级状态和用户流程。
- **Feature**：负责一个业务用例，例如订单编辑或报表筛选。
- **Presentational UI**：通过 props 和 emits 工作，不直接访问后端。
- **Data access / Composable**：封装查询、命令、缓存和错误映射。
- **Shared UI**：提供跨业务复用、可访问和主题一致的基础组件。

拆分后应能独立测试、独立理解，并且不会因为一个小字段变化而牵动大量无关组件。

### Q14：props 和 emits 如何实现父子组件通信？

父组件通过 props 向下传递数据，子组件通过 emits 向上表达用户意图。子组件不应直接修改 props；如果需要编辑，应建立本地草稿或通过事件请求父组件更新。

```vue
<script setup lang="ts">
const props = defineProps<{ title: string }>();
const emit = defineEmits<{ save: [value: string] }>();

function save(): void {
  emit('save', props.title);
}
</script>
```

事件名称和 payload 应表达业务语义，例如 `save`、`pageChanged`，不要暴露内部 DOM 细节。

### Q15：provide/inject 适合什么场景？

`provide/inject` 适合向深层组件提供主题、表单上下文、组件组状态、插件能力或 feature 级依赖，避免不相关层级逐层传 props。

它会让依赖变得隐式，因此需要明确 token、作用域、默认值和类型。不要把所有业务状态都放到根应用的 provide 中；如果状态需要精确订阅、持久化、调试和跨路由管理，应评估 Pinia 或其他状态方案。

### Q16：插槽有哪些类型？如何设计插槽 API？

常见有默认插槽、具名插槽和作用域插槽。作用域插槽允许子组件向插槽内容提供数据，适合表格列、列表项、卡片头部和空态等可定制区域。

插槽 API 应稳定、语义明确并有默认内容。不要让调用方依赖组件内部 DOM 结构，也不要通过十几个插槽把组件的所有布局责任转嫁给使用者。

### Q17：`$attrs` 和透传属性是什么？

未被声明为 props 或 emits 的属性和监听器可以通过 `$attrs` 透传到根元素或指定子元素。多根节点组件需要显式决定属性落点，否则调用者可能误以为 `class`、`disabled` 或 aria 属性已经生效。

设计基础组件时，要明确哪些属性属于组件 API，哪些应该透传，并正确处理 class、style、事件、`aria-*` 和原生表单属性。

### Q18：`defineExpose` 什么时候使用？

`<script setup>` 组件默认不会把内部绑定暴露给父组件。`defineExpose` 可以显式暴露少量命令式能力，例如聚焦输入框、重置内部状态或打开组件。

它应是例外而不是主要通信方式。优先使用 props 和 emits 建立声明式数据流；暴露内部实例过多会让组件难以重构和测试。

### Q19：动态组件如何实现？

使用 `<component :is="componentType" />` 根据组件对象或注册名动态渲染。动态组件切换时默认可能销毁旧实例；需要保留状态时可以配合 `KeepAlive`，但要考虑缓存数量和失效策略。

不可信后端字符串不能直接决定任意组件或执行逻辑。动态组件映射应来自前端白名单，并对输入进行类型和权限校验。

### Q20：`KeepAlive` 适合什么场景？

`KeepAlive` 缓存动态组件实例，适合 tab 页面、表单草稿或切换后希望保留滚动和局部状态的场景。缓存会保留内存和订阅，因此不是所有页面都应默认缓存。

需要配合 include、exclude、max、`activated` 和 `deactivated` 生命周期，处理数据刷新、权限变化、WebSocket 和资源释放。缓存页面不代表它永远是最新数据。

### Q21：Teleport 解决什么问题？

Teleport 可以把组件模板渲染到 DOM 的另一个位置，同时保留 Vue 组件树中的状态和依赖关系。它适合 Modal、Popover、Tooltip、全局通知和需要突破 `overflow` 的 UI。

使用 Teleport 时仍要处理焦点陷阱、Esc 关闭、背景滚动、屏幕阅读器语义、卸载清理和 SSR 兼容。Teleport 不是解决组件层级混乱的通用手段。

### Q22：如何实现一个可复用的表格组件？

先定义稳定契约：列定义、行模型、排序、分页、筛选、选择、加载、空态、错误态和无障碍支持。

- 表格组件只负责展示和用户事件，不直接绑定某个业务 API。
- 通过泛型或明确的列配置保持类型安全。
- 大数据量使用虚拟滚动、服务端分页或服务端排序，不把所有数据一次性塞进 DOM。
- 选择状态应明确是页面状态还是跨页面状态。
- 输出事件应描述用户意图，例如 `sortChanged`、`pageChanged`，而不是暴露内部 DOM 细节。

## 四、响应式原理与生命周期

### Q23：Vue 3 响应式系统的核心原理是什么？

Vue 3 主要使用 Proxy 代理对象，通过 `get` 进行依赖收集，通过 `set`、`deleteProperty` 等操作触发相关副作用重新运行。`ref` 通常通过 `.value` 访问并追踪依赖，`computed` 和 watcher 建立在响应式 effect 之上。

响应式系统只知道被读取和修改的响应式边界。把普通对象、解构后的值或第三方实例直接传出去，可能丢失追踪；需要使用 `toRef`、`toRefs`、`reactive` 或 `shallowRef` 明确边界。

### Q24：`ref` 和 `reactive` 有什么区别？

- `ref` 可以包装基本值或对象，通过 `.value` 访问，适合单值、替换整个对象和作为 composable 返回值。
- `reactive` 返回对象的响应式代理，适合一组相关字段，但不能直接包装基本值，整体替换也不如 ref 直观。

```ts
const count = ref(0);
const form = reactive({ name: '', email: '' });

count.value += 1;
form.name = 'Ada';
```

选择重点是替换语义、解构行为、类型推断和团队可读性，不要把所有数据都机械地放入一个 reactive 对象。

### Q25：为什么解构 reactive 对象可能丢失响应式？

```ts
const state = reactive({ count: 0 });
const { count } = state;
```

上面的 `count` 是普通值，不再通过代理访问，因此后续变化不会被模板或 effect 追踪。可以使用 `toRefs(state)` 或 `toRef(state, 'count')` 保留响应式引用。

如果只是读取一次值，普通解构没有问题；如果要作为 composable 返回值或继续参与响应式计算，应明确保留 ref 语义。

### Q26：`computed` 为什么有缓存？它什么时候重新计算？

computed 会记录执行过程中读取的响应式依赖，并缓存上一次结果。只有依赖变化时才会标记为 dirty，下次读取时重新计算；如果没有新的读取，变化不一定立即执行 getter。

computed getter 应是纯函数。副作用、异步请求和写入其他状态应放在 watcher、事件处理函数或数据层，否则缓存和执行时机会变得不可预测。

### Q27：Vue 的更新为什么是异步批量的？

同一同步任务中可能发生多次状态变更，Vue 会将相关组件更新放入队列并合并调度，以避免每次赋值都同步修改 DOM。这样可以减少重复渲染，但意味着状态赋值后立即读取 DOM 可能仍是旧值。

需要操作最新 DOM 时使用 `nextTick`，需要验证逻辑时读取响应式状态本身，而不是依赖 DOM 是否已经更新。

### Q28：`watch` 的 flush 选项有什么区别？

watcher 的执行时机可以影响读取的 DOM 和副作用顺序。常见选项包括：

- `pre`：默认倾向于在组件更新前执行，适合响应式副作用，但不适合读取更新后的 DOM。
- `post`：组件更新后执行，适合读取最新 DOM。
- `sync`：同步执行，可能破坏批量更新并造成递归或性能问题，应谨慎使用。

具体调度细节应以项目 Vue 版本和官方文档为准。使用 flush 不是为了掩盖状态设计问题。

### Q29：Vue 生命周期如何选择？

- `setup`：建立响应式状态、计算值和 composable 组合。
- `onMounted`：需要 DOM 或浏览器环境的初始化。
- `onUpdated`：DOM 更新后执行少量同步工作，避免昂贵逻辑。
- `onBeforeUnmount` / `onUnmounted`：释放订阅、定时器、监听和第三方实例。
- `onActivated` / `onDeactivated`：配合 KeepAlive 管理缓存组件资源。

不要在 `onMounted` 中堆积所有数据加载和业务逻辑；能在 setup 或路由数据层完成的工作应保持边界清晰。

### Q30：Vue 2 和 Vue 3 的响应式差异是什么？

Vue 2 使用 `Object.defineProperty` 拦截已存在属性，因此对新增属性、删除属性和部分数组变化存在限制，常见经验是使用 `Vue.set` 或替换数组。Vue 3 使用 Proxy，能够覆盖更完整的对象操作。

这不意味着 Vue 3 中可以随意修改任意数据。普通对象、解构、浅响应式、第三方实例、冻结对象和 markRaw 都可能建立不同边界，仍需理解数据是否被代理。

### Q31：`shallowRef`、`shallowReactive` 和 `markRaw` 什么时候使用？

- `shallowRef`：只追踪 `.value` 的替换，不深度代理内部对象，适合大型不可变数据或第三方实例。
- `shallowReactive`：只代理第一层，适合明确控制深层更新的场景。
- `markRaw`：标记对象不应被 Vue 代理，适合第三方类实例、图表对象或不可代理资源。

这些 API 是边界工具，不应作为默认性能优化。使用前要证明深层变化不需要驱动 UI，否则会产生“数据变了但视图不更新”的问题。

### Q32：为什么要给组件或列表使用稳定 key？

稳定 key 让 Vue 保留组件实例和 DOM 节点的正确身份，避免输入焦点、局部状态、动画和原生元素状态错配。改变 key 可以有意强制销毁重建组件，用于重置内部状态，但这应是明确的设计选择。

key 不能解决所有列表性能问题。十万条数据仍然需要分页、虚拟列表或服务端查询。

### Q33：如何排查 Vue 组件频繁更新？

先用 Vue DevTools 和浏览器 Performance 确认哪个组件、哪个响应式依赖和哪个 commit 过程耗时。再检查模板中的复杂表达式、错误的 watch、父组件频繁传入新对象、过大的 reactive 对象、列表 key 和第三方组件。

优化可以包括拆分组件、使用 computed、稳定 props、shallow ref、虚拟列表和减少 DOM；每次改动后都要在真实数据规模下复测，而不是只看开发环境主观感觉。

## 五、Composition API 与异步编程

### Q34：`<script setup>` 有什么优势？

`<script setup>` 是编译时语法，减少 `setup()` 返回对象和组件选项样板，使模板可以直接访问顶层绑定，并改善类型推断和 tree-shaking。它还提供 `defineProps`、`defineEmits`、`defineExpose`、`defineSlots` 等编译宏。

这些宏通常不需要运行时导入，具体能力和语法要以项目 Vue 版本为准。不要把所有内容都放在一个 script setup 中；复杂业务仍需要拆 composable、data-access 和领域函数。

### Q35：如何设计一个 composable？

Composable 应封装一组有明确生命周期和业务意义的响应式逻辑，例如 `usePagination`、`useUserSearch` 或 `useWebSocket`。它应有清晰输入输出、错误和加载状态、取消与清理策略，并说明状态是每次调用独立还是连接到共享 store。

```ts
export function useCounter(initialValue = 0) {
  const count = ref(initialValue);

  function increment(): void {
    count.value += 1;
  }

  return { count: readonly(count), increment };
}
```

不要把整个页面模板、路由跳转和多个不相关请求都塞入一个“万能 composable”。

### Q36：composable 每次调用是共享状态还是独立状态？

如果 composable 在函数内部创建 `ref`、`reactive` 或 watcher，每次调用通常拥有独立状态。若状态放在模块顶层或连接到 Pinia，则可能被多个调用共享。

共享状态必须明确生命周期、SSR 隔离、权限边界和清理策略。尤其在 SSR 中，不能用模块级可变对象保存用户请求数据，否则可能发生跨请求泄漏。

### Q37：如何处理 composable 中的副作用和清理？

在创建订阅、定时器、WebSocket、Observer 或第三方实例时，同时定义销毁动作。使用 `onUnmounted`、`onScopeDispose` 或返回显式的 `stop` 方法，取决于资源所有权。

```ts
const timer = window.setInterval(refresh, 30000);
onUnmounted(() => window.clearInterval(timer));
```

如果 composable 可在组件外调用，不能假设总有组件生命周期，应提供清晰的手动停止方式或使用 effect scope。

### Q38：如何实现搜索框的请求流？

应包含输入清洗、去抖、去重、旧请求取消、加载态、空结果、错误恢复和销毁处理：

```ts
const query = ref('');
const results = ref<User[]>([]);
const isLoading = ref(false);
let requestId = 0;

watch(query, async value => {
  const currentRequestId = ++requestId;
  const normalizedValue = value.trim();

  if (normalizedValue.length < 2) {
    results.value = [];
    return;
  }

  isLoading.value = true;
  try {
    const nextResults = await searchUsers(normalizedValue);
    if (currentRequestId === requestId) {
      results.value = nextResults;
    }
  } finally {
    if (currentRequestId === requestId) {
      isLoading.value = false;
    }
  }
}, { flush: 'post' });
```

生产代码还应使用 AbortController 或数据请求库提供的取消能力，并处理网络错误、重试和组件卸载。

### Q39：如何避免 watch 造成无限循环？

不要在监听源的 watcher 中无条件修改同一个监听源，也不要在多个 watcher 之间互相同步同一组状态。能通过 computed 得到的派生值，不要使用双向 watch 复制。

如果确实需要状态机转换，应明确事件、前置条件和终态；必要时使用 `once`、比较新旧值、拆分可写状态，或把更新移动到用户命令处理函数中。

### Q40：Vue 中如何处理异步错误？

错误处理要分层：

- 组件或 composable：展示用户可理解的错误，并允许重试或恢复。
- 数据访问层：统一转换 HTTP 错误、超时和业务错误。
- 全局层：通过 `app.config.errorHandler`、日志服务和监控上报未知错误。
- 路由层：处理加载失败、权限失败和数据准备失败。
- 交互层：防止重复提交，避免把堆栈信息直接展示给用户。

不要在每个组件中复制一套 toast 逻辑。应区分可恢复错误、需要重新认证的错误、参数错误和系统故障。

### Q41：如何处理 Vue 中的 DOM 操作？

优先使用声明式模板、组件 props、emits 和指令。必须访问 DOM 时使用模板 ref 或自定义指令，并在正确生命周期读取和清理。

直接修改 DOM 可能与 Vue 的下一次渲染冲突，影响 SSR、测试、无障碍和第三方集成。第三方图表、编辑器和地图实例应由专门 composable 或指令拥有，并在卸载时销毁。

### Q42：自定义指令适合什么场景？

自定义指令适合复用与单个 DOM 元素相关的行为，例如自动聚焦、点击外部关闭、权限属性、拖拽和 IntersectionObserver。

如果逻辑涉及多个组件、业务状态或请求流程，应使用组件、composable 或服务，而不是把业务逻辑隐藏在指令里。指令必须处理更新、卸载、SSR 和事件监听清理。

### Q43：`defineModel` 或组件多 `v-model` 如何设计？

组件可以为不同字段建立明确的模型，例如 `v-model:title`、`v-model:visible`，让调用方表达多个可编辑值。模型应有清晰类型、默认值、更新时机和修饰符语义。

不要把整个复杂对象作为一个可随意深改的模型传递。对于保存、取消、校验和脏状态，通常需要区分草稿值和提交命令。

### Q44：如何设计异步组件和加载边界？

使用异步组件或路由懒加载拆分非首屏 feature，并定义加载、错误、重试和超时 UI。懒加载失败可能来自网络、缓存或版本不匹配，不能只展示一个永久 spinner。

加载边界应与用户感知的独立区域对应，fallback 保持布局稳定。发布时使用内容哈希、正确缓存头和资源存在性检查，避免新旧入口文件引用错误版本。

### Q45：Vue 中如何使用 `Suspense`？

Suspense 可以围绕含有异步 setup 或异步组件的子树提供 fallback，具体行为和框架集成依赖 Vue 版本。它适合表达一组内容的加载边界，但不是自动的数据缓存、重试和错误管理方案。

使用时要设计加载区域、错误处理、超时、SSR、hydration 和重复请求。不要把所有异步请求都塞进一个巨大的 Suspense 边界，否则一个慢请求会阻塞整页。

## 六、状态管理与数据流

### Q46：Vue 应用中有哪些状态类型？

至少应区分：

- **Local UI state**：弹窗、展开项、输入草稿、hover 和当前 tab。
- **URL state**：分页、筛选、排序、搜索词和可分享的页面视图。
- **Server state**：由后端拥有、需要缓存、重试、失效和重新验证的数据。
- **Session state**：登录身份、租户、权限和用户偏好。
- **Shared client state**：多个 feature 共享且由前端拥有的工作流状态。
- **Derived state**：由其他状态计算出的值，不应重复存储。

分类后才能决定使用组件 ref、composable、URL、Pinia 还是数据请求库。

### Q47：Pinia 解决什么问题？

Pinia 为 Vue 应用提供模块化 store、响应式状态、getters、actions、插件和较好的 TypeScript 支持。每个 store 可以按业务域组织，避免把所有状态堆到单一巨型模块。

Pinia 不会自动解决服务端缓存、请求竞态、权限和组件边界。应明确 state 所有权、action 语义、数据失效、SSR 隔离和组件消费方式。

### Q48：Pinia 的 state、getters 和 actions 如何选择？

- **state**：保存该 store 真正拥有的源数据。
- **getters**：从 state 派生的只读结果，保持纯净并可缓存。
- **actions**：表达业务命令、异步流程和状态转换。

不要把后端所有原始响应永久存进 state，也不要在 getter 中执行请求或修改状态。复杂流程可以由 action 编排，但数据访问和 DTO 转换仍应有清晰边界。

### Q49：`storeToRefs` 为什么有用？

从 Pinia store 直接解构 state 或 getters 可能丢失响应式连接。`storeToRefs` 会把可响应的 state 和 getters 转为 refs，适合在组件中解构使用；action 通常可以直接解构。

```ts
const store = useUserStore();
const { currentUser, isLoading } = storeToRefs(store);
const { loadUser } = store;
```

要区分 store 的 ref 与普通值，避免把响应式引用不小心传成一次性快照。

### Q50：什么时候使用 Pinia，什么时候不用？

如果状态只属于一个组件或页面流程，优先使用局部 ref、reactive 或 composable。跨路由共享、多个更新来源、复杂业务流程、持久化或需要统一调试时，Pinia 更有价值。

server state 应由专门的数据请求层管理，Pinia 只在有明确理由时承载它。引入 store 的判断标准是状态复杂度和协作收益，而不是项目是否“足够大”。

### Q51：如何避免 Pinia store 变成上帝模块？

按业务域拆分 store，限制每个 store 的职责和公开 API。页面通过语义化 action 或 getter 访问，不直接修改其他 store 的内部结构。

跨 store 流程应明确依赖方向和循环依赖风险。基础认证、配置和权限可以独立；订单、支付和通知等业务状态不应全部堆在一个全局 store。

### Q52：如何处理 server state 的缓存？

先定义 query key、TTL、失效、重新验证、重试、取消、分页和请求去重。读取数据时区分 loading、stale、success、empty 和 error，不要把所有非成功状态都展示成空列表。

写操作后要明确是重新查询、局部更新还是失效缓存。缓存 key 必须包含用户、租户和权限维度，敏感数据不能被不同用户共享。

### Q53：如何做乐观更新？

乐观更新先更新 UI，再发送命令；成功时确认，失败时回滚或展示冲突状态。必须保存前置状态或定义可逆操作，并处理重复提交、超时、权限变化和服务端版本冲突。

收藏、点赞适合简单乐观更新；涉及库存、支付或权限的操作不能只相信前端结果。服务端仍是事实来源，前端需要重新验证最终状态。

### Q54：如何实现权限和菜单状态？

将菜单、路由元数据和权限能力建立清晰映射，由统一的权限 composable、store 或 guard 判断。按钮级权限是用户体验控制，不是安全控制。

权限变化、登出和租户切换时，必须清理缓存、store、路由上下文和页面草稿。不能把服务器下发的任意字符串直接当作组件名、脚本或可执行代码。

### Q55：如何处理表单状态？

简单表单可以使用局部 refs；复杂表单应使用明确的字段模型或成熟表单库，管理值、dirty、touched、同步和异步校验、提交和服务端错误。

不要把每个键盘输入都同步到全局 store，除非确实需要跨页面恢复或协同编辑。提交动作要处理重复点击、网络失败、部分成功、离开确认和重新加载恢复。

### Q56：如何设计 Vue 的数据访问层？

组件不应直接散落 HTTP 请求、错误转换和缓存逻辑。可以用 API client 负责传输，用 repository 或 query composable 负责数据访问，用 store 或 feature composable 负责业务状态编排。

数据层还要明确 DTO 与页面模型的转换、请求 ID、超时、重试、认证刷新、分页、错误 code 和取消。不要让模板直接依赖后端深层响应结构。

### Q57：如何处理登录 token 过期？

认证模块应统一处理 token 生命周期、刷新、登出、回跳和跨标签页同步。多个请求同时收到 401 时，应共享一次刷新请求，避免刷新风暴；刷新接口失败后清理会话，并限制原请求重试次数。

token 存储必须结合威胁模型决定。HttpOnly cookie 需要 CSRF 防护和正确的 SameSite/Secure 配置；前端可读存储容易受到 XSS 读取。任何 token 都不能写入日志或错误上报。

## 七、Vue 架构设计

### Q58：如何设计大型 Vue 项目的架构分层？

可以采用以下逻辑分层：

1. **展示层**：纯 UI 组件、布局、可访问性和交互事件。
2. **用例层**：页面流程、表单提交、加载态和用户意图编排。
3. **数据访问层**：HTTP、缓存、序列化、DTO 转换和错误映射。
4. **领域层**：业务规则、状态转换和与 UI 无关的模型。
5. **基础设施层**：认证、配置、日志、Feature Flag 和监控。

不要求每个 feature 都机械地建立五层，但依赖方向要清楚。组件不应各自实现 token 刷新、缓存和错误映射，页面也不应直接依赖后端深层 DTO。

### Q59：如何组织大型 Vue 项目的目录？

推荐按业务 feature 组织，而不是把所有组件、composable 和 services 分别放在全局目录：

```text
src/
  app/
    providers/
    router/
    layouts/
  shared/
    ui/
    composables/
    lib/
  features/
    orders/
      pages/
      ui/
      model/
      api/
      routes.ts
  entities/
    user/
```

`shared` 放真正跨业务复用的能力，`features` 内聚业务用例，`api` 负责数据访问和转换。目录只是结果，真正重要的是依赖方向：shared 不应依赖具体 feature，UI 不应绕过数据层复制鉴权和缓存逻辑。

### Q60：如何设计可复用的 composable 和业务组件？

可复用 composable 应封装逻辑，不依赖具体页面模板；可复用 UI 组件应通过 props、emits、slots 和明确的类型契约提供能力。业务组件可以依赖 feature 数据层，但不要把它伪装成跨业务通用组件。

复用前先确认变化原因是否相同。过早抽象会造成大量配置项、隐式约定和难以修改的万能组件。

### Q61：如何设计 Vue 组件库？

组件库应有稳定的公共 API、设计 token、无障碍规范、主题机制、文档、示例、变更日志和兼容策略。基础组件应避免依赖具体业务 store 和路由。

重点验证键盘操作、焦点管理、屏幕阅读器、表单状态、RTL、响应式、错误态和动态内容。组件库需要明确 Vue 版本、CSS 策略、按需加载和破坏性变更流程。

### Q62：如何选择 Vue Router 的路由组织方式？

按业务 feature 拆分路由配置，使用懒加载隔离非首屏 chunk，并通过 meta 描述标题、权限和布局等稳定元数据。路由页面只负责流程编排，复杂数据应由 feature 数据层加载。

需要区分导航前必须准备的数据和进入页面后可渐进加载的数据。一个慢 resolver 或全局守卫不应阻塞整个应用的每次导航。

### Q63：如何设计 Vue 微前端？

先确认微前端解决的是团队自治和独立交付问题，而不是单纯的组件复用。需要明确主应用与子应用的路由、认证、权限、菜单、错误边界、依赖共享和独立回滚。

还要设计 Vue 版本策略、设计系统、主题、国际化、公共 API、事件契约和可观测性。跨子应用共享可变状态会增加耦合；能通过 URL、后端或明确事件传递的数据，不要默认放入共享单例。

### Q64：如何处理前后端 API 契约？

建议使用 OpenAPI、代码生成或共享 schema 定义请求和响应，明确字段可选性、分页、排序、错误格式、版本策略和幂等语义。

- DTO 不一定等同于领域模型或页面模型。
- 数据访问层负责转换和兼容旧字段。
- 对破坏性变更建立契约测试。
- 错误响应应包含稳定的机器可读 code 和可展示 message。

不要让模板直接依赖后端返回的深层结构，否则后端小改动会传播到大量组件。

### Q65：如何做国际化和主题切换？

国际化需要考虑翻译资源加载、复数规则、日期数字格式、时区、RTL、文本扩展和动态内容。不要通过字符串拼接构造完整句子，应让翻译资源控制语序和复数。

主题切换可使用 CSS custom properties 配合设计 token，并处理初始化闪烁、系统主题、对比度和第三方组件适配。主题 token 应有命名规则和所有权，避免业务页面依赖内部 CSS 类名。

### Q66：如何设计 Feature Flag？

Feature Flag 应有 owner、默认值、作用范围、过期时间、审计和回滚策略。区分发布开关、实验开关、权限开关和紧急降级开关，避免所有开关都变成永久配置债务。

前端开关只能控制体验和代码路径，不能作为安全边界。敏感能力仍需后端授权，Flag 变化时要考虑缓存、SSR、跨标签页和已打开页面的状态。

### Q67：如何设计可观测性？

至少需要：

- 前端错误：错误类型、版本、路由、用户操作上下文和关联请求 ID。
- 性能指标：导航、资源加载、Core Web Vitals、API 延迟和长任务。
- 业务指标：登录成功、提交成功、失败原因和关键流程耗时。
- 网络诊断：状态码、重试、超时、后端 trace ID。

日志要脱敏，不记录 token、密码、完整个人信息或不必要的表单内容。监控应支持采样、版本关联和 source map 管理。

### Q68：如何升级大型 Vue 项目？

先建立 Vue、Vue Router、Pinia、构建器、Node、TypeScript、第三方组件库和浏览器支持矩阵，记录构建、测试、Bundle 和关键页面基线。然后按官方迁移路径处理弃用 API、插件兼容和构建变化。

每一步都应有：

1. 可重复的构建和测试。
2. 关键页面的 E2E 或人工验收。
3. Bundle、Core Web Vitals 和错误率对比。
4. 回滚方案和兼容窗口。

不要在同一个改动中同时迁移 Vue 3、重写状态管理、改造 SSR 和重构目录，除非有明确的拆分策略。

## 八、性能优化

### Q69：Vue 性能问题应该如何排查？

先测量再优化：

1. 区分首屏、交互响应、路由切换、列表滚动和后台请求性能。
2. 使用 Vue DevTools、浏览器 Performance、Lighthouse 和构建统计定位瓶颈。
3. 查看组件更新、watcher、长任务、Bundle 体积、网络瀑布和内存增长。
4. 每次只改变一个主要因素，并在代表性设备和网络下复测。

常见根因包括大列表 DOM、过大的响应式对象、复杂模板计算、错误的 watch、重复请求、过大的初始 chunk、图片字体、无界缓存和第三方脚本。

### Q70：`v-once`、`v-memo` 和 `v-pre` 有什么用途？

- `v-once`：只渲染一次，适合确定不会变化的内容。
- `v-memo`：在满足依赖条件时跳过部分子树更新，适合经过测量的大列表或复杂子树。
- `v-pre`：跳过模板编译，适合展示原始模板语法的极少数场景。

这些是针对特定瓶颈的工具，不应默认到处添加。错误使用会导致界面不更新、维护困难或掩盖状态设计问题。

### Q71：如何优化大列表？

- 使用稳定的 `key`，避免索引作为长期身份。
- 使用服务端分页、筛选和排序，限制一次传输的数据量。
- 需要大量行时使用虚拟列表或窗口化，并处理动态行高和键盘访问。
- 避免每一行创建昂贵计算、重复 watcher 和不必要对象。
- 只在确实需要时渲染详情、菜单和操作面板。

虚拟列表不是所有列表的默认答案。它会影响滚动定位、SEO、复制、可访问性和动态高度，需要用真实交互验证。

### Q72：如何减少初始 Bundle 体积？

- 按路由或 feature 做懒加载和动态 import。
- 检查构建统计，移除未使用依赖和重复库。
- 避免在根入口导入仅少数页面使用的大型库。
- 选择合适的预加载策略，平衡下一步导航和网络占用。
- 优化图片、字体、source map 发布策略和缓存头。

不要只追求 Bundle 数字。还要关注真实用户的 LCP、INP、CLS、TTFB、错误率和业务完成时间。

### Q73：如何减少响应式开销？

对于大型不可变数据或第三方实例，可以使用 `shallowRef`、`markRaw` 或替换整体引用；对于复杂派生值使用 computed；对于高频输入使用局部状态、防抖和渐进更新。

优化前要确认深层变化是否需要驱动 UI。浅响应式会降低代理开销，但如果错误地忽略深层依赖，会造成数据与视图不一致。

### Q74：如何避免重复请求？

先区分是组件重复挂载、多个组件同时查询、watch 触发过多、路由重复加载还是浏览器重试。可以在数据访问层使用 query key、缓存、共享请求和请求去重，但要定义过期和失效。

查询可以共享，写命令通常不能随意合并。非幂等命令需要幂等键、提交状态和明确的重复请求策略。

### Q75：如何优化表单输入性能？

先确认是整个页面因每次输入更新，还是字段校验、派生计算、网络请求或第三方控件变慢。可以使用字段级 composable、局部状态、非受控元素、延迟非关键更新和防抖查询。

不要为了性能完全放弃响应式表单模型；复杂校验和可恢复草稿仍需要明确状态。应通过性能录制和真实设备确认优化没有破坏输入体验、校验和无障碍。

### Q76：如何处理图片、字体和第三方脚本？

根据内容重要性使用合适尺寸、格式、懒加载和响应式图片；关键字体控制 preload、display 和字体回退；第三方脚本延迟加载、隔离权限并测量对主线程和隐私的影响。

不要只压缩 JS。首屏资源优先级、布局稳定、图片尺寸和第三方脚本往往对 LCP、CLS 和 INP 有更明显影响。

### Q77：如何处理内存泄漏？

检查 watcher、事件监听、定时器、WebSocket、Observer、KeepAlive、Teleport、第三方插件和缓存。离开页面时，组件拥有的资源应被释放；全局资源则要有明确的生命周期和订阅管理。

通过重复进入退出页面、切换路由、执行关键流程和对比 heap snapshot 定位保留路径。不要仅通过刷新页面或增加浏览器内存规避问题。

## 九、路由、SSR 与 Nuxt

### Q78：Vue Router 的核心概念有哪些？

Vue Router 将 URL 映射到组件，支持嵌套路由、路径参数、查询参数、导航、懒加载、路由 meta、导航守卫和导航失败处理。

路由应按 feature 组织，使用懒加载隔离业务 chunk。页面数据要区分必须阻塞导航的数据和进入页面后可渐进加载的数据。

### Q79：导航守卫有哪些用途？

守卫可以处理认证、权限、离开未保存表单确认、动态重定向和页面级前置条件。它改善导航体验，但不能替代后端授权。

守卫逻辑应轻量、可测试、可取消，并避免在每个守卫中复制 token 刷新和业务查询。失败时要区分跳转登录、无权限页、取消导航和展示错误。

### Q80：路由参数和查询参数如何选择？

路径参数适合资源身份，例如 `/users/:id`；查询参数适合筛选、分页、排序、搜索词和可分享的视图状态。能被复制、刷新和浏览器前进后退恢复的页面状态，通常更适合放在 URL。

需要校验类型、默认值、编码和非法输入。不要把敏感 token、完整表单或无法信任的权限数据直接放在 URL 中。

### Q81：CSR、SSR、预渲染和 Nuxt 如何选择？

- **CSR**：浏览器下载 JavaScript 后渲染，适合内部系统和 SEO 不重要的应用。
- **SSR**：服务端生成请求对应的 HTML，有利于首屏和 SEO，但要处理服务端运行时、缓存、请求隔离和 hydration。
- **预渲染**：构建时生成页面，适合内容相对稳定的公开页面。
- **Nuxt**：在 Vue 之上提供路由约定、数据获取、服务端渲染、预渲染、Nitro 服务端和部署能力，具体行为取决于 Nuxt 版本和配置。

选择取决于 SEO、首屏性能、内容更新频率、服务端成本、数据隐私、部署环境和团队经验。不能把 Nuxt 或 SSR 当作自动性能优化。

### Q82：SSR 中浏览器 API 如何处理？

`window`、`document`、`localStorage`、`navigator` 等对象在服务端可能不存在。使用平台判断、客户端生命周期或框架提供的安全抽象，并为服务端路径提供合理行为。

还要注意服务端不能共享不同用户的请求状态，认证 cookie 和缓存头要防止跨用户泄露，第三方浏览器插件和随机值可能造成 hydration 不一致。

### Q83：hydration 常见问题有哪些？

Hydration 让客户端复用服务端生成的 DOM 并接管交互，而不是无条件重新创建全部 DOM。服务端和客户端对初始模板结果必须一致。

常见问题是时间、随机值、地区格式、用户状态、浏览器 API、条件分支和第三方组件不一致。修复方向是稳定初始数据、延迟浏览器专属内容、传递服务端状态并避免渲染期副作用。

### Q84：Nuxt 的数据获取应该如何设计？

区分服务端可获取的初始数据、客户端交互数据和用户专属数据。使用框架提供的数据获取约定时，要确认请求是否在服务端执行、结果如何传输、缓存 key 如何生成以及客户端是否会重复请求。

数据层应处理 loading、error、刷新、失效、请求取消和权限。敏感响应不能被公共缓存，用户维度和租户维度必须进入缓存隔离策略。

### Q85：SSR 应用如何部署和回滚？

构建产物和服务端运行时应使用可重复版本，静态资源使用内容哈希，入口 HTML 或 SSR 响应设置合理缓存。部署需要保证入口引用的资源版本存在，避免新旧 HTML 与资源错配。

回滚时应考虑 API 兼容性、缓存清理、SSR 节点版本、Feature Flag、source map、监控告警和数据库迁移。SSR 发布不是只上传静态 dist 目录。

## 十、安全、测试与工程化

### Q86：Vue 如何防范 XSS？

Vue 模板中的普通插值会把内容作为文本处理，降低直接注入风险。风险通常来自 `v-html`、不可信 URL、第三方 HTML、服务端拼接 HTML、富文本转换和绕过安全处理。

- 尽量使用普通插值和属性绑定，不拼接 HTML。
- 富文本必须经过可信 sanitizer，并限制允许的标签、属性和 URL 协议。
- 不要把用户输入放入脚本、样式或资源 URL 上下文。
- 配置 CSP、Trusted Types 和服务端输出编码。
- 前端校验只是体验优化，后端必须重新校验和授权。

### Q87：JWT 放在哪里？如何回答更严谨？

没有对所有应用都正确的单一答案。`localStorage` 容易受到 XSS 读取；HttpOnly cookie 不能被 JavaScript 读取，但要设计 CSRF 防护、SameSite、Secure、域和过期策略。还要考虑刷新 token、撤销、跨标签页登出和 SSR。

关键是说明威胁模型和完整方案，而不是简单说“JWT 一定放 localStorage”或“一定放 cookie”。敏感 token、日志和错误上报都必须避免泄漏。

### Q88：单元测试、集成测试和端到端测试如何分工？

- **单元测试**：验证纯函数、computed、composable、store、validator 和组件局部行为，反馈快。
- **集成测试**：验证组件、provide/inject、Pinia、路由、数据请求 mock 和状态组合。
- **端到端测试**：验证真实用户流程、权限、跨页面跳转和关键业务。

测试应关注公开行为而非内部实现。不要为了提高覆盖率大量断言私有 ref、watch 次数或 Vue 内部细节。

### Q89：Vue Test Utils 的测试原则是什么？

优先通过用户可感知的文本、角色、标签、键盘和交互查询元素，而不是依赖内部 class、组件实例字段或测试专用实现细节。测试应验证页面在用户操作后展示了什么、能做什么。

网络请求可以使用请求拦截或 mock server，覆盖成功、加载、空数据、401、403、404、429 和 5xx 路径。不要让测试依赖真实生产服务。

### Q90：如何测试 composable？

从使用者角度验证初始值、状态更新、异步状态、错误、清理和重新挂载。若 composable 只是纯计算，直接测试纯函数比挂载组件更简单；若依赖 provide/inject，应通过最小测试 provider 注入依赖。

不要只断言 composable 内部调用了多少次 `watch` 或 `ref`，这些都是可变实现细节。

### Q91：如何测试异步组件和 Suspense？

测试加载、成功、空态、错误、重试和取消等用户可见状态。等待异步结果时要等待明确的 DOM 或状态变化，而不是依赖任意延时。

对于 Suspense，要验证 fallback 不会遮挡不相关区域、内容出现后布局稳定、错误边界能恢复，并覆盖 SSR 和 hydration 相关路径。

### Q92：如何提升 Vue 项目的代码质量？

- 启用严格 TypeScript、Vue language tooling 和模板类型检查。
- 使用 ESLint、格式化、提交检查和 CI 质量门禁。
- 对公共组件库建立 API 兼容策略、可访问性规则和变更日志。
- 对高风险页面配置 E2E、视觉回归和性能预算。
- 升级 Vue、Vue Router、Pinia、Nuxt 和构建器时阅读兼容矩阵并分阶段验证。

代码质量不是工具数量，而是团队能否及时发现错误、理解改动影响并可靠发布。

### Q93：如何设计 Vue 项目的 CI/CD？

CI 至少应包含依赖安装锁定、类型检查、Lint、单元测试、构建、Bundle 预算和关键 E2E。CD 应支持环境配置校验、预览部署、灰度或 Feature Flag、静态资源缓存策略和快速回滚。

生产构建要固定依赖和 Node 版本，避免本地可用而 CI 失败。发布后需要把版本和 source map 关联到错误监控，以便定位线上问题。

### Q94：Vue 应用如何管理环境配置？

区分构建时配置和运行时配置，明确哪些值可以公开。前端 Bundle 中的变量都可能被用户读取，不能放入密钥、私有 token 或后端凭据。

运行时配置可通过受保护接口或部署生成的配置文件注入，并校验 schema、默认值和版本。API 地址、Feature Flag 和监控配置要支持环境隔离和回滚。

### Q95：如何做无障碍 Vue 组件？

先优先使用原生 HTML 语义，再补充 ARIA。确保键盘可操作、焦点顺序合理、焦点可见、状态可被屏幕阅读器感知、颜色对比度足够，并覆盖加载、错误、禁用和动态更新状态。

不要把 `div` 加上 `role="button"` 就认为完成了按钮组件。还要实现键盘事件、焦点管理和正确的禁用语义，并通过自动化工具和真实辅助技术验证。

## 十一、高频场景题

### Q96：用户连续点击“提交订单”三次，Vue 前端如何处理？

前端在提交过程中禁用按钮、使用状态机或忽略重复命令，防止重复触发；但这只能改善客户端行为。服务端必须使用幂等键、业务唯一约束或状态机防止重复创建。请求超时后不能简单重试非幂等写操作，应先查询订单状态或使用幂等重试。

回答时补充按钮恢复时机、错误提示、网络断开、页面刷新、重复响应和审计日志如何处理。

### Q97：搜索结果返回乱序，页面展示了旧结果，如何解决？

使用 AbortController、请求版本或数据请求库的 query key，让新查询不会被旧响应覆盖。可以用防抖减少请求，但防抖不能代替请求竞态处理。

后端已经处理的请求可能仍在运行，因此服务端或客户端必须丢弃过期响应；写操作还需要幂等和版本保护。

### Q98：登录 token 过期时多个请求同时返回 401，如何避免刷新风暴？

使用单例认证模块维护一个正在进行的刷新 Promise，让其他请求等待同一刷新结果。刷新成功后重放原请求；刷新失败则清理会话并跳转登录；刷新接口自身不能再次进入同样的重试逻辑。

必须限制重试次数，避免 401、刷新、重放之间形成无限循环，并处理并发登出和跨标签页状态同步。

### Q99：一个页面首屏很慢，你会如何定位？

先用真实设备和网络确认是 TTFB、JavaScript 下载、脚本执行、渲染、图片字体还是后端 API。再检查初始 chunk、路由是否懒加载、是否存在阻塞数据加载、重复请求、大量同步计算和第三方脚本。

优化方案要与证据对应：拆分 chunk、调整预加载、延迟非关键组件、压缩媒体、缓存 API 或改进后端查询。上线后比较 LCP、INP、错误率和业务转化，而不是只看本地 Lighthouse。

### Q100：一个列表有十万条数据，如何设计？

通常不把十万条一次性返回和渲染。先确定用户是否需要全量数据；优先使用服务端分页、筛选、排序和导出任务。页面使用虚拟列表或有限窗口，并提供加载、空态、错误、定位和可访问性。

如果必须本地处理全量数据，应评估内存、Worker、分块处理、取消和弱设备体验，并设置明确的数据上限。

### Q101：两个页面需要共享筛选条件和结果，怎么做？

先判断状态范围和生命周期。如果只在一个流程内共享，用 feature composable、Pinia 或 URL query params；如果需要刷新后恢复，考虑 URL、session storage 或服务端草稿；如果多个区域实时联动且逻辑复杂，再使用受约束的 store。

不要为了“共享”把状态直接放根级 store 并永久保留。需要定义清理、回退、浏览器前进后退和权限变化时的行为。

### Q102：如何设计离线和网络恢复？

区分可缓存读取、可离线编辑和不可离线操作。读取可使用 Service Worker 或本地缓存；编辑需要本地队列、冲突策略、版本号、重试和用户可见的同步状态；敏感操作通常要求在线确认。

网络恢复后不能无条件重放所有命令。要处理过期权限、重复提交、服务端状态变化和用户取消，并提供人工解决冲突的入口。

### Q103：如何把一个 Vue 单体拆成多团队可协作的系统？

先按业务边界和发布责任拆 feature，再建立依赖规则、公共库所有权、API 契约、设计系统和 CI 门禁。可以先做模块化单体，使用 lint 或依赖图防止跨 feature 私有实现互相引用。

只有当团队自治、独立发布和故障隔离收益足够覆盖运行时复杂度时，才考虑微前端。架构演进要有迁移边界和回滚路径，不能只改目录名称。

### Q104：如何设计一个可取消、可重试的文件上传？

上传流程需要进度、暂停或取消、失败重试、文件校验、断点续传、并发限制、服务端幂等和最终确认。取消客户端等待不一定停止服务端已接收的数据。

大文件应考虑分片和上传会话；重试应使用指数退避并限制次数；文件名、大小、类型和内容必须在服务端校验，不能只信任浏览器提供的 MIME 类型。

### Q105：生产环境出现内存持续上涨，你怎么排查？

先确认是浏览器标签页、SSR 进程还是构建节点的内存增长。浏览器页面检查 heap snapshot、watcher、WebSocket、定时器、DOM 监听、KeepAlive、第三方实例和无界缓存；SSR 还要检查请求数据是否被放到全局变量或单例中。

通过重复进入退出页面、切换路由、执行关键流程和对比快照定位保留路径。不要仅通过增加内存或刷新页面规避问题。

### Q106：如何设计一个可访问的 Vue Modal？

使用语义正确的 dialog 结构，管理打开时焦点、关闭时焦点返回、Tab 焦点循环、Esc、遮罩点击、背景滚动和屏幕阅读器标题关联。Teleport 只解决 DOM 挂载位置，不会自动完成可访问性。

还要处理加载、错误、禁用关闭、异步提交和 SSR。组件应通过 props/emits 提供受控契约，而不是让父组件直接修改内部 DOM。

### Q107：为什么选择 Vue 而不是 React 或 Angular？

先承认三者都能完成常见 UI 开发，再根据约束回答。Vue 的优势通常是渐进式采用、模板可读性、响应式模型、官方生态和较低的上手成本；代价是团队需要治理 Options/Composition 风格、响应式边界和生态选择。

成熟答案还应说明团队技能、现有生态、招聘、应用生命周期、SSR、性能、维护成本和交付风险，而不是进行绝对化的优劣比较。
