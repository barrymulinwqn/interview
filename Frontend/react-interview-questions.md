## 一、面试考察重点

### 1. 初级开发工程师

- 是否理解组件、JSX、props、state、事件和条件渲染的基本职责。
- 是否能够编写函数组件、处理表单、调用 API 和组织基础路由。
- 是否知道 Hooks 的调用规则，能避免常见的 stale closure 和重复副作用。
- 是否能写出可读、可测试、符合 React 数据流习惯的代码。

### 2. 中高级开发工程师

- 能否解释 render、commit、Fiber、key、批量更新和状态快照之间的关系。
- 能否正确使用 `useEffect`、`useMemo`、`useCallback`、`useRef` 和自定义 Hook。
- 能否按业务边界组织 feature、UI、data-access 和状态，而不是建立万能组件。
- 能否通过 Profiler、Bundle 分析、网络指标和真实压测证明性能优化有效。

### 3. 架构师或技术负责人

- 能否设计可演进的 React 应用架构，并明确状态、数据和依赖的所有权。
- 能否处理多团队协作、设计系统、共享库、微前端、版本升级和发布策略。
- 能否在 CSR、SSR、预渲染、Server Components 和纯客户端 SPA 之间做出有依据的选择。
- 能否把安全、可观测性、质量门禁、成本和回滚纳入整体设计。

### 4. 高分回答的通用框架

面对 React 架构题，可以依次说明：

1. **业务目标**：用户是谁，核心流程是什么，成功指标是什么。
2. **约束条件**：首屏性能、SEO、浏览器、流量、团队、交付周期和后端契约。
3. **状态边界**：哪些是本地 UI state，哪些是 URL state、server state 或共享业务 state。
4. **失败路径**：超时、重复提交、权限变化、刷新、网络中断和服务端错误怎么处理。
5. **验证与演进**：如何测试、监控、灰度和回滚，未来需求变化时哪里需要调整。

## 二、React 基础题

### Q1：React 是什么？它与传统模板引擎或 jQuery 有什么区别？

**核心回答：** React 是一个以组件为核心的 UI 库，使用声明式方式描述 UI 如何由当前状态产生。它将 UI 拆成可组合组件，通过 render 计算下一棵元素树，再把必要变化提交到宿主环境。

React 本身主要解决 UI 和组件模型，路由、数据请求、表单和服务端渲染通常由生态或上层框架提供。它的优势是组合性和生态灵活性，代价是架构决策更多。选型不能只看 JSX，应结合团队能力、应用生命周期、SEO、性能预算、框架能力和运维成本。

### Q2：React 应用的基本组成是什么？

- **Component**：输入 props，读取 state，并返回描述 UI 的 React element。
- **Props**：父组件传给子组件的只读输入。
- **State**：由组件或状态层拥有的可变业务或 UI 状态。
- **JSX**：把 UI 结构表达为 JavaScript/TypeScript 语法。
- **Hook**：让函数组件使用状态、上下文、引用和副作用能力。
- **Context**：在组件树中传递相对稳定的共享值。
- **Renderer**：把 React element 提交到 DOM、原生平台或其他宿主环境。

组件应保持聚焦。不要把所有 API 调用、缓存、权限、表单规则和布局细节堆进一个页面组件。

### Q3：函数组件和类组件有什么区别？

函数组件通过 Hooks 使用状态和生命周期相关能力，代码通常更容易组合。类组件通过实例、生命周期方法和 `this` 管理状态，在旧项目中仍然常见。

两者都可以表达 UI，但不能把函数组件理解成“每次 render 都创建一个新的组件实例”。函数组件是一次 render 的计算过程；Hooks 保持状态关联依赖的是调用顺序和 React 内部记录。新代码通常优先使用函数组件，但迁移旧类组件时应先覆盖行为和测试，不要只做机械语法替换。

### Q4：什么是 JSX？它和 HTML 有什么区别？

JSX 是一种编译为 React element 创建表达式的语法。它看起来像 HTML，但属性名、表达式、事件和组件规则由 JavaScript 和 React 决定。

- 使用 `className` 而不是 `class`。
- 属性值可以使用 `{}` 放入 JavaScript 表达式。
- 组件名通常以大写字母开头，原生标签使用小写字母。
- JSX 必须返回一个根节点或 fragment。
- `style` 接收对象，而不是 CSS 字符串。

```tsx
type GreetingProps = { name: string };

export function Greeting({ name }: GreetingProps) {
  return <h1 className="greeting">Hello, {name}</h1>;
}
```

JSX 只是表达 UI 的语法，不是模板字符串，也不能把任意字符串当作安全 HTML 执行。

### Q5：props 和 state 有什么区别？

- **Props**：由父组件拥有并传入，子组件不应直接修改。
- **State**：由组件或状态管理器拥有，通过更新函数产生新的状态快照。

props 描述组件从外部接收什么，state 描述组件需要记住什么。能由 props 或其他 state 计算出的值通常不应再次复制成 state，否则会产生同步问题。

### Q6：React 为什么强调单向数据流？

单向数据流意味着父组件通过 props 向下传值，子组件通过回调向上表达事件或用户意图。这样状态所有权清晰，更新路径容易追踪，也更容易测试和调试。

当多个组件需要同一状态时，可以把状态提升到最近公共父组件，或者建立明确作用域的 context、store 或 facade。不要为了省一个回调就把所有数据放到全局状态。

### Q7：React 中为什么不能直接修改 state？

直接修改 state 会破坏不可变更新和变更检测的假设，还可能让旧 render 的快照被悄悄改变。应通过 setter、reducer 或状态库提供的更新 API 产生新引用。

```tsx
setItems(currentItems => [...currentItems, newItem]);
```

如果嵌套对象很深，优先重新审视状态结构；可以使用 reducer 或不可变数据工具，但不能用工具掩盖不清晰的状态所有权。

### Q8：React 的 `key` 有什么作用？为什么不推荐使用数组索引？

`key` 用于帮助 React 识别列表项在不同 render 之间的稳定身份，从而正确复用、移动或销毁对应组件和 DOM。key 应来自业务上稳定且唯一的身份，例如数据库 ID。

数组索引在列表只追加且永不重排时可能工作，但在插入、删除、排序或过滤后，索引对应的身份会变化，导致输入状态、焦点、动画或局部 state 错配。

### Q9：React 事件和原生 DOM 事件有什么区别？

React 通过事件系统把事件处理接入组件树，并使用 JSX 属性传入函数，例如 `onClick={handleClick}`。事件处理函数不应在 render 中直接执行：`onClick={handleClick()}` 会在 render 阶段调用。

现代 React 已不应依赖旧版本事件池的行为。需要把事件对象异步保存时，仍应遵循当前版本文档和类型约束，而不是照搬旧的 `persist()` 经验。

### Q10：受控组件和非受控组件如何选择？

受控组件的值由 React state 管理，校验、条件显示和提交行为更可预测；非受控组件把当前值保存在 DOM，通过 ref 或 `FormData` 读取，代码更轻量，适合简单表单或高频输入场景。

复杂业务表单通常需要受控或由成熟表单库管理，但不必把每一次输入都复制到全局 store。大量字段和高频输入应测量 render 成本，并考虑字段级订阅、非受控策略或局部状态。

### Q11：条件渲染时 `&&` 有什么陷阱？

```tsx
{items.length && <ItemList items={items} />}
```

当 `items.length` 为 `0` 时，React 可能渲染数字 `0`，而不是“不渲染任何内容”。应使用显式布尔判断：

```tsx
{items.length > 0 && <ItemList items={items} />}
```

还要注意条件切换会导致组件挂载和卸载，局部 state、焦点、订阅和动画可能随之重置。

### Q12：`React.memo` 是什么？什么时候不应该使用？

`React.memo` 可以在 props 按比较规则没有变化时跳过函数组件的重新渲染，但它不是全局缓存，也不能阻止组件因自身 state 或读取的 context 变化而更新。

如果 props 每次 render 都创建新对象、数组或函数，浅比较仍然会失败。盲目包装所有组件会增加比较成本、认知成本和调试复杂度。先通过 Profiler 证明重复渲染是瓶颈，再结合稳定 props 或自定义比较函数使用。

## 三、组件、JSX 与渲染

### Q13：React render 阶段和 commit 阶段有什么区别？

**Render 阶段**负责根据当前 props、state 和上下文计算下一棵 React element 树。它应当是纯的，React 可以在并发模式下开始、暂停、重新执行或丢弃这次计算。

**Commit 阶段**负责把确定的变化应用到 DOM 或其他宿主环境，并执行相关提交后的逻辑。副作用不应放在 render 阶段，因为 render 可能被执行多次而不一定提交。

### Q14：为什么 React 组件 render 必须保持纯净？

同样的 props、state 和 context 应该得到相同的 UI 描述，且不修改外部可观察状态。纯 render 让 React 能够重试、并发、服务端渲染和开发模式检查。

不应在 render 中发请求、修改全局变量、写入 localStorage、订阅事件或直接操作 DOM。需要在提交后执行的同步应放在 effect，用户触发的动作应放在事件处理函数；但更好的选择往往是把数据请求放到路由或框架的数据层。

### Q15：React 为什么会重新渲染？重新渲染是否等于 DOM 更新？

组件可能因自身 state 更新、父组件 render、context 值变化、外部 store 通知或订阅的响应式数据变化而重新计算。重新渲染只意味着 render 函数重新执行，不代表真实 DOM 一定发生变化。

React 会比较新的 element 树和之前的结果，再在 commit 阶段应用必要 DOM 变化。性能优化重点是减少昂贵的计算和不必要的提交，而不是把所有 render 次数都压到零。

### Q16：为什么组件会因为父组件更新而重新渲染？

默认情况下，父组件 render 后，React 会继续计算子树，以确认子组件输出是否变化。即使子组件最终 DOM 不变，子组件函数仍可能执行。

可以通过合理组件边界、`memo`、稳定 props、局部状态和 selector 降低无意义计算。但如果父组件的更新本来就会改变子组件需要的数据，阻止 render 也没有意义。

### Q17：React 如何处理列表更新？

React 根据元素类型和 key 判断节点是否可以复用：类型和 key 稳定时通常复用对应实例；key 改变时，React 会把它视为新的组件身份，旧 state 和 DOM 会被销毁。

列表项应有稳定 key，列表渲染函数应避免在每一项中执行昂贵计算。大列表还要结合分页、虚拟化、窗口化和后端查询，不能只依赖 key。

### Q18：`Fragment` 有什么用途？

Fragment 允许组件返回多个兄弟节点而不额外插入 DOM 包装元素：

```tsx
return (
  <>
    <Header />
    <MainContent />
  </>
);
```

在列表中需要 key 时，应使用显式 `<Fragment key={item.id}>`，简写语法不能直接设置 key。

### Q19：Portal 适合什么场景？

Portal 可以把子树渲染到 DOM 的另一个位置，同时保留 React 树中的事件和上下文关系。它适合模态框、下拉菜单、tooltip、全局通知和需要突破 `overflow` 或 stacking context 的 UI。

使用 Portal 时仍要处理焦点陷阱、Esc 关闭、背景滚动、屏幕阅读器语义、卸载清理和服务端渲染兼容。Portal 不是解决组件层级混乱的通用手段。

### Q20：`children` 是什么？如何设计复合组件？

`children` 是组件调用方传入的 React node，可以是文本、元素、函数或多个节点。复合组件可以通过 children、context 和明确的子组件 API 组合出稳定的交互模型，例如 `Menu`、`MenuItem` 和 `MenuGroup`。

设计时要定义状态由谁拥有、子组件如何注册、键盘行为如何协调以及是否支持受控和非受控模式。不要通过读取内部 DOM 结构来推断子组件身份。

### Q21：如何避免 prop drilling？

先判断数据传递层级是否真的复杂。局部的 prop drilling 有时最显式、最容易理解；跨多层的主题、认证用户或 feature 配置可以使用 Context；复杂、频繁更新或需要精确订阅的业务状态可以使用 store 或 facade。

Context 解决的是传递依赖，不自动解决状态管理、缓存、异步请求或性能隔离。把一个频繁变化的大对象放到单一 context 中，可能导致大量消费者更新。

### Q22：如何设计一个可复用的 Modal 组件？

先定义受控契约：`open`、`onClose`、关闭原因、标题、内容、操作区、加载态和错误态。Modal 内部负责语义、焦点、Esc、遮罩点击、滚动锁定和 Portal；业务页面负责提交和业务规则。

要支持键盘和屏幕阅读器，设置正确的 dialog 角色、标题关联和焦点返回。不能只实现一个带遮罩的 `div` 就称为可复用弹窗。

## 四、Hooks 与副作用

### Q23：Hooks 的调用规则是什么？为什么不能在条件语句中调用？

Hooks 必须在组件或自定义 Hook 的顶层调用，不能放在条件、循环、嵌套函数或事件处理函数中。React 依赖 Hooks 每次 render 的调用顺序关联对应状态；顺序改变会让状态错位。

```tsx
function Panel({ enabled }: { enabled: boolean }) {
  const [count, setCount] = useState(0);

  if (!enabled) {
    return null;
  }

  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

条件应包裹 Hook 使用后的逻辑，或拆分成两个组件，而不是条件调用 Hook。

### Q24：`useState` 的更新为什么可能不是立即生效？

state 更新是对后续 render 的请求，不是同步修改当前 render 已捕获的变量。React 可能批量处理多个更新，因此当前事件函数中的 state 仍然是当前 render 的快照。

需要基于前一个值更新时，使用函数式更新：

```tsx
setCount(currentCount => currentCount + 1);
```

这能正确表达更新依赖，也能避免在批量更新、异步回调或并发调度中读取过期值。

### Q25：什么是 React state snapshot？

每次 render 都会得到一份独立的 props、state 和事件处理函数闭包。事件处理函数看到的是创建它的那次 render 的快照，而不是某个可以随时变化的实例变量。

理解快照可以解释异步回调读到旧值、连续 `setState` 的结果和函数式更新的必要性。需要获取最新可变值时可以考虑 ref，但 ref 不会自动触发 render，不能把它当作普通 UI state。

### Q26：`useEffect` 用来做什么？

Effect 用于把 React 与外部系统同步，例如订阅事件、连接 WebSocket、调用非 React UI 库、更新浏览器 API 或发起确实需要由组件生命周期触发的请求。

它不是“所有业务逻辑的生命周期容器”。能在 render 中计算的派生值不应放 effect；由用户操作触发的动作通常应放事件处理函数；框架支持的数据加载应优先使用框架约定的数据层。

### Q27：`useEffect` 的依赖数组如何理解？

依赖数组描述 effect 使用的响应式值。当依赖变化时，React 会先执行上一次 effect 的 cleanup，再执行新的 effect。依赖应反映 effect 读取的外部值，而不是为了消除警告随意删除。

- 没有依赖数组：每次提交后运行。
- 空数组：在该组件实例生命周期中只在挂载后运行一次，但开发模式可能有额外检查。
- 有依赖：依赖变化后重新运行。

如果依赖不断变化，先检查对象和函数是否在 render 中无意义地重新创建，再考虑拆分 effect 或重新设计状态流。

### Q28：如何处理 `useEffect` 中的竞态条件？

搜索或详情请求可能在用户改变参数后乱序返回。可以在 cleanup 中标记失效、使用 AbortController 取消请求，或由数据请求库管理请求身份和缓存。

```tsx
useEffect(() => {
  const controller = new AbortController();

  fetch(`/api/users/${userId}`, { signal: controller.signal })
    .then(response => response.json())
    .then(data => setUser(data))
    .catch(error => {
      if (error.name !== 'AbortError') {
        setError(error);
      }
    });

  return () => controller.abort();
}, [userId]);
```

取消客户端等待不一定取消服务端已经处理的请求，因此写操作仍需要幂等和版本保护。

### Q29：`useLayoutEffect` 和 `useEffect` 有什么区别？

`useEffect` 通常在浏览器绘制后执行，适合不阻塞绘制的同步工作；`useLayoutEffect` 在 DOM 提交后、浏览器绘制前同步执行，适合读取布局并在用户看到画面前修正位置。

`useLayoutEffect` 会阻塞绘制，使用过多会降低首屏和交互性能，且在 SSR 环境需要特别处理。只有确实存在布局闪烁或测量依赖时才使用它。

### Q30：`useRef` 和 `useState` 如何选择？

- `useState`：值变化需要驱动 UI 更新。
- `useRef`：保存跨 render 的可变引用，但变化不需要触发 UI 更新。

常见 ref 用途包括 DOM 节点、定时器 ID、上一次值、外部实例和取消控制器。不要用 ref 偷偷存储页面显示状态，否则 UI 可能与数据不一致。

### Q31：`useMemo` 和 `useCallback` 解决什么问题？

`useMemo` 缓存计算结果，`useCallback` 缓存函数引用。它们的主要价值是避免昂贵计算或配合依赖引用稳定的 `memo` 子组件，而不是让普通代码“更快”。缓存本身也有比较和内存成本。

```tsx
const visibleItems = useMemo(
  () => filterItems(items, query),
  [items, query]
);

const handleSelect = useCallback(
  (id: string) => onSelect(id),
  [onSelect]
);
```

如果依赖每次都变化，缓存不会带来收益。现代 React Compiler 或框架优化可能自动处理部分 memoization，项目应按实际工具链决定是否手写。

### Q32：什么是 stale closure？如何避免？

闭包捕获的是创建它的 render 的变量。如果定时器、事件监听或异步回调长期存在，它可能继续读取旧的 state 或 props。

处理方式包括：使用函数式 state 更新、正确声明 effect 依赖、在 effect 中重建订阅、使用 ref 保存最新值，或采用当前 React 版本提供的事件回调能力。不要通过关闭 ESLint Hooks 规则隐藏依赖问题。

### Q33：什么是自定义 Hook？如何设计？

自定义 Hook 是以 `use` 开头、封装状态逻辑和副作用的函数。它共享的是逻辑，不是同一个 state 实例；每次调用都拥有自己的 Hook 状态，除非底层连接到共享 store。

好的自定义 Hook 应有明确输入输出、处理加载和错误状态、声明副作用所有权，并且不把页面布局或业务组件渲染硬编码进去。

### Q34：`useReducer` 适合什么场景？

当状态转换多、字段之间有联系、事件类型明确或希望把状态转换写成可测试纯函数时，`useReducer` 比多个互相依赖的 `useState` 更清晰。

```tsx
type State = { status: 'idle' | 'saving' | 'error'; message?: string };
type Action =
  | { type: 'saveStarted' }
  | { type: 'saveSucceeded' }
  | { type: 'saveFailed'; message: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case 'saveStarted':
      return { status: 'saving' };
    case 'saveSucceeded':
      return { status: 'idle' };
    case 'saveFailed':
      return { status: 'error', message: action.message };
  }
}
```

Reducer 不是自动的全局状态管理器。它仍然需要明确作用域和副作用编排位置。

### Q35：`useEffectEvent` 适合解决什么问题？

在支持该能力的 React 版本中，Effect Event 可以让 effect 使用最新的非响应式逻辑，同时不因为该逻辑引用的普通值变化而重新建立外部订阅。它适合把“订阅何时重建”和“回调执行时读取什么最新值”分开。

它不是让任意 effect 忽略依赖的工具，也不能代替正确的状态建模。使用前要确认项目 React 版本、lint 规则和框架支持情况。

## 五、状态管理与数据流

### Q36：React 中有哪些状态类型？

至少应区分：

- **Local UI state**：弹窗、展开项、输入草稿、hover 和当前 tab。
- **URL state**：分页、筛选、排序、搜索词和可分享的页面视图。
- **Server state**：由后端拥有、需要缓存、重试、失效和重新验证的数据。
- **Session state**：登录身份、租户、权限和用户偏好。
- **Shared client state**：多个 feature 共享且由前端拥有的工作流状态。
- **Derived state**：由其他状态计算出的值，不应重复存储。

分类后才能决定使用组件 state、Context、URL、数据请求库还是全局 store。

### Q37：什么时候使用 Context？

Context 适合向深层组件提供主题、语言、认证用户、feature 配置或相对稳定的依赖。它可以避免逐层传递，但消费者会受到 provider value 变化的影响。

如果 Context value 是一个频繁变化的大对象，可能让大量组件更新。可以拆分 context、稳定 value、使用 selector store 或把高频状态放在更接近消费者的位置。

### Q38：Context 和全局状态管理库有什么区别？

Context 是 React 的依赖传递机制；状态管理库通常还提供事件模型、选择器、持久化、中间件、开发工具、异步流程和精确订阅。Context 本身不负责缓存失效、请求重试或复杂状态转换。

小范围共享状态优先保持简单。只有当跨路由共享、更新来源多、状态转换复杂或调试收益明显时，才引入更完整的 store。

### Q39：Server State 和 Client State 为什么不能混为一谈？

Server state 的真实来源在服务端，具有缓存、过期、重新验证、分页、竞态和乐观更新等特征；client state 由浏览器当前会话拥有，通常不需要和服务端自动同步。

把所有 API 响应复制到全局 Redux 类 store，容易产生重复缓存、失效困难和陈旧数据。应让专门的数据请求层管理 server state，把页面 UI 状态留在组件或 feature store 中。

### Q40：Redux 的核心思想是什么？

Redux 通过单一 store、不可变 state、action 和纯 reducer 表达状态变化，强调可预测的更新和可追踪的事件。现代 Redux 推荐使用 Redux Toolkit，减少样板代码并提供更安全的默认配置。

Redux 不会自动解决服务端缓存、组件拆分或所有异步问题。要明确 action 的业务语义、状态归属、selector 边界和持久化策略，避免建立一个包含所有 API 原始响应的巨型 store。

### Q41：如何设计 selector？

Selector 应从状态中读取稳定、最小且符合业务语义的数据。派生计算可以通过记忆化避免重复计算，但必须保证输入和输出契约清楚。

不要让组件直接了解 store 的深层结构，也不要在组件中到处拼接多个原始字段。selector 可以成为状态层和 UI 层之间的稳定边界，方便重构和测试。

### Q42：乐观更新如何设计？

乐观更新先更新 UI，再发送命令；成功时确认，失败时回滚或显示冲突状态。必须保存足够的前置状态或使用可逆操作，并处理重复提交、请求超时、权限变化和服务端版本冲突。

收藏、点赞适合简单乐观更新；涉及库存、支付或权限的操作不能只相信前端结果。服务端仍是事实来源，前端需要重新验证或重新拉取最终状态。

### Q43：如何处理数据请求的加载、错误和缓存？

数据层应明确请求状态，而不是只返回一个可能为 `undefined` 的数据字段：

```ts
type RequestState<T> =
  | { status: 'idle' }
  | { status: 'loading'; data?: T }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error; data?: T };
```

还要定义缓存 key、TTL、失效、重试、取消、请求去重、分页和错误恢复。空数组、加载中和加载失败不能都展示成“暂无数据”。

### Q44：如何处理表单状态？

简单表单可使用局部 state 或非受控表单；复杂表单应使用成熟表单库或 reducer，明确字段值、dirty、touched、校验、异步校验、提交和服务端错误。

不要把每个键盘输入都同步到全局 store，除非确实需要跨页面恢复或协同编辑。提交动作要处理重复点击、网络失败、部分成功、离开确认和重新加载恢复。

### Q45：如何组织大型 React 项目的目录？

推荐按业务 feature 组织，而不是把所有组件、hooks 和 services 分别放在全局目录：

```text
src/
  app/
    providers/
    routes/
    layouts/
  shared/
    ui/
    hooks/
    lib/
  features/
    orders/
      pages/
      ui/
      model/
      api/
      routes.tsx
  entities/
    user/
```

`shared` 放真正跨业务复用的能力，`features` 内聚业务用例，`api` 负责数据访问和转换。目录只是结果，真正重要的是依赖方向：shared 不应依赖具体 feature，UI 不应绕过数据层直接复制鉴权和缓存逻辑。

## 六、并发渲染与现代 React

### Q46：React 18 的并发渲染是什么？

并发渲染不是让 JavaScript 同时在多个线程执行，而是让 React 能够把更新分成不同优先级，暂停、继续或放弃某次 render，以保持交互响应。

并发能力要求 render 保持纯净，因为一次计算可能没有 commit 就被丢弃。它不会自动让所有代码更快，也不能替代减少计算、优化网络和控制 DOM 数量。

### Q47：`startTransition` 和 `useTransition` 适合什么场景？

它们用于把不紧急的 UI 更新标记为 transition，例如搜索结果、复杂列表或标签页内容更新，让输入、点击和反馈优先保持响应。

```tsx
const [isPending, startTransition] = useTransition();

function handleQueryChange(value: string): void {
  setQuery(value);
  startTransition(() => {
    setFilter(value);
  });
}
```

transition 不是防抖、不是取消网络请求，也不能解决算法复杂度。被标记的更新仍然可能执行，数据层仍需处理竞态和请求取消。

### Q48：`useDeferredValue` 适合什么场景？

`useDeferredValue` 可以让一个非紧急的值落后于高优先级输入，适合把搜索输入与大型结果列表解耦。它不会阻止计算，也不会自动缓存结果。

如果瓶颈来自每次输入都触发后端请求，还需要防抖、请求取消或数据请求库；如果瓶颈来自列表渲染，还需要虚拟化和组件拆分。

### Q49：什么是 Suspense？

Suspense 提供一个声明式的加载边界：当其子树暂时不能完成渲染时，React 可以展示 fallback，并在内容准备好后恢复。它可以用于代码分割，也可由支持 Suspense 的数据框架使用。

Suspense 不是把任意 `fetch` 放进组件就自动获得完整缓存和错误处理。要明确数据框架、缓存、错误边界、fallback 层级、SSR 流式传输和重复请求策略。

### Q50：Suspense boundary 应该如何划分？

边界应与用户感知的独立加载区域对应，例如页面壳、主内容、侧栏和非关键推荐区。过大的 boundary 会让一个慢请求阻塞整页，过小的 boundary 会产生大量闪烁和 loading 结构。

fallback 应保持布局稳定，避免 CLS；错误边界应与恢复动作匹配，例如重试当前区域，而不是每次都刷新整个应用。

### Q51：什么是 Error Boundary？

Error Boundary 可以捕获其子树渲染、生命周期或构造过程中的错误，并展示降级 UI。它不能捕获事件处理函数、异步回调、服务端渲染错误或 Boundary 自身的错误，除非由框架额外处理。

错误边界应按恢复范围划分：页面级、feature 级和组件级。记录错误时要包含应用版本、路由、用户操作上下文和关联请求 ID，同时避免记录 token 和敏感表单内容。

### Q52：自动批量更新是什么？

现代 React 会在更多异步上下文中合并多个 state 更新，减少重复 render。不要依赖某一次更新是否立即提交来编写业务逻辑；当更新依赖前一状态时，始终使用函数式更新。

批量更新不代表多个业务命令自动具备事务语义。跨请求、跨 store 或跨页面的业务一致性仍需要明确的状态机和后端契约。

### Q53：React Compiler 解决什么问题？

React Compiler 旨在通过分析组件和 Hook 的代码，自动进行部分 memoization，减少手写 `useMemo`、`useCallback` 和 `memo` 的需求。是否使用取决于项目 React 版本、构建配置、代码约束和库兼容性。

Compiler 不是性能免责卡。副作用、可变数据、依赖不完整和不纯 render 仍然是问题；上线前要通过构建、测试、Profiler 和真实指标验证。

### Q54：如何理解 React Strict Mode？

Strict Mode 是开发期检查工具，会帮助发现不纯 render、过时 API、缺少 cleanup 等问题。开发环境中某些逻辑可能被额外调用或挂载清理再挂载，以暴露不安全副作用；这不等同于生产环境行为。

正确做法是让 render 幂等、effect 有完整 cleanup、请求和订阅具备可取消或去重策略，而不是简单关闭 Strict Mode 来隐藏问题。

## 七、React 架构设计

### Q55：如何设计大型 React 应用的架构分层？

可以采用以下逻辑分层：

1. **展示层**：纯 UI 组件、布局、可访问性和交互事件。
2. **用例层**：页面流程、表单提交、加载态和用户意图编排。
3. **数据访问层**：HTTP、缓存、序列化、DTO 转换和错误映射。
4. **领域层**：业务规则、状态转换和与 UI 无关的模型。
5. **基础设施层**：认证、配置、日志、Feature Flag 和监控。

不要求每个 feature 都机械地建立五层，但依赖方向要清楚。组件不应各自实现 token 刷新、缓存和错误映射，页面也不应直接依赖后端深层 DTO。

### Q56：Facade 模式在 React 中解决什么问题？

Facade 为页面或 feature 提供稳定的业务入口，隐藏多个 API、状态流和副作用的组合。例如页面只调用 `loadOrders()` 和 `approveOrder()`，不需要知道请求、缓存、刷新和错误映射细节。

Facade 不应变成上帝对象。如果一个 facade 同时管理多个不相关业务流程，应按用例或子领域拆分。好的 facade 让调用者表达业务意图，让内部实现可以独立演进。

### Q57：如何设计 React 组件边界？

按职责和变化原因拆分，而不是按 JSX 行数拆分。常见边界是：

- **Page / Container**：负责路由参数、页面级状态和用户流程。
- **Feature**：负责一个业务用例，例如订单编辑或报表筛选。
- **Presentational UI**：通过 props 和回调工作，不直接访问后端。
- **Data access / Facade**：封装查询、命令、缓存和状态组合。
- **Shared UI**：提供稳定、可访问、与具体业务无关的组件。

拆分后应能独立测试、独立理解，并且不会因为一个字段变化而牵动大量无关组件。

### Q58：如何设计可复用组件库？

组件库应有稳定的公共 API、设计 token、无障碍规范、主题机制、文档、示例、变更日志和兼容策略。组件应避免依赖某个业务 feature，props 和回调要表达语义而不是暴露内部 DOM。

重点验证键盘操作、焦点管理、屏幕阅读器、表单状态、RTL、响应式、错误态和动态内容。共享库的最大成本通常不是第一次开发，而是跨团队维护和破坏性变更协调。

### Q59：如何选择 React 状态管理方案？

先按状态类型和生命周期选择：局部 UI state 留在组件，URL state 放 URL，server state 交给数据请求库，跨 feature 且复杂的 client state 才使用 store。

比较方案时关注类型安全、selector、异步处理、调试工具、持久化、Bundle、团队习惯和迁移成本。不要为了项目“看起来专业”而给一个简单表单引入完整全局 store。

### Q60：如何设计 React 微前端？

先确认微前端解决的是组织和独立交付问题，而不是单纯的组件复用。需要明确主应用与子应用的路由、认证、权限、菜单、错误边界、依赖共享和独立回滚。

还要设计 React 版本策略、设计系统、主题、国际化、公共 API、事件契约和可观测性。跨子应用共享可变状态会增加耦合；能通过 URL、后端或明确事件传递的数据，不要默认放入共享单例。

### Q61：如何处理前后端 API 契约？

建议使用 OpenAPI、代码生成或共享 schema 定义请求和响应，明确字段可选性、分页、排序、错误格式、版本策略和幂等语义。

- DTO 不一定等同于领域模型或页面模型。
- 数据访问层负责转换和兼容旧字段。
- 对破坏性变更建立契约测试。
- 错误响应应包含稳定的机器可读 code 和可展示 message。

不要让 JSX 直接依赖后端返回的深层结构，否则后端小改动会传播到大量组件。

### Q62：如何设计登录、权限和路由保护？

认证解决“你是谁”，授权解决“你能做什么”。前端路由保护只能改善导航体验，不能替代服务端授权；任何 API 都必须在服务端重新验证身份、权限、租户和资源归属。

前端应统一处理 token 生命周期、登录过期、无权限页面、回跳地址校验、加载态和登出清理。权限模型最好使用能力或权限 code，而不是在 JSX 中散落角色字符串和业务判断。

### Q63：如何实现可配置菜单和权限按钮？

将菜单、路由元数据和权限能力建立清晰映射，由统一的权限服务或 hook 判断。按钮级权限是用户体验控制，不是安全控制。

配置应支持隐藏、禁用、无权限提示和异步权限加载，且不能把服务器下发的任意字符串直接当作组件、脚本或可执行代码。

### Q64：如何做国际化和主题切换？

国际化需要考虑翻译资源加载、复数规则、日期数字格式、时区、RTL、文本扩展和动态内容。不要通过字符串拼接构造句子，应让翻译资源控制完整语句。

主题切换可使用 CSS custom properties 配合设计 token，并处理初始化闪烁、系统主题、对比度和第三方组件适配。主题 token 应有命名规则和所有权，避免业务页面直接依赖组件库内部 CSS 类名。

## 八、性能优化

### Q65：React 性能问题应该如何排查？

先测量再优化：

1. 区分首屏、交互响应、路由切换、列表滚动和后台请求性能。
2. 使用 React DevTools Profiler、浏览器 Performance、Lighthouse 和构建统计定位瓶颈。
3. 查看 commit 耗时、组件 render 数量、长任务、Bundle 体积、网络瀑布和内存增长。
4. 每次只改变一个主要因素，并在代表性设备和网络下复测。

常见根因包括大列表 DOM、父组件级联 render、重复请求、过大的初始 chunk、图片和字体、模板计算、无界缓存以及第三方脚本。

### Q66：`React.memo`、`useMemo` 和 `useCallback` 应该如何组合？

先找出昂贵子树或昂贵计算，再考虑稳定 props 和引用。`memo` 只有在 props 比较能够复用结果时才有价值；`useCallback` 只有在函数作为稳定依赖或传给 memo 子组件时才有意义；`useMemo` 只有在计算或引用稳定确实节省成本时才有意义。

三者一起滥用会增加代码复杂度和比较成本。React Compiler 可用时还要遵循团队约定，避免手写优化与自动优化互相干扰。

### Q67：如何优化大列表？

- 使用稳定 key，避免索引作为长期身份。
- 使用服务端分页、筛选和排序，限制一次传输的数据量。
- 需要大量行时使用虚拟列表或窗口化，并处理动态行高和键盘访问。
- 避免每一行创建昂贵计算、重复订阅和不必要对象。
- 只在确实需要时渲染详情、菜单和操作面板。

虚拟列表不是所有列表的默认答案。它会影响滚动定位、SEO、复制、可访问性和动态高度，需要用真实交互验证。

### Q68：如何减少初始 Bundle 体积？

- 按路由或 feature 做 lazy loading 和动态 import。
- 检查构建统计，移除未使用依赖和重复库。
- 避免在根入口导入仅少数页面使用的大型库。
- 选择合适的预加载策略，平衡下一步导航和网络占用。
- 优化图片、字体、source map 发布策略和缓存头。

不要只追求 Bundle 数字。还要关注真实用户的 LCP、INP、CLS、TTFB、错误率和业务完成时间。

### Q69：如何设计缓存和请求去重？

先区分缓存对象：静态资源、配置、查询结果、用户会话、权限和表单草稿的有效期与一致性要求不同。

- HTTP 缓存优先解决静态资源和可缓存 GET。
- 数据请求层负责 key、TTL、失效、重试、分页和共享请求。
- 用户或租户敏感数据不能无边界地存入共享缓存。
- 写操作后要明确失效、局部更新还是重新查询。
- `share promise` 或请求去重不能把非幂等命令错误合并。

缓存不是免费加速器。陈旧数据、登出后的残留数据、内存增长和跨标签页不一致都要纳入设计。

### Q70：如何避免 Context 导致的大范围更新？

拆分不同职责的 context，避免把高频变化数据和低频配置放在同一个 provider value 中。可以将 provider value 拆成稳定引用，或者使用 selector store，让消费者只订阅需要的字段。

更根本的方式是把状态放到最接近消费者的边界，减少不必要的全局依赖。不要只通过 `useMemo` 包装一个包含频繁变化字段的大对象，就认为更新问题已经解决。

### Q71：如何优化表单输入性能？

先确认是整个页面因每次输入 render，还是单字段校验、派生计算、网络请求或第三方控件变慢。可以使用字段级订阅、局部 state、非受控输入、延迟非关键更新和防抖查询。

不要为了性能完全放弃受控模型；复杂校验和可恢复草稿仍然需要明确状态。应通过 Profiler 和真实设备确认优化没有破坏输入体验、校验和无障碍。

### Q72：如何处理内存泄漏？

检查 effect cleanup、事件监听、WebSocket、定时器、Observer、Portal、第三方插件和缓存。离开页面时，组件拥有的资源应被释放；全局资源则要有明确的生命周期和订阅管理。

通过重复进入退出页面、切换路由、执行关键流程和对比 heap snapshot 定位保留路径。不要仅通过刷新页面或增加浏览器内存规避问题。

### Q73：React 应用如何做可观测性？

至少需要：

- 前端错误：错误类型、版本、路由、用户操作上下文和关联请求 ID。
- 性能指标：导航、资源加载、Core Web Vitals、API 延迟和长任务。
- 业务指标：登录成功、提交成功、失败原因和关键流程耗时。
- 网络诊断：状态码、重试、超时、后端 trace ID。

日志要脱敏，不记录 token、密码、完整个人信息或不必要的表单内容。前端监控应支持采样、版本关联和 source map 管理。

## 九、路由、SSR 与 Server Components

### Q74：React Router 的核心概念有哪些？

React 本身不内置业务路由，常由 React Router 或上层框架提供。核心概念包括 URL 与组件映射、嵌套路由、路径参数、查询参数、导航、懒加载、错误边界和数据加载。

路由应按 feature 组织，使用 lazy loading 隔离业务 chunk。页面数据加载要区分必须阻塞导航的数据和可以进入页面后渐进加载的数据。

### Q75：路由级权限保护应该怎么做？

路由保护可以阻止未登录用户进入页面、展示 loading 或引导到无权限页，但它只是客户端体验控制。API 和资源操作必须由后端验证身份、权限、租户和资源归属。

还要处理登录回跳地址校验、权限异步加载、权限过期、刷新、浏览器前进后退和多标签页登出。不要把权限判断散落在每个按钮和页面分支里。

### Q76：CSR、SSR、预渲染和 React Server Components 如何选择？

- **CSR**：浏览器下载 JavaScript 后渲染，适合内部系统和 SEO 不重要的应用。
- **SSR**：服务端生成请求对应的 HTML，有利于首屏和 SEO，但要处理服务端运行时、缓存、请求隔离和 hydration。
- **预渲染**：构建时生成页面，适合内容相对稳定的公开页面。
- **Server Components**：在支持的框架中，部分组件只在服务端运行并把结果或可序列化边界交给客户端，可减少客户端 JavaScript，但要求遵守服务端和客户端组件边界。

选择取决于 SEO、首屏性能、内容更新频率、服务端成本、数据隐私、部署环境和团队经验。不能把“SSR”或“Server Components”当作自动性能优化。

### Q77：Server Components 和 Client Components 的边界是什么？

Server Component 可以访问服务端资源和安全环境，通常不能使用浏览器 API、交互 state 或事件处理；Client Component 才负责浏览器交互、Hooks、事件和客户端状态。具体边界由所用框架定义。

服务端组件向客户端传递的数据必须可序列化，不能随意传函数、数据库连接或服务端对象。应把交互尽量限制在需要的叶子节点，避免整个页面因一个按钮变成客户端组件。

### Q78：SSR 或 RSC 中如何避免数据泄漏？

服务端请求必须按用户和请求隔离，不能把用户数据、token 或数据库结果放进跨请求共享的模块级变量。缓存 key 要包含租户、用户或权限维度，公共缓存不能误缓存私有响应。

传到客户端的数据应经过最小化和序列化，只暴露 UI 真正需要的字段。错误信息、日志、HTML 和 source map 也不能泄漏凭据或内部系统细节。

### Q79：什么是 hydration？常见问题有哪些？

Hydration 让客户端复用服务端生成的 DOM 并接管交互，而不是无条件重新创建全部 DOM。服务端和客户端对初始 UI 的判断必须一致。

常见问题是服务端和客户端时间、随机值、地区格式、用户状态或浏览器 API 不一致，导致 hydration mismatch。修复方向是稳定初始数据、延迟浏览器专属内容、传递服务端状态并避免渲染期副作用。

### Q80：React 应用如何部署和回滚？

构建产物应使用内容哈希，静态资源设置长期缓存，入口 HTML 设置较短缓存或重新验证。部署需要保证入口文件引用的资源版本存在，避免新旧 HTML 与资源错配。

回滚时应考虑服务端 API 兼容性、缓存清理、SSR 节点版本、Feature Flag、source map、监控告警和数据库迁移。前端发布不是只把构建目录复制到服务器。

## 十、安全、测试与工程化

### Q81：React 如何防范 XSS？

React 对普通 JSX 文本和属性会进行转义，降低直接注入风险。风险通常来自 `dangerouslySetInnerHTML`、不可信 URL、第三方 HTML、服务端拼接 HTML、富文本转换和绕过安全处理。

- 尽量使用普通文本和属性绑定，不拼接 HTML。
- 富文本必须经过可信 sanitizer，并限制允许的标签、属性和 URL 协议。
- 不要把用户输入放进脚本、样式或资源 URL 上下文。
- 配置 CSP、Trusted Types 和服务端输出编码。
- 前端校验只是体验优化，后端必须重新校验和授权。

### Q82：JWT 放在哪里？如何回答更严谨？

没有对所有应用都正确的单一答案。`localStorage` 容易受到 XSS 读取；HttpOnly cookie 不能被 JavaScript 读取，但要设计 CSRF 防护、SameSite、Secure、域和过期策略。还需要考虑刷新 token、撤销、跨标签页登出和 SSR。

关键是说明威胁模型和完整方案，而不是简单说“JWT 一定放 localStorage”或“一定放 cookie”。敏感 token、日志和错误上报都必须避免泄漏。

### Q83：单元测试、集成测试和端到端测试如何分工？

- **单元测试**：验证纯函数、格式化、selector、reducer、Hook 局部逻辑和组件行为，反馈快。
- **集成测试**：验证组件、Context、路由、数据请求 mock 和状态组合。
- **端到端测试**：验证真实用户流程、权限、跨页面跳转和关键业务。

测试应关注公开行为而非内部实现。不要为了提高覆盖率大量断言私有 state、Hook 调用次数或 React 内部细节。

### Q84：React Testing Library 的测试原则是什么？

优先通过用户可感知的角色、文本、标签、键盘和交互查询元素，而不是依赖组件内部 class、实现细节或测试专用属性。测试应验证页面在用户操作后展示了什么、能做什么。

网络请求可以使用请求拦截或 mock server，覆盖成功、加载、空数据、401、403、404、429 和 5xx 路径。不要让测试依赖真实生产服务。

### Q85：如何测试异步组件和 Suspense？

测试加载、成功、空态、错误、重试和取消等用户可见状态。使用 `findBy`、`waitFor` 或框架提供的异步工具时，要确保等待的是明确的结果，而不是任意延时。

对于 Suspense，要验证 fallback 不会遮挡不相关区域、内容出现后布局稳定、错误边界能恢复，并覆盖开发模式下 effect cleanup 和重复执行可能暴露的问题。

### Q86：如何测试自定义 Hook？

从使用者角度验证初始值、事件更新、异步状态、错误、清理和重新挂载。若 Hook 只是纯计算，直接测试纯函数比渲染 Hook 更简单；若依赖 context，应通过最小测试 provider 注入依赖。

不要只断言 Hook 内部调用了多少次 `useEffect` 或 `setState`，这些都是可变实现细节。

### Q87：如何提升 React 项目的代码质量？

- 启用严格 TypeScript 和合理的 JSX 类型检查。
- 使用 ESLint Hooks 规则、格式化、预提交检查和 CI 质量门禁。
- 建立组件库公共 API、可访问性和变更日志。
- 对高风险页面配置 E2E、视觉回归和性能预算。
- 对 React、框架、TypeScript、构建器和状态库升级时阅读兼容矩阵并分阶段验证。

代码质量不是工具数量，而是团队能否及时发现错误、理解改动影响并可靠发布。

### Q88：如何升级一个大型 React 项目？

先建立当前 React、React DOM、框架、Node、TypeScript、构建器、状态库和浏览器支持矩阵，记录构建、测试、Bundle 和关键页面基线。然后按官方迁移路径处理弃用 API、Strict Mode 问题、依赖兼容和构建变化。

每一步都应有：

1. 可重复的构建和测试。
2. 关键页面的 E2E 或人工验收。
3. Bundle、Core Web Vitals 和错误率对比。
4. 回滚方案和兼容窗口。

不要在同一个改动中同时升级框架、重写状态管理、迁移 SSR 和重构目录，除非有明确的拆分策略。

### Q89：如何设计前端 CI/CD？

CI 至少应包含依赖安装锁定、类型检查、Lint、单元测试、构建、Bundle 预算和关键 E2E。CD 应支持环境配置校验、预览部署、灰度或 Feature Flag、静态资源缓存策略和快速回滚。

生产构建要固定依赖和 Node 版本，避免本地可用而 CI 失败。发布后需要把版本和 source map 关联到错误监控，以便定位线上问题。

### Q90：React 应用如何管理环境配置？

区分构建时配置和运行时配置，明确哪些值可以公开。前端 Bundle 中的变量都可能被用户读取，不能放入密钥、私有 token 或后端凭据。

运行时配置可通过受保护接口或部署生成的配置文件注入，并校验 schema、默认值和版本。API 地址、Feature Flag 和监控配置要支持环境隔离和回滚。

## 十一、高频场景题

### Q91：用户连续点击“提交订单”三次，React 前端如何处理？

前端在提交过程中禁用按钮、使用状态机或忽略重复命令，防止重复触发；但这只能改善客户端行为。服务端必须使用幂等键、业务唯一约束或状态机防止重复创建。请求超时后不能简单重试非幂等写操作，应先查询订单状态或使用幂等重试。

回答时补充按钮恢复时机、错误提示、网络断开、页面刷新、重复响应和审计日志如何处理。

### Q92：搜索结果返回乱序，页面展示了旧结果，如何解决？

使用请求取消、请求版本或数据请求库的 query key，让新查询不会被旧响应覆盖。可以用防抖减少请求，用 `useDeferredValue` 或 transition 保持输入响应，但它们不能代替请求竞态处理。

后端已经处理的请求可能仍在运行，因此服务端或客户端必须丢弃过期响应；写操作还需要幂等和版本保护。

### Q93：登录 token 过期时多个请求同时返回 401，如何避免刷新风暴？

使用单例认证服务维护一个正在进行的刷新 Promise 或请求，让其他请求等待同一刷新结果。刷新成功后重放原请求；刷新失败则清理会话并跳转登录；刷新接口自身不能再次进入同样的重试逻辑。

必须限制重试次数，避免 401、刷新、重放之间形成无限循环，并处理并发登出和跨标签页状态同步。

### Q94：一个页面首屏很慢，你会如何定位？

先用真实设备和网络确认是 TTFB、JavaScript 下载、脚本执行、渲染、图片字体还是后端 API。再检查初始 chunk、路由是否懒加载、是否存在阻塞数据加载、重复请求、大量同步计算和第三方脚本。

优化方案要与证据对应：拆分 chunk、调整预加载、延迟非关键组件、压缩媒体、缓存 API 或改进后端查询。上线后比较 LCP、INP、错误率和业务转化，而不是只看本地 Lighthouse。

### Q95：一个列表有十万条数据，如何设计？

通常不把十万条一次性返回和渲染。先确定用户是否需要全量数据；优先使用服务端分页、筛选、排序和导出任务。页面使用虚拟列表或有限窗口，并提供加载、空态、错误、定位和可访问性。

如果必须本地处理全量数据，应评估内存、Worker、分块处理、取消和弱设备体验，并设置明确的数据上限。

### Q96：两个页面需要共享筛选条件和结果，怎么做？

先判断状态范围和生命周期。如果只在一个流程内共享，用 feature store 或 URL query params；如果需要刷新后恢复，考虑 URL、session storage 或服务端草稿；如果多个区域实时联动且逻辑复杂，再使用受约束的状态 store。

不要为了“共享”把状态直接放根级 context 或 store 并永久保留。需要定义清理、回退、浏览器前进后退和权限变化时的行为。

### Q97：如何设计离线和网络恢复？

区分可缓存读取、可离线编辑和不可离线操作。读取可使用 Service Worker 或本地缓存；编辑需要本地队列、冲突策略、版本号、重试和用户可见的同步状态；敏感操作通常要求在线确认。

网络恢复后不能无条件重放所有命令。要处理过期权限、重复提交、服务端状态变化和用户取消，并提供人工解决冲突的入口。

### Q98：如何把一个 React 单体拆成多团队可协作的系统？

先按业务边界和发布责任拆 feature，再建立依赖规则、公共库所有权、API 契约、设计系统和 CI 门禁。可以先做模块化单体，使用 lint 或依赖图防止跨 feature 私有实现互相引用。

只有当团队自治、独立发布和故障隔离收益足够覆盖运行时复杂度时，才考虑微前端。架构演进要有迁移边界和回滚路径，不能只改目录名称。

### Q99：如何设计一个可取消、可重试的文件上传？

上传流程需要进度、暂停或取消、失败重试、文件校验、断点续传、并发限制、服务端幂等和最终确认。取消客户端等待不一定停止服务端已接收的数据。

大文件应考虑分片和上传会话；重试应使用指数退避并限制次数；文件名、大小、类型和内容必须在服务端校验，不能只信任浏览器提供的 MIME 类型。

### Q100：如何设计一个可访问的 React 组件？

先优先使用原生 HTML 语义，再补充 ARIA。确保键盘可操作、焦点顺序合理、焦点可见、状态可被屏幕阅读器感知、颜色对比度足够，并覆盖加载、错误、禁用和动态更新状态。

不要把 `div` 加上 `role="button"` 就认为完成了按钮组件。还要实现键盘事件、焦点管理和正确的禁用语义，并通过自动化工具和真实辅助技术验证。

### Q101：生产环境出现内存持续上涨，你怎么排查？

先确认是浏览器标签页、SSR 进程还是构建节点的内存增长。浏览器页面检查 heap snapshot、长生命周期 effect、WebSocket、定时器、DOM 监听、第三方实例和无界缓存；SSR 还要检查请求数据是否被放到全局变量或单例中。

通过重复进入退出页面、切换路由、执行关键流程和对比快照定位保留路径。不要仅通过增加内存或刷新页面规避问题。

### Q102：如何回答“为什么选择 React 而不是 Angular/Vue”？

先承认三者都能完成常见 UI 开发，再根据约束回答。React 的优势通常是组件组合能力、生态广、渲染目标多、招聘和社区资源丰富；代价是核心库边界较窄，需要团队自行治理路由、数据、表单和工程约定。

真正成熟的答案还应说明团队技能、现有生态、招聘、应用生命周期、SSR、性能、维护成本和交付风险，而不是进行绝对化的优劣比较。
