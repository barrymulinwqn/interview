## 一、面试考察重点与答题框架

| 方向 | 面试官真正想确认的能力 | 应准备的证据 |
| --- | --- | --- |
| LLM 基础 | 理解生成、上下文、采样、推理成本和模型局限 | 一次模型选型或推理性能优化经历 |
| Transformer / 算法 | 能说清注意力、训练目标、位置编码和长上下文的取舍 | 一次训练、评估或算法改进实验 |
| RAG | 能设计可检索、可评估、可治理的知识问答系统 | 知识库规模、召回/答案指标、失败案例和优化结果 |
| LoRA / 微调 | 能判断何时微调，理解数据质量、训练风险和部署方式 | 数据构造、评估集、训练配置和线上验证 |
| Agent | 能把开放式模型行为约束成可靠工作流 | 工具契约、权限、状态、失败恢复和审计方案 |
| LangChain | 把它当作编排工具而不是魔法框架，能控制抽象边界 | Runnable、检索链、工具调用、追踪和替换策略 |
| 生产工程 | 能处理延迟、成本、稳定性、安全、评估和迭代 | SLO、监控面板、灰度实验、回滚和反馈闭环 |

### 1. 高分技术题回答结构

1. **结论和适用条件**：先说推荐方案，以及它在什么约束下成立。
2. **运行机制**：说明关键数据流或算法原理，避免只列名词。
3. **取舍与边界**：至少说明一个失败模式、成本或不适用场景。
4. **验证方法**：说清离线指标、线上指标、测试集或监控信号。
5. **项目证据**：用自己的业务、数据规模和结果收尾；无法量化时说明如何量化。

例如，回答“为什么使用 RAG”时，不要只说“降低幻觉”。更完整的回答是：

> 对频繁更新且需要可追溯证据的企业知识，我优先使用 RAG，而不是把事实写进模型参数。检索结果作为受控上下文，使回答可以附带来源并快速更新。它不能自动消除幻觉，因此我会分别评估检索召回、重排质量和答案忠实度，并在低置信度时拒答或转人工。对于稳定的格式、语气或特定决策流程，才考虑通过微调补充。

### 2. 常见失分方式

- 把模型名称、向量数据库或框架名称当作架构设计。
- 声称“温度设为 0 就不会幻觉”或“RAG 一定比微调好”。
- 只报一个总体准确率，不区分检索、生成、延迟、成本和安全。
- 忽略提示注入、数据权限、个人信息、工具权限和审计。
- 在 Agent 设计中让模型直接拥有数据库写权限、生产命令权限或无限循环能力。
- 只描述正常路径，没有超时、空检索、重复工具调用、模型不可用或版本回滚方案。

## 二、LLM 基础与推理高频题

### Q1：什么是大语言模型？它如何生成文本？

**核心回答：**

大语言模型通常是基于 Transformer 的概率模型。给定已有 token 序列 $x_{<t}$，它学习下一个 token 的条件概率分布：

$$
p(x_t \mid x_{<t})
$$

推理时，分词器先把输入转换为 token；模型输出下一个 token 的 logits；经过 softmax 和采样或搜索策略选出 token；再把该 token 追加到上下文，重复直到遇到停止条件。

**必须说明的边界：**

- 模型不是数据库，也不保证输出为事实；它生成的是在训练分布和当前上下文下概率较高的序列。
- 它的知识受训练数据截止日期、数据质量和上下文影响，且不天然具有实时性、权限感知或引用能力。
- 生成时每输出一个 token 都会依赖前面 token，因此普通自回归解码难以像训练阶段那样完全并行。

### Q2：Token、词、字符有什么区别？为什么它会影响成本和性能？

Token 是 tokenizer 切分后的基本单位，不等同于一个中文字符、英文单词或字节。不同模型的 tokenizer 不同，同一段文本的 token 数也可能不同。

它影响：

- **上下文容量**：模型限制的是 token 数，不是“文档篇数”。
- **费用**：多数 API 按输入和输出 token 计费。
- **延迟**：长输入增加 prefill 时间；长输出增加逐 token 解码时间。
- **RAG 质量**：chunk 太大浪费上下文并稀释证据，太小则丢失语义和上下文。

工程中应使用目标模型对应的 tokenizer 统计真实 token，不能用字符数估算后就把预算当成准确值。

### Q3：Temperature、top-p、top-k 如何影响输出？

模型先给每个候选 token 一个 logit，temperature $T$ 会缩放其分布：

$$
p_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}
$$

- **temperature 较低**：分布更尖锐，输出更稳定，适合抽取、分类、结构化输出；但不保证事实正确。
- **temperature 较高**：更多样、更有创造性，也更容易偏离格式或引入不可靠内容。
- **top-k**：只从概率最高的 $k$ 个 token 中采样。
- **top-p / nucleus sampling**：取累计概率达到 $p$ 的最小候选集合，候选数会随上下文变化。

生产系统不应只调一个 temperature。要根据任务设置输出长度、stop tokens、JSON schema、检索证据和评估集。高风险任务优先约束输出并做验证。

### Q4：什么是幻觉？如何系统性降低而不是“消除”它？

幻觉是输出看似合理但不受真实证据支持、与来源冲突或虚构引用的内容。它来自模型的概率生成本质，也可能由模糊问题、知识过期、检索错误、上下文冲突和过长提示引发。

**分层治理：**

1. **输入层**：澄清问题、限制任务范围、使用结构化输入和权限过滤。
2. **证据层**：为时效或私有事实使用 RAG，要求引用检索证据，空检索时明确拒答。
3. **生成层**：明确“仅基于上下文回答”，使用合适采样参数和输出 schema。
4. **验证层**：对关键字段做规则、数据库或工具校验；对高风险答案使用二次核验或人工审批。
5. **产品层**：展示来源、置信度或不确定性，提供反馈入口并记录失败样本。

不要承诺“完全没有幻觉”。正确目标是量化特定任务的忠实度、降低风险，并让失败可检测、可追踪、可恢复。

### Q5：Prompt Engineering 的核心原则是什么？

Prompt 的作用是明确任务、约束模型行为和提供必要上下文，而不是用冗长的人设替代系统设计。一个可维护的 prompt 通常包括：

- 角色和任务边界：模型要做什么、不做什么。
- 输入数据和可信度边界：哪些材料可作为事实依据。
- 输出契约：语言、字段、JSON schema、引用格式、长度和拒答规则。
- 少量高代表性示例：用于稳定风格或解决歧义。
- 失败策略：信息不足、冲突、无权限或工具失败时如何响应。

**工程实践：** 把 prompt 版本化，把变量和固定指令分离，用真实评估集回归测试。不要把用户输入直接拼进系统指令；需要明确分隔并把外部内容标记为不可信数据。

### Q6：In-context learning、few-shot 和微调有什么区别？

| 方法 | 改变模型参数 | 主要优点 | 主要限制 | 适用场景 |
| --- | --- | --- | --- |
| Zero-shot / 指令 | 否 | 快、成本低 | 一致性和复杂行为有限 | 通用任务、原型 |
| Few-shot | 否 | 可快速示范格式或判定边界 | 占用上下文，示例敏感 | 分类、抽取、特定输出风格 |
| RAG | 否 | 知识可更新、可引用、可控权限 | 受检索质量制约 | 企业知识、政策、产品文档 |
| 微调 | 是 | 稳定风格、领域行为、格式遵循 | 需要高质量数据和评估，知识易过期 | 稳定任务、特定术语或行为模式 |

选型应从问题根因出发：缺少最新事实优先 RAG；格式不稳定先试 schema 和 few-shot；需要稳定领域行为且有大量高质量标注数据时，再考虑微调。

### Q7：如何估算 LLM 推理延迟和吞吐？

端到端延迟可拆成排队、网络、输入处理、首 token 生成和后续解码：

$$
T_{end-to-end} = T_{queue} + T_{network} + T_{prefill} + T_{decode}
$$

- **Prefill**：处理输入上下文，可并行度较高，但会受上下文长度影响。
- **Decode**：逐 token 生成输出，通常是交互场景的主要瓶颈。
- **TTFT**（time to first token）反映首字响应体验。
- **Tokens/s**、P50/P95/P99、队列长度、拒绝率、缓存命中率共同描述性能。

优化顺序通常是减少无用上下文和输出、流式返回、缓存、批处理/连续批处理、选择合适模型和量化方式。不能只看平均响应时间；交互产品应重点关注 P95 TTFT 和完整响应时间。

### Q8：什么是 KV Cache？它带来什么收益和代价？

在自回归生成时，当前 token 需要关注历史 token。KV Cache 保存各层已计算的 Key 和 Value，避免每生成一个新 token 都重新计算整个历史上下文的注意力投影。

收益是显著降低解码阶段重复计算；代价是显存随 batch size、层数、隐藏维度和上下文长度增长。长上下文和多并发会使 KV Cache 成为容量瓶颈。

工程上要结合最大上下文、并发、分页/块状 KV 管理、请求调度和缓存淘汰策略设计。Prefix cache 还能复用相同系统提示或公共前缀，但必须隔离租户和权限，避免跨用户泄露上下文。

### Q9：如何实现结构化输出，并保证它可靠？

优先级从强到弱通常是：

1. 使用模型/API 支持的 JSON Schema 或 constrained decoding。
2. 在 prompt 中明确 schema、字段含义、枚举和示例。
3. 服务端做 schema 校验、类型校验、业务校验和必要的重试修复。
4. 对可能写入数据库、调用工具或影响用户的字段，使用 allowlist 和确定性校验。

仅仅要求“请输出 JSON”不可靠。解析失败、字段缺失、未知枚举、过长字符串和恶意值都必须被当作正常失败路径处理。重试次数需有上限，并记录原始输出以便诊断。

## 三、Transformer 与大模型算法高频题

### Q10：Transformer 的核心结构是什么？为什么它替代了 RNN？

标准 Transformer 由 embedding、位置编码、多头自注意力、前馈网络（FFN）、残差连接和 LayerNorm 组成。Decoder-only LLM 通过因果掩码预测下一个 token；Encoder-only 模型更适合理解和表征任务；Encoder-Decoder 适合条件生成，如翻译。

相比 RNN，Transformer 可以并行处理训练序列中的多个位置，更容易捕捉远距离依赖；代价是标准全注意力在序列长度 $n$ 上具有 $O(n^2)$ 的时间和内存复杂度，因此长上下文是重要工程挑战。

### Q11：Self-Attention 的计算过程是什么？

输入表示 $X$ 经过线性投影得到 Query、Key 和 Value：

$$
Q = XW_Q, \quad K = XW_K, \quad V = XW_V
$$

缩放点积注意力为：

$$
\operatorname{Attention}(Q,K,V) = \operatorname{softmax}\left(\frac{QK^T}{\sqrt{d_k}} + M\right)V
$$

其中 $M$ 是 mask。Causal mask 会遮住未来 token，保证生成时位置 $t$ 只能看到不晚于 $t$ 的信息。除以 $\sqrt{d_k}$ 是为了避免维度增大时点积方差过大，导致 softmax 过于尖锐、梯度不稳定。

### Q12：Multi-Head Attention 有什么作用？

多头注意力把表示投影到多个子空间，每个 head 可以学习不同的关系模式，例如局部依赖、长程依赖、实体关联或语法结构；各 head 的结果拼接后再投影。

它不是“头越多越好”。头数、每头维度、显存、通信开销和模型规模需要共同平衡。面试中应避免把 attention map 的可视化直接当作严格因果解释；它最多是分析线索之一。

### Q13：为什么需要位置编码？RoPE、绝对位置和 ALiBi 有什么区别？

注意力本身对输入排列是置换不变的，因此模型需要位置信息来理解顺序。

- **绝对位置编码**：向 token embedding 加入每个位置的向量，直观但对长度外推可能有限。
- **RoPE**（Rotary Position Embedding）：通过旋转 Q/K 注入相对位置信息，现代 LLM 常用，对相对距离建模较好。
- **ALiBi**：在注意力分数上加随距离变化的偏置，结构简单，对长度外推有一定优势。

长上下文扩展还涉及训练长度、位置插值/缩放、数据分布和评估，不能只改一个位置编码参数就宣称支持更长上下文。

### Q14：Pre-training、SFT、RLHF / DPO 分别解决什么问题？

- **Pre-training**：在大规模语料上做 next-token prediction，学习语言、世界知识和通用模式。
- **SFT**（Supervised Fine-Tuning）：用高质量指令-回答样本，让模型更符合任务格式和指令。
- **RLHF**：通常先训练偏好/奖励模型，再用强化学习优化输出偏好；可提升有用性与对齐，但训练复杂且可能引入 reward hacking。
- **DPO**（Direct Preference Optimization）：直接利用偏好对优化相对偏好，通常比完整 RLHF 流程更简单稳定。

这些阶段都不能代替安全评估和产品治理。偏好数据中的偏差会被放大，且“更符合偏好”不等于“事实更准确”。

### Q15：什么是 Cross-Entropy Loss？语言模型如何训练？

对目标 token $y_t$，语言模型最小化负对数似然：

$$
\mathcal{L} = -\sum_{t=1}^{T} \log p_\theta(y_t \mid y_{<t})
$$

训练时常用 teacher forcing：输入真实前缀并预测下一个真实 token，因此可对一个序列中多个位置并行计算损失。推理时模型只能使用自己先前生成的 token，这种训练与推理的分布差异是暴露偏差的来源之一。

Perplexity 是交叉熵的指数形式，可衡量语言建模分布拟合，但不能单独代表问答质量、安全性、工具调用正确性或业务成功率。

### Q16：为什么 Transformer 训练容易不稳定？常见稳定化手段有哪些？

常见问题包括梯度爆炸/消失、混合精度溢出、学习率过大、数据异常、长序列显存压力和分布不一致。

常用手段：合理初始化、warmup 加学习率衰减、gradient clipping、LayerNorm/RMSNorm、AdamW、混合精度的 loss scaling、梯度累积、数据清洗和训练监控。应持续监测训练/验证损失、梯度范数、学习率、吞吐、NaN/Inf、数据分布和下游评估。

回答时要强调：loss 下降并不自动说明模型可用，还必须防止评估集泄漏，并测试目标任务和安全边界。

### Q17：长上下文面临哪些挑战？

- 标准注意力的计算和内存通常随 $n^2$ 增长。
- 模型即使支持很长窗口，也可能出现“lost in the middle”，对中间信息利用不足。
- 长 prompt 增加成本、TTFT 和噪声，可能反而降低回答质量。
- 内容越多，提示注入、权限混杂和过期信息风险越高。

解决方式包括检索和重排、摘要/分层记忆、滑动窗口、稀疏注意力或高效注意力实现、合理的上下文压缩与位置编码策略。最终应以任务成功率、证据覆盖率、延迟和成本验证，而不是只比较最大 token 数。

### Q18：模型量化是什么？INT8、INT4 的主要取舍是什么？

量化将权重或激活用更低比特表示，以降低显存占用、带宽和推理成本。INT8 往往质量损失较小；INT4 压缩更明显，但对模型、任务和量化算法更敏感。

要区分：

- **PTQ**（Post-Training Quantization）：训练后量化，部署快。
- **QAT**（Quantization-Aware Training）：训练中模拟量化误差，通常质量更好，成本更高。
- 权重量化、激活量化和 KV Cache 量化的影响不同。

不能只测通用 benchmark。应在目标语言、长短输入、工具调用、结构化输出和关键业务评估集上，比较质量、吞吐、显存、P95 延迟和单位请求成本。

## 四、RAG 高频题

### Q19：什么是 RAG？完整链路包含哪些步骤？

RAG（Retrieval-Augmented Generation）是在生成前，从受控外部知识源检索相关内容并注入上下文。典型链路：

1. 文档接入：解析、OCR、清洗、去重、版本管理和权限标记。
2. 切分与元数据：根据语义和结构生成 chunk，保留来源、标题、时间、ACL 等。
3. 索引：生成 embedding，写入向量索引；必要时同时建立关键词索引。
4. 查询理解：改写、分解、意图识别或条件过滤。
5. 召回与重排：得到候选文档后排序、去重、压缩。
6. 生成：把问题和可信上下文交给 LLM，要求基于证据回答并附引用。
7. 评估与观测：分别测检索和生成，记录证据、版本、延迟、成本和用户反馈。

核心认识是：RAG 不是“向量数据库 + prompt”。文档质量、chunk 策略、权限、检索、重排、回答约束和评估任何一环失控都会造成错误答案。

### Q20：如何设计文档 Chunk？chunk size 和 overlap 如何选择？

优先按文档结构和语义边界切分，如标题、段落、表格、代码块、问答对，而不是机械按固定字符数切。每个 chunk 应能独立表达一个可检索事实，同时保留父文档、章节路径、页码、时间、语言和 ACL 元数据。

- **chunk 过大**：主题混杂、embedding 被稀释、上下文成本高。
- **chunk 过小**：上下文不完整、答案证据被拆散、召回噪声增加。
- **overlap**：可减少边界断裂，但会增加索引量、近似重复和检索冗余。

起点可用固定 token 窗口加少量重叠，但最终应根据问题类型和评估集比较 chunk recall、答案忠实度、上下文 token、延迟和成本。对表格、扫描件、代码和多语言文档应单独处理。

### Q21：Embedding 是什么？如何选择 embedding 模型？

Embedding 是把文本映射到高维向量，使语义相近的文本在向量空间中更接近。检索常用余弦相似度、内积或欧氏距离，但必须与模型训练方式及向量是否归一化一致。

选择时应考虑：

- 业务语言、跨语言需求、领域术语和文本长度。
- 检索任务类型：问答、相似案例、代码、商品或多模态。
- 向量维度、索引内存、编码吞吐、部署位置和数据合规。
- 是否能在自己的标注集上取得足够的 Recall@k、MRR 或 nDCG。

不要因为 embedding 模型参数更大就默认更好。错误的 chunk、缺失元数据或不匹配的距离度量会掩盖模型本身的提升。

### Q22：向量检索、BM25 和 Hybrid Search 如何选择？

- **BM25 / 关键词检索**：对精确术语、错误码、产品型号、人名和罕见实体通常很强，可解释性好。
- **向量检索**：擅长同义改写和语义匹配，但可能漏掉精确关键字约束。
- **Hybrid Search**：结合两者候选，常通过加权、RRF（Reciprocal Rank Fusion）或学习排序融合，在企业语料中通常更稳健。

推荐先建立 BM25 和向量检索的独立基线，再使用真实 query 集验证混合策略。无论使用何种方法，都应加入 metadata filter，以保证租户、文档类型、有效期和权限边界。

### Q23：为什么需要 Reranker？它与 Retriever 的区别是什么？

Retriever 的目标是在大规模语料中快速从百万级甚至更大集合中召回候选，通常使用向量 ANN 或关键词索引。Reranker 针对较小候选集，联合编码 query 与 document，做更精细的相关性判断。

典型设计是“宽召回 + 精排”：先取 top-$k$ 候选，再重排取 top-$n$ 给 LLM。这样能在质量和延迟之间平衡。

**注意：** reranker 只能重排已召回的文档，不能挽救完全漏召。需要分别检查 Recall@k 和重排后的 nDCG/MRR，并监控它增加的延迟与成本。

### Q24：如何评估一个 RAG 系统？

必须拆层评估，不能只问“模型回答像不像”：

| 层级 | 常见指标 | 要回答的问题 |
| --- | --- | --- |
| 文档与索引 | 覆盖率、解析错误率、索引时效 | 知识是否完整、最新、可检索？ |
| 召回 | Recall@k、MRR、nDCG、过滤正确率 | 正确证据是否进了候选集？ |
| 重排 | nDCG、MRR、top-n 证据覆盖 | 最相关证据是否排在前面？ |
| 生成 | Correctness、Faithfulness、引用准确率、拒答正确率 | 答案是否正确且受证据支持？ |
| 系统 | P95 延迟、成本、可用性、缓存命中率 | 系统能否在预算和 SLA 内运行？ |
| 业务 | 解决率、人工转接率、CSAT、风险事件 | 是否真正改善业务流程？ |

评估集应包含常规问题、无答案问题、时效冲突、权限边界、长文档、多跳问题和提示注入样本。自动 LLM-as-a-judge 可辅助扩展，但要用人工标注校准并保留可复现的版本。

### Q25：RAG 中如何处理引用、可追溯性和无答案问题？

每个生成结论应尽量链接到具体 chunk 或文档片段，而不是只列一份模糊的参考文档。保存回答使用的检索结果、chunk ID、文档版本、prompt 和模型版本，支持审计与复现。

当检索证据不足、证据相互冲突、文档过期或用户无权限时，系统应明确说明无法依据现有资料回答，并引导搜索范围、转人工或请求更多信息。强制编造答案会破坏信任和可审计性。

### Q26：如何处理知识库增量更新、删除和版本冲突？

为源文档建立稳定 ID、内容哈希、更新时间、版本、有效期和删除状态。更新时做差异化解析与重嵌入；删除或权限回收时必须从检索索引、缓存和可能的派生摘要中清除或失效。

对同一政策的多个版本，应将最新生效版本作为默认候选，并保留历史版本及适用时间。答案引用应带版本或生效日期。不能只向量追加不清理，否则旧内容会长期被召回。

### Q27：如何防止 RAG 的权限泄露？

权限过滤必须在检索阶段发生，而不是仅让 LLM 在生成时“不要泄露”。具体做法：

- 将用户/租户/部门/文档 ACL 等可验证元数据写入索引。
- 每次检索使用经过认证的主体生成服务端 filter。
- 分离索引、命名空间或密钥以降低跨租户误配的爆炸半径。
- 不把原始机密内容写入客户端日志、trace 或第三方观测平台。
- 对缓存键绑定权限上下文，避免管理员答案命中普通用户缓存。

上线前应做越权 query、缓存穿透、文档删除后访问和 prompt injection 的红队测试。

### Q28：RAG 效果差时，你如何定位问题？

按链路分诊，不要先盲目换更大的模型：

1. 检查问题是否清晰、是否有答案、用户是否有权限。
2. 查看 query 改写、filter 和实际召回内容，确认正确文档是否进入 top-$k$。
3. 若漏召，检查解析、chunk、embedding、关键词索引、metadata 和召回参数。
4. 若召回有正确材料但排位低，优化 hybrid fusion 或 reranker。
5. 若上下文正确但答案错误，检查 prompt、上下文截断、引用约束和生成模型。
6. 用失败样本回归测试，确保优化没有牺牲其他类别。

一个好的线上 trace 应能让工程师看见：原问题、改写问题、权限 filter、召回候选、分数、重排结果、最终上下文、模型输出、延迟和版本信息。

## 五、LoRA 与模型微调高频题

### Q29：什么是 LoRA？它为什么能降低微调成本？

LoRA（Low-Rank Adaptation）冻结预训练权重 $W$，只学习一个低秩增量：

$$
W' = W + \Delta W = W + BA
$$

其中 $A \in \mathbb{R}^{r \times d_{in}}$、$B \in \mathbb{R}^{d_{out} \times r}$，且秩 $r$ 远小于原始维度。训练参数、优化器状态和存储开销因此显著减少，多个任务也能共享同一个基础模型而加载不同 adapter。

它不是无损压缩：rank、目标层、数据质量和任务复杂度会影响效果；如果需要大幅改变基础能力或领域知识，低秩适配未必足够。

### Q30：LoRA、QLoRA、全参数微调如何选择？

| 方法 | 显存/训练成本 | 适用情况 | 主要风险 |
| --- | --- | --- | --- |
| Prompt / RAG | 最低 | 知识更新、轻量约束 | 格式和复杂行为稳定性有限 |
| LoRA | 低 | 领域风格、抽取、分类、指令遵循 | 需选择 rank 和目标模块 |
| QLoRA | 更低 | 显存受限时训练较大模型 | 量化配置和吞吐更复杂，需验证质量 |
| 全参数微调 | 最高 | 数据和预算充足、任务需要深度适配 | 灾难性遗忘、训练和部署成本高 |

QLoRA 通常以低比特量化加载基础模型，并训练 LoRA adapter，显著降低显存要求。选型前先证明 prompt、schema、RAG 和 LoRA 是否已满足目标，不要把微调当作解决所有质量问题的默认答案。

### Q31：LoRA 的 rank、alpha、target modules 如何设置？

- **rank $r$** 决定低秩更新容量。过低可能欠拟合，过高增加参数、过拟合和成本。
- **alpha** 通常用于缩放 LoRA 更新，实际效果取决于实现中的缩放规则。
- **target modules** 常从 attention 的 Q/V 投影开始，也可能覆盖 K/O 或 MLP 层；应由任务、模型架构、预算和实验决定。
- **dropout** 可在小数据上帮助正则化，但不是替代数据质量的工具。

合理方法是选一个小而可重复的搜索范围，固定训练/验证划分，比较任务质量、格式合法率、遗忘测试、推理延迟和 adapter 大小。不要仅以训练 loss 最低来选配置。

### Q32：什么样的数据适合 SFT 或 LoRA 微调？

高质量数据要与线上输入分布和目标行为对齐，并具备明确的输入、期望输出和质量标准。数据应覆盖典型样本、困难样本、拒答场景、边界条件、格式要求和安全约束。

**数据治理要点：**

- 去重、去模板泄漏、纠正噪声和冲突标签。
- 清理个人信息、受版权或保密约束的内容，并记录授权来源。
- 按实体、时间或来源切分训练/验证/测试，避免同一问题的近重复版本泄漏。
- 保留独立的 golden set，不能被训练和提示样例反复污染。

几千条准确、覆盖真实失败模式的数据，通常比大量自动生成却未验证的数据更有价值。

### Q33：什么是灾难性遗忘？如何缓解？

灾难性遗忘指模型在适配新任务时，原有通用能力或旧任务性能显著下降。常见原因是数据单一、学习率过高、训练过久或全参数更新范围过大。

缓解方式包括：使用 LoRA 等参数高效方法、降低学习率/训练步数、混入通用或旧任务样本、使用多任务数据、冻结更多层，并在评估中同时测试目标任务和通用能力。部署时保留基础模型和 adapter 的可回滚版本，不能只测试新任务分数。

### Q34：如何评估一次微调是否成功？

至少比较 base model、prompt baseline 和微调模型，并在完全隔离的测试集上评价：

- 目标任务正确率、F1、ROUGE 或业务成功率。
- JSON/schema 合法率、工具调用正确率、拒答与安全策略遵循率。
- 领域外和旧任务表现，检查遗忘与过拟合。
- P95 延迟、显存、吞吐、加载时间和单位请求成本。
- 人工盲评：准确性、完整性、风格和风险。

提升必须具有统计和业务意义。若只提升了固定 benchmark 的分数，却引入安全退化或成本不可接受，就不应上线。

### Q35：Adapter 合并和多 Adapter 服务有什么取舍？

将 LoRA delta 合并到基础权重后，推理路径更简单，可能获得更好吞吐；但会产生独立模型副本，回滚和多租户管理成本更高。运行时加载 adapter 有利于一套基础模型支持多任务或客户，但需要管理加载延迟、显存碎片、版本路由和并发隔离。

生产设计应明确模型注册表、基础模型版本、adapter 兼容性、灰度路由、回滚和评估证据。不能把不同基础模型训练出的 adapter 随意混用。

## 六、Agent 高频题

### Q36：什么是 LLM Agent？它和普通 Chatbot 有何区别？

Agent 是以 LLM 作为决策或语言接口，并能够规划、调用工具、读取状态、根据结果继续执行任务的系统。普通 chatbot 可能只做单轮或多轮文本生成；Agent 需要额外解决工具契约、状态机、权限、循环控制、错误恢复、可观测性和人类审批。

Agent 的价值不在于“自主”本身，而在于把复杂任务分解、连接可信工具并在可控边界内完成工作。高风险流程往往应采用受限工作流，让模型做分类、参数抽取或建议，而非自由执行。

### Q37：ReAct、Plan-and-Execute 和工作流编排如何选择？

- **ReAct**：模型交替生成推理/行动，适合探索性查询和工具数量有限的任务；缺点是轨迹不稳定、调用次数可能失控。
- **Plan-and-Execute**：先产出计划，再由执行器逐步完成，可审阅计划；但计划可能过时或过度复杂。
- **确定性工作流/状态机**：把步骤、分支和审批固化，模型负责窄范围判断，适合金融、运维、审批和高风险业务。

实际系统常是混合模式：固定主流程 + 在受控节点调用 LLM。选择依据是风险、可预测性、可审计性、任务变化频率和失败代价，而不是 Agent 名称。

### Q38：如何设计 Agent Tool？

每个工具都应有清晰、狭窄、可验证的契约：

- 明确名称、自然语言描述、输入 JSON Schema、输出 schema、错误码和超时。
- 参数使用枚举、ID 或 allowlist，而不是开放式 shell 命令或 SQL 字符串。
- 服务端重新认证和授权，不能信任模型声称的用户身份。
- 区分只读、可逆写入和不可逆操作；后两者设置幂等键、审批和审计。
- 返回结构化、最小必要的数据，避免把敏感原文直接塞回上下文。

工具描述也应防御歧义。一个“execute_any_command”式工具几乎必然造成安全和可靠性风险，应按业务操作拆分。

### Q39：如何防止 Agent 无限循环、重复调用或成本失控？

设置明确的运行预算：最大步骤数、最大工具调用数、最大 token、最大墙钟时间和最大成本；达到阈值后保存状态并返回可解释的失败或转人工。

对写工具使用幂等键，对相同参数做去重或缓存，并检测重复轨迹。每一步记录状态转换、输入摘要、工具结果和原因。遇到工具超时或结果不确定时，不应盲目重试写操作；先查询操作状态或进入人工处理队列。

### Q40：Agent Memory 有哪些类型？为什么不能无限保存对话？

- **短期记忆**：当前会话上下文、任务状态和最近工具结果。
- **长期记忆**：用户偏好、历史任务摘要、可检索知识或经验。
- **程序化记忆**：规则、工作流和工具使用策略。

无限拼接历史会导致上下文成本上升、注意力稀释、过期信息、敏感数据泄露和提示注入传播。应使用任务状态机、摘要、带来源的可检索记忆、TTL、用户可管理的存储策略，并为敏感信息设置最小化保留和删除机制。

### Q41：Agent 如何应对工具失败和部分成功？

工具调用应把超时、限流、认证失败、参数错误、业务拒绝和未知状态区分开来。只对明确可重试且幂等的瞬态失败做有上限的退避重试。

多步骤任务要有状态持久化和补偿逻辑。例如先创建工单再发通知时，通知失败不能简单重跑整个流程导致重复工单；应查询现有工单、记录阶段并只恢复失败步骤。对于不可逆业务动作，需要人审或事务/补偿设计，而不是让模型自行“猜测恢复”。

### Q42：什么是 Prompt Injection？如何防御 Agent 场景中的攻击？

Prompt injection 是不可信内容试图改变模型优先级、诱导泄密、绕过规则或触发危险工具调用。RAG 文档、网页、邮件和用户输入都可能携带恶意指令。

**防御原则：**

- 把外部内容视为数据，不视为系统指令；明确分隔和标注来源。
- 不把“忽略之前指令”之类文本作为可信控制信号。
- 工具权限、数据访问和审批必须由服务端策略强制，不能由 prompt 保证。
- 使用最小权限、敏感动作二次确认、输出过滤、审计和红队测试。
- 为高风险工具建立确定性参数校验和业务规则。

没有单一 prompt 能彻底防住注入。安全边界必须在模型外实现。

### Q43：多 Agent 系统何时有价值，何时是过度设计？

多 Agent 适合职责天然分离、需要不同工具/权限、可并行独立研究或需要相互审阅的任务，例如检索、合规检查与报告生成。但它会引入更多上下文传递、协调延迟、成本、失败模式和调试难度。

若任务可由一个受控工作流或一个模型调用完成，多 Agent 通常是过度设计。先用单 Agent/单工作流建立可测基线，只有在职责隔离或并行带来可证明收益时再拆分。

## 七、LangChain 高频题

### Q44：LangChain 解决什么问题？它不解决什么问题？

LangChain 提供模型、prompt、输出解析、retriever、tools、chain/runnable 和观测集成等编排抽象，帮助快速组合 LLM 应用。

它不替你解决知识质量、权限、安全、评估、模型幻觉、分布式事务或业务正确性。生产系统仍需自己定义数据契约、超时、重试、缓存、指标、版本和访问控制。框架 API 会演进，应将业务逻辑封装在自己的接口后，不让框架类型渗透所有领域代码。

### Q45：LCEL / Runnable 的价值是什么？

LangChain Expression Language（LCEL）以 Runnable 为统一可组合接口，常见操作包括 sequence、parallel、branch、stream、batch 和配置传递。它的价值是让 prompt、model、parser 和 retriever 可以组合，并统一支持 invoke、batch、stream、async 和 tracing。

使用时仍要清楚每一步的输入输出类型、异常语义和并发限制。复杂业务不应隐藏在一条过长的链表达式中；关键步骤要拆成可测试函数，明确超时和观测字段。

### Q46：如何用 LangChain 组织一个可维护的 RAG 链？

可按职责拆为独立组件：

1. 输入校验和认证上下文。
2. 查询改写或意图路由。
3. 带 ACL metadata filter 的 retriever。
4. 可选的 reranker 和上下文压缩。
5. 带引用约束的 answer prompt。
6. 结构化输出 parser 和服务端业务校验。
7. 记录 trace、检索结果、模型/索引版本与评估标签。

不要把这些全部写进一个 `RetrievalQA` 黑盒。面试中应说明可以使用高层 helper 加速原型，但生产排障与评估需要暴露关键中间结果。

### Q47：LangChain 中如何处理流式输出、异步和并发？

对用户可见的生成，使用 streaming 改善 TTFT；同时要能在用户取消连接时传播 cancellation，避免后台继续消耗 token。对独立任务可使用 async/batch 提升吞吐，但必须控制模型供应商限流、向量库连接池和下游工具容量。

并发不应无限放大。应设置 semaphore、队列、超时、退避和背压，并区分读操作与写操作。流式 JSON 或工具参数需要增量缓冲和完整 schema 校验，不能在半个对象到达时立即执行危险动作。

### Q48：LangChain 的 Memory 应如何使用？

Memory 适合管理有限的会话状态，但不应作为企业长期知识或权限系统。对话历史应设置 token 预算，采用窗口、摘要或检索式记忆，并在身份切换、会话结束、用户删除和敏感内容场景中正确隔离和清理。

生产中更推荐把真实业务状态保存在显式数据库/状态机，把历史会话作为受治理的数据源；LLM 只读取当前任务所需的最小上下文。

### Q49：LangSmith 或类似追踪系统应该记录什么？

应记录可复现又不泄露秘密的关键信息：请求 ID、用户/租户匿名标识、链路步骤、prompt/template 版本、模型和参数、检索 chunk ID/版本、工具调用、token 用量、延迟、错误类型、输出校验和用户反馈。

对原始 prompt、文档和输出进行脱敏、访问控制、保留期管理和采样。观测平台不能成为新的数据泄露路径。优秀 trace 能回答“本次答案为何如此、用过哪些证据、哪个环节慢或错、能否复现”。

## 八、系统设计与生产实践题

### Q50：设计一个企业内部知识助手，你会怎么做？

**先澄清约束：** 用户是谁、文档类型与规模、更新频率、语言、SLA、数据分级、是否允许回答无来源内容、是否要执行操作。

**推荐架构：**

1. 文档接入服务解析 PDF/HTML/Office/扫描件，做去重、OCR、版本与 ACL 提取。
2. 索引流水线生成结构化 chunk、embedding 和关键词索引，并支持增量更新与删除。
3. 查询服务完成认证、ACL filter、hybrid retrieval、rerank 和上下文构建。
4. LLM 服务使用版本化 prompt，生成带句级引用的答案；无证据或低置信度时拒答或转人工。
5. 网关负责限流、缓存、审计、内容安全、成本配额和模型路由。
6. 评估与观测服务记录检索、生成、延迟、费用和反馈，驱动回归集更新。

**验收指标：** 不只看“回答满意度”，还要有权限越界率为零、引用忠实度、关键问题正确率、无答案拒答准确率、P95 延迟、索引新鲜度和单位会话成本。

### Q51：如何为 LLM 应用建立离线评估和线上实验闭环？

离线阶段建立版本化黄金集，覆盖常规、长尾、无答案、安全、权限、时效冲突和工具失败问题。每次变更模型、prompt、chunk、embedding、reranker 或工具契约，都跑同一套回归。

线上阶段采用 shadow、canary 或 A/B，在不损害用户体验和合规的前提下比较任务成功率、人工接管率、引用点击/纠错率、延迟、成本和负反馈。将生产失败样本脱敏后进入标注和评估流程，但不要无审查地把用户数据直接用于训练。

### Q52：如何控制 LLM 成本？

先拆分成本来源：输入 token、输出 token、检索/rerank、模型调用、GPU/托管容量、缓存和人工审核。常见策略：

- 对简单分类、路由或抽取使用更小模型，把复杂问题路由到强模型。
- 精简系统 prompt、检索上下文和输出长度，避免“把所有文档塞进 prompt”。
- 使用语义缓存或精确缓存，但缓存键必须考虑版本、权限和时效。
- 批处理离线任务，对交互任务使用流式和并发治理。
- 对租户、功能和工作流设置预算、配额和异常告警。

成本优化不能牺牲证据、权限或关键任务质量。任何降本措施都要在评估集和生产指标上验证。

### Q53：如何保障 LLM 应用安全与合规？

从数据、身份、模型和操作四层回答：

- **数据**：最小化收集、分级分类、加密、脱敏、保留期、删除机制和供应商数据协议。
- **身份与权限**：统一认证、服务端 ACL filter、最小权限、租户隔离和审计日志。
- **模型输入输出**：提示注入防御、敏感信息检测、内容安全策略、来源引用和高风险拒答。
- **工具与操作**：参数校验、审批、幂等、环境隔离、不可逆操作保护和紧急停用开关。

合规不是上线前的一次扫描。数据源、模型版本、日志、评估集、访问策略和供应商能力变化时，都需要持续复核。

### Q54：线上 LLM 答案质量突然下降，如何排查？

1. 定义下降：是正确率、引用忠实度、拒答率、用户反馈、格式合法率还是某个租户受影响。
2. 比较最近的模型、prompt、索引、embedding、reranker、文档、权限、工具和配置版本。
3. 抽取有代表性的失败 trace，分辨是输入变化、漏召、错排、上下文截断、生成偏移还是工具故障。
4. 检查供应商模型版本、限流、区域、tokenizer 或安全过滤行为是否变化。
5. 先采用低风险动作：回滚已验证版本、缩小流量、关闭高风险功能或切换备用模型。
6. 用黄金集、关键业务样本和线上指标确认恢复，再形成 RCA 和回归测试。

不要只问“模型是不是变笨了”。可观测性要能把质量问题定位到具体链路和版本。

### Q55：如何设计 LLM 应用的可观测性？

至少关联一个端到端 trace ID，记录：

- 请求维度：租户、场景、语言、输入 token、权限结果和安全拦截结果。
- 检索维度：query、filter、候选 ID/分数、rerank、最终上下文长度、索引版本。
- 模型维度：provider、模型版本、prompt 版本、参数、TTFT、输出 token、完成原因和错误。
- 工具维度：工具名、参数摘要、授权、耗时、重试、幂等键和结果状态。
- 质量维度：引用、schema 合法率、用户反馈、人工标注、自动评估结果。
- 系统维度：P50/P95/P99、错误率、排队、缓存、限流、成本和 GPU 利用率。

同时实施 PII 脱敏、采样、访问控制和保留策略。日志越全不等于越好，未经治理的 trace 会成为隐私与成本风险。

### Q56：什么时候不应该使用 LLM 或 Agent？

当规则明确、输入结构稳定、错误代价高且需要确定性结果时，优先使用传统规则、SQL、工作流、搜索或专用模型。例如金额计算、权限判断、数据库迁移、库存扣减和不可逆生产操作不应交给自由生成模型决定。

LLM 可以辅助解释、提取、归类、生成草稿或提出建议，但最终决策和执行应由确定性系统、审批流程或人工负责。成熟方案往往是“LLM 在边界内增强传统系统”，不是以 LLM 替换所有逻辑。

## 九、面试前速查清单

### 1. 每个主题至少准备一个真实案例

- 一个 LLM 模型/供应商选型，说明质量、延迟、成本和合规取舍。
- 一个 RAG 故障样本，说明如何定位漏召、错排或不忠实生成。
- 一次微调或 LoRA 实验，说明数据、基线、评估与回滚。
- 一个 Agent/工具调用流程，说明权限、幂等、审批和异常恢复。
- 一次线上质量或性能问题，说明指标、止损、根因和预防措施。

### 2. 高频追问要能回答

| 追问 | 应答方向 |
| --- | --- |
| 如何证明 RAG 有效果？ | 分层指标、golden set、线上业务指标与失败样本。 |
| 为什么不直接微调？ | 区分知识更新、格式约束和稳定行为，比较成本与可追溯性。 |
| RAG 会不会泄露数据？ | 服务器端 ACL filter、索引隔离、缓存权限绑定、审计与测试。 |
| Agent 如何避免乱操作？ | 最小权限、结构化工具、参数校验、预算、审批、幂等和审计。 |
| 如何降低 LLM 延迟和成本？ | 减 token、模型路由、缓存、流式、批处理和评估验证。 |
| 温度为 0 是否没有幻觉？ | 否；只降低随机性，事实性仍取决于模型、上下文、检索和验证。 |

### 3. 面试最后的表达原则

- 说清输入、输出、数据规模、约束和成功指标。
- 主动说明不确定性和失败路径，体现工程判断而不是背诵。
- 对高风险能力强调人审、权限、审计和可回滚性。
- 使用真实、可验证的指标；不知道的数据不要编造，可说明会如何采集和验证。
- 把“用了某个框架/模型”升级为“为什么选、怎么验证、出了问题怎么定位与回退”。
