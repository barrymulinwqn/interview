## 一、岗位真正考察什么

| JD 能力 | 面试官真正想确认的能力 | 需要准备的证明材料 |
| --- | --- | --- |
| UI 与 API 自动化 | 能把高价值回归场景稳定地自动化，而不是只会录制脚本 | 一个端到端业务流、一个 API 测试分层案例、稳定性数据 |
| 测试设计经验 | 能从需求、风险和数据流导出覆盖策略、测试用例和准入标准 | 一份测试计划、风险矩阵、缺陷案例和测试报告 |
| 编程语言 | 能写可读、可维护、可复用、可诊断的测试代码 | Page Object 或 Client 封装、fixture、断言和异常处理示例 |
| 自动化框架 | 知道框架生命周期、并发、报告、失败诊断和适用边界 | Pytest/Playwright/TestNG/Cucumber 等的落地实践 |
| SQL | 能准备数据、验证持久化结果，并通过查询定位问题 | 复杂查询、事务、索引与数据清理案例 |
| Git 平台 | 能在团队中安全地协作、评审、合并和追踪发布 | 分支策略、Merge Request/PR、冲突处理、流水线门禁案例 |

一个资深自动化测试工程师不只是“把手工用例翻译成代码”。更重要的是：

1. 根据风险决定哪些内容值得自动化，哪些应保留探索性测试或人工验收。
2. 让自动化测试可重复、可定位、可维护，并能提供可信的质量信号。
3. 在需求、开发、运维和产品之间推动可测试性，例如稳定的测试数据、可观测性和 API 契约。
4. 用失败率、执行时长、缺陷逃逸率、覆盖的关键路径等指标，证明自动化带来的价值。

## 二、高分回答方法

### 1. 技术题回答结构：结论 -> 原理 -> 取舍 -> 验证

例如被问到“为什么 UI 自动化不稳定”时，不要只回答“加等待”。更完整的回答是：

> 我优先把不稳定定位为同步、定位器、数据、环境或产品缺陷中的哪一类。对前端异步渲染，使用基于业务状态的显式等待，例如元素可见、请求完成或按钮可点击，而不是固定 `sleep`。定位器优先使用无障碍角色、标签或稳定的 `data-testid`，避免依赖层级和动态 CSS class。测试数据通过 API 或数据库在执行前创建，并在后续清理。对于仍然失败的用例，我会保留 trace、截图、视频、控制台日志和网络日志，按失败原因统计后再决定修复脚本、修复产品还是隔离环境问题。最终用重跑率、假失败率和平均定位时长衡量改进效果。

### 2. 项目题回答结构：STAR + 测试决策 + 量化结果

- **Situation（背景）**：系统、用户、业务关键路径和原有质量问题。
- **Task（任务）**：你的职责、范围、时间限制和质量目标。
- **Action（行动）**：如何分析风险、设计分层、实现框架、推动协作和处理失败。
- **Result（结果）**：用数据说明回归时间、稳定性、缺陷发现阶段、线上事故或交付频率的变化。
- **Decision（取舍）**：为什么选择该技术或测试层级，放弃了什么方案。
- **Learning（沉淀）**：留下了哪些模板、规范、监控、测试数据机制或团队能力。

### 3. 自动化金字塔

```text
                少量 UI 端到端测试
             关键用户旅程、跨系统验证

            服务/API 测试
         业务规则、错误处理、契约

       单元测试
    快速、隔离、覆盖分支与边界
```

金字塔不是要求绝对数量比例。它表达的是：越靠近 UI，执行成本和不稳定性通常越高；越靠近业务逻辑，反馈越快、定位越清晰。资深测试工程师应将大多数规则验证放在 API 或更底层，只保留覆盖核心业务路径的 UI 测试。

## 三、测试设计与全流程高频题

### Q1：拿到一份需求文档后，你如何完成测试设计？

**回答要点：**

1. 澄清业务目标、角色、范围、非目标、依赖系统、上线时间和验收标准。
2. 将需求拆分为业务规则、状态流转、输入字段、权限、异常、集成、数据和非功能要求。
3. 识别风险：资金、订单、身份、隐私、权限、数据一致性、历史兼容和高并发场景优先级最高。
4. 选择测试技术：等价类、边界值、判定表、状态迁移、因果图、错误推测、组合覆盖和探索性测试。
5. 建立需求到测试用例、自动化用例和缺陷的可追溯关系。
6. 定义测试环境、数据、Mock、准入准出标准、回归范围、缺陷分级和报告口径。
7. 评审测试设计，确保开发、产品和测试对规则和可观测性达成一致。

**示例：订单取消需求。**

除了“用户点击取消成功”，还应覆盖：订单状态是否允许取消、支付成功但库存释放失败、取消与发货并发、重复提交取消请求、优惠券返还规则、退款异步状态、不同用户是否有权限取消、消息是否重复投递、审计记录和通知失败的补偿。

**加分表达：**

> 我会先把需求转换为可验证的规则和状态机，再写用例。这样能更早发现歧义，例如“取消成功”究竟表示前端显示成功、数据库状态改变、退款提交成功，还是最终到账成功。

### Q2：如何判断哪些测试适合自动化？

**优先自动化：**

- 高频重复执行的冒烟、回归、接口契约和关键交易路径。
- 规则明确、结果可稳定断言、测试数据可控的场景。
- 手工执行成本高、跨浏览器或跨配置组合多的场景。
- 曾发生线上缺陷且可通过自动化可靠防回归的场景。

**不优先自动化：**

- 一次性验证、需求频繁变化且业务规则尚未稳定的功能。
- 需要主观判断的视觉体验、文案语气和复杂可用性问题。
- 环境、依赖或数据尚不受控，导致结果无法重复的场景。

**关键原则：** 自动化不是覆盖率竞赛。应比较开发和维护成本与节省的手工回归成本、质量风险和反馈速度。可以先从稳定且高价值的冒烟/API 回归开始，再逐步扩大覆盖范围。

---

### Q3：如何设计登录功能的测试用例？

从多个维度设计：

| 维度 | 示例 |
| --- | --- |
| 正常流程 | 正确用户名和密码登录成功，跳转正确页面，生成会话 |
| 输入校验 | 空值、长度边界、特殊字符、前后空格、非法格式 |
| 身份认证 | 错误密码、禁用账号、未激活账号、密码过期、MFA 成功与失败 |
| 安全 | 暴力破解锁定、验证码、会话固定、Cookie 的 `HttpOnly`/`Secure`/`SameSite`、登出后令牌失效 |
| 权限 | 不同角色登录后的菜单、接口和数据范围一致 |
| 并发与会话 | 多设备登录策略、重复登录、过期、刷新令牌、主动撤销 |
| 可用性 | 网络超时、认证服务故障、重试提示、错误信息不泄露账号存在性 |
| 审计 | 登录成功/失败、来源、时间、设备信息是否按规范记录 |

UI 用例验证真实用户路径；API 用例验证状态码、令牌、响应结构和错误码；必要时通过数据库或审计日志验证最终状态。不要把密码明文写入代码、日志、报告或截图。

---

### Q4：等价类、边界值、判定表和状态迁移分别何时使用？

- **等价类划分**：输入可分成行为相同的类别时使用，例如年龄字段的合法整数、负数、非数字、空值。
- **边界值分析**：错误常出现在临界点，例如允许金额范围 $[1, 10000]$，至少验证 $0, 1, 2, 9999, 10000, 10001$。
- **判定表**：多个条件组合决定结果时使用，例如折扣由会员等级、优惠券、促销时间和库存共同决定。
- **状态迁移**：对象有生命周期和合法状态转换时使用，例如订单的“创建、支付、发货、签收、取消、退款”。

实际项目常组合使用。例如订单状态机确定合法路径，再对每个状态下的退款金额做边界值和判定表覆盖。

---

### Q5：测试计划、测试策略和测试报告应包含什么？

**测试策略**说明总体方法：测试层级、风险优先级、环境策略、工具、自动化范围、质量门禁和各角色职责。

**测试计划**说明本次迭代如何执行：范围、排期、资源、测试数据、依赖、测试项、风险、准入准出标准和交付物。

**测试报告**必须让决策者能判断是否可发布，至少包含：

- 测试范围和未测范围。
- 环境、版本、数据和执行时间。
- 用例总数、通过/失败/阻塞/跳过情况。
- 按严重级别统计的开放缺陷，以及已知风险和临时规避方案。
- 自动化执行结果、失败归因和趋势。
- 性能、安全、兼容性等专项结果（如适用）。
- 发布建议：可发布、有条件发布或不可发布；条件必须可执行、可验证且有责任人。

---

### Q6：如何定义测试准入和准出标准？

**准入标准示例：** 需求和验收标准完成评审；接口契约可用；代码部署到可用环境；关键依赖可访问或 Mock 已就绪；测试数据和账号准备完成；开发自测和单元测试通过。

**准出标准示例：** P0/P1 缺陷为零或获得明确风险接受；关键冒烟和核心回归通过；失败用例有已确认原因；代码覆盖、API 契约、性能或安全门禁达到团队阈值；测试报告、遗留风险和回滚方案已确认。

阈值不应脱离业务风险。例如支付和权限变更的门禁通常高于普通内容页改动。

## 四、UI 自动化高频题

### Q7：UI 自动化常见不稳定原因及治理方法是什么？

| 失败原因 | 典型现象 | 治理方式 |
| --- | --- | --- |
| 同步问题 | 元素未出现、动画未完成、请求未返回 | 使用条件等待和自动等待；等待业务状态而非固定时间 |
| 定位器脆弱 | UI 小改后大量元素找不到 | 优先角色、标签、`data-testid`；避免 XPath 层级和动态 class |
| 数据污染 | 用例互相影响、重复执行失败 | 每个用例创建独立数据；幂等清理；隔离账号和租户 |
| 环境不稳 | 服务超时、依赖波动 | 健康检查、环境隔离、依赖 Mock、失败归因 |
| 用例耦合 | 必须按顺序执行 | 每个用例独立初始化；不依赖前一用例结果 |
| 产品缺陷 | 偶发错误、前端控制台异常 | 保存可复现证据，作为产品缺陷处理而不是无限重试 |
| 并发冲突 | 共享库存、共享账号、同一资源被修改 | 使用唯一测试数据、资源池或按 worker 分区 |

**不推荐：** 将 `sleep(5)` 当成稳定性方案、无差别重试所有失败、使用绝对 XPath、让所有 UI 用例串行执行。

### Q8：Playwright 相对 Selenium 的特点是什么？什么时候仍可选择 Selenium？

**Playwright 的常见优势：**

- 对 Chromium、Firefox、WebKit 提供统一支持，适合跨浏览器测试。
- Locator 自动等待和严格模式减少手工同步代码。
- 内置浏览器上下文隔离，适合并发执行和多用户会话测试。
- 原生支持网络拦截、trace、截图、视频和多标签页，失败诊断体验较完整。
- API 测试能力可与浏览器测试结合，例如通过 API 快速准备数据、通过 UI 验证关键路径。

**仍可选择 Selenium 的情况：** 团队已有成熟的 Selenium/Grid 基础设施和大量可维护资产；需要兼容特殊浏览器或企业环境；组织已标准化 Java + TestNG + Selenium 并有明确维护能力。选择工具时看团队生态、覆盖目标、维护成本和运行环境，不应把工具偏好当作架构结论。

### Q9：什么是 Page Object Model？它有哪些边界？

Page Object Model（POM）将页面定位器和页面交互封装成对象，让测试用例表达业务行为而不是 CSS/XPath 细节。

```python
from playwright.sync_api import Page, expect

class LoginPage:
    def __init__(self, page: Page) -> None:
        self.page = page
        self.username = page.get_by_label("Username")
        self.password = page.get_by_label("Password")
        self.sign_in_button = page.get_by_role("button", name="Sign in")

    def login(self, username: str, password: str) -> None:
        self.username.fill(username)
        self.password.fill(password)
        self.sign_in_button.click()

    def expect_login_error(self, message: str) -> None:
        expect(self.page.get_by_role("alert")).to_have_text(message)
```

**设计边界：**

- 页面对象负责页面交互和局部状态，不负责完整业务流程编排。
- 测试用例负责业务断言、场景意图和可读性。
- API Client、数据工厂、数据库校验应分别封装，不要全部塞进 Page Object。
- 避免让一个“万能 BasePage”积累几十个不相关方法，继承层次过深会使维护更困难。

### Q10：如何处理 iframe、新窗口、文件上传和下载？

以 Playwright 为例：

```python
# iframe
payment_frame = page.frame_locator("iframe[title='payment']")
payment_frame.get_by_label("Card number").fill("4111111111111111")

# 新窗口
with page.expect_popup() as popup_info:
    page.get_by_role("link", name="Open statement").click()
statement_page = popup_info.value
expect(statement_page).to_have_title("Statement")

# 上传
page.get_by_label("Upload receipt").set_input_files("tests/fixtures/receipt.pdf")

# 下载
with page.expect_download() as download_info:
    page.get_by_role("button", name="Export CSV").click()
download = download_info.value
assert download.suggested_filename.endswith(".csv")
```

除了 UI 操作本身，回答中应补充：文件内容、大小、类型、权限、病毒扫描结果、失败提示、下载文件格式和服务端记录也需要验证。

### Q11：如何并发执行 UI 自动化，又避免互相干扰？

- 每个 worker 使用独立浏览器上下文，避免 Cookie、local storage 和 session 相互污染。
- 使用唯一的测试数据标识，例如 `test_run_id + worker_id + 时间戳`。
- 测试账号、库存、订单等共享资源采用资源池或按 worker 分区。
- 用例必须独立可执行，不依赖前一个用例创建的状态。
- 控制并发量，关注环境容量、下游限流和数据库连接池；更高并发不一定意味着更快反馈。
- 将无法隔离的少数场景打上串行标记并说明原因，不能让整个测试套件因此串行。

## 五、API 自动化高频题

### Q12：API 自动化应该验证哪些内容？

至少从以下层次检查：

1. **协议层**：HTTP 方法、状态码、请求头、认证、超时、Content-Type、缓存语义。
2. **契约层**：请求/响应字段、类型、必填项、枚举、兼容性和错误码。
3. **业务层**：规则、状态变化、权限、幂等性、边界和异常分支。
4. **数据层**：数据库持久化、审计记录、消息事件、下游调用和最终一致性。
5. **非功能层**：响应时间、并发、限流、安全、可观测性和可靠性。

只断言状态码 `200` 远远不够。例如创建订单接口还应检查订单状态、金额计算、库存预占、事件消息、重复请求处理和无权限访问。

### Q13：如何设计一个 REST API 的测试用例？

假设 `POST /orders` 创建订单：

| 类别 | 用例示例 |
| --- | --- |
| 成功路径 | 合法商品、数量、地址和支付方式，返回正确状态和订单 ID |
| 输入校验 | 必填字段缺失、非法枚举、数量为 $0$ 或超过上限、金额精度异常 |
| 鉴权授权 | 无 token、过期 token、伪造 token、无权限访问他人资源 |
| 业务规则 | 商品下架、库存不足、优惠券不可用、地址不可配送 |
| 幂等 | 同一幂等键重复请求只创建一笔订单；不同键允许创建新订单 |
| 并发 | 最后一件库存被同时抢购，不可超卖；响应与最终状态一致 |
| 错误恢复 | 支付或库存服务超时，返回约定错误并可重试/补偿 |
| 数据验证 | 订单、明细、库存、审计和消息状态符合预期 |
| 契约兼容 | 新增字段不破坏旧客户端；不随意修改既有字段类型或语义 |

测试必须根据真实 API 契约和业务约定确定预期状态码。不要机械地规定“所有参数错误都必须是某一个状态码”。

---

### Q14：什么是 API 幂等性？如何测试？

幂等性表示同一个请求执行一次或多次，业务最终结果相同。`GET`、`PUT`、`DELETE` 在语义上通常应幂等；`POST` 不天然幂等，但创建订单、支付等高风险操作常通过幂等键实现。

**测试方法：**

1. 使用相同请求体和相同 `Idempotency-Key` 连续调用两次。
2. 断言第二次返回同一业务资源或明确的重复请求结果。
3. 查询数据库和消息系统，确认只产生一条订单、一次扣款或一个事件。
4. 模拟第一次请求在服务端已成功但客户端超时，再重试，验证不会重复执行。
5. 使用不同幂等键验证业务是否允许创建不同资源。

幂等键需要有过期策略、请求内容一致性校验和可追踪日志，否则可能出现“同一键但请求内容不同”的风险。

---

### Q15：如何测试异步接口或消息驱动流程？

例如提交订单后通过消息队列完成库存扣减和通知：

- 先断言同步响应，例如订单被受理且状态为 `PENDING`。
- 使用轮询加超时等待最终业务状态，而不是固定等待几秒。
- 查询事件、消息消费记录和数据库状态，验证最终一致性。
- 验证消息至少一次投递带来的重复消费，消费者必须能幂等处理。
- 模拟消费失败、消息乱序、延迟和死信，检查重试、告警、补偿和人工处理路径。
- 记录 correlation ID，将 API 请求、日志、追踪、消息和数据库记录关联起来。

**加分点：** 测试不是假设异步系统“最终一定成功”，而是验证它在超时、重复、乱序和失败时仍然可观测、可恢复且不破坏数据。

---

### Q16：如何做 API 契约测试？

契约测试验证服务提供方和调用方对接口格式与语义的共同约定。常见做法包括 OpenAPI schema 校验、消费者驱动契约（Consumer-Driven Contract）和发布前兼容性检查。

**关键实践：**

- 将 OpenAPI/JSON Schema 纳入版本控制和代码评审。
- CI 中校验响应是否符合 schema，检查破坏性变更，例如删除字段、修改类型、改变必填性或枚举含义。
- 对关键消费者维护契约样例，提供方发布前验证。
- API 演进优先新增可选字段；废弃字段应经过版本、迁移期和使用情况确认。
- 契约测试不能替代端到端集成测试：它验证协议兼容性，但不覆盖所有真实环境、权限和数据流问题。

---

### Q17：如何管理 API 测试的认证和敏感数据？

- 使用 CI 密钥库、环境变量或受控的 secret manager 注入凭据；禁止提交到 Git。
- 测试账号按最小权限原则创建，生产数据不得复制到低权限环境。
- 令牌应通过登录/API 获取或 fixture 注入，并在有效期、刷新和撤销场景中明确处理。
- 日志、报告、trace 和截图必须脱敏 `Authorization`、Cookie、密码、身份证号、银行卡号等数据。
- 在 CI 输出中避免 `print` 完整请求头或响应体；失败时只保留定位所需的安全字段。

## 六、Python、Pytest 与 Playwright 高频题

### Q18：Pytest 的 fixture 是什么？为什么比 `setup/teardown` 更适合复杂测试？

Fixture 是可声明依赖、可复用且有作用域的测试准备与清理机制。测试函数通过参数直接声明需要的资源，Pytest 会负责依赖解析和执行顺序。

```python
import pytest
from playwright.sync_api import Browser, Page

@pytest.fixture(scope="session")
def api_base_url() -> str:
    return "https://test.example.com/api"

@pytest.fixture
def page(browser: Browser) -> Page:
    context = browser.new_context()
    test_page = context.new_page()
    yield test_page
    context.close()
```

常用作用域包括：

- `function`：每个用例独立，隔离最强。
- `class`：同一测试类共享。
- `module`：同一文件共享。
- `session`：整个测试会话共享，例如启动一次测试服务或加载静态配置。

使用 `yield` 可以确保即使断言失败也执行清理。Fixture 不应隐藏过多业务动作，否则测试读者难以理解前置条件；复杂数据初始化应保留清晰、可调用的工厂方法。

---

### Q19：如何使用 Pytest 参数化？

参数化适合对同一规则验证多组输入，能避免复制测试代码。

```python
import pytest

@pytest.mark.parametrize(
    ("quantity", "expected_status"),
    [
        (1, 201),
        (0, 400),
        (-1, 400),
        (10001, 400),
    ],
    ids=["minimum-valid", "zero", "negative", "over-maximum"],
)
def test_create_order_quantity(api_client, quantity: int, expected_status: int):
    response = api_client.post("/orders", json={"productId": "P-1", "quantity": quantity})
    assert response.status_code == expected_status
```

参数化的价值不在于“把所有数据塞进去”，而在于表达等价类和边界设计。每组参数应有清晰意义，失败时可快速知道哪条规则被破坏。

### Q20：如何组织一个可维护的 Python 自动化测试项目？

```text
tests/
  api/
    test_orders.py
  ui/
    test_checkout.py
  pages/
    login_page.py
    checkout_page.py
  clients/
    order_client.py
  factories/
    order_factory.py
  fixtures/
    users.py
  conftest.py
  config.py
  assertions.py
  resources/
    schemas/
    test_files/
```

**组织原则：**

- 测试文件按业务能力或测试层级组织，而不是按单个页面元素组织。
- Page Object 管 UI；API Client 管 HTTP 调用；Factory 管测试数据；断言可提取为领域级断言。
- 配置与秘密分离：配置可版本化，秘密只能从安全注入渠道读取。
- 保持测试独立，不用全局可变状态传递数据。
- 统一日志、失败证据、标签、重试策略和报告格式。
- 公共封装必须服务于可读性；不要为了“框架化”把一行清楚的断言隐藏到多层抽象后。

### Q21：`requests` 中 timeout、重试和异常处理应如何设计？

- 始终设置连接和读取超时，避免测试无限挂起，例如 `timeout=(3, 15)`。
- 仅对可安全重试的请求或具备幂等键的操作重试；不能盲目重试创建支付、发货等有副作用的请求。
- 区分连接失败、超时、$5xx$、限流和业务 $4xx$，每类的处理策略不同。
- 对重试设置最大次数、指数退避和抖动，避免测试对下游造成流量尖峰。
- 异常信息应包含方法、URL、请求关联 ID、响应码和安全脱敏后的响应摘要，便于定位。

示例：

```python
import requests

response = requests.get(
    "https://test.example.com/api/health",
    timeout=(3, 10),
)
response.raise_for_status()
assert response.json()["status"] == "UP"
```

`raise_for_status()` 有助于及早暴露 HTTP 错误，但不能替代业务断言。即使状态码为 `200`，响应内容、数据副作用和权限也可能错误。

---

### Q22：如何实现失败时的诊断信息收集？

对于 UI 测试，失败时自动保留：截图、视频、trace、浏览器控制台错误、网络请求和 DOM 快照。对于 API 测试，保留脱敏后的请求、响应、耗时、correlation ID 和服务器日志链接。

以 Playwright 为例，可在 CI 失败时启用 trace：

```python
context = browser.new_context(record_video_dir="test-results/videos")
context.tracing.start(screenshots=True, snapshots=True, sources=True)
try:
    # 执行测试
    pass
finally:
    context.tracing.stop(path="test-results/trace.zip")
    context.close()
```

证据收集应与失败原因关联，并设置保留期限。记录过少无法定位，记录完整敏感请求又有泄露风险，因此必须做脱敏和访问控制。

---

### Q23：同步 Playwright 和异步 Playwright 如何选择？

Python 版本的 Playwright 同时提供同步和异步 API。

- 团队测试代码以同步调用为主、依赖库也主要同步时，使用同步 API，代码更直观。
- 需要在一个事件循环中组织大量并发 I/O，或项目本身使用 `asyncio` 时，使用异步 API。
- 不要在同一调用链中混用同步和异步风格；避免在已有事件循环中错误调用 `asyncio.run()`。
- 并发数量应由环境容量和业务目标决定，不能为了“异步”而无控制地创建任务。

技术选择的关键是统一性、可维护性和诊断能力，而不是语法偏好。

## 七、数据库与 SQL 高频题

### Q24：如何用 SQL 验证 API 或 UI 操作的数据库结果？

假设创建订单后需要确认订单和明细：

```sql
SELECT
    o.order_id,
    o.status,
    o.total_amount,
    COUNT(i.item_id) AS item_count
FROM orders AS o
LEFT JOIN order_items AS i ON i.order_id = o.order_id
WHERE o.order_id = :order_id
GROUP BY o.order_id, o.status, o.total_amount;
```

自动化中应使用参数化查询，而不是字符串拼接。断言应围绕业务结果，例如状态、金额、明细数量、库存变化和审计记录，而不是只断言“查到了某一行”。

另外要注意：如果系统使用异步写入、读写分离或最终一致性，不能在 API 返回后立刻假设数据库已更新；应该按业务 SLA 轮询或读取正确的数据源。

---

### Q25：`INNER JOIN`、`LEFT JOIN` 和 `WHERE` 条件位置有什么区别？

- `INNER JOIN` 只返回两边都匹配的记录。
- `LEFT JOIN` 保留左表全部记录，右表无匹配时返回 `NULL`。
- 对 `LEFT JOIN` 的右表字段添加 `WHERE` 条件，常会过滤掉 `NULL` 行，效果接近 `INNER JOIN`。

例如要找“没有订单的用户”：

```sql
SELECT u.user_id, u.email
FROM users AS u
LEFT JOIN orders AS o ON o.user_id = u.user_id
WHERE o.order_id IS NULL;
```

如果要保留所有用户，只统计已支付订单，则应将状态条件放在 `ON` 中：

```sql
SELECT u.user_id, COUNT(o.order_id) AS paid_order_count
FROM users AS u
LEFT JOIN orders AS o
    ON o.user_id = u.user_id
   AND o.status = 'PAID'
GROUP BY u.user_id;
```

这是测试数据验证中常见的误判来源。

---

### Q26：如何安全地进行增删改查？

- `SELECT`：先使用精确条件和 `LIMIT` 验证目标集合，避免大查询影响测试环境。
- `INSERT`：显式指定字段；使用事务；记录生成的业务 ID；准备可追踪的测试数据标识。
- `UPDATE`：先 `SELECT` 确认影响范围，再按主键或唯一键更新；检查影响行数。
- `DELETE`：极其谨慎，先确认环境和条件，使用事务或软删除策略；绝不执行缺少 `WHERE` 的删除。

测试数据清理应只删除本次测试创建的数据，例如按 `test_run_id`、前缀或独立租户过滤。不可通过“清空整张表”解决数据问题。

---

### Q27：什么是事务？测试时如何验证事务一致性？

事务将多个操作作为一个原子单元处理，并通常具备 ACID 特性：原子性、一致性、隔离性和持久性。

例如转账从账户 A 扣款并向账户 B 加款，测试应验证：

- 两个更新同时成功，或在失败时同时回滚。
- 余额总和和账务流水符合业务不变量。
- 并发转账时不会丢失更新或产生超额余额。
- 数据库异常、服务重试和消息重放不会造成重复扣款。

不要只检查接口返回成功。应结合余额、流水、状态机和审计事件验证业务一致性。

---

### Q28：索引为什么会影响测试和故障定位？

索引可加速筛选、连接和排序，但会增加写入成本和存储开销。测试工程师不一定负责设计索引，但应能识别性能风险：

- 用 `EXPLAIN` 或数据库执行计划确认查询是否全表扫描。
- 测试查询应按索引字段过滤，避免在大表上无条件查找。
- 发现 API 在数据量增加后变慢时，将慢查询、参数、数据量、执行计划和索引情况提供给开发或 DBA。
- 测试环境数据量过小可能掩盖生产问题，关键性能场景要准备接近真实分布的数据。

## 八、Git 与持续集成高频题

### Q29：你如何使用 Git 管理自动化测试代码？

一个可行的协作流程是：

1. 从受保护的主分支或发布分支创建短生命周期 feature branch。
2. 每个提交聚焦一个可评审目的，例如新增订单 API 测试或修复登录 Page Object。
3. 提交前执行格式化、静态检查和相关测试，避免把明显失败的代码交给 CI。
4. 提交 Merge Request/PR，描述变更、风险、测试结果、环境影响和关联需求/缺陷。
5. 通过代码评审和流水线门禁后合并；重要变更采用 squash 或保留有意义的提交历史，遵循团队规范。
6. 发布后通过冒烟测试、报告和监控确认变更效果。

测试代码也是生产工程资产，需要同样的评审、版本控制、依赖管理和质量门禁。

---

### Q30：`merge`、`rebase` 和 `cherry-pick` 有什么区别？

- `merge`：将另一个分支的历史合并到当前分支，可能产生 merge commit，保留真实分支拓扑。
- `rebase`：将当前分支的提交重新应用到新的基点上，历史更线性，但会重写提交哈希。
- `cherry-pick`：选择某一个或几个特定提交应用到当前分支，常用于紧急修复回移。

**重要边界：** 不应对其他人正在使用的共享分支随意 rebase 后强推。若团队允许更新个人 feature branch，也应使用安全的 `--force-with-lease`，并在 MR/PR 中同步说明。

---

### Q31：发生 Git 冲突时如何处理？

1. 先理解两个分支的意图和最新需求，不要只按编辑器的“接受左侧/右侧”机械处理。
2. 拉取目标分支最新变更，在本地 merge 或 rebase。
3. 手工合并冲突区域，确保配置、测试数据和测试代码语义都正确。
4. 运行受影响的格式检查和测试；冲突解决后最容易出现导入丢失、重复配置或断言不一致。
5. 只提交解决冲突所需的内容，避免混入无关格式化。

面试官关注的不只是命令，而是你是否会在冲突后重新验证行为。

---

### Q32：如何把自动化测试接入 CI/CD？

典型流水线分层：

```text
代码提交
  -> 格式化 / 静态检查 / 单元测试
  -> 构建测试镜像或安装依赖
  -> API 合约与 API 回归测试
  -> 部署临时环境或测试环境
  -> UI 冒烟 / 关键端到端测试
  -> 汇总报告、trace、截图和质量门禁
  -> 部署后冒烟与监控验证
```

**实践要点：**

- 快速、确定性的检查尽早运行；昂贵的跨系统 E2E 测试放在后续阶段。
- 按标签拆分测试，例如 `smoke`、`regression`、`ui`、`api`、`serial`，支持按风险执行。
- 失败时上传报告和诊断产物，避免只能看到“pipeline failed”。
- 对基础设施或已知环境故障进行明确归因，不能以无条件重试掩盖真实测试失败。
- 质量门禁应由风险决定，例如核心 API 冒烟失败阻止部署，非关键视觉回归可进入人工审核。
- 密钥由 CI secret 管理，日志默认脱敏。

---

### Q33：如何衡量自动化测试的价值？

不要只报告“自动化用例数量”或“代码覆盖率”。更有意义的指标包括：

- 核心业务路径的风险覆盖率和需求可追溯率。
- 冒烟反馈时间、完整回归耗时和发布频率。
- 自动化通过率、假失败率、重跑率和平均修复时间。
- 缺陷发现阶段、缺陷逃逸率和同类问题复发率。
- 失败归因分布：产品、脚本、数据、环境、依赖和未知。
- 测试维护投入与节省的人工回归时间。

指标必须能导向行动。假失败率升高时，应治理同步、数据和环境；回归时间过长时，应优化分层、并发和选择性执行，而非简单扩大机器数量。

## 九、综合场景题

### Q34：一个 UI 自动化套件在 CI 中经常失败，你会如何排查和改进？

**推荐回答步骤：**

1. 收集失败数据：失败用例、浏览器、环境、时间、错误栈、截图、trace、网络日志和重跑结果。
2. 给失败归类：产品缺陷、脚本同步、定位器、数据、环境、网络/依赖、容量或未知。
3. 优先处理高频和高影响类别，而不是逐个用例随机修补。
4. 修复同步问题时等待业务可观察状态；修复定位器时与前端约定语义化 locator；修复数据时创建独立数据和清理机制。
5. 控制重试：只对确认的瞬态基础设施问题有限重试，并分别报告初次成功率和最终成功率。
6. 对每项治理设定目标，例如将假失败率从 $12\%$ 降到 $2\%$ 以下，并持续看趋势。
7. 对真正的产品偶发缺陷提交可复现证据，不能把它标记成“flaky test”后忽略。

---

### Q35：开发说“接口返回 200，所以不是后端问题”，你如何分析？

`200` 只表示 HTTP 请求成功处理，不代表业务正确。应从以下方向验证：

- 响应体字段、金额、状态和错误语义是否正确。
- 数据库是否正确写入，是否产生重复或遗漏记录。
- 是否触发了必要的异步事件、库存更新、审计和通知。
- 是否因缓存、读写延迟或权限过滤返回了错误数据。
- 下游服务失败时是否被错误地吞掉。
- 用 correlation ID 关联网关、应用、消息和数据库日志，建立完整调用链。

可以礼貌地将讨论从“谁的问题”转为“业务结果在哪一层偏离预期，以及证据是什么”。

---

### Q36：如何为一个新项目从零搭建自动化测试框架？

1. 先确认系统架构、发布节奏、核心风险、环境、测试数据、团队语言和 CI 平台。
2. 选择分层目标：单元测试由开发主导，测试团队聚焦 API、契约、关键 UI 和端到端链路。
3. 确定技术栈，例如 Python + Pytest + Playwright + Requests；选择应与团队维护能力匹配。
4. 建立最小可用骨架：配置管理、fixture、API Client、Page Object、数据工厂、日志、报告和失败证据。
5. 先实现少量关键冒烟路径，接入 CI，确保每次提交都能得到可信反馈。
6. 建立测试数据策略、环境健康检查、标签和并发策略，避免规模扩大后才治理不稳定。
7. 制定代码评审、命名、locator、断言、重试、秘密管理和缺陷归因规范。
8. 逐步增加回归覆盖，用稳定性和缺陷发现数据校正投资方向。

**关键取舍：** 不要一开始就构建复杂的“万能框架”。框架应随着真实场景演进，任何抽象都应减少重复或提升诊断，而不是制造学习成本。

---

### Q37：需求没有写清楚，你会怎么做？

- 明确记录不确定点，并按业务风险排序，例如金额计算、权限、状态流转和异常处理优先澄清。
- 将歧义转换为具体问题和可选规则，例如“取消后优惠券是立即返还、退款成功后返还，还是不返还？”
- 通过示例、判定表、状态图或 Given-When-Then 场景与产品、开发确认。
- 没有得到结论时，不把猜测伪装成确定需求；在测试计划和风险报告中标记假设和影响。
- 对已经确认的规则尽早创建自动化验收测试，减少后续口头理解偏差。

测试工程师的价值之一是让需求变得可测试、可观察、可验收。

---

### Q38：生产发现严重缺陷，但自动化没有拦住，你会如何复盘？

1. 先确认影响、临时规避和修复验证，避免复盘干扰恢复。
2. 建立时间线：需求、设计、代码评审、测试、发布、告警和发现过程。
3. 判断漏测原因：需求遗漏、风险评估错误、环境/数据不代表生产、测试层级不合适、断言不足、执行被跳过，还是已知风险被接受。
4. 增加最接近故障机制的防线。例如业务规则错了，优先添加单元/API 规则测试，而不是只添加缓慢的 UI 回归。
5. 补齐监控、发布校验、数据校验或回滚机制；每项行动都应有负责人、完成时间和验证标准。
6. 使用无责复盘：关注系统和流程条件，不把复杂质量问题简单归咎于个人。

## 十、行为与项目经历题

### Q39：讲一个你通过自动化显著提升质量或交付效率的案例。

**建议回答框架：**

> 在 `[项目]` 中，团队每次发布前需要 `[X]` 人天完成核心回归，且 UI 脚本不稳定导致发布经常延迟。我负责分析失败记录并按业务风险重构测试分层：将大部分规则下沉到 API 测试，仅保留 `[数量]` 条关键 UI 路径；同时引入独立测试数据、稳定 locator、trace 和 CI 分层执行。经过 `[周期]`，核心冒烟反馈从 `[原耗时]` 降至 `[新耗时]`，假失败率从 `[原比例]` 降至 `[新比例]`，并在上线前捕获了 `[一个真实缺陷类型]`。我还将 locator、数据和失败归因规范写入评审清单，使后续模块按同一方式接入。

不要编造指标。若没有精确数字，可使用可证实的相对结果，并说明数据来源，例如流水线记录、发布统计或缺陷系统。

---

### Q40：讲一次你与开发或产品对质量标准存在分歧的经历。

高分回答应体现合作和证据：

- 先说明分歧是什么，例如开发认为某异常提示无需覆盖，测试认为会泄露账号信息。
- 用需求、用户影响、日志、复现步骤、行业规范或历史缺陷说明风险。
- 提供成本不同的选项，例如本迭代修复、加 feature flag、限制上线范围或接受风险并记录。
- 促成明确决策者作出可追踪决定，而不是无限争论。
- 最后说明结果和沉淀，例如新增安全测试清单或接口错误码规范。

避免把故事讲成“我坚持，所以别人都听我的”。资深工程师应能把风险转化为团队可共同决策的信息。

---

### Q41：你如何指导初级测试工程师？

- 先通过结对评审了解其在测试设计、编码、业务理解或沟通上的具体差距。
- 用真实需求一起练习风险识别、边界设计和失败定位，而不是只让对方背模板。
- 为测试代码提供小而清晰的评审反馈，例如 locator 语义、fixture 作用域、断言质量和数据隔离。
- 逐步授权：先共同完成一个模块，再让对方独立负责并复盘。
- 将重复问题沉淀为示例、模板、检查清单和团队分享，避免知识只留在个人身上。

### UI 与 API 自动化

- [ ] 能解释 UI 自动化不稳定的根因及治理，不会只说“加等待”。
- [ ] 能说明 Playwright/Selenium 的选择、Locator、等待、并发和失败证据。

### 项目经历
